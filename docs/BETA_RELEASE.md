# How a release goes out

This page is about the mechanics of publishing a build, not about what is in
one. For what has shipped, see [the changelog](changelog.md). For what still
does not work, see [what is built and what is not](IMPLEMENTATION_STATUS.md).

## Tell testers about the SmartScreen warning

Every alpha and beta build is unsigned, so everyone who downloads one meets
"Windows protected your PC" before they meet Wixen Mail. Say so in the message
that invites them, not only in the documentation, because somebody who hits an
unexplained security warning on the first thing you asked them to do reasonably
stops there.

The wording to give them:

> Windows will warn you that it does not recognise this program. It is not
> signed yet. Choose **More info**, then **Run anyway**. The button you land on
> first is **Don't run**, so do not just press Enter.

That last sentence is the one that matters for screen reader users: the Run
button only exists after the More info link is activated, and the default
button cancels.

## Releases are triggered by hand, never by a push

A push to `main` used to trigger the release workflow, which meant any merge
bumped the version and published a tag with nobody deciding to. That is why
Wixen Mail keeps a standing guardrail against it now: publishing happens on
purpose, or not at all.

The real trigger today is `workflow_dispatch`, run by hand from the Actions
tab:

- Workflow file: `.github/workflows/release.yml`
- GitHub Actions URL: `https://github.com/PratikP1/Wixen-Mail/actions/workflows/release.yml`
- Running it asks for one choice, **How to bump**: `patch` or `minor` for
  ordinary development versions, `alpha`, `beta`, or `rc` to start or advance
  a prerelease series from the current version, or `release` to drop a
  prerelease suffix and cut the thing the prereleases were staging.

Wixen Mail develops on a plain `0.x.y` version with no suffix. `0.x` already
means unstable, so a version does not need to say that twice. A prerelease
suffix is added only when a build is about to go to testers: `alpha`
through a run or two, then `beta` when it is closer, then `release` to drop
the suffix and cut the thing the prereleases were staging.

## What the workflow does

A quality gate runs first, on a Windows runner: `cargo fmt --check`, clippy
with warnings denied, and the test suite. Only once that passes does
`cargo release` bump the version in `Cargo.toml`, tag the commit, and push
both. The setup executable is then built with the same script a person would
run locally, `scripts/build-installer.sh`, so the file testers download was
built the way the one you tested was.

The workflow publishes three files, plus the changelog, to a GitHub Release:

- `Wixen-Mail-Setup-<tag>.exe`, the installer
- `wixen-mail-<tag>.exe`, the portable executable on its own
- `Wixen-Mail-<tag>-windows.zip`, the portable executable zipped
- `changelog.md`

A tag carrying `-alpha`, `-beta`, or `-rc` is published as a prerelease
automatically; a bare version is published as a real release. Release notes
are generated by GitHub from the commits between tags.
