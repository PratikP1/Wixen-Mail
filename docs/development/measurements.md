# Measurements

This is the one page a figure about this tree is written on. How many guard
records there are, how many mutants the configuration allows, how long the
suite takes: each of those is a number that was true on the day somebody took
it, and this page says which day, which command, and which commit. Every other
page points here instead of restating a number, so that a figure which has
moved reads as a dated measurement rather than as a current fact.

**Nothing on this page is promised to be current.** A row says that its value
is what its command reported on its date at its commit, under its conditions,
and nothing more. The check that reads this page,
`tests/every_number_carries_its_command_and_its_date.rs`, holds the shape of
every row and never its value: it refuses a row without a command, a date or a
commit, and it never compares a value with what the command reports today.
That is on purpose. PERF-06 records that a check asserting a written count
equals today's count is false the next time somebody adds a test.

## What belongs here, and what does not

Four kinds of number live in this project's documents, and only the first
belongs on this page.

| Kind | Example | Where it lives |
|---|---|---|
| A measurement of the tree | how many guard records there are; how long the suite took; the rate one guard record costs | here, one row each |
| A target | memory under 150 MB with 1,000 cached messages | `.planning/REQUIREMENTS.md`, marked as a target |
| A constant the code holds | a single attachment is kept up to 25 MB, which is `LARGEST_ATTACHMENT_KEPT_BYTES` | the code, and a check that the prose agrees with it |
| A historical record | what a sweep found on 2026-08-12 | wherever it was written, and never corrected |

A duration belongs here with the settings that change it: the thread count,
whether the build was warm, what else was running. A duration without those is
a number without its conditions, and this project has quoted several of them
to people planning work.

## How to add a row

Run the command. Write the value it printed, the command as you ran it, the
date, the short hash of the commit you ran it at, and what would move the
figure. If nothing would, write `none`. Do not copy a figure from a plan, a
research document or `CLAUDE.md`; run the command. If the same figure is taken
again on a later day, add a row rather than editing the old one, so the page
keeps the series. Two rows with the same `what` and the same date are refused.

Pipes inside a command are written `\|` so the table stays a table.

## The definitions the start and memory rows were taken under

Three of the project's targets use words they do not define: memory under
150 MB with 1,000 cached messages, cold start under 2 seconds to a usable
list, and idle memory under 100 MB. The rows below were taken under these
meanings, which are the same words the harness's header states in
`tests/the_numbers_the_targets_ask_for.rs`, so the next person re-taking a
number takes the same one.

**1,000 cached messages** means 1,000 rows in `messages` for one IMAP
account's `INBOX`, written through the same call the sync uses, with a
plain-text body of about 2 KB each through the body store, no attachment
content and no signed originals. Because that is what the list reads at
startup and what the target was written about; the attachment and
signed-original budgets are constants with their own rows and their own
limits, and mixing them in would measure the budgets rather than the
messages.

**Cold start** means a fresh process of the release binary against the
1,000-message profile, from the first instruction of `main` to the usable
line. The first start after the binary is built is reported on its own as
the file-cache-cold figure; the next five starts are the series and their
median is the number. The requirement says "cold" and does not say cold
for what; both readings are given so nobody has to guess which was meant.

**Usable** means the first `MessagesLoaded` after startup whose rows
reached the list control's count and were at least one, which is the line
`wixen_mail::common::started` writes once per process.

**Idle** means no input after the usable line, the window left where the
start put it, and memory read at 60 s and at 120 s; the 120 s reading is
the number, the 60 s reading sits beside it, and the difference is
reported as idle growth.

**Memory with 1,000 cached messages** is the peak working set of the
application process between start and the 60 s reading, plus the WebView2
tree's working set at 60 s, on the 1,000-message profile, because "with
1,000 cached messages" is about what loading them costs and the peak is
when it cost most. The empty profile's 120 s reading is the floor and is
reported beside both.

Two things the first taking found that the definitions did not say. The
list the usable line reports holds 500 rows and not 1,000, because the
window opens on All Inboxes and that view lists its first page,
`ALL_INBOXES_LIMIT` in `src/presentation/wx_app.rs`; the other 500 are in
the cache and are read when somebody asks for older mail. And the WebView2
tree is not the application's own memory in any sense the targets were
written about: it is six `msedgewebview2.exe` processes Windows starts for
the preview pane, and it weighs the same on an empty profile as on the
1,000-message one, so every memory row gives the application process and
the tree separately as well as summed. Whether a target is met against
the sum or against the process is 08-09's judgement, not this page's.

## What the scale rows time, and what they do not

The rows over 200,000 rows were taken on 2026-09-14 by
`tests/the_list_at_two_hundred_thousand_rows.rs`, a harness that builds the
rows through `sample_mailbox`, the generator on the Help menu, and runs the
real functions with no window. Its header says what each kind of row means;
the short form is here so the rows can be read without it.

**Listing** is `MessageCache::get_messages_for_folder`, an unsorted read of
one folder. Until 2026-10-18 this paragraph called it the read the list
takes when a folder opens and the one that precedes any scroll. It was not:
no user path called it, plan 13.2-31 deleted it on 2026-10-18, and the
harness no longer prints the two listing rows. The rows below stay as they
were taken, with their date; the read a folder opening really takes is
timed by the list's own read path, described further down. The rows were
written into a cache in a `tempfile` directory through `upsert_messages`,
the call the sync uses, because the Help menu's sample never enters SQLite.
Cold is the first read on a connection opened after the rows were written;
the file was warm in the operating system's cache either way, because the
same process had just written it.

**Filter** is `MessageCache::search_messages`, the query the search box
runs, at the limit the box passes, under All Folders and under the
narrowest answer the In list offers for that kind of word. One row raises
the limit to every match, which the box never does, so the page says what
reading every match costs.

**Sort** is `mail_sort::sort_messages` over the generated rows in memory,
each order on a fresh clone with the clone outside the timing. In the
running program `apply_sort` runs it off the interface thread and sends the
result back through `MessagesLoaded`; the cost of the list control taking
that result was not timed, because there is no window.

**Page paint** and **full pass** are `virtual_rows::text_for`, the whole of
what the list's paint callback does after taking the lock, over one page of
every visible inbox column and over every row of one column. A scroll in the
running program is the page paint plus wxWidgets' own painting, which was
not timed, for the same reason. The full pass is what painting the whole
list once would cost the callback, which no scroll does.

**The list's own read path**, rows added 2026-09-17 by the same harness for
10-02, is a different quantity from the listing above, and the difference
is the reason the rows exist. The window never called
`get_messages_for_folder`, which was deleted on 2026-10-18. When a folder opens, `load_folder_messages` in
`src/presentation/wx_app.rs` runs three steps on the interface thread, where
no key is answered until they end: `get_message_list_sorted`, with the sort
inside the query and, until 10-02, a `LIMIT` of 500 that the listing row
above never had; then the threading, `threading::thread_messages` over every
row read, which walks every row to find its relatives; then one labels query
over the rows. The rows time each step on its own, cold and warm for the
read, over a folder with a label on one row in ten, at two counts: the
tester's folder of 12,872 messages, the count the phase 10 README quotes
from his profile, and 200,000. The 200,000 labels row before the change
says `refused` rather than a time: the query sent one bound parameter per
row, and the bundled SQLite refuses more than 32,766 of them, so the window
dropped the error and showed the folder with no labels. The generated rows
carry no `References`, so every message is a conversation of one, which is
the cheapest shape the threading has. The rows at `dbcddb93` were taken
before the page came off, on the tree that still passed `Some(500)`; the
harness passes `None` itself, so those rows are the cost of the whole folder
under the old read, which is the cost the page was about to be dropped
against. The rows named "after 10-02", at `760a4d87`, were taken after it,
on the same machine, with the same command, and their labels step is the
read by folder. The command carries `--test-threads=1` since that day
because the target holds two ignored tests and, left to itself, the harness
runs them at once.

**Read the two sets against each other with care, because the machine
slowed between them and the page holds a control for it.** The before rows
were taken at 14:47Z and the after rows at 15:57Z on 2026-09-17, and every
step that did not change reads slower in the second set: the `Listing`
rows above, whose code no commit of 10-02 touched, printed by the same runs
and not written here, read 256.71 ms cold at 14:47Z and 360.23 ms cold at
15:57Z. So the before commit was checked out into a worktree and run again
at 16:00Z, three minutes after the after rows, with the same command,
`cargo test --release --test the_list_at_two_hundred_thousand_rows --
--ignored --nocapture --test-threads=1` at `dbcddb93`: at 200,000 rows the
sorted read 482.08 ms cold and 499.59 ms warm, the threading 244.84 ms and
the labels refused; at 12,872 rows 24.19 ms cold, 22.30 ms warm, the
threading 7.42 ms and the labels 6.64 ms. Those are the figures to hold the
after rows against, and they say the sorted read and the threading cost
what they cost before within the spread of three takes, and the labels went
from a refusal to 103.45 ms at 200,000 and from 6.64 ms to 5.05 ms at
12,872. What slowed the machine between 14:47Z and 15:57Z is not known; the
processor load read 2 to 5 percent, the clock its nominal 2000 MHz, and
nothing was building, checked with `tasklist` before each run. The 14:47Z
rows stay on the page as taken, because they are the rows the page was
dropped against and the day's fastest reading of the same code. What moving
the three steps off the interface thread would buy is the sum of the three
"after 10-02" rows at a count, and nothing else: 817 ms of answered keys on
the first open of a folder of 200,000 (464.94 + 248.73 + 103.45, taken
2026-09-17 at `760a4d87` by the command above), and 39 ms at the tester's
12,872 (23.89 + 10.31 + 5.05), which is under the time a key takes to be
pressed and released.

**All Inboxes in a chosen sort**, rows added 2026-09-17 by the same harness
for 10-02.1, times the combined view's read, `unified_inbox` with no
`LIMIT`, in the fixed order the index `idx_messages_date` serves and in four
of the orders the Sort Messages menu offers, three takes warm after one
untimed read, the median the value. The fixed order is the control: it is
what the view read before 10-02.1 whatever was chosen, and what a person
who never chose a sort still reads. A chosen order is a sort of every inbox
row, Date newest from the menu included, because `Received` sorts on
`COALESCE(m.internaldate, m.date)` and no index serves that; a folder
already pays the same, by the read path's sorted read above, which is the
default sort of an inbox over the same expression. The rows say what that
sort costs on top of reading every row, and at 200,000 it is little: the
fixed order 500.31 ms, Date newest 511.84 ms, Date oldest 499.98 ms, Unread
first 518.62 ms, Sender A to Z 570.93 ms, taken 2026-09-17 at `b39a7409`.
At 12,872 the five orders sit between 21.02 ms and 23.96 ms and the spread
of three takes is wider than the gap between them. Read the two sizes
against each other as a whole read that grows with the count and a sort
that adds a few percent at either size, rather than as an index that
serves one order and not the others: the index's own comment quotes 0.15
ms and 3.07 ms for the fixed order at 200,000, and those were reads with a
`LIMIT`, one screenful walked off the index, where these read the whole
of it, so the two are not the same quantity and are not reconciled here.
The machine was in the state of the "after 10-02" rows when these were
taken: the read-path rows the same run printed, not written here because
the page holds a row once per name and date, read 483.97 ms cold, 507.44
ms warm, 240.04 ms and 100.53 ms at 200,000 and 23.29, 22.49, 8.82 and
4.60 ms at 12,872, within a few percent of the rows at `760a4d87`, so no
same-state re-take was owed.

Every one of these rows is over synthetic rows and no provider mailbox, and
each says so in its conditions.

The row for marking the bound's worth of messages read is the cost of a
command over the largest selection the list allows (#30, 11-07): the
message list selects more than one message since 2026-09-19, and Mark as
Read, Star, the Labels, Delete, Move to and Copy to act on every selected
message up to `MOST_ROWS_WORTH_SELECTING`, which is 5,000 and is the bound
Select All already had. The row times the cache alone: 5,000 rows written
unread through `upsert_messages`, then one `update_message_flags` per row,
the write the arm makes for each message, on the interface thread. The
server changes queue behind it, one task per message through
`spawn_server_change`, and what those cost against a provider has not been
measured, because nothing here has met one with a thousand flag changes.
So the row bounds the part of the command that holds the window; the part
that holds the network is a queue and is not on this page.

The row for the count before a rule run, added 2026-10-01 for 13-44
(#61), is what somebody waits for between choosing a rule to run over a
folder and hearing the question: the read the count's worker makes, the
folder's messages without their text and the labels on them, and 13-43's
count over them, for a rule on the subject that marks read. It runs on a
worker, so the window is not held while it does; the status line says it
is counting. It does not time a rule on the message text, which reads
every body and costs more, the question itself, or the run a Yes starts,
which goes through the set commands one message at a time and is bounded
by the row above for marking.

## What the forgetting rows measure, and what they do not

The rows that begin "Forgetting at" were taken on 2026-10-02 by
`src/data/message_cache/what_forgetting_costs.rs`, a module of the mail
store compiled only for tests (13-44.9). They answer, with figures, the
question put to Pratik on 2026-09-30: whether every write should overwrite
the space it frees, or a command should compact the mail database. The
module's header says what each step does; the short form is here.

**The mail.** Each store holds 12,872 or 200,000 synthetic messages. All
but 1,000 are written the way an IMAP check writes them: headers in batches
of 500, then each message's text. The other 1,000 are written the way a POP
check writes them, each carrying one planted word in its subject and text
that no other message carries, then marked read and deleted into the shared
Trash. The planted texts are short enough to be stored as text rather than
packed, so a byte search can see them.

**The three settings.** SQLite's secure delete decides what a write does
with the space it frees. Off leaves the old bytes. On overwrites them with
zeros. Fast overwrites them only where that costs no extra disk writes,
which leaves free pages holding old bytes. Each setting is set on a fresh
store's connection and read back before the mail is written. Off was the
program until 13.1-03; since then every connection the program opens is on.
13-44.8's removal switches secure delete on for itself whatever the setting,
so the setting decides what every other write leaves.

**The rows of 2026-10-03.** 13.1-03 took the measurement again at
`cd22f70c`, after turning secure delete on for every connection, and added
the thirty secure delete rows of that run below 13-44.9's, which stay as the
series; the VACUUM and incremental vacuum rows it printed are not added,
because no command is built. Each setting is still set by hand on its store,
so the off rows measure the old behaviour and not the program. After the
next check, on left 0 of 1,000 at 12,872 and 1 at 200,000, fast 1 and 0,
and off 0 and 7. At 200,000 on wrote 1143 messages a second against 1258
for off, about 9% slower in this one run, where 13-44.9's pair was within
8%; the emptying and the compaction were level.

**What each setting's rows time.** The writing row is the whole write as
messages a second, the reading and deleting of the 1,000 included. The size
row is the file and its write log once the mail is written. The emptying
row is the 1,000 taken off through `local_delete::perform`. The compaction
row is the next check's `let_the_search_index_forget_what_was_taken_off`.

**The two commands.** Both run on the store written with secure delete off.
VACUUM rewrites the whole file. Then `PRAGMA auto_vacuum = INCREMENTAL`,
which takes a VACUUM of its own, a second 1,000 planted and taken off, and
`PRAGMA incremental_vacuum`, which hands the free pages back and shortens
the file. Each runs while the temporary folder and the write log are
sampled every 2 ms, and while a second store on the same file, on another
thread, reads the Inbox and then writes one message, as the window would
during a check. `TMP` and `TEMP` point at a folder inside the run's
directory, because SQLite on Windows takes its temporary folder from them,
and that folder is the one sampled. A second connection's row says whether
it began while the command ran; one that began after says nothing about
waiting.

**What the keep rows count.** Each "what the file and its write log keep"
row counts the planted messages whose word is still in `message_cache.db`
or `message_cache.db-wal`, read as bytes, and its conditions say where each
copy lies: on a page of a named table or index, on a free page, or in the
write log. The settings are read after the next check. The commands are
read straight after they finish, with nothing checkpointed, so a copy in a
free page or the write log after VACUUM is one that stays until a
checkpoint copies the write log into the file and cuts the file to its new
length.

**One run each, and runs vary.** Every figure is one run. The small-size
finding in the same module takes 300 messages off with secure delete off,
and over fifteen runs on 2026-10-03 it left copies of one message in eight
and none in seven, because which earlier versions of a row survive depends
on the lengths of the times the store writes. So 9 of 1,000 against 1 of
1,000 is a difference worth reading from one pair of runs, and 0 against 1
is not a difference at all.

**What none of it sees.** A copy the search index keeps in a form a byte
search cannot match, because FTS5 stores most words as the letters that
differ from the word before. Text stored packed. Anything the disk or
Windows keeps outside the two files. SQLite's pragma page, read on
2026-09-30, says the FTS5 tables "might leave forensic traces in their
shadow tables even if the secure_delete pragma is enabled".

**What the rows show.** After the next check at 200,000, secure delete off
left words of 9 of the 1,000 messages, all in unused space on pages of
`messages`, and on and fast left 1 each. At 12,872, off and fast left none
and on left 1. No setting moved the cost of a check's writes, the emptying
or the compaction by more than 8% in these runs. VACUUM took 5.07 s at
200,000 and peaked at 349.0 MB of temporary disk and 352.0 MB of write log,
each about the size of the 358.6 MB file. The second connection's write
began 2.21 s in, waited 2.31 s and succeeded, so a write arriving at the
start would have waited about 4.5 s against the store's 5 s busy timeout;
that 4.5 s is derived from those two figures, not measured. Read straight
after it, VACUUM left words of 9 messages on free pages and in the write
log. Incremental vacuum took 1.5 ms at 12,872 and 0.3 ms at 200,000 and
left words of 4 and 7 messages. What follows from the figures is ledger
788, for Pratik.

## What the coverage rows count

The coverage rows were taken on 2026-09-14 by `cargo llvm-cov --lib
--summary-only`, the command the 2026-07-26 reading of 60.4% came from, so
the whole-library figure is the same quantity as that one and the gap between
them is real. `--lib` means the library's own tests under `#[cfg(test)]` and
nothing under `tests/`: none of the integration targets ran, including the
ones that open a window. Line coverage is what the rows give; regions,
functions and branches are in the same output and are not written here.

The area rows are not separate runs. The one run leaves its profile data
under `target/llvm-cov-target`, and `cargo llvm-cov report --json
--summary-only` reads that data back per file in about a second without
building or running anything. Each area row is the sum of the covered lines
and the sum of the lines over the files it names, from that per-file table,
with both sums in the value so the percentage can be checked by division.
The per-file table's own total agrees with the summary's `TOTAL` line to the
line, and the row for the table says so.

The areas are the ones `PERF-05` names in `.planning/REQUIREMENTS.md`,
chosen before the run and not from it: the wire protocols under
`src/service/protocols/`, the two OAuth files, and the six provider clients
for Google, Microsoft Graph, CalDAV, CardDAV and OneNote. One more row is
the low area the run found outside those three, the wxWidgets windows, which
is reported on its own so that a reader can see it is not covered by the
attribution the requirement gives.

## What the mutation rate rows measure, and what they do not

A mutation run costs two things that scale with different counts. Each
shard pays once for the copy of the tree, the build and the baseline run
before its first mutant, plus the tool's bookkeeping between mutants; each
mutant then pays a rebuild and a suite run. The `timed:` line
`scripts/mutants.sh --shard` prints after a shard keeps the two apart, and
the rows below quote them apart, so a product over the whole tree is the
rate times the mutant count plus the fixed cost times the shard count, and
not one rate under conditions nobody wrote down.

The rate rows were taken on 2026-09-15 on shard 0 of 496, which the tool's
slice sharding fills with the first 25 mutants of its list, all in
`src/presentation/accessibility.rs`. Most of the presentation layer depends
on that file, so each mutant rebuilt 58 to 75 s where the guard-record rate
row above reads 44 to 46 s for a rebuild after a one-file change in
`src/presentation/managers.rs`. Read the rate as a rate for a file at the
heavy end, and the products as what the tree would cost if every file were
that file. A shard of a leaf module rebuilds faster; nothing here measured
one.

Two of the four runs the rows come from could not be the runs the plan
asked for, and the rows say which. The every-target shape cannot run in a
scratch copy at all: the tool copies the tree without `.git`, and
`test_the_share_of_history_before_red_green_is_computed_and_printed` runs
`git merge-base`, so that baseline fails in the copy and the tool refuses
to start. It ran in place instead, which is the only way it can. And the
every-target shape is `-- --all-targets`, the way the gate runs the suite;
the tool's own default, nothing after `--`, also builds and runs every
doctest, which the gate does not.

The runner rows were taken on 2026-09-15 from two dispatches of
`.github/workflows/mutants.yml`, one runner per shard, and read from each
shard's own `timing.txt` after `gh run download`. A runner's rate is given as
a median and a mean over the shards rather than one figure, because the
shards differ by a factor of nearly three on the same machine class: a shard
whose mutants the compiler mostly rejected pays a build and no run for each,
and a shard whose mutants all reached the suite pays both. The fixed term on
a runner is a build from nothing unless the workflow's cache had been filled
by an earlier job, and the rows say which shards had it.

## What the Settings rows time, and what they do not

The Settings rows were taken by `tests/the_settings_dialog_opens_in.rs`,
the harness written for #34 on 2026-09-16, whose header defines each term;
the short form is here so the rows can be read without it.

**Built** is the span of the line the application writes, `settings built
in N ms`: from the top of the window's `ID_SETTINGS` arm, where `Ctrl+,`
lands, to the moment before `show_modal`. It holds the configuration read,
the calendar-server query and every page's controls. It is not the tester's
"until the dialog is spoken and takes keys": the show, the focus landing and
the screen reader's first announcement all come after that moment, and no
row here can see them.

**A candidate on its own** is one of the three things the build asks the
machine for, timed in a test process before any window exists:
`spellcheck::available_languages()`, `fonts::installed_families()` and
`SoundScheme::discover`. Each row gives the first run, which is what a
process pays the first time it asks, and the median of five.

**The dialog build in a test process** is `build_settings_dialog` with a
default `AppConfig`, no accounts and no calendar server, five times under
one `wxdragon::main`, each dialog destroyed before the next is built. It
includes the three candidates, so the difference between it and their sum
is what building the pages of controls costs.

**The release binary's own line** is the built line read off the log of the
release binary started against a throwaway profile with no account, with
Settings opened five times in one process through the same menu command the
accelerator sends and closed each time. The first open is on its own, the
median of five beside it. The harness sends nothing to any window it did not
start.

**The first visit of each later tab** is what showing each tab after General
costs the first time, in the test process, on one more dialog built after
the five: since 09-09 a page is built when its tab is first shown, so this
is where the cost that left the open went. The test process's frame is never
shown, and a scratch run on 2026-09-16 that showed it found every control
about twice as dear under the screen reader running in this session; the
figure understates what a person with a screen reader pays by about that
much, and the release binary's line is the figure that counts for the open.
