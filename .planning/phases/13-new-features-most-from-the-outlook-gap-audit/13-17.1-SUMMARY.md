# Phase 13 Plan 17.1: Keys locked with a passphrase Summary

A PGP key locked with a passphrase is now imported and kept as it came, and the key manager
lists it as "Private key, locked with a passphrase". Opening a message that needs it in either
reader window, alone or as a conversation, first opens Unlock a PGP Key: it names the key from
the key itself, asks for the passphrase in a password field named Passphrase where focus lands
and which takes a paste, and says the passphrase is remembered until Wixen Mail closes and
never saved. The right passphrase is held in memory as the OpenPGP crate's own type, which
clears its bytes when dropped, and opens every message to that key until the program closes or
the key is removed. A wrong one asks again, saying so first. Cancel, the preview pane and
Space's second press say a fifth reason: the key is locked and the reader is where to type it.
GAP-03 is ticked.

`actuals.tokens` is chars/4 over the lines added under `src`, `tests`, `guards`, `docs` and
`.github` against `main` at `ce37a03d`, about 86,000 characters with the pages.

**The fixture.** Dave's key, locked by GnuPG with `correct horse`, came with 13-16. The message
to him is new, made the same way as the others:

```text
GNUPGHOME=/c/g171 gpg --batch --pinentry-mode loopback --passphrase 'correct horse' \
    --import dave_locked.asc
GNUPGHOME=/c/g171 gpg --batch --armor --trust-model always --encrypt \
    -r dave@example.com -o to_dave.asc to_dave.txt
gpg --batch --pinentry-mode loopback --passphrase 'wrong' --decrypt to_dave.asc
    -> gpg: decryption failed: Bad passphrase
gpg --batch --pinentry-mode loopback --passphrase 'correct horse' --decrypt to_dave.asc \
    | cmp - to_dave.txt
    -> same
```

## Deviations from Plan

**1. [Shape] Dave's key, and a new message to him, stand in for Alice's key locked anew.**
13-16 had already made a GnuPG-locked fixture; a message to it is all that was missing.

**2. [Shape] `TheKeyIsLocked(LockedKey { whose, fingerprint })`, not `{ whose }`.** The reader
has to name the key to `unlock` it, and `whose` is for people. `Unlocking` has a fourth answer,
`TheKeyCouldNotBeRead`, for a credential store that will not give the key back, since answering
`NoSuchKey` there would be false.

**3. [Rule 1] Which key a message needs is read from its recipients.** With every key offered to
the crate, a locked key with no passphrase and a message meant for somebody else both end in the
crate's `MissingKey`. The open path reads the message's own list of public-key recipients, the
list the crate chooses a key by, and answers `TheKeyIsLocked` only for a locked key it names.
`test_a_message_to_somebody_else_is_not_reported_as_locked` holds it.

**4. [Rule 2] The held map is one per test under test.** A process-wide map would let one test's
passphrase open another's key while they run side by side; under `cfg(test)` it is thread-local,
as the credential store under test is. The production map is a `LazyLock<Mutex<...>>` in
`keys.rs`, the only place `Password` is named.

**5. [Shape] The File menu's refusal of a locked key is gone**, with
`WhatImportingAKeyFound::TheKeyIsLockedWithAPassphrase` and
`WhatBecameOfAKey::LockedWithAPassphrase`: nothing produces either now. The limits sentence
was rewritten in task 1 rather than task 2, because keeping a locked key turns its old case red
the moment import changes.

**6. [Scope] A conversation asks too.** The plan named the reader's open path; a conversation
opened in either reader window is that path for several messages, so it asks once per locked
key before its parts are built. One message chosen from the conversation asks through
`open_single_message`.

**7. [Rule 1] The ask comes before the reading is timed.** Opening is reading (#25), and the
main timer marks a message read after a wait counted from the open. Timed before a modal dialog,
the minutes spent finding a passphrase would count as reading it.

**8. [Rule 2, safety] The open path's case is in the library, not the target.** An integration
target is built without the test backing, so importing Dave's key there would write it to the
credential store of whoever runs the tests (13-17's deviation 1). The target holds the dialog
and the reading of `wx_app.rs`; `application::pgp_keys::tests::test_a_message_to_a_locked_key_opens_once_its_passphrase_is_typed`
holds the open path through `put_together`, `the_locked_key_it_needs` and `unlock`.

**9. [Rule 2, safety] The paste runs on a clipboard of the test's own.** The plan asked for text
on the clipboard and `WM_PASTE`, and 13-17 had refused the real clipboard in a test for
overwriting what the person running it had copied. The target moves its window thread onto a
window station and desktop it makes before any window exists; a named window station was
refused with error 5, the unnamed one works. Focus was read with `GetFocus` there, and none of
it reached the screen. Logged as observation 0863.

**10. [House rule] The label is "&Passphrase", without a colon.** The first green run found the
field named "Passphrase,": `name_from_label` turns a trailing colon into a comma, on purpose,
for a pause before the role. The password fields of Add Calendar and Add Address Book carry no
colon, and neither does this one now. The target's two expectations changed with the green: the
label, and the wrap's line breaks read as the spaces they replaced.

**11. [Order] The reason line is said first**, before the sentence it qualifies, so a person
hears that the passphrase was wrong before hearing the question again.

**12. [Rule 1] The fifth sentence ends with its siblings' clause**, "What is shown below is the
encrypted form rather than the message.", because the body below it is still the armour.

**13. [Shape] The `:1803` record was re-anchored, not only re-measured.** The fifth reason is a
sentence of its own words, so the function returns a `Cow` and the four arms lost their
`Some(...)`; the anchor line changed with them.

**14. [Shape] The `wx_app.rs` record's break removes the ask from `open_single_message`.** The
plan's break, the preview asking too, cannot compile: the preview has no window to hang a dialog
on. That direction is held by the target's planted companion.

**15. [Rule 2] The Kind column is wider**, 230 rather than 110, so "Private key, locked with a
passphrase" is not cut off for somebody reading the screen.

**16. [Brief] A scan target, `unlock-a-pgp-key`, and the shortcuts page in task 2.** The brief
asks every new control to be verified through the scan and every key to reach the shortcuts
page in the commit that adds it. `docs/ALPHA_TESTING.md` also said a locked key could not be
imported and was corrected.

**17. [Brief] The banned tool's name, again.** Two read-only commands began with a do-nothing
assignment carrying `sed` in a variable name (`sed_none=;`, `sed_free=;`), the second minutes
after the first was logged. Neither tool ran and nothing was written through them. Logged as
observation 0864.
