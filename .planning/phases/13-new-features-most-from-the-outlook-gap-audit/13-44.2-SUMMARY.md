# Phase 13 Plan 44.2: a sign-in refused at OK, and the account's name Summary

Look People Up at Work refuses a sign-in name for an `ldap://` address when OK is pressed,
in the sentence a lookup says, with focus on the Directory address box and nothing written;
a password the Windows credential store will not keep is named by the account's name or as
"this account's password", never by its id; and the marker reading no longer fails when two
runs of it overlap.

## What works, and how it is known

- **The refusal at OK (ledger 699).** `what_the_window_keeps` answers
  `Result<WhatIsKept, NotKept>`; one arm after the no-name arm refuses any sign-in name over
  an address `directory::is_reached_without_encryption` reads as `ldap://`, whatever the
  password box holds and whether a password is saved, with
  `directory::no_password_is_sent_unencrypted_to(host)` and `TheBox::Address`.
  `keep_what_the_directory_window_holds` maps the box to the control. The lookup calls the
  same sentence function and the same scheme reading (`is_encrypted_by_its_scheme`), so the
  two cannot drift. Read in the built window by
  `test_a_sign_in_over_an_unencrypted_address_is_refused_at_ok_with_focus_on_the_address`:
  the window stays shown, its line equals the lookup's sentence, and focus is on the
  control named "Directory address," that is not a password box.
- **The store's sentence (ledger 696).** `credentials::store(account_id, called, password)`;
  `whose_password` gives "the password for Work", or "this account's password" for a blank
  name; `load` and `forget` say "this account's password". The private helpers keep their
  signatures and first lines; the public functions make the sentence. `save_account` passes
  `&account.name`, the load passes the name to `move_password`, whose log lines keep the id.
- **The marker reading (ledger 754).** `OneRunAtATime` takes a named mutex,
  `Local\<executable>-one-run-at-a-time`, before the reading opens a window, and waits up to
  five minutes for another run of the same executable.

## Ledger 754: the cause, with the runs

The cause is in the reading, not the editor. WebView2 runs one browser process per user data
folder, and the editor's folder is `%LOCALAPPDATA%\<test executable>\EBWebView`, named for the
executable. Two runs of the target at once share one browser and, through it, one keyboard
focus; the run log showed both processes posting to the same window handle.

The one red in each "after" row lost its keys at the start of a batch ("the page never saw"),

## Deviations from Plan

**1. [Safety] The window reading over `ldap://` presses OK with the password box empty, not
with a typed password.** Against the red, which had no scheme rule, the save with a password
typed was kept: the target, which only ever presses refused saves, headed for the credential
store of whoever runs it and hung on the window closing. The process was stopped and
`cmdkey /list` showed no Wixen entry. An empty box is refused either way, for the missing
password in the red and for the address in the green, so the red stays harmless; the
typed-password case is held by the rows. `refused_with` takes the address alone.

**2. [Order] The encryption record was rewritten in the red, measured in the green.** The
extraction landed in the red, which removed its anchor; rewriting it there kept the anchor
check green, and a remeasure cannot run on a red tree.

**3. [Brief] Ledger 754 fixed in the test, without a red commit.** The failure is not a case
that fails every time on one run, so nothing could be named under `Fails-until-green`; the
runs before and after are in the commit message and above. Two shapes were tried first and
dropped: posting keys only to windows under the run's own editor stopped letters crossing
and still lost them; a fresh user data folder per run was measured during the hour first runs
were losing keys anyway, so it could not be judged, and the mutex keeps the folder every
run used before.

**4. [Measurement] One task 1 record came out short** and was corrected by hand, as above.

**5. [Tooling] An Edit appending task 2's record split task 1's focus record from its
`tests_last_seen`**; the remeasure rewrote the block under the new record, the count check
caught it, and the two lines were put back from `9bf185ff`.

**6. [Brief] Read-only tooling.** Python read the TOML, the ledger's JSON and long lines of the
planning files; nothing tracked was written by it. No `sed` or `awk`. Throwaway probes of the
marker target were made with Edit and undone with `git checkout -- <file>`; every tracked file
was changed with Edit or by `cargo fmt`.
