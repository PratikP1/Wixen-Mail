**2. Why a token per permission, which RESEARCH-3 did not weigh.**
`refresh_with_scopes` sends the scopes on a refresh (`oauth.rs:251-275`).
Microsoft's page "Microsoft identity platform and OAuth 2.0 authorization
code flow" (learn.microsoft.com, read by the planner on 2026-09-24, the
page dated 2026-01-09) says of a refresh's `scope`: "The scopes requested
in this leg must be equivalent to or a subset of the scopes requested in
the original `authorization_code` request leg." Read that way, adding
`People.Read` or `Tasks.ReadWrite` to the shared list asks, for every
account that signed in before the permission was on the consent list,
for something its sign-in never covered, and the shared token feeds
contacts, calendar, free/busy and notes: all four could stop for those
accounts until they signed in again. Nothing here can run that against
Microsoft, so it is a reading of the documentation and not a
measurement; the per-permission token removes the risk whichever way
Microsoft behaves, for the cost of one function. The executor quotes the
sentence in the summary.
