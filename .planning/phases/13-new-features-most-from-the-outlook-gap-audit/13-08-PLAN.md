```
sed -n 405,425p src/application/moves_waiting.rs   -> undo_here(cache, waiting): the row back in the folder and under the number it never left (or a copy made here gone), the waiting row gone, bytes held for a crossing let go; used today when the server refuses (wx_app.rs:19967)

```

So: while a waiting row exists, the server has not heard, and the undo
is `undo_here`, which ends the row and puts the message back without
asking the server anything. Once the row is gone and the message's row
carries its new folder and number, the undo is a new move back through
the same path the action took. When the row was dropped because the
server could not say where the message landed, this computer holds
nothing to move, and the undo says to refresh the folder. The one case
not answered by reading is a push in flight at the moment of the undo:
task 1 reads the push (`complete_here_then_tell_the_server`'s
background half, from about :21633) and the in-flight marker, and the
decision refuses with a sentence to try again when a push for that
message is under way, rather than racing it.

| a waiting row and a background push | two threads that may reach one message |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|

| T-13-27 | Denial of service | an undone copy deleting the wrong message outright | high | mitigate | a copy's undo goes to the trash, never outright; a guard record holds it |
