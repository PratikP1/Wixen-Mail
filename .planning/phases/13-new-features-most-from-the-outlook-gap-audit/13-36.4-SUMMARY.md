# Phase 13 Plan 36.4: One day of a repeating meeting, answered Summary

**An invitation for one day of a repeating meeting is now offered Accept, Tentative and
Decline, the reply names that day, and the answer is filed on that day alone; a whole
repeating meeting answered stays repeating here and in what a calendar server would be
sent.** On a calendar server or a calendar kept here the day is kept apart with the answer's
busy, tentative or free; on Google, Outlook or a calendar only read the calendar is left as
it was and the status line says so after the answer.

## What runs now

A button or the list's menu reaches `wx_app::answer_the_invitation`, which asks
`answering::whether_it_can_be_answered` (the day read off the meeting's own lines), builds
the reply through `invitations::a_reply_to` (the day's `RECURRENCE-ID`), queues it, then
calls `answered_meetings::file_the_answer`. For one day that asks
`one_day_of_a_series::what_the_calendar_holds_for_that_day` and either answers on the day's
own row, keeps the day apart through `reading_a_message::the_day_kept_apart_saved` (13-36.3's
order), files the day alone, answers a single appointment at that day's time as the meeting,
or answers `Filed::LeftAsItIs`, which the handler says through `what_answering_said` in its
one `send_status`. The buttons read the earlier answer from that day's row. The new target
walks this from raw invitations to the reply and the rows the calendar panel shows.

## Deviations from Plan

**1. [Premise] The reply is read as `the_answer_to_send` builds it, not from the outbox.**
The queue lives in the main window's state, which the target does not start; the document
it reads is the one `send_the_answer` writes. The handler's flush and single status line
stay held by the two existing source readings, which pass.

**2. [Shape] One-day filing returns `OneDaysAnswer`,** a two-arm value saying filed or
"file as the whole meeting", so a single appointment at that day's time goes through the
whole-meeting lines in `file_the_answer` without moving or repeating the four anchored lines.
`what_answering_said` is the handler's wording of `Filed`, a pure function the target tests,
rather than a match in the handler.

**3. [Rule 2] The value written back is checked for the calendar format's shape.** The plan
rebuilt the line from the value and the zone; a stranger can also write text after the
value, so `the_day_named_on` keeps `as_written` only when it is eight digits, or that, a `T`
and six more with an optional `Z`, and refuses anything else with the unreadable-day sentence
(T-13-36.4-01). A quote mark in the zone is dropped, as a name's is.

**4. [Environment] The green commit for task 2 was refused while this machine's session was
locked.** `a_locked_key_asks_for_its_passphrase` reaches `wx_app.rs` and fails six cases
with "OpenClipboard failed" whenever LockApp and LogonUI run, which is ledger 716; it was
the only target that failed. The commit waited about five hours for the session to be
unlocked, polling for LogonUI, and was made again at 02:08; nothing in the code changed
between the two tries. The documents in this commit were written during the wait.

**5. [Record] "a series sent with a changed day is answered as the series" was written in
task 1 and rewritten in task 2,** whose own text replaced the line it anchored on; measured
both times. Observation 0912.

**6. [Brief] A read-only command carried the text `sed_is_not=1;`,** an assignment that runs
nothing. No file was changed by it.

**7. [TDD] Every expected value was reasoned before its green.** The reply lines from the
three shapes of `RECURRENCE-ID`; the declined day's rows by date against the series' EXDATE
and the kept row; the Google sentence from `WhereAChangeGoes::named`; the lone day's key
against `what_the_calendar_holds_for_that_day`'s `day.at` when nothing is held. Two target
cases passed on the stub, as they should: the series repeating is task 1's, and the
companion's plant was already refused.
