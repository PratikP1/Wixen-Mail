<objective>
A rule that adds a label puts the label on.

Purpose: RESEARCH-4's finding F1, derived from the code and not yet
run: `FilterAction::AddTag` carries the label's typed name, and
`carry_out` passes that name to `add_tag_to_message` as a `tag_id`, a
foreign key into `tags(id)` with foreign keys on for every connection,
while every label id in the tree is `tag-<uuid>` or
`<account>:<keyword>`. So the insert is refused, `apply_rules` logs "A
rule could not be carried out", and no label arrives. The one target
that runs such a rule asserts only the sound count, so nothing has
caught it. Quick Steps and a rule run over a folder reuse this
vocabulary, so it is fixed before them; that is why the cross-check
moved it ahead of 13-25.

Output: the resolver, the fix in `carry_out`, the target that takes the
defect red first, the changelog and the ledger.
</objective>
