# Phase 13 Plan 44.6.1: The Clipboard When the Session Is Locked Summary

**The passphrase dialog's reading no longer opens a clipboard, so a locked Windows session cannot fail it. The real paste runs in a target of its own that only a change to the passphrase dialog reaches, and a refused clipboard fails that target with one sentence naming the cause, the lock as Windows reports it.**

This plan was finished by a second executor. The first stopped when the hook's clipboard test refused its red commit on a locked session (ledger 716 itself). Its red for task 1 was saved as a patch; this executor applied it with `git apply`, checked it gave exactly the planned red, committed it, and built the rest from the first executor's drafts, compiling and checking each piece. The lock was read before every commit through `WTSQuerySessionInformationW`, never from `LockApp.exe`, and Windows reported the session unlocked each time.

## Deviations from Plan

1. **Finished by a second executor.** The first stopped on a locked session; its red patch for task 1 was applied as saved and its drafts used as a starting point. Task 1's green differs from the original harvest in one place: the companion field is built on the first dialog, since the dialog asked again no longer exists in the paste target.
2. **[Rule 1] The turn record's break skips the wait rather than waiting 0 ms.** Five runs of the plan's 0 ms break reddened the turn case alone, but a 0 ms wait also refuses this target's own harvest whenever the turn case holds the turn when the harvest asks, so the red list could change with thread timing. Skipping the wait reddens the turn case alone every time.
3. **Two records redden two tests where the plan expected one.** The lock-state break also fails the held-throughout case, which asserts the session unlocked; the brief-hold break also fails the locked sentence's "50 tries". Each record names what really went red.
4. **[Rule 2] The holding thread checks its desktop and its window.** If `SetThreadDesktop` or `CreateWindowExW` fails it says so in a sentence. A hold through no window refuses nobody (premise 5), so carrying on would turn the held cases into a reading of nothing.
5. **The turn case records "first refused" as well as "first took"**, so a first thread that could not take the turn is not written down as having taken it.
6. **Five extra rounds started together**, because two runs half a second apart barely overlapped. Those rounds show the second run waiting.
7. **No commit on `main` after the merge.** The plan's verification asks for one adding the merge's mode line to this summary; the brief for this run allows one documents commit before the merge and nothing after, so the merge's mode line is in the run's report instead.
8. `progress.completed_plans` in `STATE.md` went from 231 to 232, as 13-44.6 did for its own.
