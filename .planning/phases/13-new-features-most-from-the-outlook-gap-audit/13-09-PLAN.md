Taken 2026-09-24 against `main` at `630e2a67`. The research said a
delete in these modules could be undone "by recreating from the record
the undo kept, with the deletion note removed when the provider has not
taken it". Reading the store today found that removing such a note is
exactly what this codebase forbids callers to decide for themselves, so
premise 2 says how this plan does it without breaking that rule.

**2. Deletion notes, and the rule the undo must keep.**

```
sed -n 1,90p src/application/deletions.rs   -> contacts, events and tasks keep a note when deleted here; "A note is also refused outright to anybody asking to drop it while a provider could still name the thing ... Contacts have no way to drop a note at all. Every one of these refusals exists because a caller decided for itself that a note was safe to drop and put a deleted thing back on the screen."
grep -n 'CREATE TABLE IF NOT EXISTS deleted_' src/data/message_cache/mod.rs   -> deleted_contacts :2068, deleted_tasks :2490, deleted_calendar_events :2513, deleted_notes :2546; no table for reminders
sed -n 720,746p src/data/message_cache/calendar.rs   -> forget_deleted_calendar_event drops a note only WHERE provider_event_id IS NULL, an event never sent; a note naming a provider's event stays until the clock releases it
grep -n 'pub fn forget_deleted_task\|pub fn the_provider_took_the_deletion_of_a_task\|pub fn the_address_book_took_the_deletion\|pub fn a_backend_took_the_deletion_of_a_note' src/data/message_cache/*.rs   -> tasks.rs:526 and :493, contacts.rs:1111, notes.rs:629
```

A deleted synced item whose deletion is still owed carries a note the
push will send. Undoing it must stop that send, which means dropping an
owed note for a thing a provider can name, which the rule forbids to
any caller that decides it alone. So the undo is not such a caller: it
is one store operation, `take_a_deletion_back`, per kind, that in one
transaction restores the row from the record the undo kept and drops
the note only if it is still owed (not taken), and refuses a taken note
by leaving it. `deletions.rs`'s header gains a paragraph naming this as
the one path allowed to drop an owed note of a synced item, and why it
cannot resurrect anything by mistake: it is the person asking for the
thing back, and the row and the note change together. A taken
deletion is answered by a new item made from the record, with no
provider identity, which the push sends as any new item.

The race: a push that has sent the deletion but not yet recorded the
provider's answer. Task 2 reads how each sync marks its push under way
(the contacts, calendar and tasks syncs), and `take_a_deletion_back`
refuses while one is, with a sentence to try again.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a deletion note and the push | the note is what stops a sync writing a deleted item back down |
| a local undo to a provider | a restore or a new item sent to Google, Microsoft or a CalDAV server |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-30 | Tampering | a deleted item resurrected by a note dropped on its own | high | mitigate | the note is dropped only inside `take_a_deletion_back`, in one transaction with the row, only while owed; a rollback case and a guard record hold it; `deletions.rs` names this as the one path |
| T-13-31 | Tampering | an undo racing a sync's push of the same deletion | high | mitigate | refused with a sentence while a push is under way; a case holds it |
| T-13-32 | Tampering | an undo sent when the account forbids changes | high | mitigate | the restore and the new item go out through the sync's own push, which asks `allowed_for(account).personal_information` as any edit does; the executor quotes the line |
| T-13-33 | Information disclosure | a deleted item's record held beyond its step | low | mitigate | held in memory in `last_action` only, replaced by the next action, never written to disk or the log |
| T-13-SC | Tampering | npm, pip or cargo installs | high | mitigate | nothing is added to the manifest; the summary says so |
