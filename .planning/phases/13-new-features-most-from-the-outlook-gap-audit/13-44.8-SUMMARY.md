# Phase 13 Plan 44.8: Mail taken off this computer keeps none of its words Summary

A message kept on this computer alone and taken off it, by the Empty the Trash setting, Empty
Folder on the Trash, Delete in the Trash, Delete Permanently or a redo, now keeps only its POP
identifier, download time, owner and place; everything else it said is removed under secure
delete, and the search index lets go of the words at the end of the next check for mail.

## What works now

- **The removal** (`MessageCache::take_off_this_computer`). Under secure delete, switched on by
  `OverwritingWhatIsFreed` and put back to what it found when dropped, in one transaction: the
  kept columns read, the row removed (so the six foreign-key tables cascade, `attachment_file_gone`
  takes a file nobody else carries, `message_gone_from_search` tombstones the entry), the row
  written back under its own id with `KEPT_WHEN_TAKEN_OFF`, `deleted` 1, the NOT NULL columns
  with no default empty and every other column its default, the Trash stamp the insert trigger
  wrote removed, an empty search entry written, and one more removal counted in
  `search_index_owes_a_compaction`.
- **The arm.** `local_delete::perform`'s `RemoveFromThisComputer` calls it; its sentence stays
  "Deleted from this computer". 13-44.7's POP emptying, Empty Folder, Delete, Delete Permanently
  and a redo all reach it through that arm. A rule's Delete still calls `delete_message` (D33).
- **The index letting go.** `spawn_mail_sync` calls `the_search_index_forgets_what_was_taken_off`
  after the account loop and before `if nothing_went_through {`, so a check of POP accounts alone
  reaches it. It opens its own cache and calls `let_the_search_index_forget_what_was_taken_off`:
  nothing owed, nothing done; otherwise FTS5 `'merge'` statements of `-64` pages
  (`MERGE_PAGES_A_STEP`) under secure delete until one changes fewer than two rows or 10,000
  (`MOST_COMPACTION_STEPS`) have run, then `PRAGMA wal_checkpoint(TRUNCATE)`, whose refusal is
  logged, and the record settled only while its count is unchanged. One log line: steps and a
  verdict.
- **Nothing spoken or shown changes.** Premise 9's command exited 1 at the start and at the end:
  13-44.7's description says nothing of emptied text, so the constant was not touched and the
  branch was not pushed.

Reachability: a delete or emptying in the running program reaches the arm through the paths
premise 1 lists; every check reaches the helper, held by the reading in the new target.
Nothing has met a real POP server (ledger 787).

## Deviations from Plan

**1. [Rule 2] Preconditions in the cases that would otherwise pass against the stub.** The
still-mail, twice, shared-file and `pop_sync` cases each first assert the message really was
taken off (its subject empty, or its attachment gone). Without that, a stub doing nothing passes
them; with it, all were red at the first red, so the `pop_sync` case is in its trailer as the
plan's acceptance asks. The plan's own text expected it might pass.

**2. [Rule 1] A removal left the search index short, and every open would have rebuilt it.**
`build_any_missing_search_index` runs on every open and reindexes every message when the index
holds fewer entries than there are rows. The written-back row had none, so the first open after
any removal would rewrite every message's words into the index. Shown red at `9be4b2f7`
(`left: 2`, two messages reindexed), fixed at `08ff9847` by indexing the written-back row, which
holds no word. The secure-delete put-back case came with it, passing, taken red by its record.

**3. [Shape] The kept list is a slice, `&[&str]`, not `[&str; 8]`,** so a guard's break adding a
column is one contiguous edit.

**4. [Shape] The window's call sat after the return at the red** rather than being absent, since
an uncalled private function is a dead-code refusal from clippy (13-44.6 and 13-44.7's finding).
The reading was red on it; the green moved it before the return.

**5. [Shape] Two more guard records than the plan named** (the overwrite and the put-back of
secure delete, and the index level), nine in all against six.

**6. [Measurement] "Nothing else compacts the index" passed at the red,** since nothing called
the function; it was taken red by hand with an untracked file planted under `src/` and removed
straight after.

**7. [Docs] The changelog's "Deleting does not erase" is under `[Unreleased]`, not a released
entry** as premise 2 said, so it gained a dated sentence saying it is now true only of a rule's
Delete, rather than being left contradicting the new Changed entry.

**8. [Brief] Read-only tooling.** Five read-only shell commands carried a do-nothing assignment
named after the banned text tool (the slip 13-44.6 and 13-44.7 recorded); no such tool ran and
nothing was written by them. Python read the TOML, the ledger and STATE's long lines. Every
tracked file was changed with Edit or Write or by `cargo fmt`; breaks were taken with Edit and
