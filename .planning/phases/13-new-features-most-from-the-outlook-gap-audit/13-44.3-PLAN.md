<objective>
A rule's Mark as read, Mark as unread, Flag, Unflag and Add a label on
arriving mail reach the mail server through the gate and the waiting queue
the menu commands use, in the check that brought the message, and the next
check stops undoing them. A rule's Delete on arriving mail goes to the
Trash at the mail server through the gated delete path the menu's Delete
uses, in the same check, and the next check stops bringing the message
back.

13-36. Item 3: "Rules on incoming mail (Mark as read, Flag, Add a label)
change only the local copy and the next check can undo them (ledger 678)
[send them through the same gated server queue the menu commands use; this
reverses the earlier 'keep it local' decision]." The earlier decision is
the phase README's decision 37, second half, taken on 2026-09-24 and
ledgered by 13-23. Since 13-24.1, Quick Steps (13-42) and a rule run over a
folder (13-44) send the same actions through the runner's do-halves and
`spawn_server_change`; after this plan the check's own arms reach the
server through the same gate and the same queue, which is GAP-12's `[D]`
clause "the run through the same arms a check uses" read from the other
side.

Later on 2026-09-29 Pratik answered "yes." to the question this plan's
planner raised (premise 11 (c), the phase README's decision 107): "Should a
rule's Delete go through the gated delete the menu's Delete uses, to Trash

this plan already uses for the rule's other actions (D10). Today `carry_out`
only marks the message deleted here, and the next check can bring it back
on a server that cannot report only what changed.
