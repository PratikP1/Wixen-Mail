<decisions date="2026-09-24">
**1. When a change reaches the calendar.** Taken 2026-09-24 from the
research's recommendation (question 3); Pratik may overrule: updates from
the organiser applied on opening and said; cancellations shown with a
Remove from Calendar button, the way Outlook does it; never applied for a
message whose sender is not the organiser.

**2. What "the calendar's copy's version" is.** The version answered here
where one was (`the_version_answered_here`); where none was, an update
counts as a change when its start or end differs from the copy's. A copy a
provider already moved (Gmail and Exchange apply updates themselves) then
reads as nothing new. The plan's own reading of the research's "higher
SEQUENCE than the calendar's copy", because only rows answered here record
a version.

**Experimental where the person sees it.** A move or a removal is a write
to the calendar, so it goes through the account's Allow Changes answer, and
that gate's own sentences already say every write is experimental, in the
settings screen, the first-run screen and the end of `--help`
(`application::allowed`); the ledger's phase 14 line is the real-account
check. No second marker is added to the bar, which would be read on every
update.

**3. Decrypted content never changes the calendar on its own.** Taken
2026-09-24 from the research's recommendation (question 9); Pratik may
overrule. This plan's decision reads only stored parts, which are never
decrypted; 13-14 adds the decrypted provenance and the case that refuses it.
</decisions>
