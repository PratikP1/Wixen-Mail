**3. What SQLite says, read on 2026-09-30.**

- `https://www.sqlite.org/pragma.html#pragma_secure_delete`: "When
  secure_delete is on, SQLite overwrites deleted content with zeros." "The
  off setting for secure_delete improves performance by reducing the number
  of CPU cycles and the amount of disk I/O. Applications that wish to avoid
  leaving forensic traces after content is deleted or updated should enable
  the secure_delete pragma prior to performing the delete or update, or else
  run VACUUM after the delete or update." Of "fast": it "will overwrite
  deleted content with zeros only if doing so does not increase the amount
  of I/O", which "has the effect of purging all old content from b-tree
  pages, but leaving forensic traces on freelist pages." And: "the FTS3 and
  FTS5 virtual tables that come bundled with SQLite might leave forensic
  traces in their shadow tables even if the secure_delete pragma is
  enabled", which is why 13-44.8 compacts the index.
- The same page on `auto_vacuum`: "changing from 'none' to 'full' or
  'incremental' can only occur when the database is new (no tables have yet
  been created) or by running the VACUUM command." On `incremental_vacuum`:
  it "causes up to N pages to be removed from the freelist. The database
  file is truncated by the same amount." It says nothing of the unused space
  inside pages in use, which is what the reading below looks at.
- `https://www.sqlite.org/lang_vacuum.html`: "as much as twice the size of
  the original database file is required in free disk space"; "When
  overwriting the original, a rollback journal or write-ahead log WAL file
  is used just as it would be for any other database transaction"; "VACUUM
  (but not VACUUM INTO) is a write operation and so if another database
  connection is holding a lock that prevents writes, then the VACUUM will
  fail"; and "Running VACUUM will clean the database of all traces of
  deleted content".

These are claims the measurement tests, not results: the rows say what this
machine did.
