<objective>
Give a reminder somewhere to go, which is another account, and build the first
PIM move that crosses one.

Purpose: criterion 2 of phase 5, and PIM-02's first `[D]` line, which decision 3
settled as all five modules and decision 4 gave a meaning for. Until 2026-09-06
"move a reminder" had no meaning: `pim_command.rs:49` to 54 says the module
sorts reminders into buckets worked out from when each is due, so there is
nothing to move one between, and `new_item.rs` says reminders sync nowhere and
always will. Decision 4 answers it with the container reminders already have,
which is the account, so there is no new table and no invented concept.

Decision 4 says a reminder moves between accounts "the way mail already moves
between accounts". When this plan was written that precedent was false, and
phase 4.1 has since made it true: `destinations::where_mail_can_go` builds one
`Branch` per account and `where_this_message_can_go` calls it from
`wx_app.rs:17310`, so a production picker offers folders in another account
today. Corrected 2026-09-08, in the same pass that corrected the phase README.

Read that as a smaller job rather than a larger one, and do not go looking for
code to copy. Mail's precedent is a *tree* of folders inside accounts, and this
plan needs a flat list of accounts, which the tree structurally cannot give: see
premise 3 below, where `build_destination_dialog` pushes `None` for every
account row on purpose. `pick_one` is still the right tool and the reason is
unchanged.

Output: a reminder that moves and copies to another account by keyboard, an
account chooser, and PIM-02's first criterion reworded once all five modules
really do it.
</objective>

**1. The container exists and decision 4 is right about that.**
`grep -n "CREATE TABLE IF NOT EXISTS reminders" -A 13 src/data/message_cache/mod.rs`
gives eleven columns: `id`, `account_id`, `title`, `description`,
`due_datetime`, `is_completed`, `priority`, `repeat_rule`, `related_event_id`,

`sed -n '/pub struct ReminderEntry/,/^}/p' src/data/message_cache/mod.rs` gives

**No new table, no new column, no migration.**

**2. `save_reminder` cannot move a reminder between accounts, and this is the
one thing that has to be built in storage.** Read it at
`src/data/message_cache/reminders.rs:36`. It is
`INSERT INTO reminders (...) VALUES (...) ON CONFLICT(id) DO UPDATE SET ...`
and the `DO UPDATE SET` list is `title`, `description`, `due_datetime`,
`is_completed`, `priority`, `repeat_rule`, `related_event_id`, `updated_at`.
**`account_id` is not in it.** So calling `save_reminder` with a changed
`account_id` on an existing reminder writes every other column and silently
leaves the account where it was. A move built on `save_reminder` would report
success, change the title if you changed it, and not move anything. Nothing in
decision 4, in PIM-02, or in the old plans says this.

Whether the answer is a new write or an added column in the `DO UPDATE SET` is
task 1's decision, and it is not a free one: `save_reminder` is called from
several places that are not moving anything, and adding `account_id` to its
update list changes what every one of them does. Read the callers before
choosing. `grep -rn "save_reminder" src/ --include=*.rs`.

**3. A reminder move does not go through `move_item`, and the reason is one
line.** `where_it_could_go` in `src/presentation/managers.rs` opens with
`let holder = kind.kept_in()?;`, and `ItemKind::kept_in`
(`src/application/new_item.rs:56`) answers `None` for `Mail`, `Contact` and
`Reminder`. So `move_item` on a reminder returns `None`, which its doc comment
says means nothing was offered or somebody cancelled, and that is announced as
nothing at all.

**4. The destination tree structurally cannot answer an account, so do not try
to make it.** Read `build_destination_dialog` in
`src/presentation/wx_destination.rs`. For each `Branch` it appends a row for the
account and pushes `None` into the `destinations` vector, then appends each
place and pushes `Some(place.id)`. `what_a_selection_means` returns the entry at
the selected position, so **an account row always means nothing was chosen**,
and its doc comment says so in as many words: "An account heading has a position
and no destination, because it is somewhere to look rather than somewhere to put
something, and somebody who meant a folder and landed on the account gets no
move, which they can see, instead of a move somewhere they did not name."

Three ways to get an account out of that dialog and two are bad. Putting one
`Destination` under each account branch makes the tree read "work@example.com"
and then "work@example.com" again on the row below it, which is a row somebody
hears twice and cannot tell apart. Making one branch stand for "another account"
and hanging the accounts under it as places works, and it makes `Branch.account_id`
a fiction against its own doc comment, which says the field is the address that
tells two accounts apart when read aloud.

The third is to not use that dialog. **A flat set of accounts is a flat list,
and `pick_one` is what this program already uses for a flat list.**
`which_group` uses it, and its doc comment argues for it: "A list also reads the
names out in order, which is how somebody who cannot see the tree finds the one
they meant." That is the recommendation. If you deviate, say why in a paragraph
and name what a tree buys here that a list does not.

**5. `Moving` needs no new variant if `pick_one` is used**, which is most of the
argument for `pick_one`. `Moving` is `Message`, `Item(ContainerKind)` and
`Folder`, and `nothing_to_offer`, `heading` and `nowhere` all match on it
exhaustively with an arm per `ContainerKind`. A reminder is not
`Item(ContainerKind)`, because `ContainerKind` has four variants and none of them
holds a reminder, and adding a fifth would put a "New reminder container" line
in every menu that iterates `ContainerKind::ALL`. Using `pick_one` means none of
those files is touched. Say in the summary that this was the reason.

**6. `file_under` returns success and writes nothing for a reminder, and the
compiler will not tell you.** Its last arm is
`ItemKind::Mail | ItemKind::Contact | ItemKind::Reminder => Ok(())`, with a
comment saying these are never reached because `kept_in` gives them no container
and that they are written out "so a new kind of item is a compile error here".
True of a new `ItemKind` variant, false of `Reminder` becoming reachable, which
is what this plan does. If a reminder move is routed anywhere near `file_under`,
that arm has to lose `Reminder` or the move reports success and does nothing.
The recommendation in premise 4 keeps a reminder out of `file_under` entirely,
which is the safer answer, and the summary should say which route was taken.
