<objective>
Give copy the same shape move already has: one item on the Action menu, one
key, and an answer that follows the module somebody is in.

Purpose: criterion 2 of phase 5. Move ships for events, tasks and notes and is
reached from the Action menu at `Ctrl+Shift+V` and from the context menu in each
of those modules. Copy does not: `ID_COPY_TO_FOLDER` has one handler and it is
the mail one, and `PimCommand` has four variants and none of them copies. The
chooser for a copy, on the other hand, is already written and has never been
reached.

Output: a copy that works in the three modules that have containers.

Contacts and reminders are not in this plan and are not out of scope. They are
`05-04` and `05-05`, and they are separate because they share no code with this
one: a contact move is two writes to `contact_group_members` inside one
transaction, and a reminder move is the first destination tree in this program
that crosses an account.
</objective>

**2. What a copy really differs by is two lines, and they are not the ones the

- `pending` is set by `file_under` for an event and a task already

  columns.
- The provider question answers itself. `tasks_sync::a_provider_holds(id)` is
  `!Provider::made_here(id)`, and `Provider::made_here` is
  `![Google, Microsoft].iter().any(|p| id.starts_with(p.prefix()))`. A copy
  minting a fresh id is made here by construction. **Assert it in a test rather
  than resting on it**, because it is a property of an id prefix and somebody
  could change the prefix rule.
- The third difference the research does not name: `destinations::offer(branches,
  already_in)` removes the container the item is in, with a comment saying
  offering it would be a command that silently does nothing. That is right for a
  move and wrong for a copy. A copy passes `None`.

**3. `moving_can_be_told` refuses a move of a provider-held item, and a copy
must not inherit that refusal.** Read `moving_can_be_told` and
`pim_command::cannot_be_moved` together. The refusal exists because moving a
provider-held item means deleting it there, creating it here and writing the new
identity over the old, and none of that is built. **None of that reasoning
applies to a copy**: the original is untouched, and the new one is a locally made
item the next push creates. So `copy_item` does not ask `moving_can_be_told`.
Say that in the code with the reason, because the tempting thing is to reuse
`where_it_could_go` whole and inherit a refusal that makes no sense.

**4. `can_only_be_read` does apply, and for the same reason.** A calendar this
program can only read cannot take a new event either, and
`pim_command::cannot_be_moved_into`'s doc comment gives the reason: the row
would be filed there, marked as waiting, and every sync from then on would find
nothing that could send it. That refusal is about the destination and applies to
both acts. Its sentence says "moved", so a copy needs its own wording or a
parameter; decide which and say why.
