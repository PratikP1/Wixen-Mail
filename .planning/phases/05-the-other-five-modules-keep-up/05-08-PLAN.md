<objective>
Let a task a provider holds move to another list, and make the failure between
the two calls recoverable rather than survivable.

Purpose: criterion 1 of phase 5, and decision 1 of 2026-09-06. Until now a
provider-held task is refused a move before any window opens, with a sentence
saying why, and PIM-01's criterion about ending in exactly one list "even when
the move fails at the provider" is satisfied by that refusal rather than by
handling. Decision 1 overturns it: build the move, with the local cache as the
safeguard across the gap.

**This is the only work in phases 5, 5.1 and 5.2 that can lose somebody's
data**, and it is deliberately last. `05-06` proved the local half and made a
move say what has and has not happened. `05-07` built the state a half-finished
move leaves behind, made it survive the program closing, and made the push
refuse to delete a provider's only copy. Everything that makes this plan's
failures visible is already in and already tested before this plan writes a
line.

Output: the refusal lifted, a move that is finished by the next successful sync
whatever interrupted it, and an honest account of the one failure nobody here
can produce.
</objective>

**7. What each failure leaves, written out, because this is the whole

- **The create fails.** The row is still pending and is retried on every sync.
  The note is still blocked. The provider still holds the old copy in the old
  list. Nothing is lost; the move has not happened at the provider yet, and the
  sentence `05-06` built already says that is the state.
- **The create succeeds and the delete fails.** The provider holds it in both
  lists. The note is still owed and is retried. Visible, and correctable by
  anybody who looks. This is the failure the ordering was chosen to produce.
- **The create succeeds and the program closes before the delete.** Same as
  above, and the next sync sends the delete, because the note is a row and
  `let_go_of_deletions_taken_before` never releases a note nobody has taken.
- **Allow Changes is off.** Neither call goes. Both are counted, both are still
  owed, and the sync summary says which setting to turn on. `05-06` made the
  move itself say the same thing at the moment it happens.
- **The create succeeds, the delete succeeds, and the pull runs between them.**
  The provider may still name the old copy. `application::deletions`'s whole
  module exists for this: the note is consulted by the read before anything is
  written down, and it is kept for seven days after the provider takes it. This
  is the case that module's header calls the one that was open for a long time.
- **The list the task is moving to is deleted at the provider before the create
  lands.** The create fails for ever, the note stays blocked for ever, and the
  provider keeps the old copy. Nothing is lost and nothing drains. Task 2 has to
  decide what is said about that, and `05-07` task 2 already had to decide what
  happens to a note waiting on something that will never arrive.
