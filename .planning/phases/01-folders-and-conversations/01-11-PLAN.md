<objective>
What a conversation is, and what its row says.

D-02 is the decision everything here turns on: a row describes the **whole
conversation**, not its newest message, with one rule per column family stated
once and used by both the displayed value and the SQL `ORDER BY`, because
`MessageColumn` supplies both from the same enum today and they must not come
apart. Its own doc comment already states the safety property that keeps it
honest: the sort expressions are fixed strings chosen by matching on the enum,
never built from anything a user typed, because the result is interpolated into a
query. The aggregate sibling must keep that property, which means fixed strings
per arm in both methods and no string surgery on the message expression.

D-03 turns the Thread column from a thread id no person wants read aloud into
"5 messages, 2 unread", which is what makes THREAD-01's announcement possible at
all: there is no per-item accessible name API on this list control, so what a
screen reader reads for a conversation row is exactly the cell text and nothing
else.

Purpose: roadmap criterion 6's second half, and the data every row in plan 01-12
renders.

Output: the account-wide aggregate, the conversation's name, the aggregate column
rules, and the fourth of the five settings.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sender → subject and headers → a row a person reads | Subjects and sender names are attacker-controlled text reaching a screen reader. |
| column choice → SQL `ORDER BY` | An expression is interpolated into a query. |
| account scope → conversation aggregate | A query that spans folders must not span accounts. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-46 | Tampering | SQL injection through a sort or filter | high | mitigate | Already mitigated by design and this plan keeps the property: `conversation_sort_expression` returns fixed strings matched off the enum, never built from user input, exactly as `sort_expression`'s doc comment requires. Every value in the aggregate query is a bound parameter. A guard record breaks the agreement. |
| T-01-47 | Spoofing | A conversation spanning two accounts | medium | mitigate | The aggregate filters on `account_id` and a test with two accounts asserts counts do not merge. A conversation crossing accounts would show one account's mail while the user believes they are in another. |
| T-01-48 | Denial of service | An unbounded aggregate over a large mailbox | medium | mitigate | `idx_messages_thread` from plan 01-02 serves the grouping and the subquery; without it SQLite reads every message in every folder and sorts the lot, which `messages.rs:101-104` documents for a query of the same shape. The reach setting also bounds it to one folder for a user who wants that. |
| T-01-49 | Information disclosure | A sender-controlled subject read aloud | low | accept | A subject has always been displayed and read aloud; this plan changes which subject, not whether. Sanitising a subject into unreadability would cost more accessibility than it buys, and the body sanitiser is where untrusted markup is handled. |
| T-01-50 | Repudiation | A count that is quietly wrong | medium | mitigate | The all-mail exclusion is guarded, because without it every Gmail conversation reports twice its size and the number looks plausible. A plausible wrong number is worse than an obviously wrong one. |
</threat_model>
