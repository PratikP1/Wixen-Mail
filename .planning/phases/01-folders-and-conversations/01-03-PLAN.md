<objective>
Store the nesting instead of computing it.

`imap::list_folders` already reads the hierarchy delimiter out of each LIST
response, uses it to find the leaf, and throws it away. The comment there says
why and what would change it: "It is not carried on the struct: the tree is one
flat level, so nothing downstream has anything to do with it. It comes back when
the tree gains a hierarchy." This plan is that.

D-22: nesting is stored, not computed. Sync splits the path where the delimiter is
known and writes a nullable `parent_id` on the folders row. The tree reads a
parent and never splits anything. The delimiter is per mailbox in the LIST
response, not per server, so it cannot be assumed.

D-23: local folders nest with `/`, which their paths already use. A name
containing `/` is escaped rather than refused, because refusing it invites a
second spelling of the same folder.

Purpose: plan 01-05 builds the tree from this, and plan 01-04's depth-first delete
walks it. Neither can be written until a folder knows its parent.

Output: `ImapFolder.delimiter`, `folders.parent_id`, the write/read pair for it,
the split at sync, and a local-name escape that round-trips under a guard.
</objective>

  <behavior>
    RED first.

    - A name with no separator is stored unchanged: `escape_leaf("Receipts")` returns `Receipts`.
    - A name containing the separator is escaped, and `unescape_leaf` returns the original exactly.
    - The escape character itself is escaped, so a name that already contains it round-trips too. This is the case that makes the round trip a real property rather than one direction working by luck.
    - Round trip over a table of awkward names: the separator at the start, at the end, doubled, the escape character alone, both mixed, an empty string, and a name that is only separators.
    - `escape_leaf` is idempotent in the sense that matters: `unescape_leaf(escape_leaf(x)) == x` for every name in the table. `escape_leaf(escape_leaf(x))` is deliberately not asserted equal to `escape_leaf(x)`, because it is not, and asserting it would be asserting the wrong property.
    - A name that cannot be used at all — a device name, a trailing dot, a right-to-left override, a name too long — is still refused by `is_a_name_that_can_be_used` and not silently repaired.
  </behavior>

  <action>
    Local folder paths already nest with `/`. D-23 escapes a name containing it
    rather than refusing, and that choice was made against a named risk: refusing
    invites the user to type a second spelling, and then one folder has two names.

    Add `escape_leaf` and `unescape_leaf` to `src/application/local_folders.rs`.
    The exact scheme is Claude's discretion under two rules that are not: the
    escaped form is the stored identity, and the readable form is only ever what a
    person sees. That is the same split `ImapFolder` makes between `path` and
    `display_path`, and its doc comment gives the reason to copy — re-deriving the
    stored form from the readable form makes unreachable exactly the folder that
    could not be decoded. One escape function, one unescape, and a guard that they
    round-trip.

    Whatever scheme is chosen must escape the escape character, or the round trip
    is not a round trip. Choose a character that cannot appear in a name a user can
    type, in the spirit of `LOCAL_PREFIX`'s `\u{1}`, whose choice is justified at
    line 54 on exactly that ground and restated at `mail_sync.rs:410`.

    Escaping is not validating. `import_tree::is_a_name_that_can_be_used` is
    currently private and is the one function that knows what name Windows will
    take: a step out of a folder, a device like `NUL`, a trailing dot the
    filesystem would strip after this had finished checking, a character Windows
    will not take, a name written backwards by an override, a name too long to
    write. Make it `pub(crate)` and call it. Do not write a second character check;
    a second answer to that question is how the two drift, and this is a name a
    stranger's archive can supply.

    A name that fails that check is still refused, with a reason and a count, per
    `import_tree`'s stated rule that the repaired form is a different import nobody
    asked for. Escaping the separator and refusing an unusable name are two
    different answers to two different questions and both are kept.

    Add a guard record whose break removes the escaping of the escape character,
    measured by hand, with every test that really goes red written down. Raise the
    header's count of records arrived since the sweep by one.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server → LIST response → stored path and delimiter | A server names its own mailboxes and chooses its own delimiter; both are untrusted input. |
| archive file → folder name → local path | An imported archive supplies names that decide where bytes are written. |
| user → folder name → stored identity | A typed name becomes a database key. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-09 | Tampering, elevation | A local folder name from an archive reaching the filesystem | high | mitigate | `is_a_name_that_can_be_used`, made `pub(crate)` in task 3, wraps `attachment_name::safe_file_name` and covers a step out of a folder, a device name, a trailing dot, a character Windows refuses, a right-to-left override, and an over-long name. `import_tree`'s rule stands: refuse, count, say so; never repair, because the repaired form is a different import nobody asked for. |
| T-01-10 | Tampering | A hostile delimiter or path in a LIST response | medium | mitigate | The delimiter is used only to find a separator inside a path the same server sent, never to build a filesystem path. A test feeds a multi-character delimiter and an empty one and asserts neither splits anything unexpectedly. `is_local` still guards the `store_folders` loop, so a server claiming a name that looks like a local folder is left out of the list, as it is today. |
| T-01-11 | Tampering | `parent_id` pointing at another account's folder | medium | mitigate | The parent lookup runs over the pairs from one account's `store_folders` call only, never over a whole-table query, and a test with two accounts asserts each child links inside its own. A cross-account parent would put one account's mail under another's branch in the tree. |
| T-01-12 | Denial of service | A deeply nested or self-referencing hierarchy | low | mitigate | Parents are resolved in one pass over a vector with no recursion, so a cycle cannot hang the sync. Plan 01-05, which walks the tree for display, is where a depth bound belongs and is noted there. |
