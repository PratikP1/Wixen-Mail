<objective>
Rethread as mail arrives, not only when a folder is opened.

Two things make this harder than it looks, and both are recorded rather than
guessed.

The first is the merge. A conversation's id is the root its `References` chain
points at, so a message with no chain roots its own thread. When a later message
arrives whose chain names both that message and an earlier root, two threads that
were separate are revealed to be one. The mail-at-scale plan names that merge as
the case worth testing and THREAD-02's own criterion says the test must fail if
the two trees are left separate.

The second is agreement. An implementation that looks up the references, finds a
thread and adopts its id will disagree with whatever recomputes later, and the
row's identity flips under the user. That is the lenient-reader-strict-writer
shape this project has been bitten by before. One function decides, in both paths.

Purpose: roadmap criterion 7, and the last requirement in this phase.

Output: the arrival lookup, the merge, and a row that repaints without shouting.
</objective>

  <files>src/application/thread_identity.rs</files>

  <behavior>
    RED first. This is pure, so every case is testable with no database and no window.

    - A message whose chain names no known root joins nothing: `rejoin` returns nothing to do, and the message's own root from `conversation_root` stands.
    - A message whose chain names one known root and whose chain's first element is that same root has nothing to rewrite.
    - **The merge.** A message whose chain is `[A, C]`, where `A` and `C` are each already the root of a thread, returns a rerooting with `A` winning and `C` to be rewritten. `A` wins because it is earlier in the chain and the chain is oldest first, which is what `as_stored` writes and what `conversation_root` already reads.
    - Three trees merged by one arriving message rewrite two roots onto one, not one onto one.
    - The winning root is the chain's first element even when the arriving message's own identifier sorts before it. This is the case the rejected rule got wrong: adding a message must never rename a conversation.
    - `rejoin` is idempotent: applying its answer and asking again returns nothing to do.
    - **Agreement with the batch.** For a set of messages, assigning ids one at a time in arrival order and then again in reverse order gives the same final assignment as computing them all at once. A test drives at least three orders over a set that includes a merge.
  </behavior>

  <action>
    Add `rejoin` to `src/application/thread_identity.rs`, beside `conversation_root`,
    so both halves of the rule live in one module and one file. It takes the
    arriving message's chain and which of that chain's identifiers are already
    thread roots, and returns which root wins and which must be rewritten onto it.

    The winner is the chain's earliest element that is a root, because the chain is
    oldest first. That is not a new rule: it is `conversation_root`'s rule applied
    to the case where more than one candidate exists, which is why this belongs
    beside it rather than in the sync.

    **Do not adopt a found thread's id.** Pitfall 6 names this as the warning sign:
    a task phrased as "look up the references and adopt that thread's id" is the
    implementation that disagrees with the next recompute. The rule here is not
    adoption, it is recomputing the affected component: the arriving message and
    every thread its chain connects settle on the root the chain names, and that
    answer is the same whoever asks and in whatever order.

    Write the order-independence test as a property over at least three orders. It
    is the test that would catch a future change reintroducing batch dependence,
    and it is cheap because the function takes no batch.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a stranger's `References` chain → which conversations merge | An arriving message decides that two stored conversations are one. |
| arrival rate → announcement queue | A syncing mailbox drives UI updates on a timer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-56 | Spoofing | A forged `References` chain merging a stranger's message into a private conversation | medium | mitigate | Inherent to RFC 5322 threading and present in every mail client; bound the damage rather than claim to prevent it. The rewrite is scoped to one account, so no chain can merge two accounts' mail. The thread id is only ever a grouping key, never a permission. A test with two accounts sharing a root identifier asserts neither is rewritten into the other. |
| T-01-57 | Denial of service | A chain that rewrites a very large number of rows | medium | mitigate | The rewrite is one `UPDATE` over an indexed column, not a per-row loop, and it returns a count. `rejoin` reads only the chain, so a long chain does not drive quadratic work; a test with a thousand identifiers pins that. |
| T-01-58 | Denial of service | Announcement flooding from a syncing mailbox | high | mitigate | Nothing announces per message; a timer-driven arrival uses `announce_topic` at `Priority::Low` on one topic, which supersedes rather than queues. `set_item_count` is called only when the row count changed. Guardrail 5 requires feedback to be bounded and this is the path most able to break it. |
| T-01-59 | Repudiation | A conversation silently changing identity under the user | high | mitigate | The order-independence tests and the agreement guard: the incremental path and a whole-folder recompute give the same answer, so per-folder state keyed on a thread id cannot be silently orphaned. This is Pitfall 6 and the reason the batch-independent derivation was chosen in D-39. |
</threat_model>
