  <behavior>
    RED first, over pure state so no window is needed.

    - Switching to conversations selects every conversation containing a selected message.
    - Switching back selects **exactly** the messages that were selected before, not everything in those conversations. This is the half an implementation gets wrong, because the obvious round trip loses it: the original set is held across the switch rather than recomputed.
    - Two messages from one conversation selected, switched to conversations and back, gives those two messages selected and not the conversation's other three.
    - A selection of nothing survives as nothing.
    - The sort column and direction are unchanged by a switch in either direction, and the header announces the same thing before and after.
    - The view is stored per folder, and a folder never set is flat.
    - Applying the view elsewhere offers three scopes: this folder's subtree, this account, everywhere. Each names what it will change and how many folders that is, in a plain sentence, before it happens.
    - Applying confirms, because it overwrites settings the user may have set by hand.
    - Applying to a scope containing no other folder says so rather than confirming a change to nothing.
  </behavior>

  <action>
    **Hold the original set.** D-11 requires the switch to survive both ways, and
    switching back must restore exactly the messages that were selected, not the
    contents of their conversations. Recomputing from the conversation selection
    cannot do that, because the mapping is lossy in one direction. Keep the original
    message selection in `view_state` across the switch and restore from it. Write
    the two-of-five test explicitly; it is the one that fails against the obvious
    implementation.

    **Sort survives unchanged.** D-12: the same column and direction, applied through
    D-02's aggregate rule from plan 01-11. `Sort::order_by_clause` is the only
    `ORDER BY` producer for this list, which a census in the research confirmed, so
    switching modes changes which expression each column contributes and not which
    column is sorted on. The header says the same thing before and after.

    **Per folder, beside the collapsed state.** Read and write `thread_view` on
    `tree_state` keyed by the same identity, so D-09's "both restore together" is
    structural rather than remembered.

    **Apply View To Other Folders**, `ID_APPLY_VIEW_ELSEWHERE` on the View menu, with
    the three scopes. Each scope is a plain sentence naming what it will change and
    how many folders that is, spoken before it happens, and it confirms, because it
    overwrites settings the user may have set by hand. Compose the sentences in
    `view_state` as pure functions with their own tests. Use
    `yes_no_where_enter_answers_no()`: this is not destructive but it is
    unrecoverable in bulk, and the house pattern for a bulk overwrite is the same.

    D-10 exists because a per-folder setting is otherwise tedious enough that nobody
    uses it. If a scope covers no other folder, say so rather than confirming a
    change to nothing, which is the same rule `destinations::anywhere` states for
    the move dialog.

    Two guard records, measured by hand: one whose break restores whole conversations
    when switching back, one whose break drops the sort across a switch. Raise the
    header count by two. If `ID_APPLY_VIEW_ELSEWHERE` takes a chord,
    `docs/KEYBOARD_SHORTCUTS.md` carries it in the same commit.
  </action>
