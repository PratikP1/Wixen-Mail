<objective>
The other two verbs, and the two commands that split them.

RENAME is one verb doing two jobs. RFC 9051 §6.3.6 requires that renaming a
folder renames its inferior names too, so moving `Archive/2026` to `Old/2026`
takes its children with it in a single command and the server generally creates
`Old` on the way. D-26 splits that one verb into two commands anyway: rename
changes the leaf only, and moving to a different parent is its own `Move To` on
the Action menu, naming the new parent from a list, confirming, and saying where
it went. The safety argument is the whole point — separating them stops a typo in
a text box moving a folder irreversibly.

DELETE is the opposite shape. RFC 9051 §6.3.5: "The DELETE command MUST NOT
remove inferior hierarchical names." So deleting a subtree is a client-side
depth-first walk, deepest first, and there is no transaction to wrap it in.

Purpose: finish FOLDER-01's server half on the path plan 01-01 proved.

Output: `rename_mailbox` and `delete_mailbox` verbs, three commands on the Action
menu, a folder destination list reusing `destinations`, and the record of how far
a batch got that plan 01-09 also needs.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user → folder name → RENAME argument | Two names typed by a person become one protocol command. |
| application → `Allowed::mail` → server | Three verbs now write to somebody's mailbox; the gate is off for a new install. |
| stored parent tree → delete walk | A tree read from the database decides which mailboxes are destroyed and in what order. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-13 | Elevation of privilege | A verb missing its gate | critical | mitigate | `may_i` is the first statement of both new verbs' bodies, and task 3 records a guard whose break removes it. Two of the three verbs in this phase now carry such a record. |
| T-01-14 | Tampering | Renaming INBOX | high | mitigate | Refused before a command is built, by `folder_type`, with the reason spoken. The RFC makes this succeed and empty the inbox, so it cannot be caught by handling an error: it must be refused up front. Guarded. |
| T-01-15 | Tampering | Moving a folder into its own descendant | medium | mitigate | The destination list excludes the target and its subtree, and a request for one is refused. The walk is depth-bounded so a cycle in stored parents cannot hang the window. |
