# Phase 1 — Validation Strategy

## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework** | Rust built-in `#[test]` and `#[tokio::test]`, with `tokio-test 0.4` in dev-dependencies |
| **Config file** | None. `cargo test` reads `Cargo.toml`. Guard records live in `guards/guards.toml` |
| **Quick run command** | `cargo test --lib <module>::`, for example `cargo test --lib threading::` |
| **Full suite command** | `bash scripts/check.sh` (format, clippy with `-D warnings`, tests, release build) |
| **Estimated runtime** | Quick: seconds. Full: about four minutes, most of it the release build |
| **Scale** | 5,430 tests: 5,269 unit and 161 integration, counted 2026-08-29 with `cargo test --all-targets -- --list` |
| **Integration tests** | 20 files under `tests/`, each run as its own process, which matters for wx |

Two things about this project change how those numbers read.

**Use `bash scripts/check.sh`, not `cargo test`, for the full run.** Cargo shares
build fingerprints between `check`, `build`, `test` and `clippy`, so a clippy run
following a build can report success without linting anything. That has already
put a clippy failure on `main` after a local run reported clean. The script
touches `src/lib.rs` first to force the work, and a pre-commit hook runs it, so
every commit in this phase pays that cost.

**A green suite does not mean the tests would notice.** Red and green started at
commit 182 of 344, so many tests here describe the code rather than specify it.
That is why every task below is RED-first, and why `guards/guards.toml` records
exist: each names the exact edit that must turn named tests red, and
`scripts/guards.sh` checks both directions.

---

## Sampling Rate

- **After every task commit:** the module's own tests, per the map below. Seconds.
- **After every plan wave:** `bash scripts/check.sh`.
- **After any task that adds or invalidates a guard record:** `bash scripts/guards.sh <name>`.
- **Before `/gsd-verify-work`:** full suite green, and `scripts/guards.sh` clean for every record this phase touched.
- **Max feedback latency:** under 30 seconds for a per-task run.

verbs test against. `a_server_answering` needs no change. `a_server_that_can`
would need `CREATE`, `RENAME` and `DELETE` added to its match arm, and only
becomes a Wave 0 task if a capability line is needed.

## Manual-Only Verifications

| Behaviour | Requirement | Why manual | Instructions |
|---|---|---|---|
| Every announcement this phase adds, heard | FOLDER-01/02/03, THREAD-01/02 | Structure present is not experience good, and the automated scan covers about half of WCAG. MSAA and UI Automation are two channels, and only a real screen reader exercises both the way a person meets them. | Pratik runs this and decides when. No task in these plans requires it, and none may be rewritten to. |
| Alt+Shift+Up/Down on a machine with more than one input language | FOLDER-02, D-14 | Bare Alt+Shift is the Windows layout-switch hotkey. Whether releasing the combination after the arrow trips it is a property of the machine, not of this code. | Pratik's, as above. |

**Nothing in Wixen Mail has ever run against a real mail account.** Protocol work
here is tested against parsing and against loopback servers, and no criterion in
this phase claims otherwise. A loopback server proves the command this client
builds and how it reads the reply. It cannot prove what a real server does with
that command. That gap is tracked as work, not as a hole in the tests.
