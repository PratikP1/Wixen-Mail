<objective>
Give `messages.thread_id` a producer.

`thread_id` is a column nothing writes and nothing reads back. Its only occurrence
in `src/data/` is the `ensure_column_exists` at `mod.rs:2065` that creates it.
Meanwhile `message_columns.rs:131` sorts on `m.thread_id`, so sorting by Thread
orders every row by NULL and does not fail. Threading today is an in-memory pass
over one folder's loaded page, whose result is never persisted, and whose id is
the least Message-ID in that batch — so the same conversation gets a different id
in Inbox than in Archive.

D-08 asks for a conversation that spans an account. There is no stored,
account-wide conversation key to span it with. That is not a query to write
against existing data; it is a producer to build, and it must land before
anything reads a thread id. Plans 01-11, 01-12 and 01-13 all read one.

Purpose: unblock four later plans, and stop a column that looks like working
infrastructure from being treated as one.

Output: `src/application/thread_identity.rs`, writes on both cache entry paths, a
backfill for rows already stored, two indexes, and a Thread column that sorts.
</objective>

  <decision>Write a stable conversation id onto every message in the database, derived as D-39 specifies</decision>
  <context>
    D-39 is locked and this gate does not re-open it. It exists because writing
    these ids is a one-way door, and the reversibility rule shows you a one-way
    door before it is walked through rather than after.

    What is about to happen, in plain terms. Every message in your database gets a
    `thread_id` derived from the first identifier in its `refs_header` chain,
    falling back to its own `message_id` when the chain is empty. Nothing is
    deleted and no existing column is changed: `thread_id` is NULL on every row
    today, so the backfill can only add.

    Why it is one-way. Once ids are written, changing the derivation means
    recomputing every stored row. It is free today only because the column has
    never held a value, which makes now the cheapest moment this choice will ever
    be available.

    The rejected shape, for the record. Today's in-memory id is the least
    Message-ID in the loaded batch, so the same conversation gets a different id
    per folder and an arriving message can lower it. A later implementation
    adopting a found thread's id would then disagree with the next recompute. That
    is the lenient-reader-strict-writer shape this project has been bitten by
    before.

    `gate="blocking-human"` because auto-approving a one-way write over the user's
    only copy of their mail would defeat the purpose of asking.
  </context>

    RED first. Each of these is a failing test in the new module's `mod tests` before any production line exists.

    - A message with no chain is its own conversation: `conversation_root("a@x", None)` returns `a@x`.
    - A reply takes the first identifier of the chain: `conversation_root("c@x", Some("a@x b@x"))` returns `a@x`.
    - Batch independence, which is the whole point: the answer for one message never depends on which other messages are present, because the function is not given any. A test asserts that the same three messages fed in three different orders produce the same three answers.

    - Identifiers are bare, matching what `as_stored` writes: angle brackets around a stored chain are trimmed, so `conversation_root("c@x", Some("<a@x> <b@x>"))` also returns `a@x`.
    - An empty or whitespace-only chain falls back to the message's own identifier rather than returning an empty string.
    - An empty `message_id` with an empty chain returns an empty string rather than panicking, and the caller is what decides not to store it.
  </behavior>

  <action>
    Create `src/application/thread_identity.rs` with one public function,
    `pub fn conversation_root(message_id: &str, refs_header: Option<&str>) -> String`,
    and register the module in `src/application/mod.rs` beside `threading`.

    The rule, per D-39: the conversation is named by the root its `References`
    chain points at. `refs_header` holds that chain oldest first, which
    `threading::as_stored`'s doc comment states and which `mail_sync::reference_chain`
    and `pop_sync` both write. So the root is the first whitespace-separated
    identifier of the chain, with any angle brackets trimmed the way
    `threading::bracketed` handles them, and the message's own `message_id` when
    the chain is absent or empty.

    Why this and not the existing rule: the id must not depend on the batch. The
    rule in `threading.rs` picks the least Message-ID among the messages present,
    so the same conversation is named differently in each folder and an arriving
    message can rename it under the user. This function is given one message and
    cannot see a batch, which is what makes the property structural rather than
    remembered.

    a column that has never held a value, an id that changed depending on which

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sender → `References` header → stored id | A `refs_header` chain is written by whoever sent the message and is attacker-controlled for any message a stranger can send. |
| backfill → the user's only copy of their mail | A migration writing to every message row. |
| derived id → SQL `ORDER BY` and `GROUP BY` | A value derived from a header reaching a query. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-05 | Tampering | `conversation_root` from a hostile `References` chain | medium | mitigate | A sender can name any root and so place their message in someone else's conversation. This is inherent to RFC 5322 threading and every mail client has it. Bound the damage: the id is only ever a grouping key, never a permission, a path or a filename, and it is bound as a SQL parameter, never interpolated. A test feeds a chain containing quotes, a newline and a very long identifier and asserts it is stored and read back unchanged with no query error. |
| T-01-06 | Denial of service | An unbounded `refs_header` chain | low | mitigate | Only the first identifier is read, so chain length does not drive work. A test with a chain of a thousand identifiers asserts the function is not quadratic in it. |
| T-01-07 | Tampering | `backfill_thread_ids` writing every row | high | mitigate | The `WHERE thread_id IS NULL` clause means it can only fill, never overwrite. Copied from `migrate_inline_bodies`: read candidates into a `Vec` first, drop nothing, return the count as the contract. Non-fatal at the call site, so a failure leaves the data as it was and the next open tries again. Covered by the idempotence test and the untouched-existing-value test. |
| T-01-08 | Information disclosure | Message identifiers in logs | low | mitigate | The backfill logs a count, never an identifier. A `Message-ID` can carry a hostname and a local part. |
</threat_model>
