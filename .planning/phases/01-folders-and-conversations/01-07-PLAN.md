## The noun that is now primary

A local folder's identity moves from `(account, path)` to `(this-computer, path)`.

Today `LocalFolder::path()` carries no account id and `folders` is keyed
`UNIQUE(account_id, path)`, so each account owns its own local Sent, Outbox,
Drafts, Junk and Trash. D-18 makes those five one each, owned by a reserved
"this computer" account id.

**The decision: `promote`.** The shared five become primary and per-account local
folders stop existing, migrated away by D-19. This is explicitly **not**
add-alongside: the user was offered "keep the existing ones alone" and rejected it
as the two-shapes-forever outcome.

**The invariant that keeps it decided.** After migration, no folder row outside
the reserved account id has a path under `LOCAL_PREFIX` for any of the five shared
kinds. Task 3 writes that as a test. It goes red the moment a future phase
reintroduces a per-account local Trash, which is the failure mode a promotion
without an invariant always drifts back into.

What does **not** move: `Inbox` stays per account. `FOR_IMAP` stays `[Outbox]`, so
an IMAP account keeps its server Sent, Drafts, Trash and Junk. A folder a user
creates under a POP account (D-20) is per account too, beside that account's
Inbox.
</assumption_delta_decision>

<objective>
Make the five local folders one each, and move existing mail into them without
losing any of it.

`importing_messages` opens by warning that this is how mail gets lost quietly.
This migration is the same risk and needs the same care: it rewrites `folder_id`
on messages in the user's only copy of that mail, and it does it across a
`UNIQUE(folder_id, uid)` constraint that two accounts' local Trash will both
violate, because IMAP UIDs are per mailbox and POP ones are per download, so two
accounts each holding uid 42 is expected rather than hypothetical. Nothing in this
tree has ever rewritten a uid.

Purpose: roadmap criterion 4.

Output: a reserved account id, the shared five, the migration with its count and
its report, and the invariant that keeps the shape from drifting back.
</objective>

## Where the migration lives, and why

RESEARCH.md places this in `src/application/`, "so it belongs where it can be
tested without a UI". Every existing migration in this tree is a `MessageCache`
method called from `MessageCache::new`. **Follow the existing convention.** The
tension is not real: `migrate_inline_bodies` is a `MessageCache` method at
`bodies.rs:458`, called non-fatally from `MessageCache::new` at `mod.rs:1179`,
and it **is** tested, at `bodies.rs:1078`, against a cache built on a tempfile. So
the existing pattern already satisfies the property the research was worried
about, and inventing a second home for migrations would be this project's
two-answers-to-one-question shape again.

The new file is therefore `src/data/message_cache/shared_folders.rs`, a sibling of
`bodies.rs`, not `src/application/shared_folders_migration.rs`.

    What is about to happen to an existing database. Each account's local Sent,
    Outbox, Drafts, Junk and Trash are merged into five shared folders owned by a
    reserved "this computer" account id. Messages move by having their `folder_id`
    rewritten, and nothing is removed until every message has landed. Where two
    accounts' folders hold the same uid, the second message is given a fresh uid
    unique within the shared folder and its original is recorded in a new column
    beside it. A summary says how many moved and from where, spoken and written to
    the log.

    IMAP UIDs are per mailbox and POP ones per download, so two accounts' local
    Trash both holding uid 42 is expected rather than hypothetical. Without the
    reassignment the migration either fails or drops a message, and it is the
    likeliest way this loses mail.

    Why undoing it is hard. After the merge, knowing which account a message came
    from means reading the column that recorded it. That column is the whole of the
    traceability, which is why D-40 adds it rather than renumbering silently.

    Two things that are not happening: no column is dropped or renamed, and
    `UNIQUE(account_id, path)` is untouched. The reserved account id is the same
    trick `LOCAL_PREFIX` plays with paths, one level up.

    `gate="blocking-human"` because this rewrites the user's only copy of that mail
