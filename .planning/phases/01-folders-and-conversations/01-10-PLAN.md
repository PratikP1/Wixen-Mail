<objective>
A folder the server has stopped listing.

D-27 chose a modal dialog raised right away, and the dialog-during-background-sync
risk was raised in discussion and the modal chosen deliberately. So the modal
carries two constraints that no existing dialog in this tree models, both named by
prior fixes in this codebase: **one at a time**, never one per folder or per
concurrently syncing account, and **not while an editor has focus** — it waits.

Neither has an analog. The `MessageDialog` pattern covers the dialog and not the
gating, so both need their own tests.

The rule underneath is the one that makes this safe at all: cached mail in the
folder is untouched until the user answers. A sync is a timer event, and a timer
event must never destroy mail while deciding what to ask.

Purpose: the half of FOLDER-02 that is about the tree keeping up with a server
that changed.

Output: detection at sync, a gone state the tree shows, and a queued,
focus-respecting way of asking.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server LIST response → what the client believes exists | A server's answer, or its failure to answer, decides whether the user is asked to delete mail. |
| background sync → a modal dialog | A timer event raising a window over whatever the user is doing. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-41 | Tampering | A server outage read as a mass deletion | critical | mitigate | An empty LIST is treated as a failed sync and reports nothing gone. On the wire an empty answer and a total deletion are identical, and only one is survivable. Tested directly. |
| T-01-42 | Tampering | Cached mail destroyed before the user answers | critical | mitigate | Nothing is deleted until an answer arrives, asserted by an unchanged message count while a question is pending, and guarded by a record whose break deletes early. D-27 states this rule and it is the reason the modal was acceptable at all. |
| T-01-43 | Denial of service | A dialog storm from a background sync | high | mitigate | One pending set, one question, raised only when no editor has focus. Two accounts syncing together still produce one. Guarded by a record whose break asks per folder. |
| T-01-44 | Spoofing | A server claiming a local folder is gone | high | mitigate | Local folders and the reserved this-computer account are filtered out before the comparison, so no server answer can put the user's Drafts or Outbox in the question. Tested with an empty LIST. |
| T-01-45 | Repudiation | A folder disappearing with no record | medium | mitigate | Answering yes reports how many folders and how many messages went, spoken at `Priority::High` and written with `send_status`. Answering no leaves them visible and marked, so neither answer leaves the user without a trace. |
</threat_model>
