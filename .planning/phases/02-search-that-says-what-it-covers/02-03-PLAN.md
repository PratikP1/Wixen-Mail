<premise_corrections>
**The IMAP command already exists and is not new work.** `02-PATTERNS.md` lists
this file under "No Analog Found" on the strength of the gate being new, which is
true, but `src/service/protocols/imap.rs:1088` already holds
`fetch_body(&mut self, uid: u32) -> Result<Vec<u8>>`, using `BODY.PEEK` so that
reading does not mark a message read on the server, and
`src/application/mail_controller.rs:379` already wraps it as
`fetch_message_body(folder, uid)`. There is also already a single-message
on-demand download in `src/presentation/wx_app.rs`, near `:17570`, started when a
message is selected and its body is not held, which parses and calls
`save_message_body`. So this plan writes no new IMAP command and no new parse:
it writes the routine that decides which messages to ask for, and the offer.
Read that existing download before writing the backfill; it is the shape to
follow and it already handles the signed-mail case.

**`EXPERIMENTAL_WARNING` is about writes and must not be extended.**
`src/application/allowed.rs:175` opens with "Both are experimental" and names
sending, deleting and guest lists; its content is asserted verbatim by six
assertions at `:351-383`. Adding a read to it would break those tests and would
put a read inside a warning about irreversible writes. The fetch gets its own
constant beside it.
</premise_corrections>

    - Turning reading off part-way through stops the run at the next message, because the gate is asked per message rather than once.
    - A message that fails to fetch does not stop the run: it is counted and reported, and the rest continue. The report says how many were fetched and how many were not.

    - A run over an empty list does nothing and says so, rather than reporting success over nought messages.
  </behavior>

A test filter that matches nothing exits zero, so name the filter and confirm the test count is non-zero before believing a green run.

    Write the backfill in `application::mail_sync`, which is where every other long-running mail job lives and where the Architectural Responsibility Map puts it. It takes an account, asks task 1's query for the list, and for each row calls `fetch_message_body`, parses through `service::mime::parse`, and stores through `save_message_body`. The gate is `fetch_body`'s first line and it is asked once per message because the loop calls that function once per message, which is the property the behaviour block asks for. This is not decoration: the coverage sentence tells somebody a number, and a fetch that then runs silently for an unknown time is the shape somebody kills half way. Report at the end with both numbers, fetched and not fetched, because a run that reports only successes reads as complete.

Name in it the one risk no test here can settle: whether a provider will permit it at all, or will slow down or drop the connection. Keep the register of the existing warning: plain language, second person, no machine names.

    Errors through `common::Error`. Every failure is counted and reported, never swallowed: a fetch that quietly skips messages produces exactly the "short answer that looks complete" this requirement exists to prevent.

| Boundary | Description |

| the offer -> a bulk request against somebody's provider | One keypress can start hundreds or thousands of requests |
