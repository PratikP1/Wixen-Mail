<objective>
Give the search box the same honesty the saved search already has: say how much
of this account's message text the box could look inside, so a short answer
reads as narrow coverage rather than as an empty mailbox.

Purpose: closes the half of SEARCH-02 that phase verification found open on
2026-09-01. The saved search says what it covers; the box does not, and the box
is the path people reach for first.

This is not a new defect. `02-CONTEXT.md`'s D-2-09 already names it: "A search
can silently cover a fraction of the mailbox today, and that is a live defect
rather than one this phase is about to introduce." The phase then built the
disclosure for the saved search only.

Output: one counting query, one sentence through the existing builder, one
wiring, and the guard that notices if the number stops being said.
</objective>

<premise_corrections>
**The box's coverage is not the saved search's coverage, and reusing 02-02's
number would state a falsehood.** This is the whole difficulty of the plan and
it comes straight out of D-2-13.

02-02 counts how many messages have their text in `message_bodies`. The box
does not read `message_bodies`. It runs an unqualified `message_search MATCH`
(`src/data/message_cache/searching.rs`, `search_messages`), so it reads the FTS
`body` column, and `evict_bodies_over` deliberately does not reindex. So:

- A message whose body was fetched and later evicted is **absent** from
  02-02's count and **present** in the FTS index. The box can still find it by
  a word from its text; the saved-search scan cannot.
- A message whose body was never fetched is absent from both, because
  `index_message_for_search` writes no body for it.

So the box's number is "how many messages the index holds text for", which is
its own query. Measure both on a fixture holding an evicted message and confirm
they differ, before writing either sentence. If they do not differ on your
fixture, the fixture is wrong, not the premise.

**Do not add a reindex to `evict_bodies_over`.** D-2-10 asked for it and D-2-13
answered in the opposite direction on the same day. Reindexing would make a
message unfindable at the moment its body is evicted, taking away a search that
works today. 02-02 already has a test holding this.

**The snippet is indexed too and is never evicted.** 02-02 measured this: the
snippet is the first 200 characters and it stays in the index, so a word inside
it is findable whatever happened to the body. A fixture whose test word sits
inside the snippet cannot tell any of this apart and will pass against anything.
Put the word past the snippet.
</premise_corrections>

  <name>Task 1: How much text the box can look inside</name>

  An account-scoped count of the messages whose body text the FTS index holds,
  beside `search_messages` in `src/data/message_cache/searching.rs`, where the
  search it describes lives.

  Not a copy of 02-02's query. That one counts `message_bodies`; this one counts
  what the index holds, and the two answers differ by exactly the evicted
  messages. Prove that difference in a test rather than asserting it in a
  comment.

  A search that reads no message text must not pay for this. `WhereToSearch`
  already says what the box is looking in, and a subject-only search asks no
  coverage question.

  RED first. Prefer the widest wrong stub to an empty one: an empty return makes
  the absence assertions vacuously green, which 02-03 measured.
</task>

<task type="auto" tdd="true">
  <name>Task 2: Say it, on the channel the count already uses</name>

  The sentence, through the builder `src/application/saved_searches.rs` already
  has, so the box and the saved search cannot describe themselves in two
  different voices. It takes the box's numbers, and it names which search it is
  about, because a person may see both numbers in one session and they will not
  agree.

  Wired in `src/presentation/managers.rs`, where the result count is already
  reported, and reaching a person the same way. `Event::NothingFound` already
  carries the zero-result case to the earcon channel; do not displace it, and
  check what happens when both would speak. 02-02 found that same-topic
  announcements coalesce, so a sentence said and then wiped is a sentence not
  said.

  **The guard for this task must be broken by `let _ = ...`, not by deletion.**
  02-02's first version of exactly this guard looked only for the call and
  stayed green while the answer was computed and thrown away, which is the
  defect the criterion exists to prevent. Require the answer bound to a name,
  not to `_`, and take that break by hand.
</task>
