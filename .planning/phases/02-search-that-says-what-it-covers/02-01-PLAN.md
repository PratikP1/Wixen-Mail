<objective>
Give `application::allowed` a read dimension and wire it end to end through the
one path that already fetches message text, so that turning reading off refuses
that fetch with a sentence, and turning it on is a control somebody can find.

Purpose: this is the phase's tracer. It is also the only part of the phase that
can damage an existing installation, because `Allowed` is serialised into
`app_config.json` and a struct that stops parsing takes every other setting with
it. Doing it first, on the agent's best context, means an architectural mistake
here costs one commit rather than seven.

Output: a third field on `Allowed` with a hand-written `Default`, a session-level
read gate in `imap.rs` reached by `fetch_body`, a settings control, and three
guard records.
</objective>

<premise_corrections>
Three claims in the phase documents were checked against the tree at commit
`67d12c5` and two of them are wrong. Read this before starting.

1. **`02-RESEARCH.md` contradicts itself about how many `may_i` sites exist.**
   It says "All sixteen are writes. Fourteen in `src/service/protocols/imap.rs`
   ... and two in `src/service/protocols/pop3.rs`", and in the same sentence
   lists eleven line numbers plus a definition. `grep -rn "may_i" src/` gives
   fourteen lines in total: twelve in `imap.rs` (one definition at `:1180` and
   eleven call sites) and two in `pop3.rs` (one definition at `:284` and one
   call at `:361`). `02-PATTERNS.md` says eleven call sites and is right. Do not
   quote sixteen anywhere. Count before writing any number into a guard record.

2. **`02-RESEARCH.md`'s assumption A2 is settled and the answer is that the
   limit is already set.** `src/application/filters.rs:233-235` builds its
   regex through `RegexBuilder` with `.size_limit(1 << 20)`. There is no work
   here and no task for it. It is recorded in this plan's threat model as
   already mitigated, so nobody re-opens it.

3. **The phase brief's claim that "this phase adds a read gate that both
   protocols need" does not survive reading `pop3.rs`.** POP3's `retrieve` at
   `:340` sends `RETR`, which is how a POP account receives a message at all;
   `src/application/pop_sync.rs:278-286` stores the body in the same breath as
   the message row, and `messages::ONLY_COPY_IS_HERE` then excludes it from
   eviction forever. So a POP account never holds a message with headers and no
   text, and gating `RETR` on the read dimension would not stop a body backfill
   — it would stop mail arriving. That is a different question from the one
   `Allowed::reading` asks, and task 3 records the difference in the code rather
   than leaving it as a silence. What the brief is right about, and what task 3
   builds, is that a structural guard reading only `imap.rs` measures half the
   thing.
</premise_corrections>
