<objective>
Put saved searches inside the account structure the way pinned folders already
are, and make opening one run it against its own account.

Purpose: D-2-05 and roadmap criterion 6. They are already account-scoped in the
data; only the tree placement was global, which was invisible while one account
showed at a time and stopped being invisible in `01-14`.

Output: an account branch per account that has searches, the account carried on
the row identity, and the run path taking the account from the row.
</objective>

<premise_corrections>
**D-2-05 is described as a tree-shape change, and it is not only that. It
reintroduces the defect `01-14` closed for folders.** Verified this session:

- `src/presentation/folder_tree.rs`'s `the_account_a_row_belongs_to` returns
  `None` for both `WhichRow::SavedSearches` and `WhichRow::SavedSearch(_)`, with
  a comment giving a correct reason: those rows are a heading and a global group,
  they name no account, and answering with one would make the next command act
  against a thing no row names. That reasoning is true of the shape the tree has
  today and stops being true the moment those rows sit inside account branches.
- `run_a_saved_search` at `src/presentation/wx_app.rs:6278` takes its account
  from `lock_state(state).active_account_id`, and `every_saved_search` is fed by
  a read for the active account at `:9530`.

So moving the rows without changing either would give: a search sitting under
account B's branch, opened, run against account A, returning nothing, which is
indistinguishable from a search that legitimately matched nothing. `STATE.md`
records the identical shape from `01-14`, where selecting a folder read whichever
account was open rather than the folder's own, and calls it out as the writers
being wrong after hidden state was made visible. Task 1 and task 3 are that fix,
and they are the substance of this plan rather than the tree drawing.

**`D-2-05`'s reversibility rating of "reversible" was given for the tree shape.**
It holds for the drawing. It does not hold for the row identity, which is a
stored key: see task 1's action for what that costs and how it is checked.
</premise_corrections>
