<objective>
Make an S/MIME encrypted message say why it cannot be read instead of reading as
empty, and take on OpenPGP: choose the implementation on the record, then read a
PGP message somebody holds the key for.

Purpose: success criterion 5, both clauses. The second clause first, because an
enveloped message has no `text/*` part at all, so `mime::parse`'s
`first_of_kind` yields nothing for both bodies and the reader shows a message
with nothing in it and no explanation. That is the exact failure the note editor
stub taught this project to avoid, and `EncryptedMessage::read` and `spoken()`
already do the work with no caller anywhere. Then the first clause, which needs
an OpenPGP implementation this project has never had.

Output: an S/MIME message that explains itself; a written, audited choice of
OpenPGP crate and a permanent credential-store owner; and one PGP message read
end to end through an interface the crate sits behind.
</objective>

**1. `04-RESEARCH.md`'s third decision is settled: both.** It offered three

**2. The three things that made PGP unplannable are still true, and they are now
tasks rather than a question.** An earlier draft of this plan held PGP behind a
blocking checkpoint on the grounds that no crate had been evaluated, the package
legitimacy gate had not run, and the credential-store service name is permanent

The one thing in that list that stays a human gate is the package legitimacy

specific crate, not a re-asking of whether to do PGP, and it must not be written
as one.

**3. PGP and S/MIME fail differently and READ-02 treats them as one.** A PGP
armoured block is a text part, so it renders as armour rather than as nothing,
and 04-03 already puts a sentence beside it. An S/MIME enveloped message has no
text part at all, so it reads as empty. They need different handling and get it
in different tasks: task 1 is S/MIME, task 3 is PGP, and neither borrows the
other's path.

**4. The detection already ships and already handles the hard case.**
`signed_mail::layout_of` returns `SmimeLayout::Encrypted` for
`smime-type=enveloped-data`, folds the value to lower case because a sender
writing `Signed-Data` once had their message read as not S/MIME at all, and
falls back to the `p7m` file suffix when the sender left `smime-type` off. What
is missing is a caller. `claims_a_signature` is the sibling to copy, and its own
comment says why it deliberately answers no for encrypted mail: sending an
encrypted message down the signature path makes every surface downstream say
"it says it is signed, but it carries no signature to check" about a message
that never said anything of the kind. **So do not widen `claims_a_signature`.
Write `claims_encryption` beside it.**

**5. `spoken` takes `Option<bool>` and the three states are the design.**
`Some(true)` says this computer holds a certificate the message was encrypted
to; `Some(false)` says it does not; `None` says how many certificates it names
and claims nothing. A failure to reach the certificate store is `None`. This is
the same distinction `spellcheck::WhatThisMachineOffers` draws between an answer
and a failure to ask, and the doc comment there records what happened when the
two were the same value: a French user got English on a first run where the call
happened to fail. Getting it wrong here is worse, because `Some(false)` tells
somebody a message was not meant for them.

**6. `CertificateStore` has a real Windows implementation and nothing else.**
`CLAUDE.md` requires platform code behind `#[cfg(target_os = "windows")]` with a
fallback that keeps the crate building. On any other platform the answer is
`None`, not `Some(false)`, for the reason above.

**7. Nothing in task 1 decrypts, and nothing in task 1 may imply it does.**
There is no signing or encrypting path either. The sentence `spoken` writes is
already careful about this and should not be reworded. Task 3 does decrypt, for
PGP only, and must not borrow the S/MIME wording: a PGP message that opened and
an S/MIME message that could not are opposite outcomes and the reader has to say
which.

**8. The credential-store name for a PGP private key is permanent from the
commit that writes it, and this project has exactly one place that proves it.**
`CLAUDE.md`: every secret goes to the OS credential store, each service name has
exactly one owner, and the code that erases them has to name the same entries as
the code that wrote them. That erasing code is
`application::forget::entries_for`, which builds the whole list by hand from
`security::KEYRING_SERVICE`, `credentials::KEYRING_SERVICE`,
`oauth::entries_for_account` and `caldav::keyring_service`. A fifth owner that is
not added there is a private key still on the machine after an uninstall says
everything was erased.

**Nothing would notice.** `forget.rs` has eighteen tests and not one of them
asks whether the list is complete; they each assert that a particular known
entry is present. That function's own comment records the same failure happening
once already, between the account-removal path and this one, and says the two
lists "came apart". So task 2 registers the owner and writes the guard that
would catch the next one, and the guard is not optional garnish: it is the only
thing standing between this decision and the failure its own precedent
describes.
