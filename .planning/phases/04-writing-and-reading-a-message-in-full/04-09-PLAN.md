<objective>
Make an S/MIME encrypted message say why it cannot be read, instead of reading
as empty, using the sentence this project already wrote for it.

Purpose: success criterion 5's second clause. An enveloped message has no
`text/*` part at all, so `mime::parse`'s `first_of_kind` yields nothing for both
bodies and the reader shows a message with nothing in it and no explanation.
That is the exact failure the note editor stub taught this project to avoid.
Meanwhile `EncryptedMessage::read` parses the outside of a PKCS #7 envelope and
`spoken()` already writes the sentence, and neither has a caller anywhere.

Output: the smallest, most provable half of READ-02, and an honest stop in front
of the half that needs a decision nobody has made.
</objective>

<premise_corrections>
**1. This plan is one half of a decision Pratik has not made, and the other half
is deliberately not built here.** `04-RESEARCH.md`'s third decision offers three
answers for READ-02: take on an OpenPGP crate with key import and decryption,
which is large and whose last mile cannot be tested in this repository; reach the
S/MIME half that already exists, which is small and provable; or both. **This
plan is the second.** Task 2 is where the first is put to Pratik rather than
guessed at, and this plan lifts out whole if he wants neither.

**2. PGP and S/MIME fail differently and READ-02 treats them as one.** A PGP
armoured block is a text part, so it renders as armour rather than as nothing,
and 04-03 already puts a sentence beside it. An S/MIME enveloped message has no
text part at all, so it reads as empty. Those need different handling and this
plan is only about the second.

**3. The detection already ships and already handles the hard case.**
`signed_mail::layout_of` returns `SmimeLayout::Encrypted` for
`smime-type=enveloped-data`, folds the value to lower case because a sender
writing `Signed-Data` once had their message read as not S/MIME at all, and
falls back to the `p7m` file suffix when the sender left `smime-type` off. What
is missing is a caller. `claims_a_signature` is the sibling to copy, and its own
comment says why it deliberately answers no for encrypted mail: sending an
encrypted message down the signature path makes every surface downstream say
"it says it is signed, but it carries no signature to check" about a message
that never said anything of the kind. **So do not widen `claims_a_signature`.
Write `claims_encryption` beside it.**

**4. `spoken` takes `Option<bool>` and the three states are the design.**
`Some(true)` says this computer holds a certificate the message was encrypted
to; `Some(false)` says it does not; `None` says how many certificates it names
and claims nothing. A failure to reach the certificate store is `None`. This is
the same distinction `spellcheck::WhatThisMachineOffers` draws between an answer
and a failure to ask, and the doc comment there records what happened when the
two were the same value: a French user got English on a first run where the call
happened to fail. Getting it wrong here is worse, because `Some(false)` tells
somebody a message was not meant for them.

**5. `CertificateStore` has a real Windows implementation and nothing else.**
`CLAUDE.md` requires platform code behind `#[cfg(target_os = "windows")]` with a
fallback that keeps the crate building. On any other platform the answer is
`None`, not `Some(false)`, for the reason above.

**6. Nothing decrypts, and nothing may imply it does.** There is no signing or
encrypting path either. The sentence `spoken` writes is already careful about
this and should not be reworded.

**7. Everything was located by symbol on 2026-09-05.** `04-RESEARCH.md` carries
line numbers from commit `d3c6c7d`.

**8. Guard-record cost, measured by parsing `tests_last_seen` rather than by
grepping for a file name. Six plans in phase 3 quoted the grep and all six were
corrected.**

| file | records fingerprinting it | test functions today |
|---|---|---|
| `src/service/signed_mail.rs` | 1 | 103 |
| `src/presentation/reader_text.rs` | 0 | 76 |
| `src/presentation/wx_app.rs` | **39** | 199 |
| `src/service/mime.rs` | 1 | 37 |

New tests go in `signed_mail.rs`, which costs one record, and `reader_text.rs`,
which costs nothing. **No `#[test]` goes in `wx_app.rs`.**

**9. `EncryptedMessage::read` is tested against constructed DER only.** Whether
it parses a real envelope from Outlook or Thunderbird is unknown and
unmeasurable here, and it is the assumption this whole plan rests on. If it does
not, criterion 5's message is wrong rather than absent, which is a worse
failure. So the refusal path matters as much as the success path: a message
whose envelope will not parse must still say it is encrypted and say that its
details could not be read, rather than falling back to an empty body.
</premise_corrections>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a stranger's PKCS #7 envelope -> the DER reader | attacker-controlled binary handed to a parser that has only ever seen constructed input |
| the certificate store -> a claim about who a message was meant for | a wrong answer here tells somebody a private message was or was not meant for them |
| a recipient name out of the envelope -> a sentence said aloud | the names come from the envelope and are attacker-controlled |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-36 | Denial of service | a malformed or hostile envelope crashing or hanging the DER reader | high | mitigate | the reader already returns `Result` and the refusal path is a behaviour of this task rather than an afterthought: a message that will not parse says so and the reader stays open. `unwrap` is forbidden outside tests. Add a fixture of truncated and of deeply nested DER and say what each did. |
| T-04-37 | Spoofing | an envelope naming a recipient it was not encrypted to | medium | accept | the sentence describes what the envelope says, and says so. Nothing here decrypts, so nothing here can contradict it, and `spoken`'s existing wording does not claim to have verified anything. |
| T-04-38 | Repudiation | saying a message was not encrypted to this computer when the store could not be asked | high | mitigate | the three states, with a failure to ask mapping to `None`. A test drives an unaskable store. This is the whole of premise correction 4. |
| T-04-39 | Information disclosure | a recipient's certificate name read aloud in a room | low | accept | pre-existing shape: the reader already reads out a signature report carrying certificate details, and the mute `CLAUDE.md`'s fifth guardrail names already exists. |
| T-04-40 | Repudiation | the reader implying a message was decrypted | high | mitigate | `spoken`'s wording says the opposite in as many words and is not reworded. Assert that no sentence on this path contains a word claiming the message was opened, read or decrypted. |
