<objective>
Let a text attachment and an image attachment open in the reader. An image
preview says what the sender said about the picture **and** shows the picture.

Purpose: success criterion 4. `read_attachment` fetches bytes on a worker, calls
`pdf::read`, and posts a `ReaderDocument` that opens as a tab of its own.
Nothing about `ReaderDocument` is PDF-shaped: it is a title, text and landmarks.
`pdf_document` is the only producer and `can_be_read_here` is four lines. So
this is three producers, a widened gate, and one new thing the reader has never
had in a tab before: a picture.

Output: a text file that reads as text, and an image attachment that is both
described and shown, with the decoding done on a worker, bounded before it
starts, and refusing out loud when it cannot be done.
</objective>

<premise_corrections>
**1. `04-RESEARCH.md`'s sixth decision is settled: an image preview both
describes and shows.** The research asked whether an image preview means
decoding pixels, which serves partial sight, or announcing what is known about
the picture, which serves a blind reader directly, and an earlier draft of this
plan chose the second and held the first behind an assumption. **Pratik
overruled that.** In his words: "The mail client isn't just meant for blind
users. It's accessibility first but not alone. visuals matter as well. So ensure
that description and the visuals matter."

So both are built, and the visual half is not a concession. A partially sighted
reader and a sighted reader are both users of this product, criterion 4 says an
image *previews*, and a preview that refuses to show the picture is not one.

**The description is ordered first anyway, and the reason is not preference.**
Task 2 is the description and task 3 is the picture. That order means the
accessible half is not hostage to the decoding work: if task 3 has to be
deferred for anything found on the way, criterion 4's own sentence about
announcing a description still ships. It is an ordering for robustness, not a
ranking of who matters. Nothing in task 2 is written as though task 3 were
optional, and task 2 must not ship a sentence saying the picture is not shown
here, because within this plan it is.

**2. The research's environment table is wrong about the decoder, and the
correction changes the size of the work by an order of magnitude.** It says "An
image decoder for preview — **Not present** — Nothing in `Cargo.toml` decodes
PNG/JPEG", and the same claim reaches `REQUIREMENTS.md`. Read the manifest:

```
image = { version = "0.25", default-features = false, features = ["ico", "png", "bmp"] }
```

`image` is already a direct dependency, locked at 0.25.9, already audited, and
already carrying a twenty-line comment in `Cargo.toml` justifying its narrow
feature list. `src/presentation/art.rs` already decodes with it, already turns
the result into RGBA, and already hands those pixels to `Bitmap::from_rgba` for
the notification area. **PNG and BMP decode in this binary today.** JPEG does
not, which is the true half of the claim, and a half-true absence reads as a
whole one.

So this is not the adoption of a large new dependency. It is a feature flag on a
crate already trusted, plus a second call site for a decode path already proved
once. The full audit is task 3's first job and is written out there rather than
assumed away here, because the transitive crates the flags pull in are real and
are new.

**3. A green test asserts that this capability is absent, and it is not named by
the requirement, the research or the roadmap.**
`test_everything_else_is_not_pretended_to_be_readable` in
`src/presentation/wx_reader.rs` loops over four files and asserts
`!can_be_read_here` for each. One of them is `photo.jpg`, `image/jpeg`. That
test is right today and goes red on the first commit of task 2. It belongs in
the same commit as the widening, with its fixture corrected and its comment
rewritten to say what is still refused and why, not deleted. The other three
rows, an epub, a spreadsheet and a zip, stay and are what says the gate was
widened rather than opened.

**4. The refusal is already written and already names what to do instead.**
`describe_for_refusal` and the sentence around it exist in `wx_reader.rs`. Do not
write a second refusal. What changes is which files reach it.

**5. `looks_unsafe` is a claim, not a default.** `pdf_document` sets it false
with the reason beside it: a document read out of a file, which nothing judged.
Each new producer makes that decision for itself and writes the reason down.
Copying the line without the thought is the thing `CLAUDE.md`'s guardrails
exist to stop. Note that the answer for an image genuinely changes between task
2 and task 3: in task 2 nothing has parsed the bytes, and in task 3 a decoder
has. Task 3 revisits it rather than inheriting it.

**6. The note goes before the content.** `pdf_document`'s own comment argues it:
what the note says changes how the rest should be taken, and putting it at the
end tells somebody after they have already relied on it. Every new producer
follows that, and `pdf::read`'s three-outcome note is the shape to copy.

**7. A fault and an absence must not sound the same, and this is the property
task 3 is most likely to get wrong.** Three states have to stay apart in words:
the picture was decoded and is shown; the picture could not be read, which is a
fault of the file or of this program; and there is no picture to show, which is
a fact about what arrived. Collapsing the last two tells somebody a file is
damaged when it is fine, or that everything is fine when a decoder refused. This
project has drawn exactly this distinction twice already and written down what
it cost when it did not: `spellcheck::WhatThisMachineOffers` separates an answer
from a failure to ask after a French user got English on a first run where the
call happened to fail, and 04-09's `Option<bool>` separates "no certificate"
from "could not ask". Follow the same shape here.

**8. The bound is refused on the declaration first and on the decode as well,
and the precedent already in this tree says why both are needed.**
`sound_scheme_import` refuses a zip entry whose *declared* uncompressed size is
over the cap, and then reads through `read_capped`, refusing again if what
decompression really produces is over it. Its own comment gives the reason: "A
declared size is metadata the archive controls and can misstate." An image
header is the same kind of metadata. So: `ImageReader::into_dimensions()` reads
the header without decoding and gates the declared width and height, and
`ImageReader::limits()` bounds what decoding actually allocates. **Neither is
sufficient alone.** `image`'s own documentation says `max_alloc` "is non-strict
by default and some decoders may ignore it", while `max_image_width` and
`max_image_height` are strict, so the declared-dimension gate is not a cheap
shortcut for the allocation cap and the allocation cap is not a replacement for
the gate.

**9. Everything was located by symbol on 2026-09-05.** `04-RESEARCH.md` carries
line numbers from commit `d3c6c7d`. Five of phase 3's nine plans found theirs
stale. The `image` crate facts in this plan were read from
