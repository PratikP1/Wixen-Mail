<objective>
Let a text attachment and an image attachment open in the reader, and make the
image preview say what the sender said about the picture rather than showing it.

Purpose: success criterion 4. `read_attachment` fetches bytes on a worker, calls
`pdf::read`, and posts a `ReaderDocument` that opens as a tab of its own.
Nothing about `ReaderDocument` is PDF-shaped: it is a title, text and landmarks.
`pdf_document` is the only producer and `can_be_read_here` is four lines. So
this is two producers and a widened gate.

Output: a text file that reads as text, and an image that is described rather
than drawn, with the reason for that choice written down where somebody can
disagree with it.
</objective>

<premise_corrections>
**1. This plan assumes an answer to a question Pratik has not settled, and says
so rather than hiding it.** `04-RESEARCH.md`'s sixth decision asks what an image
preview is for this product's audience: decoding pixels, which needs a new
dependency and serves partial sight, or announcing what is known about the
picture, which needs none and serves a blind reader directly.

**This plan takes the second, and here is the whole of the reasoning so it can
be overruled cheaply.** The criterion's own words are "announcing any
description the sender supplied and saying plainly when there is none", which is
a sentence rather than a raster. The requirement's word is "previews", which is
ambiguous. `CLAUDE.md` says the primary audience is screen reader users and that
the project prefers few things excellent over many adequate. And a decoder is a
`dependency-audit` conversation, a new parser for stranger's bytes, and a real
attack surface, for a feature that serves the secondary audience.

**It is built so a decoder can be added later without a redesign.** The producer
takes the bytes, not just the metadata, so a future version that decodes has
somewhere to put the result. Say that in the module comment rather than only
here.

**If Pratik wants pixels, task 2 is the part that changes** and task 1 stands
unaltered.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a stranger's attachment bytes -> `plain_text::read` | a new parser over untrusted input, which is the first one this project has added since `pdf.rs` |
| a stranger's attachment bytes -> the reading window | whatever a producer returns is put into a text control and read aloud |
| the sender's `Content-Description` -> the top of a preview | attacker-controlled text, now in a more prominent position than an attachment row |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-13 | Denial of service | a very large or single-line text attachment read in full | high | mitigate | a bound with the note saying the file was cut, the way `PAGE_LIMIT` already works for a PDF, and read against the same bound the attachment store applies. Assert the cut and the note with a test. |
| T-04-14 | Spoofing | a binary file labelled `text/plain` rendered as a screenful of nonsense | high | mitigate | the "mostly not text" rule refuses it by name, through the refusal that already exists. `wx_reader.rs`'s own comment gives the reason: opening a spreadsheet in a text control is worse than saying it cannot be read. |
| T-04-15 | Tampering | control characters or terminal escapes in a text attachment reaching the reading window | high | mitigate | strip control characters, keep tabs and newlines, with a fixture carrying an escape sequence. |
| T-04-16 | Spoofing | a partially decoded file rendered as though it were whole | high | mitigate | the note comes before the content and says which outcome it got, which is `pdf::read`'s existing three-way answer applied to a second producer. |
| T-04-17 | Spoofing | an image preview whose description contradicts the file | medium | accept | nothing decodes the bytes, so nothing here can contradict the sender. The preview says plainly that nothing checked the file itself, which is the honest statement of exactly this limit. |
| T-04-18 | Elevation of privilege | a preview executing something out of the file | critical | mitigate | neither producer parses a format that can carry code and neither renders anything. The image producer does not decode at all. Assert that no producer reaches a renderer, and say in the summary that this is why a decoder is a separate decision. |
| T-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | no package is added, and this is the whole reason the image preview describes rather than decodes. `Cargo.toml` is touched only by the version bumps. The summary says so, and says that adding a decoder later runs the package legitimacy gate at that time. |
</threat_model>

correction 1.** An image or a text attachment previews in the application,
announcing any description the sender supplied and saying plainly when there is
none. Whether "previews" means an image is *shown* is Pratik's to settle, and if

whether the note before the content is heard before somebody starts reading, or
skipped past.

`Content-Description` on image parts at all is unmeasurable here, and if they
mostly do not then most image previews will say so. That is the honest answer
and it is still better than the silence there is today. Say it in the changelog.

**Two things are deliberately not built and are said rather than left implied:**
