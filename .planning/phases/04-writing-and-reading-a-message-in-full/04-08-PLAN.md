<objective>
Prove that a picture put into a message survives being saved as a draft and
opened again, then build the decorative answer Pratik settled on: a positive
answer, narrowed to where furniture is plausible, with a setting on the reading
side that decides whether the recipient hears about it.

Purpose: success criterion 2 says inserting an inline image requires alt text or
an explicit decorative mark, and that both survive a draft save and reload.
Inserting with compulsory alt text ships and is reached from a menu, and the
send path rewrites it into `multipart/related` properly. Two things were left.
Nothing asserts the round trip, and there was no decorative path at all because
`a_picture_to_send` refuses an empty description outright and argues for doing
so.

Output: a round trip that is a test rather than a likelihood, a decorative
answer somebody gives on purpose, and a reader who is not obliged to trust the
sender's judgement about it.
</objective>

<what_was_decided>
**The question this plan used to hold as a blocking checkpoint is answered.**
Pratik settled it on 2026-09-06, and not as one of the three options that were
written. In his words: **"1 + 3 + a setting that determines if decorative output
is announced."**

Three things, and the third is the one that changes the shape.

**A decorative path exists, and choosing it is a positive answer.** Never a
description left blank, never a prompt dismissed. Somebody says a picture is
decorative.

**It is narrowed to where furniture is plausible.** A threshold on size or
dimensions or whatever the code can really tell. This is a heuristic about
intent, not a proof, and the plan says so rather than pretending otherwise: a
small screenshot of an error qualifies under any rule of this shape, and that
false positive is named in the code rather than discovered later.

**A setting decides whether a decorative picture is announced to the person
reading.** This is the part that makes the rest safe, and the reason is worth
writing where somebody will meet it. The sender's mark can be wrong, honestly or
lazily, and the recipient is the one who pays. Moving the final say to the
receiving side means a reader who does not trust senders can hear that a picture
was there, while somebody who wants furniture to be silent gets silence. The
sender's decision stops being the last word.

**The setting is not optional and neither is its screen.** A setting the model
holds and no screen offers is the exact defect FEEDBACK-01 exists to fix, and
phase 1's criterion 8 says a phase must not add another. `CLAUDE.md` now carries
that as a standing rule: every setting a user has is reachable from the settings
screen, sorted into a section somebody would look in, in the plan that
introduces it. Two settings break that rule today and both predate it. This must
not be the third. If the control cannot be built here, the setting does not go
in and task 3 says so instead of shipping half of it.
</what_was_decided>
