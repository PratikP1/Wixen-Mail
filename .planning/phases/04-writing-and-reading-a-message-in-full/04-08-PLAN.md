<objective>
Prove that a picture put into a message survives being saved as a draft and
opened again, and settle whether a decorative picture can be put in at all.

Purpose: success criterion 2 says inserting an inline image requires alt text or
an explicit decorative mark, and that both survive a draft save and reload.
Inserting with compulsory alt text ships and is reached from a menu; the send
path rewrites it into `multipart/related` properly. Two things are left, and
both are small. Nothing asserts the round trip, and there is no decorative path
at all because `a_picture_to_send` refuses an empty description outright and
argues for doing so.

Output: a round trip that is a test rather than a likelihood, and a decision
about decorative pictures taken rather than drifted into.
</objective>

<premise_corrections>
**1. WRITE-02's old evidence said no inline image insertion path exists. It is
built end to end and reached from a menu.** `insert_picture` opens a picture
picker, reads the file, and asks "Describe the picture, for somebody who cannot
see it:" in a `TextEntryDialog`. `a_picture_to_send` refuses an empty
description and returns an `img` carrying the escaped alt. `ID_INSERT_PICTURE`
is a real menu item dispatched from the formatting menu. The sanitiser admits
exactly that shape and nothing else beginning `data:`. The send path rewrites
`data:` pictures into `multipart/related` with an inline attachment per picture,
because Gmail and Outlook both drop `data:` pictures out of a received message,
and puts the descriptions into the plain half so it has no silent hole.
**Do not rebuild any of that.** The requirement's first `[D]` line is already
satisfied in the stronger form: alt text is not asked for, it is compulsory.

**2. Task 2 rests on a decision Pratik has not made, and this plan does not
make it for him.** `04-RESEARCH.md`'s first decision: criterion 2 says alt text
*or* an explicit decorative mark, and `insert_picture`'s own doc comment argues
that letting a picture through without a description "would be the one place
this application still made the problem it exists to solve". Both positions are
defensible and they cannot both be true. **Task 2 opens with a checkpoint that
puts the question to Pratik with both arguments, and does not start until it is
answered.** Task 1 does not depend on the answer and lands first.

**3. The decorative mark probably does not survive the sanitiser today, and that
is the first thing to find out.** `ammonia::Builder::default()`'s allowed
attributes do not include `role`, and `grep -rn "role" src/presentation/html_renderer.rs
src/application/pictures.rs` returns nothing on 2026-09-05. So an `img` marked
`role="presentation"` would come back through `sanitize_html` without it, and a
decorative path designed around that mark would lose it on the first save.
**Write that as a failing test before designing anything**, rather than reading
ammonia's documentation and believing it. If the mark does survive, that is
worth knowing too and the test says so either way.

**4. Whatever the decorative path writes must still be recognised by
`is_a_picture_we_carried`.** The sanitiser's attribute filter admits a `data:`
address only on an `img` and only when that function says yes. A decorative
picture that does not satisfy it is not stripped of its mark, it is deleted
entirely, and the message loses the picture with nothing said.

**5. The plain half already filters empty descriptions.** The function that
builds "Pictures in this message" trims each description and drops the empty
ones, so a decorative picture falls out of that list without anything being
added. Confirm it rather than assuming it, because that is exactly the kind of
premise this phase keeps finding wrong.

**6. Everything was located by symbol on 2026-09-05.** `04-RESEARCH.md` carries
line numbers from commit `d3c6c7d`.

  <decision>Whether a picture may be inserted into a message as decorative, with no description.</decision>
  <context>
    Success criterion 2 says inserting an inline image requires "alt text **or an
    explicit decorative mark**". There is no decorative path:
    `a_picture_to_send` refuses an empty description outright, and
    `insert_picture`'s own doc comment argues for that refusal. So as things
    stand the criterion cannot be met, and the two positions cannot both be true.

    **The trade, in one paragraph, because that is the whole question and the
    options below are only its consequences.** What a reader gains from a
    decorative mark is silence where silence is correct: a signature flourish, a
    spacer, a horizontal rule sent as a picture is furniture, and a screen reader
    announcing it, or announcing a description somebody invented for it, is noise
    on every read for every recipient of that message and every reply that quotes
    it. There is no correct way to send one today, so the person either describes
    furniture or does not send it. What is lost is that the same mark is the
    fastest way past a prompt. Somebody attaching a photograph, a chart or a
    screenshot of an error, in a hurry, with a dialog between them and sending,
    can mark it decorative and be done, and the recipient is then told nothing
    at all rather than told something vague. That is worse than a poor
    description, because a poor description can be asked about and silence cannot:
    the recipient does not learn there was a picture. **So the question is
    whether the gain on furniture is worth the loss on the meaningful picture
    somebody marked decorative to get past a prompt, in a product whose primary
    audience is on the receiving end of that decision.** Nothing in the design of
    the prompt makes the second case impossible; the most it can do is make it
    deliberate.

    Both arguments are short and each is the whole case, so both are given in
    full below rather than summarised.

    **Report task 1's finding as part of this question**, because it changes the
    cost. Task 1 established whether `role="presentation"` survives
    `sanitize_html`. If it does not, taking the decorative path means widening
    the sanitiser's allowed attributes, which is a security-relevant change to a
    filter over every stranger's markup and needs reasoning of its own.

    Do not change any code to allow an empty description before this is answered.
  </context>
