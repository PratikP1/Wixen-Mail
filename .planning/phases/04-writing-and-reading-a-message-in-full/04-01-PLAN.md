<objective>
Carry the sender's own description of an attachment from the wire to the
sentence a screen reader says, and say plainly when the sender gave none.

Purpose: success criterion 4 says a preview must announce "any description the
sender supplied and say plainly when there is none". That is blocked before any
preview code is written, because `AttachmentInfo` (`src/service/mime.rs`)
carries `filename`, `mime_type` and `size` and nothing else, so no layer above
it has ever seen a description. This plan opens that boundary and carries the
fact all the way to a spoken sentence, so the preview plan (04-03) has something
true to say.

Output: a described attachment that says what it is, an undescribed one that
says so, and a stored column that survives a restart.
</objective>

**Everything below was located against the tree on 2026-09-05, by symbol.**
`04-RESEARCH.md` carries line numbers from commit `d3c6c7d` and they have moved.
Phase 3 found stale line numbers in five of its nine plans. Cite symbols.

**1. `is_embedded_in_the_body` already reads the disposition, so the research is
wrong about it.** `04-RESEARCH.md`'s dropped-facts table says
`is_embedded_in_the_body` "infers" the disposition and that "a sender's explicit
`attachment` on a `cid:` part is not honoured". Read the function: it requires
`content_disposition()` to say `inline` before it filters a part out, so a
`cid:` part the sender marked `attachment` is left in the attachment list, which
is honouring the sender exactly. A task written from that sentence would have a
test that could not fail. The disposition value is genuinely not *carried* onto
`AttachmentInfo`; that is a different and much smaller claim, and this plan does
not act on it because nothing needs it yet.

**2. `ParsedMessage` derives `Default`, and `AttachmentInfo` does not.** Adding a
field to `AttachmentInfo` breaks every struct literal that spells all three
fields. There are seven such literals, in `src/service/mime.rs` and
`src/application/pop_sync.rs`. Count them with the compiler rather than with a
grep before assuming that number is still right.

**3. The `alt` has to be read before `carry_the_pictures` runs.** Inside
`mime::parse`, `body_html` is built by `first_of_kind` and then handed straight
to `crate::application::pictures::carry_the_pictures`, which rewrites every
`cid:` reference into a `data:` URI. After `parse` returns there is no `cid:`
left in the body to match an attachment's content id against. So task 2's lookup
happens inside `parse`, against the html as it arrived.

**4. `receipt_to` is the route to copy, and it is already built.**
`ParsedMessage.receipt_to` reaches `CachedMessage.receipt_to` through
`mail_sync.rs` and `pop_sync.rs`, is stored by `ensure_column_exists("messages",
"receipt_to", "TEXT")` in `message_cache/mod.rs`, and arrives on
`MessageItem.receipt_to`. The attachment route is the same shape one table over:
`attachments` rather than `messages`, `CachedAttachment` rather than
`CachedMessage`, `AttachmentItem` rather than the row.

**5. Guard-record cost, measured rather than grepped.** The figure that matters
is how many records carry a `tests_last_seen` entry naming a file, not how many
mention it. Six plans in phase 3 quoted the grep and all six were corrected. For
this plan's files, measured 2026-09-05:

| `src/service/mime.rs` | 1 | 37 |
| `src/presentation/reader_text.rs` | 0 | 76 |

So new tests go in `mime.rs`, `reader_text.rs` and `attachment_content.rs`. **Add

would flag 41 records at a build and a full library run each. Editing a struct

the check; only adding or removing a test function does.

**6. Nothing here has ever met a real account.** Whether real senders supply
`Content-Description` at all is unmeasurable in this repository, and if they
mostly do not then this feature mostly says "the sender gave no description".
That is the honest answer and it is still worth having, because today the reader
cannot tell "no description" from "we dropped it". Say that in the changelog
rather than implying the feature does more.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a stranger's MIME headers -> `AttachmentInfo` | `Content-Description` is arbitrary text chosen by whoever sent the message |
| a stranger's HTML body -> an attachment's description | the `alt` attribute is attacker-controlled and is read here for the first time |
| `AttachmentInfo` -> the announcement channel | anything that reaches `label()` is spoken aloud, possibly in a room with other people in it |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Spoofing | a description claiming the file is something it is not | medium | accept | the name, the kind and the size are said first and come from the part itself; the description is last and is plainly the sender's words. A sender who can attach a file can already lie about its name. |
| T-04-02 | Denial of service | a description of unbounded length read out in full | medium | mitigate | bound what `label()` says, the way `tab_label` already bounds a subject, and cut on a word boundary. A ten thousand character description is a screen reader that cannot be interrupted out of. |
| T-04-03 | Tampering | markup or control characters in a description reaching the announcement | high | mitigate | the description is taken as text and never as markup; the `alt` lookup returns characters. Assert it with a fixture whose `alt` carries a quote and an angle bracket. |
| T-04-04 | Denial of service | a malformed HTML body making the whole message unparseable | high | mitigate | the lookup fails to no description rather than to an error, with a test. A message that cannot be parsed cannot be read at all. |
| T-04-05 | Information disclosure | a description read aloud in a room | low | accept | pre-existing and unchanged: every attachment row is already spoken. `CLAUDE.md`'s fifth guardrail names the mute as the answer and it already exists. |
| T-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | no package is added. `mail_parser 0.11.5` is already a direct dependency and `MimeHeaders` is already imported in `mime.rs`. No package-manager install runs, so the legitimacy gate does not apply, and the summary says so. |
</threat_model>
