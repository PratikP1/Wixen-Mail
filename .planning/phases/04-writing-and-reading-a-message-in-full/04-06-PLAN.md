<objective>
Give the composer a key that moves to the next misspelling and one that moves
back, leaving the caret in the message, and make landing on a word say what it
could be instead.

Purpose: success criterion 3 has three clauses and two of them already ship.
Misspellings are marked as they are typed, by the browser engine, and every
screen reader announces the marks itself. The flood clause is satisfied by
design, because the typing rules decline to run for a paste and a harness test
says so. What is missing is narrower than the requirement implies: the walk
between misspellings is a modal dialog per word and only goes forward, and the
sentence it says offers one suggestion.

Output: two keys, a sentence that offers more than one thing, and F7 unchanged.
</objective>

<premise_corrections>
**1. WRITE-03's old evidence prescribed the remedy this codebase deliberately
refused, and acting on it would have done real damage.** It said spell check
runs on send only and that the feature waits on a rich editor control, noting
helpfully that `wxdragon` ships with `richtext` enabled. Both clauses are
wrong. `src/presentation/editor_document.rs`'s module header records that the
composer's body is a `contenteditable` in a web view **rather than** a
`wxRichTextCtrl`, that the reason is accessibility rather than formatting, and
that `wxRichTextCtrl` is drawn by wxWidgets on every platform so it exposes no
per-range accessibility attributes anywhere, which means no misspelling can ever
be marked in it. **Do not adopt `wxRichTextCtrl`. Do not rebuild
spell-as-you-type.** REQUIREMENTS.md now carries the correction; this plan does
too so it cannot be lost.

**2. The research says this feature may need its own feasibility spike, and the
tree already answers the question.** `04-RESEARCH.md`'s second decision says a
key that moves the caret between marked ranges "is a different feature, and the
marks belong to the browser engine rather than to the document, so the page
cannot enumerate them", and calls it possibly a large, uncertain piece of work.

That reasoning is correct about the engine's marks and it is answering the wrong
question. `src/application/spell_session.rs`'s own module header opens by saying
so: what no engine exposes is the list, so this module builds one, from
`application::words` and this program's own speller, in the page's own
coordinates. `findings` returns every misspelling with its position and its end.
`editor_document::select_word_script` already moves the selection to such a
position, and F7 already calls it once per word. **So the enumeration and the
caret move both ship. No spike is needed and this plan builds the feature.**
The research is corrected.

**3. There is no wx-side place to bind a key here.** The composer is a dialog, a
dialog cannot own a menu bar, and a web view keeps every key once it has focus.
`editor_document.rs`'s header states this and the page already binds Escape,
`Ctrl+Enter`, `Ctrl+S`, F7, F8 and `Ctrl+\` and posts them back over the
`wixenEditor` channel. The new keys go there, and the assertions about them are
source reads of the page text, which is how the existing ones are asserted.

**4. F7 and F8 are taken, and F7 is taken twice.** In the composer F7 walks the
spelling; in the reader F7 moves to the security warning bar. F8 reaches the
attachment list. Both are in `docs/KEYBOARD_SHORTCUTS.md`. So the new keys are
new combinations, and Word's own convention for this is `Alt+F7` for the next
misspelling, which is worth following rather than inventing. Whatever is chosen,
check it against every key the document already names and against the page's own
handler before binding it, and say in the summary what was checked.

**5. A page-bound key is invisible to the shortcuts check and needs a listed
exception.** `tests/wired.rs`'s `test_the_shortcuts_document_names_no_key_the_code_has_never_heard_of`
looks for the literal combination in `src/presentation`. The page writes
`event.key === 'F7' && event.altKey`, which is not the string `Alt+F7`. So each
new key needs an entry in `bound_by_a_handler_rather_than_a_menu()` with a
comment naming the file, exactly as `Ctrl+Enter` and `Ctrl+\` already have.
Adding to that vector is not a new test function and fires no count check.

**6. `Finding::spoken` is the dialog's opening line and it is followed by a
list.** It says the word, the problem and the first suggestion, and its comment
argues for the first one saving somebody arrowing into a list. That reasoning
holds where there is a list to arrow into. For a caret move with no dialog the
announcement is the only channel, so it needs its own wording rather than a
change to `spoken`. Changing `spoken` would make the dialog say things twice.

**7. Everything was located by symbol on 2026-09-05.** `04-RESEARCH.md` carries
line numbers from commit `d3c6c7d`.

**8. Guard-record cost, measured by parsing `tests_last_seen` rather than by
grepping for a file name. Six plans in phase 3 quoted the grep and all six were
corrected.**
