<objective>
Make the mailing-list warning that already exists, and has never once fired,
reach somebody.

Purpose: `application::blocking` carries `how_to_leave_the_list`, reads it in
`may_block`, and has a whole `MayBlock::YesButFirst` arm and a written sentence
for it. Its one production construction hands it nothing, because
`List-Unsubscribe` is never parsed, so the arm is unreachable in the shipped
build. This is the smallest thing in `04-RESEARCH.md` and it is a complete
feature sitting behind one dropped header at the same boundary 04-01 has already
opened.

Output: a person who blocks a mailing list is told what blocking will and will
not do, before it is done, and told where to unsubscribe when the message said.
</objective>

doc comment gives the reason and it applies unchanged: a query on the interface
thread inside a key handler is a window that cannot repaint, and a window that
cannot repaint cannot speak.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a stranger's `List-Unsubscribe` header -> a sentence said aloud | the header is attacker-controlled text and reaches the announcement channel through `where_to_write_to_leave` |
| the header -> a decision about whether a block is made | `may_block` changes its answer on the strength of this header |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-06 | Spoofing | a phishing message carrying `List-Unsubscribe` to soften the block warning | medium | mitigate | the arm is `YesButFirst`, so the block is still made and the sentence is advice rather than a refusal. The two real refusals, blocking your own address and a block already covered, are asked before it and are unaffected. Assert the ordering with a test if `blocking.rs` does not already have one. |
| T-04-07 | Tampering | an unbounded or control-character header read aloud | medium | mitigate | the value is trimmed and taken as text. `where_to_write_to_leave` already parses only the angle-bracketed `mailto:` form and hands back nothing otherwise, so a header of arbitrary junk produces the no-address sentence rather than the junk. Confirm that with a fixture rather than assuming it. |
| T-04-08 | Information disclosure | an unsubscribe address named aloud in a room | low | accept | pre-existing shape: every warning this handler raises is already announced at high priority, and the mute is the answer `CLAUDE.md`'s fifth guardrail names. |
| T-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | no package is added. The header is read through `mail_parser`'s existing `Message::header`, the same route `receipt_request` already uses. No package-manager install runs, and the summary says so. |
</threat_model>
