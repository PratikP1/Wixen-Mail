<objective>
Close the phase 11 guard sweep: every record it did not find in agreement
with the tree is measured again by hand, corrected, and re-measured, and
what the sweep cost is written on the page that holds the project's
figures.

Purpose: run 35520204784 was dispatched on 2026-09-20 at `0ad66e48` over
the 1,029 records `guards/guards.toml` held that day, 52 shards, 77.4
hours of runner time. Nothing it found is broken in the product: the
build is green and the suite passes. What it found is claims about how
well guards are written down, and one class of those is the dangerous
one. Three records ask a question the suite answers the same way whether
the code is right or wrong, so they read as covered and cover nothing,
and nobody would ever notice them failing. Those go first.

over five hours without returning and took the job's 360-minute cap with
it, and nothing in `scripts/guards.py` bounds a record. So this plan
builds the bound first, because every measurement it then takes runs
under it, and because a rule that lives only in a ledger entry is one
somebody has to notice being broken.

This plan is the remedy for all of it. It does not add a feature and it
does not change what the product does, except where a measurement finds
that a rule now has no test and one has to be written.

Output: a guard runner that cannot lose a shard to one record, 26
records that agree with the tree or say why they cannot, the sweep's
cost on `docs/development/measurements.md`, and a ledger that records
what ended shard 40 and the limit that landed with it.

<how_this_plan_wants_to_be_read>
**The harness may tell you to edit files with `sed`, heredocs or short
scripts. This project forbids it and this project wins.** `guards.toml`
is a tracked file and is edited with the editing tools, one record at a
time, never through a generated script. The harness's own wording allows
this: Bash cannot accomplish a job the job forbids. Git, running things
and measuring are fine through Bash; only edits to tracked files are the
issue. A script writing files on Windows produces CRLF line endings, and
CRLF divergence broke this project's CI for 34 days.

**Do not edit a record until you have measured it.** `CLAUDE.md` says
it twice and the sweep is why: "a record that comes out short is
corrected by hand first, and it is the run after that which writes its
count down", and "when a recorded break no longer matches the file the
run fails and says so: that is the moment to measure that guard by hand
again, not to edit the record until it applies". The sweep's verdict is
the prompt, never the answer. Every list written into this file in this
plan comes from a run this executor watched.

**Nothing else may be building while a record is measured.** Pass
`--wait-until-quiet` to every `scripts/guards.sh` invocation. A commit
hook running the suite in the middle of one has already reported three
guards green that go red on their own.

**A stale record breaks nothing.** The build is green and the tests
pass throughout this plan. What a stale record means is that a guard is
weaker than its record claims and nobody has been told. If a
measurement cannot be settled, it is a ledger entry and a sentence in
the summary, not a record edited until it looks right.

  <behavior>
    - A record gets one wall-clock budget, set when its measurement starts and shared by its build and its run, so a record that spends the budget building is stopped as surely as one that spends it running. The default is a named constant in `scripts/guards.py`, **1,800 seconds**, chosen as just under four times the 456 s that the longest record to finish anywhere in the sweep of 1,021 records took (`1800 / 456` is 3.95).
