The brief's framing, that wx does not track the browser's own child
windows, is half right. wx gets no focus event from those windows, but
it does not need one: at deactivation it asks `::GetFocus()` and walks
the answer up to the WebView. That works whenever the window's own
thread can see the browser's window as its focus, which 12-01's reading
showed it can. So every outcome of the save except one leads the restore
back to the WebView: the WebView saved restores the WebView, and nothing
saved restores the first child that takes the keyboard, which is the
WebView too. **The one save that ends on the frame is the frame
itself**, and it is sticky: saved once, it is restored to itself on
every later activation, because this frame has a parent and
`wxSetFocusToChild` takes the saved-child branch.

What 12-01's reading set up: its first activation put the keyboard in
the browser, its deactivation sent `WA_INACTIVE` while the browser still
held the keyboard, so wx saved the WebView, and only then cleared the
focus. It chose the state wx saves. The runner's deactivation is Windows'
own, after Enter handed a link to Edge, and whatever the thread saw at
that instant is what wx saved. Three causes fit the runner's record, and
its one read, UI Automation's focused element, cannot choose between
them:

- **A. wx restored the keyboard to the frame itself**, because the frame
  was saved as its own last focused child. The end state is the
  window's own handle holding the keyboard, which is exactly what the
  record shows by class, control type and title.
- **B. wx's restore never ran**, because the activation arrived with the
  minimised flag or while wx believed the window iconised, and the
  keyboard stayed wherever Windows left it: nothing, or the frame by
  `DefWindowProc`.
- **C. The restore reached the browser and the keyboard left it
  afterwards**, through the browser process's own handling of a real
  foreground change, which no message sent by hand exercises.

**The likeliest is A.** It is the only path in wx's code that puts the
keyboard on the frame on a window whose restore runs, and nothing in
this flow minimises the window (B), while C would have had to leave the
keyboard on the frame rather than on the host or nowhere. What A does
not have is a known way for the frame to have held the keyboard at the
real deactivation, and that is why it is called likeliest and not
found. **The read that tells them apart** is the window's own thread,
not the accessibility tree: `GetGUIThreadInfo` on the page window's
thread after the return, sampled at 0, 250, 1,000 and 3,000 ms. A reads
the frame's own handle from the first sample; B reads 0, or the frame
with no restore behind it; C reads inside the WebView first and
somewhere else later. And once the fix below exists, the one line it
logs when it has to move the keyboard names where it found it, which is
the only record of the pre-fix state a green run will carry. Task 2 puts
both into the case.
