**4. The bug, got around: four routes in `phone_numbers`, each measured.**
Every number is read through all four, and the module never calls
`country().id()` or `number_type()`.
- Digits in any script become ASCII digits first, through
  `this_machine::fold_digits` (Windows' `FoldStringW` with
  `MAP_FOLDDIGITS`), because the crate's parser refuses any other digit.
- The chosen country is the reference for the first reading. When the crate
  says the code came from a `+` (`Source::Plus`, which covers `tel:`
  addresses too), the text is read again with no reference country; when it
  came from an international prefix (`Source::Idd`), that prefix is cut off
  with the chosen country's own `Metadata::international_prefix`, a `+` put
  in its place, and the text read with no reference country (pull request
  #110).
- When the crate says it took the chosen country's code out of the digits
  (`Source::Number`), `+<code> <typed>` is read as well and kept when it is
  valid, which is Google's own preference (issue #68).
- The region is read with the significant number's leading zeros kept,
  through `Database::region`, `Metadata::leading_digits` and
  `Descriptor::is_match` in the order the crate and Google use, because the
  crate's own lookup drops the zeros. Validity is the crate's `is_valid`,
  which keeps them.

What cannot be routed around is doubted and kept as typed: a foreign number
typed with its code but no `+` and no international prefix (every library
reads it as a number of the chosen country, and the sentence says to type
it with `+`), and a number with no code and no country chosen. Each route is
removable, with its rows kept, when upstream ships the fix.
</decisions>

## `phonenumber` 0.3.10, in detail

**Maintenance.** Repository `whisperfish/rust-phonenumber`, 203 stars, 22 open
issues, last push 2026-07-02. The published 0.3.10 was built from
`0a1516ee` on the `v0.3` branch, "chore: bump crate to 0.3.10+9.0.33"
(`.cargo_vcs_info.json` in the tarball). The default branch has moved on to
an unreleased 0.4.0 (edition 2024, MSRV 1.88) with three parsing fixes of
2026-06-27; a pull request against `v0.3` says 0.4 has a memory regression,
issue #107, which is why the maintenance line is the one to take. Metadata
is refreshed about twice a year: 9.0.21 in January, 9.0.33 in July.

**The defect that matters here, and how 12-07 avoids it.** Open pull request
#110 (filed 2026-08-19, read 2026-09-23) backports a fix to `v0.3`: "parsing
an international number under a mismatched reference country strips the
wrong national prefix: `parse(Some(country::GB), "+390635511397")` returns
`+39635511397` and `is_valid` reports `false`". 12-07 puts a Country choice
beside every number, so the choice and a number's own code will disagree
whenever somebody types a foreign number with its code. `phone_numbers`
therefore never hands the library a reference country for a number that
carries its code: a number typed with `+` is read with none, and one that
begins with the chosen country's international prefix (read from that
country's metadata, `Metadata::international_prefix`) has the prefix turned
into `+` first. The Italian number above is a case in 12-07 and stays one
after the fix ships. **Measured on 2026-09-24, with three more defects found
beside it**: "The defects, measured", below.

**Licence.** Apache-2.0 only, with `LICENSE` in the tarball. It sits in an
MIT program as a component; the obligation Apache-2.0 carries, that a

**Four defects, where each lands, and the route around it.**

1. **The chosen country's national prefix is stripped from a number that
   carries its own code** (pull request #110). It lands on `parse` with a
   chosen country for a number typed with `+`, with an international prefix
   (00, 011, 0011, 010, 810, 0161 were measured), or as a `tel:` address
   with `+` or `phone-context`, whenever the number's significant digits
   begin with the chosen country's trunk digits: an Italian number with GB,
   DE, FR, AU, JP, NZ or HU chosen, a Birmingham `+44 121` number or a Jersey
   one with US or CA chosen, Paris `+33 1`, German mobiles `+49 151`,
   Japanese toll-free `+81 120` and Budapest `+36 1` with US chosen. The
   validity, the type, the region and the formatted form are all read from
   the damaged number, and in one case (`+49 1512 3456789` with US chosen)
   the damage produced a different valid German number. Route: read with the
   chosen country first; when the crate says the code came from a `+`
   (`Source::Plus`), read the text again with no reference country; when it
   came from an international prefix (`Source::Idd`), cut that prefix off with
   the chosen country's own `Metadata::international_prefix`, put `+` in its
   place and read with no reference country.
2. **A number whose significant digits keep a leading zero has no region and
   no type.** `PhoneNumber::metadata`, behind `country().id()` and
   `number_type()`, reads `national().value()`, which drops the zeros, while
   `is_valid` reads `national().to_string()`, which keeps them. It lands on
   every Italian and Vatican number (`+39 0...`, both the region and the
   type) and on the type of Benin, Cote d'Ivoire, Congo, Gabon and San Marino
   numbers, whatever country is chosen; `is_valid` and the formatted form are
   right. Nothing upstream names it. Route: the module reads the region
   itself, zeros kept, through the crate's public `Database::region`,
   `Metadata::leading_digits` and `Descriptor::is_match`, in the order the
   crate and Google both use; the module never calls `country().id()` or
   `number_type()`.
3. **A national number that begins with the chosen country's own code loses
   those digits** (issue #68, open since 2024-02-28). `391 231 2312` with IT
   chosen, an Italian mobile, reads as `+39 12312312`, not valid; `4921
   123456` with DE chosen, a number in Emden, reads as a different valid
   number in Dusseldorf. Route: when the crate says it took the code out of
   the digits (`Source::Number`), read `+<code> <typed>` as well and keep that
   reading when it is valid, which is Google's own preference.
4. **Digits in other scripts are refused.** The crate carries a folding table
   for fifteen scripts, but its parser matches ASCII digits only
   (`src/parser/helper.rs:87`, "TODO: Extend with Unicode digits"), so
   full-width and Arabic-Indic digits read as `NoNumber`. Route: Windows'
   `FoldStringW` with `MAP_FOLDDIGITS` turns every decimal digit into its
   ASCII digit before the crate reads the text, on the tree's own pattern of
   taking locale answers from Windows; the typed text is still what a doubted
   number keeps.

**What cannot be routed around, and what the module does with it.** One row
of the 102 still differs, row 12, `0121 234` with GB: both libraries call it
too short and not valid and differ only in how they would print it, which
the module never stores, because a doubted number is kept as typed. One kind
of input no library can read, because it is ambiguous rather than broken: a
foreign number typed with its country code but no `+` and no international
prefix (row 64, `39 06 3551 1397` with GB chosen). The crate, the workaround
and the oracle all read it as a British number and call it not valid, so the
module doubts it, keeps it as typed on a second OK, and says to type it with
`+` and the country code. A number with no code and no country chosen (rows
79 and 80) is refused by the crate and the oracle alike, and the module
doubts it as having no country.

## `rlibphonenumber` 2.2.12, the alternative

The freshest data of any candidate: its readme says Google's 9.0.39, and a
bot has cut a release after each of Google's for months. It is also faster
and its command-line tool is released for `x86_64-pc-windows-msvc`, so it
builds on Windows. It loses on four things:

- **One maintainer and nobody depending on it.** 355 of 359 commits are
  `vloldik`'s; no crate on crates.io depends on it, against 59 for
  `phonenumber`. The bot that keeps the data fresh is also a single point:
  if it stops, the freshness does.
- **Size and what runs at build time.** In its shippable configuration it
  adds 33 entries to `Cargo.lock`: 29 new crates, three second versions
  (`dashmap` 5.5.3 beside 6.2.1, `heck` 0.5.0, `unicode-width` 0.1.14 beside
  0.2.2) and itself. Among them is a protobuf compiler, `protox` with
  `prost-build`, `logos` twice, `miette` and `petgraph`, and a procedural
  macro that parses Google's XML at compile time. The shippable
  configuration is its default: without `protox` its build runs a system
  `protoc`, which no machine or CI job here installs.
- **No licence text.** Neither `rlibphonenumber` 2.2.12 nor
  `rlibphonenumber_macro` 0.2.1 ships a licence file.
- **No headroom.** Its MSRV is 1.88, exactly this project's floor.

Its data claim was read from its readme and not verified, because its data
is a protobuf blob. Its macro crate's own copy of the XML is byte-identical to
Google's 9.0.36, which is fine for what the macro does (it builds the `Region`
enum), and is a second copy at a second version.

## Windows' own formatter, measured

`Windows.Globalization.PhoneNumberFormatting` is libphonenumber inside
Windows, reachable through the `windows` crate this tree builds, behind one
feature. It adds no package and no maintainer. Called from an unpackaged
Windows PowerShell 5.1 process on this machine it works, and it answered:

```
'+44 20 7946 0000'  no region    -> Valid, region US, kind FixedLine, international '+44 20 7946 0000'
'+49 30 901820'     no region    -> Valid, region US, kind FixedLine, international '+49 30 901820'
'12'                region GB    -> Valid, region GB, kind Unknown
'07700 900123'      region GB    -> Valid, region GB, kind Unknown
'+999 1234'         no region    -> InvalidCountryCode
'call me'           region GB    -> NotANumber
```

Three things disqualify it for this feature. `GetGeographicRegionCode`
answered this machine's region for a British and a German number, so it
cannot find a number's country from its code, which Pratik asked for. `Valid`
means the text parsed, not that the number is valid (`12` is "Valid"), so
validity has to be read off `PredictNumberKind` answering anything but
`Unknown`. And its numbering data is whatever the tester's Windows build
carries, which nothing can read or pin, so a test that passes here can fail
on another machine for a reason neither can see. It is also Windows only, so
a later port would need a second library anyway.

## `phonelib`, `phonenumber-rs`, and writing it ourselves

- **`phonelib` 2.0.0** has no dependencies and ships its licence. Its own
  readme says that outside the North American plan it checks length only and
  points readers who need per-country validation to a library built on
  libphonenumber's data. That is the thing asked for, so it is out. Its
  tables are hand-kept, which is also the reason below.
- **`phonenumber-rs` 0.1.1** is one commit old, published twice on
  2026-07-19, with no licence in its repository or tarball, and depends on
  `bincode` 1, which RustSec marks unmaintained (RUSTSEC-2025-0141).
- **Writing it ourselves** is the calling-code table 12-07 planned before this
  answer. It cannot check or format per country without Google's metadata,
  and copying that metadata into the tree is a private copy of an open
  standard, the reason 06-03 turned down a hand-written CLDR table.

## How it sits with version 2's translation

Checked against what the memory note of 2026-09-13 asks of anything chosen
now: that it is the first piece of the version 2 system, judged on whether
it carries translation, not a point fix.

- **The stored value is language-free.** A number is stored in its country's
  own digits and grouping, and its country as a two-letter ISO 3166 code.
  libphonenumber's formats are per country, not per language, so translating
  the interface never changes a stored number.
- **Country names come from Windows in its display language.** The library
  carries no names. `GetGeoInfoEx` with `GEO_FRIENDLYNAME` gives them in the
  language Windows shows, which is how this tree already takes month and day
  names (06-03): they are translated before version 2 starts. Asked on this
  machine for every one of the library's 245 regions, Windows named 242; it
  has no name for AC (Ascension), EH (Western Sahara) or TA (Tristan da
  Cunha), which 12-07 shows by their code. The control: GB answered "United
  Kingdom" and ZZ answered nothing.
- **The sentences are this program's own.** The library's errors are an enum,
  and its English messages are never shown. `phone_numbers::sentence` is one
  function composing each sentence from a typed reason, the seam where
  version 2's Fluent catalogue replaces a `format!`. One cost to know now:
  some languages decline a country's name inside a sentence, and Windows
  gives one form, so a translator will phrase around it ("a number for the
  United Kingdom" rather than an inflected adjective).
- **Digits in other scripts.** Google's libphonenumber reads Arabic-Indic
  and full-width digits. This port's parser matches ASCII digits only
  (`src/parser/helper.rs:87`, "TODO: Extend with Unicode digits"), though
  it carries a normaliser for the others. Measured on 2026-09-24: full-width
  and Arabic-Indic digits are refused as `NoNumber`, and read correctly once
  Windows' `FoldStringW` has turned them into ASCII digits, which 12-07 does
  before the crate reads a number (defect 4 above). A digit Windows does not
  fold is still counted by the no-digit rule, so at worst such a number is
  doubted and kept as typed. Version 2 should still hear it with a real
  keyboard layout.
- **Right-to-left interfaces.** A number shown inside an Arabic or Hebrew
  interface needs left-to-right isolation, and 06-03 found that the isolation
  characters Fluent inserts are read aloud badly, so it switched them off.
  That question is version 2's and is not settled by this choice either way.

## What installing it commits the project to

- **The `build(12-07)` commit pays the whole gate.** `scripts/which-checks.sh`
  answers `all` for a `Cargo.toml` or `Cargo.lock` change that is more than
  this package's version line (`:432-444`), which includes `cargo audit` over
  the new packages. The answer for a red commit is asked first (`:249-264`),
  so the manifest goes in a green commit of its own, ahead of any red, or the
  install would be judged by a scoped run.
- **The merge pays it again.** `which-checks.sh`'s arm for `main` says a
  branch that changed a dependency "still earns everything at its merge", and
  this branch's diff holds the manifest. `check.sh`'s comment above its
  advisory stage says no merge runs `all` since 12-03.2; this merge is the
  case that comment does not cover.
- **The census.** `test_every_dependency_has_been_told_apart_from_a_way_out`
  in `src/service/outward.rs` reads the manifest and is red for a dependency
  on neither of its lists. `phonenumber` opens no socket, so it goes on
  `A_CRATE_THAT_CANNOT`, whose length in the type rises by one (53 on
  2026-09-23), in the same commit.
- **The comment above the manifest line** is read by `tests/house_style.rs`
  (no em or en dash) and `the_words_that_say_nothing` (none of the six words),
  as the Fluent lines' comment is.
- **An accepted advisory.** RUSTSEC-2023-0089, `atomic-polyfill`
  unmaintained, goes into `.cargo/audit.toml` by name in the same commit, with
  its reason (compiled only for embedded targets, never for this program) and
  its exit condition (the day `heapless` 0.7 leaves the lock file or a
  Windows target starts compiling it), the default of 2026-09-24 so that a new
  warning stands out, as `paste` was accepted. `scripts/audit.sh` then checks
  on every full run that the entry still names a reported advisory.
- **A recurring cost.** Fifteen lock entries to keep current, four of them
  untouched upstream for years; numbering data that trails Google's by months
  unless somebody raises the version; and four routes in `phone_numbers` to
  retire, each with its rows, as upstream fixes ship (pull request #110 for
  the first, issue #68 for the third).

## Recommendation

1. Take `phonenumber` 0.3.10 behind `application::phone_numbers`: team-owned since 2017, 59 crates depend on it, its licence ships, it moves no floor, and it adds 15 lock entries (13 compiled on Windows) with no open advisory against anything it resolves.
2. Its numbering data is Google's 9.0.33 of June 2026, byte-identical, six releases behind today's 9.0.39 and refreshed about twice a year, so 12-07's check doubts and never refuses. Four defects were measured on 2026-09-24 and each is routed around in `phone_numbers`: the plain call agrees with the oracle on 46 of 102 numbers and the workaround on 101, the last one an invalid number the module keeps as typed anyway.
3. Not `rlibphonenumber` (fresh data, but one maintainer, no dependents, 33 entries with a protobuf compiler at build time, no licence text), not Windows' formatter (it named this machine's region for a British number), and not `phonelib` (length only outside North America).
