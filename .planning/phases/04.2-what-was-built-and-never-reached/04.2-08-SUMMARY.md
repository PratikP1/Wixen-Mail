# Phase 4.2 Plan 08: A column layout belongs to the kind of folder it was arranged in Summary

Sorting a column in Sent no longer decides how the inbox opens, moving between
folders no longer throws away what you just arranged, and Restore Defaults
restores the columns for the folder you are in.

## Does it work

**Yes, up to one hop I could not run, and one question only a screen reader
answers.**

**Does sorting one folder leave another folder's layout alone?** Yes, in both
places it did not.

Across a restart, the stored string now carries which kind of folder the layout
was arranged in, and the reader takes it from the string rather than from
whoever asked.
`test_a_sent_layout_and_both_its_levels_come_back_as_a_sent_layout` stores a
Sent layout and reads it back, and it comes back as a Sent layout. Its old form
could not have seen this: it built an inbox layout, handed `Inbox` back into
`from_stored`, and asserted the sort survived, so the kind was supplied by the
caller at both ends of a round trip that never carried it.

Within one session, `LayoutPerKind` keeps what each kind of folder was last seen
with, and
`test_coming_back_to_a_folder_kind_finds_what_was_arranged_there` arranges an
inbox layout, moves to Sent, moves back, and finds the arrangement rather than
the defaults. That is driven over the real type. The hop from the window into it
is read out of the source by
`test_a_change_of_folder_kind_restores_the_layout_rather_than_rebuilding_it`,
because the folder change sits inside a closure inside the window builder, where
reaching it needs a window, an account with stored credentials and a mail
server.

**Does Restore Defaults restore the defaults for the folder you are in?** Yes.
`test_restore_defaults_puts_back_the_columns_for_the_folder_somebody_is_in`
drives all three kinds and asserts each gets its own. The dialog is no longer
told which folder it is in by its caller, because that parameter is gone: it had
one caller, that caller passed `FolderKind::Inbox`, and `98546f8` had already
corrected the identical literal at the folder-switch site and left this one.
Deleting the parameter is what stops it coming back, and a source read holds the
deletion.

**What I did not run.** Nothing here has been seen in the running program. No
folder was opened, no column heading was clicked, no `Alt+R` was pressed, and no
build was started. Everything above is tests over the decisions plus three
source reads of the wiring, and the source reads say what they are blind to in
their own words.

## What only a screen reader settles

**Whether the list rearranging itself is announced at all, and it is not.**
Moving from the inbox to Sent now changes which columns are shown and how the
list is sorted. The columns are the list control's own headers, which a screen
reader reads from the control when asked rather than when they change, and
nothing announces the change. So the list can quietly become a different list
under somebody who cannot see it. That is ledger 167, and it is the question the
plan named. Whether it needs saying, and what it should say without flooding
somebody arrowing down a folder tree, is a judgement a run makes and I cannot.

**Whether `Alt+R` says enough.** It announces "Columns reset to the default",
which was one outcome before and is now two: the inbox's columns or Sent's, and
those differ by a whole column and by which date the list sorts on. The sentence
does not say which arrived. Ledger 168.

## What happens to a layout somebody already has stored

**They lose it once, and they will notice.**

No string written by any build before 0.85.0 says which folder its layout was
arranged in, so for anybody upgrading the program cannot tell whether those
columns were arranged in the inbox or in Sent. It does not guess. `from_stored`
brings the columns and both sort levels back with the kind as `None`, `None`
never equals the folder on screen, and the first folder opened therefore rebuilds
from that folder's own defaults.

So: somebody who has arranged columns by hand opens this build, and their
arrangement is replaced by the starting columns for whichever folder they open
first. Once. From then on it is kept per kind of folder and per restart. That is
in `docs/changelog.md` under its own heading, in the words a user would use, and
the reason is in `from_stored`'s doc for the next person to read the code.

The alternative was to call an unknown layout an inbox layout, which is what
every call site did and is the whole defect. It would have cost nothing visible
on the first start and left the inbox sorted by a date the sender chose for one
more restart, and for anybody who never sorts again, forever.

**One thing this costs in the other direction, and it is smaller.** A build older
than 0.85.0 reading a string this one wrote keeps its columns and falls back to
that folder's default sort. The kind is appended after an `@` at the end, which
puts it inside the field an older parser reads the sort from. The second sort
level got two-way compatibility for free because a semicolon inside the sort
field is where an older parser already stopped; this field cannot. Ledger 169.
Putting the kind into the comma-separated column list instead would have cost
nothing either way, because unknown column names are already skipped, and it was
rejected as smuggling a non-column through a list of columns.

**The rewrite that mattered, and why the old body could not fail.**
`test_both_levels_survive_being_stored` did this:

```rust
let mut layout = ColumnLayout::defaults_for(FolderKind::Inbox);
layout.sort.then = Some(By { column: MessageColumn::Unread, direction: SortDirection::Ascending });
let back = ColumnLayout::from_stored(&layout.to_stored(), FolderKind::Inbox);
assert_eq!(back.sort, layout.sort);
```

`Inbox` goes in at the top and `Inbox` goes in again at the read, so `back.kind`
is `Inbox` whatever `to_stored` wrote, and it wrote nothing. The name promised
that both levels survive being stored and the body measured that, correctly; what
it could not see is that the third thing in the layout never crossed the string
at all. It is now driven with a Sent layout, read back with the wrong kind
supplied on purpose because that is what every call site really did, and it
asserts the kind as well as both levels.

`test_reset_returns_to_the_folder_default` was rewritten rather than added to for
the same shape of reason and is honest about being green on both sides: it reset
an `Inbox` layout to the `Inbox` defaults, which is true of one kind and blind to
the other two, and that blindness is exactly where the shipped defect lived.

**The compatibility test is green on both sides and was taken red by hand.**
`test_a_layout_stored_before_there_was_a_kind_still_reads` uses the string
`unread,attachment,subject,correspondent,received,snippet|subject:asc;unread:desc`,
which is today's format exactly. It cannot go red against the old code because
the old code had nothing to get wrong here. It is about the format change, so I
broke the format on purpose, making `from_stored` return `None` for a string
with no `@`, and it went red along with three of its neighbours. That is
recorded rather than assumed.

**One red assertion had to be respelled in the green commit.** The rewritten test

## Where the memory lives, and which answer wins

Three levels, and the user guide now says all three.

1. **The Thread column, per folder, across restarts.** Unchanged, through
   `cache.set_folder_thread_column`. It is the only genuinely per-folder answer
   and this plan did not touch it.
2. **The rest of the arrangement, per kind of folder, for the life of the
   window.** `LayoutPerKind`, held in a `RefCell` beside the layout in effect.
   It does not survive a restart.
3. **One arrangement, in the stored string, across restarts.** Whichever kind was
   changed most recently, because `persist_column_layout` writes whatever is in
   effect into the one `AppConfig.message_columns`.

**They cannot contradict each other.** The stored string is read once, at
startup, before anything has been kept in the per-kind memory, and after that the
memory is the answer and the string is written from it. So the question of which
wins does not arise, and that is written into `LayoutPerKind`'s doc rather than
left for somebody to work out.

**What this plan does not do.** It does not store a layout per folder. The sweep
names that as the larger option and it is not taken, so two levels of memory now
exist for one control: the Thread column per folder, the rest per kind. The user
guide says so rather than the code hiding it.

## Deviations from the plan

**The dialog's kind parameter was deleted, not corrected.** The plan called this
a one-line fix passing `column_layout.borrow().kind`. Deleting the parameter is
better, because the layout already carries the kind and a parameter that can
disagree with it is what let one literal decide every folder's Restore Defaults.
It also made the plan's guard record impossible, which is written up above.

**The source-reading checks went into a new integration target**, not
`tests/wired.rs`. Sixteen `guards.toml` records name `wired.rs`, so a test added
there would owe sixteen re-measurements. The new file owes one.

**`ColumnLayout.kind` became an `Option`.** The plan asked for the answer to an
unknown kind to be decided and written into the code, and left the shape open.
This is that answer in the type, which means the comparison the folder change
already made does the rebuilding without a new branch, and every reader is made
to face the case by the compiler.

**No version bump in the third commit.** The plan says to bump if the version has
not moved in that commit. `CLAUDE.md` says a documents pass does not earn a bump,
and it takes precedence. The version moved twice for the two behaviour changes,
0.84.0 to 0.85.0 to 0.86.0.

**A doc comment in the wrong place was corrected.** `Return to the default layout
for a kind of folder.` sat at the top of `set_sort_from_option`'s doc, describing
`reset`, which had none. Moved.

**`docs/KEYBOARD_SHORTCUTS.md` is untouched.** No binding changed. Its line about
`Alt+R` putting back the default columns for this kind of folder was already
there and is now true.

**`docs/USER_GUIDE.md:220` was not treated as a correction**, as the plan asked.
The Thread column sentence is true and is unchanged. The new section is an
addition under Reading and Managing Email, beside the other paragraph about
columns, which is where somebody looks.
