# Phase 4.2 Plan 07: Shift+F6 keeps its direction out of the preview Summary

`Shift+F6` now goes back from inside the message preview and `F6` goes on round,
where both used to do the same thing.

## Does it work

**Proved through the path the key takes, not by reading source, up to one point
I could not reach.** The chain is: the page's keydown handler builds a payload,
`panes::leaving_which_way` turns that payload into a `Direction`,
`panes::leaving_the_preview` turns the `Direction` into a `Pane`, and the
preview's handler focuses that control and announces arrival. The middle two
links are run, with the exact payload strings the script posts, copied out of it
rather than retyped:

```
{"kind":"leave","back":true}   -> Direction::Back    -> Pane::List
{"kind":"leave","back":false}  -> Direction::Forward -> Pane::Sidebar
{"kind":"leave"}               -> Direction::Back    -> Pane::List
```

The two ends are read from source rather than run, because they need a running
window and a browser: that the script really posts `back` for `F6` and only for
`F6`, and that the handler really calls both functions and branches on the
answer. That is `test_shift_f6_keeps_its_direction_on_the_way_out_of_the_preview`
in `tests/wired.rs`, and it was red before the script changed.

**What is not proved, and it is the one thing that could still make this not
work in the running program.** Nothing here has run the preview. Whether the
browser delivers `Shift+F6` to the injected handler with `shiftKey` true is
unverified, and this repository already records a case of a key being kept
between the window and the page: `editor_document.rs` says in its own comment
that `Ctrl+backslash` never arrives at the composer's page handler on this
machine while `Ctrl+Shift+L` and `Ctrl+Enter` beside it arrive every time.
Plain `F6` leaving the preview is known to work, so the channel is open; the
shift flag arriving with it is the untested step. Recorded as ledger 164.

## What only a screen reader can settle

**Whether landing on the folder tree is heard as going back, or only as going
somewhere.** Arrival is announced by `panes::arrival`, which names the pane and
what is in it and says nothing about direction. So `F6` to the folder tree and
`Shift+F6` to the message list are announced exactly the way arriving by any
other route is announced. Somebody who cannot see the layout may not be able to
tell that the key went the way they asked, which would leave this fix working
and invisible. Deciding that it should say a direction is a change to every
route rather than to this one, so it is recorded rather than guessed at: ledger
165. Announcements go through `UiaRaiseNotificationEvent`, which reaches speech
and braille together, so a braille display wants checking in the same pass.

The step in ledger 164 needs the same run: press `Shift+F6` with focus in the
preview and hear whether the folder tree or the message list is announced.

## What it does not do, said plainly

**It does not make `Shift+F6` different from `F6` in the main window.** `Pane`
has two values, `Sidebar` and `List`, so `next` and `previous` return the same
answer there by construction, and `previous`'s own doc has said so since it was
written. The preview is the one place a third stop exists in practice, and it is
the only place the two keys can differ. Somebody reading that CRIT-4.2-11 is
closed without this sentence would think the whole key was fixed.

**The preview does not become a stop on the `F6` cycle.** Pratik decided that on
2026-09-06 against the draft's recommendation of considering it separately. His
reasoning: with snippets and the other ways this program offers of reading mail,
somebody working by ear reaches a message's text without going there, so a stop
costing a keypress on every trip round the cycle buys them nothing. The cost,
known when the decision was taken and recorded here so the next sweep finds an
answer rather than the question again: anybody who does want a caret in the
preview still arrives by accident or by clicking.

## How the direction is carried

The injected script now builds the payload in two steps:

```js
var data = { kind: 'leave' };
if (e.key === 'F6') { data.back = e.shiftKey; }
```

Which key it was, rather than a bare shift flag. The comment beside it says why,
and this is the sentence the plan asked for:

> Read off the shift key only for F6. Escape is not a direction and Shift+Escape
> must not invent one, so its payload carries no `back` at all and the host
> answers with its default.

So `Escape` posts `{"kind":"leave"}`, and so does the Back button rendered at
the top of every document, which has no shift key to read. Both answer
`Direction::Back`, which is `Pane::List`, which is where every key that left the
preview landed before any of this carried a direction.

`is_leaving` is gone. Its doc said it was

> Read before anything else wherever this arrives, so a malformed context menu
> payload can never swallow the one keystroke that frees somebody who is stuck.

`leaving_which_way` keeps that: every payload whose `kind` is `leave` answers a
direction, and only a payload that is not a leave message at all answers `None`.
`test_a_leave_message_with_no_direction_still_leaves` drives the bare payload and
asserts it, and `test_nothing_else_a_page_posts_is_read_as_leaving` drives a
context menu payload, a string that is not JSON, and an empty string. Both were
green before this change as well as after, and are named here for that reason:
they pin the property rather than catch the defect.

The conversation window shares the injected script and drops the direction.
Its handler now says so:

> The direction the page sends is dropped here on purpose, and that is not an
> oversight to tidy up. `wire_the_way_out` injects one script into two surfaces,
> and closing is closing whichever key was pressed. Only the preview has two
> places to land, so only the preview reads which way.

## The test that was rewritten, and what it could never have seen

`test_f6_and_shift_f6_reach_the_pane_handler` asserted that `\tF6`,
`\tShift+F6` and `id == ID_CYCLE_PANES` appeared in `wx_app.rs`. All three were
there the whole time the key was broken. Its own comment said "What this cannot
see: whether focus moves." Its name promised both keys reached the pane handler,
and one of them silently became the other at the WebView.

Rewritten in place as
`test_shift_f6_keeps_its_direction_on_the_way_out_of_the_preview`, not joined by
a second test, because leaving a green test named for a thing that does not
happen is worse than having no test. It keeps the three accelerator assertions
and adds four: that the script posts `back` inside an `e.key === 'F6'` guard,
that the unguarded form is absent so `Escape` cannot pick up a direction, and
that the handler calls both new functions. The first of those is what went red.

## The guard record

One record, and its break is the defect rather than a convenient one.

Two things can break here. Deleting `back` from the script is caught by the
source read in `wired.rs`. Keeping the field and ignoring it at the reader is
caught by nothing that reads source, because the source still says everything it
should: the page posts the direction, the host asks for it, and the answer is a
constant. That is what `is_leaving` did for as long as the preview has existed.

So the break keeps the field and fixes the answer:

```
before:     match value.get("back").and_then(serde_json::Value::as_bool) {
                Some(false) => Some(Direction::Forward),
                Some(true) | None => Some(Direction::Back),
            }

after:      Some(Direction::Back)
```

Measured by hand at `ec2a5f0` with `cargo test --all-targets --no-fail-fast`:
6563 passed, 1 failed, 1 ignored, and every other target green. The red list in
full is one test:

```
presentation::panes::tests::test_which_key_left_the_preview_survives_the_crossing
```

`tests_last_seen`: `{ file = "src/presentation/panes.rs", tests = 13 }`, which is
the only file the red list names and also the file the break is applied to.

The record was then run through the tool on the committed tree, and
`scripts/guards.sh "posted and dropped"` answered "the one test named went red,
and nothing else did". So this record is machine-applicable, which is not
something a by-hand measurement establishes.

**One test is the whole red list and the record says so rather than padding it.**
The other three tests of this reader pass against the break by construction, and
which and why is written into the record: two pin that a leave message with no
direction still leaves, which the break preserves, and one pins that nothing else
is read as leaving, which it also preserves. Only the payload carrying
`back: false` tells the two implementations apart.

Every one sat beside, or one file away from, code written because the claim is

the opposite six lines above `set_can_focus`.

Each now keeps what was right, which is that the cycle does not stop at the
preview, and drops what was false. The shortcuts page gains a section headed
"Getting out of the preview", with a table naming `Esc`, `F6` and `Shift+F6` and
where each lands, because somebody who arrives there needs to find out what
happened and the page previously told them it could not have.
