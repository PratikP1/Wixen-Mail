# Phase 4.2 Plan 03: A Meeting Reply Arrives As A Reply Summary

**It works, as far as anything in this repository can show.** The part that
leaves this program now really carries
`text/calendar; charset=utf-8; method=REPLY` and is really called `reply.ics`,
and that is proved through the path that ships rather than by calling a
function. The test builds the answer with `the_answer_to_send` the way pressing
Accept builds it, writes it down with the function the window now calls, and
reads it back with `read_all`, which is the function `mail_controller::outgoing`
calls when the send loop drains the outbox. What that test asserts is what
`SendEmailRequest` hands to SMTP.

**What only a real organiser's calendar can settle, and nothing here settles

ledger 153. Both are recorded in `.planning/WINDOWS.md` in the table and in the
JSON block.

**Before this, every answer went out as a plain calendar file.** The content
type that says otherwise was written on 2026-05-31 in `592ba56`, was correct,
was tested, and had one production line: its own definition. The organiser got
an attachment to open by hand and their meeting went on showing you as not

This is the sentence the plan required and it is the honest report.

**`test_every_guard_record_says_how_many_tests_the_files_it_names_held` is

exactly where it was, so nothing about the counts can notice that a test now

## The fix, and why the sweep's version could not have worked

The sweep said one extra field on `ComposeData` and one branch in
`mail_controller.rs`. Re-verified at `5edc3e6` before anything was written: a
reply does not go from the composer to SMTP. `send_the_answer` builds a
`ComposeData`, `queue_for_sending` turns it into a `QueuedOutboxMessage` whose
`attachments` column is `attaching::joined(&data.attachments)`, a newline-joined
list of **file paths**, and `SendEmailRequest::from_queued` reads it back with
`attaching::split`. Bytes cannot cross that column, and should not: the row
outlives a restart. A `Ready` built at the top is dropped one layer below where
the sweep was looking.

So the type is derived from what does survive, which is the file, at the moment
it is read:

```rust
pub fn content_type_of(name: &str, bytes: &[u8]) -> &'static str
```

For a name whose type is not a calendar document it answers `content_type(name)`
and never looks at the bytes. For one that is, it decodes as UTF-8, and where
that fails it answers `content_type(name)` unchanged, which carries no charset.
Where it succeeds it asks `invitations::what_it_asks`, the reading of `METHOD`
this program already has, and maps the four variants.

That is the same argument `the_calendar_part`'s doc made, one layer down: worked
out rather than stored, so it cannot come to disagree with the document beside
it. `read_all` is the last place the document and the type are in one hand.

## The security argument, and the type signature that is it

**`content_type_of` returns `&'static str` from a match over a closed set.**
That is the whole of the mitigation for T-4.2-01 and it is not a stylistic
choice.

```rust
match crate::application::invitations::what_it_asks(document) {
    WhatItAsks::SomebodysAnswer => AN_ANSWER,
    WhatItAsks::Invitation => AN_INVITATION,
    WhatItAsks::Cancellation => A_CANCELLATION,
    WhatItAsks::SomethingElse => from_the_name,
}
```

**What a `format!` there would have allowed.** The `METHOD` line comes out of a
file somebody else wrote. Interpolating it would put a stranger's text on a
Content-Type header of mail leaving somebody's own account, signed with their
name, which is a header of the sender's choosing on somebody else's message.
This codebase has already had that exact defect once in a different place: a
line break in a meeting name was smuggling a Bcc onto read receipts, which is
why `the_subject_line` runs a stranger's text through `without_line_breaks`.

`test_nothing_a_stranger_wrote_reaches_the_declaration_except_by_choosing_one_of_four`
drives six hostile `METHOD` values, among them `REQUEST\r\nBcc: watcher@example.com`
and `REPLY; boundary="--x"`, and asserts the answer is one of four written-out
strings, holds no carriage return or line feed, and holds none of the injected
text. That test is green on arrival and said so below; the type signature is what
makes it green and the test is the record that this was decided rather than
stumbled into.

**The existing untrusted-input tests were found before the path was changed**,
as required. `invitations::tests::test_a_reply_built_from_a_hostile_invitation_stays_a_calendar_document`
and `test_reading_a_hostile_invitation_never_panics` sweep 2,000 and 5,000
generated hostile documents, and
`answering::invitations_from_strangers::test_nothing_a_stranger_wrote_reaches_a_header_or_a_sentence_intact`
sweeps 2,000 more. They cover the reply **document**. None of them covered the
**declaration**, because until this plan nothing derived one. The new test is
the declaration's half of the same rule, and all three of the old ones still
pass untouched.

T-4.2-02, a malformed or enormous `.ics` handed to the method reader, is covered
by `test_a_file_named_as_a_calendar_and_holding_something_else_is_not_a_crash`,
which drives an empty file, plain prose, a truncated document, `METHOD` with no
value and `METHOD` with no colon. `what_it_asks` already runs over
attacker-controlled mail on the receiving side and answers `SomethingElse` for
anything it cannot read; bytes that are not UTF-8 never reach it.

T-4.2-SC: no dependency was added. `Cargo.toml` changed for the two version
bumps and nothing else, and the diff was read rather than assumed.

## The name, and the second thing that was lost

`WHAT_THE_PART_IS_CALLED` is `reply.ics`, and its doc says why: a client that
does not understand the content type shows a name, and `invite.ics` "would tell
somebody they had been sent an invitation when they had been sent an answer".
Production wrote `reply-<uuid>.ics` and `read_all` takes the name off the file,
so what a recipient saw was `reply-0f3a....ics`.

**Uniqueness moved up one level.** The reply now goes to
`answers/<uuid>/reply.ics`, so two answers waiting in the queue at once still
cannot land on one file and the name the recipient sees is the one this program
chose. `test_two_answers_waiting_at_once_do_not_land_on_one_file` drives two and
asserts both paths differ, both read back, and both are called `reply.ics`.

## The guard record

**`the type on an outgoing part is worked out from the document, not read off
the name`.**

The break is not deleting the call. That only asks whether the call exists,
which nobody doubts. It keeps the call and discards its answer, which is exactly
the shape a later change reaching for the simpler-looking line would take, and
which a check on the call site cannot see. The two lines, before and after:

```rust
// before
content_type: content_type_of(&name, &bytes),

// after
content_type: {
    let _ = content_type_of(&name, &bytes);
    content_type(&name)
},
```

Measured by hand with `--all-targets --no-fail-fast` from a green tree of 6,521
tests, then verified again through `scripts/guards.sh`, which agreed. **Full red
list, unfiltered, one test:**

```
application::attaching::tests::test_a_reply_arrives_declared_as_a_reply_so_the_organisers_client_records_it
```

`tests_last_seen`: `src/application/attaching.rs`, 42 tests.

**One test is the measurement, not an oversight, and the record says why.** The
four tests over the derivation call `content_type_of` directly, so a break at the
call site cannot touch them. Only a test running the whole way from a document to
a `Ready` can see the answer being thrown away. That is precisely the
discrimination this record is for, and a longer red list would have meant the
record was catching something else as well.

## The fixture, and which of the two options was taken

The plan asked for a decision and for the reason. **The invitation text is a
third copy, in `attaching.rs`'s test module**, and the reasons are in a doc
comment on the fixture rather than only here.

The two existing copies, in `answering.rs` and `invitations.rs`, are
byte-identical. Sharing one would have meant either reaching into another file's

is `super::tests::`, inside one file), or adding a shared test module and

What the copy is, and is not, matters: **only the invitation is a fixture.** The
reply document under test is not written by hand. It comes out of
`whether_it_can_be_answered` and `the_answer_to_send`, the two public steps the
window uses, so what is written down and read back is the program's own answer
rather than a calendar document written to suit the test.
