# Phase 4.2 Plan 02: Scheduled Send Summary

**It works.** You write a message, press Schedule or `Alt+H`, pick a date and a
time, and the message waits in the Outbox until then and goes on its own with
nobody pressing anything. The row says the time it is set for. Undo Send takes
it back while it waits.

**A time in the past is really refused, with words you can act on.** "That time
has gone. Pick a time still to come." The window stays open, nothing is queued,
nothing is sent, and the time you picked is not quietly moved to one that would
be accepted. Same for a time more than a year ahead and for text that is not a
date and time. Each refusal is spoken as well as shown.

Before this, `docs/changelog.md` had told people all of that since it was
written, and none of it existed. `schedule` had no caller anywhere in `src/`.

**What only a screen reader can settle, and nothing here settles it.** Whether
the six controls are heard as six named controls each saying its own value, and
whether a refusal is actually heard or is lost under the focus change. Ledger
149 and 150. **What only a real account and a real afternoon can settle:** no
message has ever waited hours and then gone; every test moves the clock. Ledger
151.

## What the plan got wrong, measured

### "Send Later" could not have a key, and the plan's premise 6 could not have seen it

Premise 6 said `Reached::ALL` is where the letters are decided and to pick a
free one by reading `label()`. I did: E was the only free letter in "Send
Later", every other one being Subject, Send, Save Draft, Cancel, Attach, To or
Redo.

E is taken. `looking_people_up::THE_LIST_LABEL` is `"P&eople found:"`, a
mnemonic in the compose window that is **not on `Reached` at all**, and
`test_the_key_that_reaches_the_list_is_not_one_this_window_already_uses` is what
said so, on the build after the RED commit.

The enum's own doc comment reads as though it were the only source: "The list is
the single place the letters are decided." That is true about the letters on the
list. The authority on how many sources the window has is the check that
enforces uniqueness across them, and reading the list confirms the belief where
reading the check tests it.

is what every other mail program calls this, and the reason for H is written
beside it. `Reached::SendLater` was renamed `Reached::Schedule` in the same
change so there is one name and not two.

## Deviations from the plan

### `[Rule 2: missing critical functionality]` The composer had no date settings to give the picker

**Found during:** task 1, wiring the dialog.

A dialog opened from another dialog is not handed the settings the main window
holds, and `date_settings_from` needs an `AppConfig`. Rather than let the picker
invent its own answer about day-and-month order and the twelve or twenty-four
hour clock, which is the exact defect `DateFields::day_first`'s doc records

added `wx_app::date_settings_from_stored_config`, the pair of
`theme::current_from_stored_config` and written beside `reading_from_settings`,
which already did this by hand.

**Commit:** `8a6c9ee`.

### Task 2's tests did not go red first, and the reason is structural

The plan had task 1 build the accept path and task 2 the refusals, and allowed
task 1 to "leave them as a single not-yet-handled path so long as it does not
send".

`what_the_picker_does` is **one exhaustive match over four answers**. Leaving
three arms unhandled for a commit would have meant shipping a window that
computes a refusal and does nothing with it, which is guardrail 3. So task 1's
GREEN wrote the whole match, and task 2's five tests describe code that already
worked.

**What took them red is the guard break**, applied by hand, which is the
measurement `CLAUDE.md`'s "Tests that would notice" section asks for and is
stronger evidence than an unchecked red. Reported rather than dressed up.

### `[Rule 1: correctness]` One changelog clause was false and is corrected

Premise 11 said every clause must be true or be corrected. Read clause by
clause:

| Clause | Verdict |
|---|---|
| "A message can also be set to go at a chosen time." | **True.** Schedule, `Alt+H`, a `Chosen` row, the send loop leaves it, the clock wakes it |
| "A time in the past is refused rather than sent immediately" | **False for the first minute.** `JUST_MISSED` grants a minute of grace on purpose |
| "one more than a year ahead is refused as a likely mistake" | **True.** `NO_FURTHER_AHEAD_THAN` is 365 days and the refusal says exactly that |

The middle clause now reads "unless it has only just gone by", and the paragraph
says it described nothing until this plan. The grace is not a defect to hide: a
window that refuses what it offered twenty seconds ago is one nobody trusts, and
that argument is in `JUST_MISSED`'s own doc.

## The dialog

**Premise 4's first route was taken.** `build_date_fields` and
`build_time_fields` are now `pub`, along with `hour_from`, `as_stored_date` and
`as_stored_time`. None of them touches `crate::application::item_fields`, which
is what made sharing clean, so no kind was added to that module. `wxDatePickerCtrl`
is **not used**: the only two hits in `src/` are the two module docs saying why
not.

**The day order is read the way `build_date_fields` reads it**, by passing
`dates.order` straight in, and the three controls are laid out from
`date.day_first` which those fields carry. One answer, in one place. The clock
setting goes in the same way, so a twelve-hour clock gets the morning-or-afternoon
choice `TimeFields` already builds.

`clamp_day_to_month` is called once at build time; `build_date_fields` already
binds it to the month and year controls, so binding it again would run it twice.

**Every control, and the exact string a person hears:**

| Control | Accessible name |
|---|---|
| Month choice | `Send on Month` |
| Day spinner | `Send on Day` |
| Year spinner | `Send on Year` |
| Hour spinner | `Send at Hour` |
| Minute spinner | `Send at Minute` |
| AM/PM choice, twelve-hour clock only | `Send at AM or PM` |
| Problem line | `Why that time will not do` |
| Set button | `Set the time this message goes` |
| Cancel button | `Cancel, and send this message the usual way` |
| Toolbar button, in the composer | `Schedule when this message goes, Alt+H` |

All set with `set_accessible_name`, never `set_name`, which writes an internal
wxWidgets identifier no screen reader reads.

**The window opens on nine tomorrow morning.** Opening on now would make an
immediate refusal the commonest thing it does, since reading six controls takes
longer than the minute of grace. Nine tomorrow is both still to come and the
likeliest thing somebody delaying a message means. Focus starts on the month
control, not on Set, so Enter pressed by reflex is not an answer nobody read.

**The refusal consumes the click.** `event.event.skip(false)`, because wxdragon
sets `Skip(true)` before calling a handler and a plain button event carries on
to `wxDialogBase::OnButton`, which sees `wxID_OK` and closes regardless.

**The existing `house_style` guard does cover this file, and that was measured
rather than assumed.** `test_a_handler_that_can_refuse_to_close_consumes_the_click`
walks every file under `src/`, so no widening was needed. Taking `skip(false)`
out made it fail naming `src\presentation\wx_send_later.rs` by path. Put back.

## The guard record

**`a time that has gone is refused rather than quietly moved to now`.** The
break is the clamp: `Scheduling::AlreadyPast => WhatThePickerDoes::SetFor(now)`,
a past time closing the window with the current moment instead of staying open.

Measured by hand over the whole library with `--no-fail-fast` from a green tree,
then verified again through `scripts/guards.sh`. **Full red list, unfiltered,
three tests:**

```
presentation::wx_send_later::tests::test_a_time_only_just_missed_is_accepted_rather_than_refused
presentation::wx_send_later::tests::test_a_time_that_has_gone_is_refused_with_the_reason_and_the_next_move
presentation::wx_send_later::tests::test_every_refusal_names_a_next_move_rather_than_only_saying_no
```

`tests_last_seen`: `src/presentation/wx_send_later.rs`, 8 tests.

The third is the one worth explaining and I did not predict it: the just-missed
case asserts **both** halves of the grace period, so the clamp reddens it by
accepting an hour-old time the test requires be refused.

**Why the clamp and not something more obvious.** It is the failure a later
change is most likely to reintroduce, because it looks like a kindness, and
because `Hold::of_seconds` next door clamps deliberately and says so in its doc.
A reader meeting both will reasonably want them consistent, and that is a
one-line change passing every other check in the tree. The contrast is written
as a comment beside the refusal, quoted here:

> Refused and explained, never moved to a time that would be accepted, and the
> contrast with the hold is worth writing down because the next person here will
> have just read `Hold::of_seconds`, which clamps, and will reasonably ask why
> one does and the other does not.
>
> The difference is where the value came from. A hold is read out of a settings
> file that has survived a restart and may hold anything an older build, a
> hand-edited file or a typo left there, and there is no sensible way for a
> stored number to stop this program sending mail, so it is brought inside what
> is offered. This is a time somebody picked seconds ago in a dialog that is
> still open and can still be corrected. Clamping it to now would send,
> immediately, a message they had just said they wanted delayed, and they would
> be told it had been set.
