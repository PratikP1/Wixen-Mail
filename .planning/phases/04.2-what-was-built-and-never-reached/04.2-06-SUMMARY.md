# Phase 4.2 Plan 06: Blocked Senders Summary

A Blocked Senders window on the Tools menu that lists who is blocked, where
their mail is being filed and whether each block is switched on, and takes one
block off without ever taking a wider one; plus the sentence saying what
blocking will do, now said before the rule is written.

## Does it work

Yes, structurally, and it has not been heard.

Somebody can open Tools, Blocked Senders, and the window lists every block on
the account being looked at. Each row says who is blocked, which folder their
mail goes to, and whether the block is working. Choosing a row and pressing
Unblock takes off exactly that block and says what that did. An account with
nothing blocked gets a sentence rather than an empty list. The whole window is
reachable by keyboard: Tab and the arrows reach the list, `Alt+U` unblocks,
`Alt+C` closes, and focus opens on the list unless there is nothing in it, in
which case it opens on Close.

All of that is asserted by tests and by the source-reading checks in
`tests/wired.rs`, and `scripts/check.sh all` passes on `main`.

**Nobody has heard it.** No screen reader has been run against it and neither
automated accessibility channel has been run over it. That is the deferred
check below, and it is the difference between structure being present and the
experience being good. This project has already shipped sixteen widgets named
through a call that never reaches the accessibility tree, compiling and passing
324 tests, so a new window going out on structure alone is the failure with a
precedent here.

## The finding that matters most: two tests that could not have gone red

The plan asked for one guard record whose break is unblocking by the wider rule.
Taking that break by hand, which is what this repository requires before a record
is written, found that **both nested-block tests passed against the defect they
were written for**. The break reddened nothing.

The cause is ordering. `get_filter_rules_for_account` orders by name, and a
block's name is `Blocked: ` then the address, or `Blocked: everyone at ` then
the domain. Both tests used `ada@example.com`, which sorts *before*
`everyone at example.com`, so the exact rule was the first one a widening
lookup met and it returned the right answer by accident.

The fixtures are now built the way the database really returns rules.
`zoe@example.com` sorts after `everyone at example.com`, which puts the domain
rule first, which is where widening bites. `ada@example.com` sorts first, which
is where the mirror bites. Each break now reddens exactly one test, and they are
different tests.

This is the same class of finding as `04.2-05`'s, and it was found the same way:
by taking the break rather than by reading the test.

## The sentence before a block, and what it is not

`what_blocking_will_do` is said through the same `told` as the `may_block`
warning, at the same `Priority::High`, immediately before `create_filter_rule`.
`allowed_for` and `what_the_junk_folder_needs` are **hoisted above** the write
rather than computed twice, so one computation serves both sentences. The junk
folder value stays mutable, so the after sentence still reports the downgrade to
`IsNotBeingDownloaded` when switching the folder on fails.

**No confirmation step was added.** Nothing about making a block became a
question, a prompt or conditional on an answer. The sentence is said and the
block is made in the same pass, which is what the `YesButFirst` arm already does
and what its own comment already says.

The pair, as somebody would hear them where `may_block` also warns:

> This message came from a mailing list. Blocking files it into Junk and the
> list carries on sending it. To stop it at the source, unsubscribe by writing
> to leave@list.example.

> Mail from ada@list.example will go to Junk from now on. This does not tell
> your mail provider anything, so the mail is still accepted and still arrives
> here. Messages that already arrived stay where they are.

They say different things, which is the argument for both. Whether they are one
clear answer or two competing ones is a question only a real run answers, and it
is ledger 162.

### First, the two automated channels, reported separately

They answer different questions and this project has been caught trusting one of
them.

1. **UI Automation**, which is what Narrator reads and what Axe.Windows scans.
   Run the accessibility scan against the new target: `--scan-target=blocked-senders`.
   *Confirm the scan actually opened this window*, rather than reporting nothing
   about a window it could not reach. A scan that opens nothing reports a clean
   pass, which is the failure this project has already shipped once.
2. **MSAA**, through `IAccessible`, which is what NVDA reads for native controls
   and the only channel `set_accessible_name` writes to. Run
   `scripts/msaa-names.ps1` over the same window.

A name that fails on either is a name somebody does not hear. Give the two
results separately, never as one pass.

**The trap in the other direction.** A control with a visible label beside it
inherits that label as its MSAA name even when nothing set one, because Windows
falls back to the nearest static text. So for each control, say whether the name
that came back is the one this code set or one Windows supplied. A clean run is
not proof the setting worked.

### Then five things to listen to, with NVDA and then Narrator

Quote what was actually spoken, not what was expected.

1. **Arrowing down the list.** Is each row read as a person, a destination and a
   state, or as one run-together string? If characters are missing or a cell ends
   oddly, that is likely `wxdragon 0.9.17`'s `get_item_text` losing the last
   character of every cell and returning a NUL: **ledger 28, upstream and
   unfixed**. Say so if it shows. It is somebody else's defect and it still lands
   on the person using this.
2. **A switched-off block.** Is it distinguishable by ear from a working one?
   Make a block, switch its rule off in Message Filters, come back. This is the
   one thing here that looking at the screen makes obvious and listening might
   not, and `still_on`'s own doc says a list showing a switched-off block as
   working would be worse than no list.
3. **Unblocking.** Is what happened said, is it said once, and is it heard over
   the list being re-read underneath it? The list is refilled and the cursor
   re-landed before the sentence is announced. If the sentence is lost, the fix
   is to announce before the refill, which is a change to the code rather than to
   the words.
4. **An account with nothing blocked.** Is the window heard as empty on purpose,
   or as a window that failed to load? Those sound the same and they are not.
   Focus should land on Close, and the line above the list should say nobody is
   blocked and how to block somebody.
5. **Making a block**, from Action, Block on a message. This one is not on this
   screen and is here because it is the same feature and the same session. Is the
   sentence saying what blocking *will* do heard **before** the block is made,
   and the one saying what it *did* heard after? Where `may_block` also warns,
   both are said first: hear them one after the other and say whether that is one
   clear thing or two competing ones. Announcements go out through
   `UiaRaiseNotificationEvent`, which reaches speech and braille at once, so check
   a braille display too, and say plainly if none was to hand.

### What each outcome means

- **Rows read cell by cell with their headings:** the list works. Record it and
  close ledger 159.
- **Rows read as one run-together string, or characters missing:** likely ledger
  28. Record it against `wxdragon`, do not absorb it silently, and the window
  needs a different way of presenting a row before this feature is finished.
- **A switched-off block sounds like a working one:** the third column is not
  doing its job by ear. The words, the column order, or both need changing; the
  data is right.
- **The unblocking sentence is not heard, or is heard twice:** move the
  announcement relative to the refill. This is a small change and a real one.
- **The empty window sounds broken:** the sentence and the focus placement are
  not enough, and the window needs something focusable that says it.
- **The two sentences before a block read as noise:** guardrail 5. That is an
  argument for shortening or merging them, and it is the one thing this plan's
  wiring could have made worse rather than better.
