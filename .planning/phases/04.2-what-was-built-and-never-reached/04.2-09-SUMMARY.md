# Phase 4.2 Plan 09: The documents name the keys that work Summary

**It works.** The shortcuts page gives `F8` for the composer's toolbar, which is
the key that arrives; `Ctrl+\` is still bound and is marked as a key that has not
been seen to work rather than as the way in. `Delete` taking a file off a message
and `F6` closing the conversation window are written down. Nobody with smooth
scrolling switched off is told Windows overruled them. Five sentences in three
documents describe what ships.

`scripts/check.sh all` passed on the branch and again on `main` through the merge
hook. Merged at `3fc3ab2`, pushed, version `0.87.0`.

## What the widened check reported, written down before anything was fixed

Two keys, and that is the whole list:

```
docs/KEYBOARD_SHORTCUTS.md names these keys and nothing in src/presentation
binds them: ["F7", "Shift+F10"]
```

Both are documented, both are really bound, and neither is bound by a menu
accelerator, which is the only thing that reader can see. `F7` opens the spelling
dialog from the composer's page (`editor_document.rs`, the `event.key === 'F7'`
arm with no modifier) and jumps to the reader window's security warning
(`wx_reader.rs`, the `WXK_F7` arm). `Shift+F10` raises the context menu for a
keyboard with no Applications key (`wx_app.rs`, `key == F10 && event.shift_down()`).

Both are now on `bound_by_a_handler_rather_than_a_menu` with a comment saying
where each is bound, which is what that list's own doc requires of an entry.
Neither is a defect and neither needed a document change.

**Nothing was narrowed to make anything pass, and that is now enforced rather
than promised.** The allow list has to be live: every entry must be a key the
reader really reported. Narrow `documented_combinations` back to modified keys
only and `F7` and `Shift+F10` stop being reported while their entries stay
behind, and the check says so by name. That is the guard record, and it was
measured. Without it the narrowing is silent, because the whole check still
passes with the filter back.

## The finding worth more than the fix

**Widening the reader could not have caught any of the three keys this plan is
about, and I did not know that until I measured it.**

`F8`, `Delete` and `F6` are each already in `docs/KEYBOARD_SHORTCUTS.md`. `F8`
nine times, `Delete` eleven, `F6` twelve. Every one of those is about a different
part of the program: `F8` reaches the attachments in the reader window and opens
the Columns dialog on the View menu; `Delete` throws a message away in the message
list; `F6` moves between panes. So both directions of the pair in `tests/wired.rs`
were green the whole time the composer's toolbar key, the composer's `Delete` and
the key that closes the conversation window were written nowhere.

The class that hid them is not "a key the document never names". It is **"a key
the document names for another surface"**, and no whole-document reader can see
it, however wide its filter.

That is why `tests/a_key_is_documented_where_the_surface_that_binds_it_is.rs`
exists and why it asks a narrower question: for each surface that binds a key of
its own, the part of the document describing that surface has to name it. All
three of its cases were red on the tree as it stood.

## Two code corrections

**The overruled note.** `add_scrolling` decided from `system_motion()` alone and
passed `what_the_machine_has_overruled(true, SystemMotion::Reduced)`, two literals
inside a guard that had already decided. It now passes `config.smooth_scrolling`
and `system_motion()` and puts the note up only when there is a sentence:

```rust
if let Some(said) = what_the_machine_has_overruled(config.smooth_scrolling, system_motion()) {
```

The return type became `Option<String>` because an empty string builds a label
perfectly happily, so a caller that forgets to check gets a blank line under the
box, announced as a nameless piece of text.

**Whether a wxWidgets list would animate at all, and how that was established.**
It cannot be asked to. Everything this program can call about scrolling a
`wxListCtrl` through wxdragon 0.9.17 is `ensure_visible`, `show_position`,
`scroll_into_view` and `is_position_visible`; none of them takes a motion, a
duration, or anything else animation-shaped, and there is no scroll entry point on
`Window` either. That is read from the binding this program has rather than from a
running window, and it is enough to decide: **narrowed, not wired**, because
wiring would mean adding a call that does not exist.

What this does not claim: that a native list control could never animate under
some other API. It could and this program cannot reach it, which does not change
the answer.

So the claim was narrowed in all three places it was made, in the same commit,
because a module comment narrowed while the label still overclaims fixes the half
nobody reads:

| Where | Before | After |
|---|---|---|
| The checkbox | "&Slide when a view scrolls, rather than jumping" | "&Slide when the message you are reading scrolls, rather than jumping" |
| Its accessible description | "Windows overrules this when it is set to reduce animation" | "The message body only. Windows overrules this when it is set to reduce animation" |
| `scrolling.rs`'s module doc | "Two places need the answer ... One decision, made here, read by both" | Two questions, each with one reader, and `Motion` reaches the message body only |
| `docs/changelog.md` | "**Scrolling can slide rather than jump**" | "**The message you are reading can slide rather than jump**", with what the list does |
