<objective>
Make accepting a meeting put it on the calendar. Every value needed to do it has
been computed since `592ba56` and consumed inside one module.

Purpose: somebody accepts a meeting, hears "Accepted Quarterly review. Ada
Lovelace will be told", opens the calendar on the day, and it is not there. No
document says that is how it works, in either direction, which is what makes it
worse than a documented limit: there is nothing to read that would have warned
them.

Output: a meeting on the calendar with the time taken according to the answer;
one entry rather than two when somebody answers twice; and three rewritten tests
whose names have been promising the calendar while measuring a struct.
</objective>

<premise_corrections>

**1. The sweep says the open question is which calendar an accepted meeting
lands in, and that question is already answered in the tree.**
`MessageCache::ensure_default_calendar(account_id)` at
`src/data/message_cache/calendars.rs:205` returns the account's default calendar
and makes one called "My Calendar" if there is none. Every other path that has to
put an event somewhere without being told uses it. So there is no decision here,
only a call. Verify that rather than trusting this paragraph.

**2. `answering.rs` may not do the writing, and its own module doc is why.**
"Values in, values out. Nothing here sends mail, writes to the calendar, reads a
clock or touches a file." That sentence names writing to the calendar
specifically. `what_the_calendar_should_hold` stays exactly where it is and
stays pure; a new module does the filing, in the shape of
`application::sent_copy`, which is this codebase's worked example of "keeping a
copy of something that has gone out".

**3. The upsert is on `id`, not on the uid, and that is where a second answer
becomes a second row.** `save_calendar_event` at
`src/data/message_cache/calendar.rs:157` is `ON CONFLICT(id) DO UPDATE`. The
invitation's `UID` lives in `provider_event_id`, not in `id`. So a second answer
that generates a fresh identifier writes a second row for the same meeting, and
the test that would notice is the one about answering twice. Look the meeting up
with `get_event_by_provider_id` first and reuse the identifier it comes back
with. This is the mechanism behind CRIT-4.2-08 and it is not visible from
`answering.rs` at all.

**4. `pending` decides whether the answer ever leaves this computer.**
`CalendarEventEntry.pending`'s doc says every path that changes an event here
sets it and the push clears it, and that it is a field rather than something
worked out precisely so the compiler names each of those paths. An accepted
meeting written with `pending` false is a meeting the account's provider never
hears about, which is a quieter version of the defect this plan is closing. Set
it, and say in the summary that it was set and why.

**5. `WhatChanged::NothingNew` must not write.** `what_changed`'s own doc says
mail arrives out of order and an invitation older than the one already accepted
is an ordinary event rather than a broken one, and that acting on it "would put
a meeting back to where it was before it moved with nothing said". So the filing
step reads `the_meeting_itself` and does nothing on `NothingNew`. A test drives
it, because a write that is correct on two of three arms is the arm nobody
notices.

**6. Answering a meeting sends with no confirmation step, and that is decided.**
Pratik answered this on 2026-09-06, against the draft's recommendation and
knowingly. `answer_the_invitation` goes on doing what it does today: it sends,
then says what happened. This plan does not add a step in front of it, does not
add a softened version of one, and does not reopen the question.

`what_pressing_it_will_do` therefore stays unwired, and this plan leaves it
alone rather than deleting it. Deleting it is a separate decision about the
product and this is not the plan to take it in. **Record it in the summary as
looked at and left, with this decision as the reason**, so the next sweep finds
a written answer instead of finding it again.

What that decision costs is recorded once, here, and it is the reason plan 01
exists and runs first: once this phase lands, answering a meeting sends mail to
a real person from one keypress, and the only brake on it is Undo Send. Do not
start this plan before `04.2-01` has landed and the hold is really written.

**7. Where the tests go was measured.** 624 records in `guards.toml` at
`5f57d3a`, counted by parsing `tests_last_seen` blocks. `application/answering.rs`
is named by 0 records, a new `application/answered_meetings.rs` by 0 by
construction, `data/message_cache/calendar.rs` by 2, `presentation/wx_app.rs` by
40. Nothing goes in `wx_app.rs`.

**8. None of the three tests being rewritten is named by any guard record.**
Measured 2026-09-06: `grep -c` on each of
`test_accepting_puts_the_meeting_on_the_calendar`,
`test_each_answer_decides_whether_the_time_is_taken` and
`test_a_change_to_a_meeting_already_accepted` against `guards.toml` answers 0. So
`test_every_test_a_guard_record_names_is_a_test_that_exists` will not fire on the
renames. And rewriting rather than adding leaves `answering.rs`'s test count
where it was, so the count fingerprint is silent by construction. Neither
silence is evidence. What neither check can see is a rewritten test that starts
reddening under some existing record's break, which makes that record name too
few; only the whole sweep sees that, and phase 8 criterion 5 owns it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| an invitation a stranger sent -> a row in `calendar_events` | every field of the event comes from a document somebody else wrote |
| an invitation's `UID` -> a lookup key against this account's calendar | a `UID` somebody chooses decides which existing row is replaced |
| an invitation's summary and location -> a sentence read aloud | attacker-controlled text spoken in a room |
| the answer -> the provider, through `pending` | what is written here leaves the machine later, by a path this plan does not run |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-4.2-05 | Tampering | an invitation choosing a `UID` that already names an event on the calendar, so answering it overwrites a meeting the sender never called | high | mitigate | the lookup is scoped to `account_id` and `provider_event_id` together, and the write happens only on a `WhatChanged` that is not `NothingNew`, so an older or equal version cannot replace anything. `whether_it_can_be_answered` has already refused an invitation this account is not a guest on, which is the door this would have to come through. A test drives an invitation whose uid collides with an unrelated event and asserts the unrelated event is unchanged. |
| T-4.2-06 | Spoofing | a guest's answer written into the meeting's own status, so the calendar says the meeting is in doubt when one guest is | medium | mitigate | `status` is not touched. `OnTheCalendar`'s doc says why in as many words and an acceptance criterion holds it. |
| T-4.2-07 | Information disclosure | a meeting summary from a stranger read aloud in a room | low | accept | the same shape as every other message subject this program reads, and the mute the project's fifth guardrail names already exists. |
| T-4.2-08 | Denial of service | an invitation with an enormous summary, a malformed start, or thousands of guests, written to the calendar | medium | mitigate | every field comes through `invitations::read_the_invitation`, which already runs over arriving mail and returns `Result`. Nothing here unwraps. A test drives an invitation with no end time and one with an unreadable start and asserts the answer is refused rather than a row written with nonsense in it. |
| T-4.2-09 | Repudiation | an answer that never left the machine written to the calendar as though it had | high | mitigate | the filing runs on the `HowItWent::Sent` path only, with a test. `what_answering_did` has just told the person nobody was told, and a calendar entry contradicting that sentence is worse than either alone. |
| T-4.2-SC | Tampering | npm/pip/cargo installs | high | mitigate | this plan adds no dependency. `Cargo.toml` changes only for the version bumps and the diff is read rather than assumed. |
