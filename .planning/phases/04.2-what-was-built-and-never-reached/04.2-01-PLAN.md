<objective>
Make the hold real, so that Undo Send takes something back.

Purpose: `Ctrl+Shift+Z` is on the Tools menu, `what_undo_send_takes_back` is
called from the handler, the send loop asks `readiness` on every pass, and every
part of it works. Nothing is ever held, so `take_back` answers `TooLate` for
every row in the queue and the command refuses every time it is pressed. The
module's own doc says "All of it runs", in a module whose doc comment is itself
a written apology for having over-claimed this exact feature once before.

This is first in the phase and not third because of what the phase does after
it. By the decision of 2026-09-06, answering a meeting sends mail to a real
person with no confirmation step. Undo Send is then the only brake on anything
this program sends, and the meeting reply work must not land in front of it.

Output: a message that waits before it goes, goes on its own when the wait is
over, says so while it waits, can be taken back while it waits, and a setting
that says how long the wait is.
</objective>

`outbox.rs:38` defines a wrapper whose whole body pins the argument:

    pub fn queue_outbox_message(&self, item: &QueuedOutboxMessage) -> Result<()> {
        self.queue_outbox_message_to_go(item, &GoAfter::AsSoonAsPossible)

`queue_outbox_message_to_go` therefore has a caller and raises no warning. Its
parameter has a value and raises no warning. The other two variants of `GoAfter`

The second half is at the call site. `queue_for_sending` does this:

    let waiting_on = crate::application::sending_later::GoAfter::AsSoonAsPossible;

        .queue_outbox_message(&queued)

`waiting_on` is never an argument to the queue call. It is returned, and the
caller branches on it through `when_it_goes`, so everything downstream reads as
though a decision about waiting reached storage. The comment above it says it "is
the only thing the composer's Send has ever written", which is exactly wrong: it
is the only thing the composer's Send has never written.

**3. Wiring the hold without wiring a flush would be a worse defect than the one

a row today and the message waits ten seconds and then waits forever, because
nothing asks again.

That is not a hypothetical: it is the shape this whole phase is about. Task 1
therefore is not "write the hold"; it is the round trip, ending with the message
actually leaving. There is a home for it. The poll timer at
`wx_app.rs`, found by grepping `HOW_OFTEN_TO_ASK_ABOUT_THE_NETWORK`, already runs
about twenty times a second and already carries two things on their own intervals,
the reminders and the network check, each with a comment saying why they are on
this timer rather than a second one: a timer event reaches every handler bound on
its owner, so a second timer would run this one as well. Follow that.
