<objective>
Give the Blocked Senders screen a door.

Purpose: `blocking.rs`'s own doc names the failure this closes. "A block
somebody cannot find is a trap. Mail stops arriving, nothing says why, and the
rule doing it is one row among however many rules they have." Three functions
were written for that screen, tested, and never called from anything that ships.
A fourth, the sentence said before a block is made, was written the same way and
is wired here too by the decision of 2026-09-06, so all four of the family become
reachable rather than three.

This is a plan rather than a task on another one because it is a screen with its
own accessibility surface: a list that has to declare a name, a role and a state
on both of the Windows channels this program has to satisfy, keyboard operation
throughout, and a menu item somebody can find. That is not the shape of the
other work in this phase, which is mostly one line and a rewritten test.

It is also the one item in this phase that is not a false promise. The
documented route works: a block is an ordinary filter rule and the rules manager
deletes rules. So this is a screen that was designed and never offered, rather
than a claim that was never true, and the changelog is corrected to say which.

Output: a Blocked Senders screen on the Tools menu, in the group with the other
managers, that lists who is blocked and lets somebody take a block off.
</objective>

**1. Re-verify all four functions before building anything, because the whole
plan rests on them being unwired.** On 2026-09-06:

    grep -rn "everyone_blocked\|the_rule_that_blocks\|what_unblocking_did\|what_blocking_will_do" src/ tests/

returned nothing outside `src/application/blocking.rs`, and inside it every
reference is at line 752 or later, which is where `#[cfg(test)]` begins.
`what_blocking_will_do` is defined at `blocking.rs:570` and every other mention of
it is at 1584 or later. Run it again. If any of them has gained a caller since,
stop and say so rather than building a second way in.

**2. `what_blocking_will_do` is the fourth function in that family and this plan
wires it, by the decision of 2026-09-06.** It is the twin of `what_blocking_did`,
which is wired, and it is the sentence said before a block is made rather than
after. It is unwired for the same reason the others are.

**Why that is not inconsistent with taking the confirmation step off answering a
meeting.** The same decision-maker answered "no confirmation step" for a meeting
reply on the same day, and the two answers look opposed until the difference is
named, so it is named here rather than argued again later.

Blocking is not racing a countdown and nothing about it is unrecoverable: a block
is an ordinary filter rule, this plan builds the screen that undoes it, and
`what_unblocking_did` says what undoing it did. Sending mail to a stranger is the
opposite on both counts.

More to the point, **this codebase already answers this question this way for this
feature**. `may_block` returns `YesButFirst(warning)` and `wx_app.rs:25446` says
it, under a comment reading "Said before the block is made, not instead of making
it". There is already a moment before a block is made in which this program
speaks. Wiring the fourth function follows the precedent the feature set for
itself rather than importing an answer from sending.

So it goes **beside** that warning, not instead of it, and not as a new question
somebody has to answer. Nothing about the making path becomes a prompt: the
sentence is said, and the block is made.

*What it needs, which is why this is a premise and not a line in a task.*
`what_blocking_will_do(&block, junk_folder, allowed, junk)` takes the same four
arguments `what_blocking_did` takes. On the making path today, `allowed` comes
from `allowed_for(&account)` and `junk` from `what_the_junk_folder_needs(...)`,
and both are computed **after** `create_filter_rule` has run. Both are pure reads,
so both hoist above it. Hoist them rather than computing them twice: two
computations of one fact is the drift this codebase keeps finding, and here it
would let the before sentence and the after sentence disagree about the junk
folder.

One thing to get right while hoisting. `what_the_junk_folder_needs` can answer
`IsSwitchedOnByBlocking`, and the making path then actually switches the folder on
and downgrades the value to `IsNotBeingDownloaded` if that fails. The before
sentence is future tense and goes through
`what_will_happen_to_the_junk_folder`, so it says what the program is about to do;
the after sentence is past tense and must go on reflecting what really happened,
including the downgrade. Do not collapse them into one value read once and used
twice without checking that. There is a test for it in task 2's list.

*Where it is said.* Through the same `told` the warning uses, at the same
`Priority`, so somebody hears one thing before the block and one after rather
than two competing announcements. Both channels apply: this is spoken through the
accessibility announcement path, which is `UiaRaiseNotificationEvent` on Windows
and reaches both a screen reader's speech and its braille display. Check that it
is announced rather than only logged, which is the distinction `set_name` versus
`set_accessible_name` is the widget-shaped version of.

*What must not happen.* Two sentences in a row saying nearly the same thing.
`YesButFirst` fires only when there is a reason, so most blocks get one sentence
before and one after; a block that has a warning gets two before. Read both
strings together in that case and say in the summary how they sound one after the
other, because that is the case this wiring can make worse.

**3. Making a block is fully wired, and it is worth knowing which half works
before touching either.** `wx_app.rs` around the `blocking::` calls runs the
whole making path: `just_this_sender`, `everyone_at_the_senders_domain`,
`where_blocked_mail_goes`, `may_block` with its three answers,
`a_rule_that_blocks`, `what_the_junk_folder_needs` and `what_blocking_did`. Do
not change any of it. This plan adds a way to see and undo what that path made.

**4. Copy `wx_conflict_choice.rs`, not `wx_managers.rs`.** The conflict-choice
dialog is 148 lines, was written recently, and is the exact shape needed: a
`ListCtrl` built with `ListCtrlStyle::Report | SingleSel | HRules`, a name set on
the control, a name set on each heading, and buttons named individually.
`wx_managers.rs` is 5,328 lines and `managers.rs` is 9,530, and taking either as
a model would double this plan.

**5. `set_name` is not `set_accessible_name`, and the difference is the whole
point of this project.** `set_name` sets an internal wxWidgets identifier and
never reaches the accessibility tree. Sixteen widgets were once named that way;
it compiled and 324 tests passed and nobody heard any of the names. Use
`set_accessible_name` and `set_accessible_name_and_description` from
`crate::presentation::accessibility::names`, which is what
`wx_conflict_choice.rs` imports.

**6. There are two Windows channels and this screen has to be right on both.**
UI Automation is what Narrator reads and is what Axe.Windows scans. MSAA, through
`IAccessible`, is what NVDA reads for native controls, and it is the only place
`set_accessible_name` writes. For an edit box or a button, Windows supplies its
own UI Automation provider that shadows the MSAA object underneath, so a UIA scan
reports the system's name and never the one the code set. `scripts/msaa-names.ps1`
is how the other channel is read. A name that fails on either is a name somebody
does not hear. The checkpoint runs both.

Note also the trap in the other direction: a control with a visible label beside
it gets that label as its MSAA name even when nothing set one, because Windows
falls back to the nearest static text. So a clean run does not prove the name
came from this code. Set every name explicitly and do not read a pass as proof
that the setting worked.

**7. Add a `ScanTarget` variant, or the screen leaves the scan behind.**
`ScanTarget`'s doc says the workflow and the tests iterate the same list.
Eight screens are in it. A ninth built without a variant is a screen the
automated accessibility scan cannot open, which is how a scan comes to report
success over a window it never looked at. Add the variant and the arm in
`open_for_scanning` in the same commit as the screen.

**8. Which menu group, and which letter, were both worked out rather than
picked.** The Tools menu is five separator-delimited groups: Choose Which Copy to
Keep; the four managers, Contact Manager, Message Filters, Signatures and Tags;
Add a Calendar by Address; Undo Send and Flush Outbox; Settings. A block is an
ordinary filter rule, so Blocked Senders goes in the managers group, immediately
after Message Filters, which is the item somebody looking for it would reach
first.

The mnemonic letters already taken in that menu are W, C, F, i, g, b, U, O and S,
and Windows treats them without case, so `B` collides with Add a Calendar `&by`
Address and `S` with Settings. `Bloc&ked Senders...` is free. Write the reason
beside it, the way the `b` in Add a Calendar by Address has its reason written
beside it.

No keyboard chord, for the reason already recorded twice in that menu: this is
opened once in a while, and a key nobody presses twice is a key in the way of one
somebody presses daily. The route still goes in `docs/KEYBOARD_SHORTCUTS.md`,
which already has the shape for it: `| Open Contact Manager | (Tools menu) | ...`
at line 476, plus a Contact Manager Dialog Accelerators section at 857 for the
`Alt+` keys inside the window. Blocked Senders gets both.

**9. Which existing tests this changes, measured rather than guessed.**

`tests/wired.rs`'s `test_every_handled_command_has_something_that_raises_it`
