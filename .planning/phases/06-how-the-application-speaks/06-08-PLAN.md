**3. A feature branch push does not run the scan.** From
`.github/workflows/accessibility.yml:23-28`:

```yaml
on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main, develop ]
  workflow_dispatch:
```

So the scan runs on a push to `main` or `develop`, on a pull request targeting
either, or on a manual dispatch. This project merges to `main`, so without a
dispatch the findings arrive after the work has landed. **That is why the
checkpoint below is a dispatch and not a wait.**

**4. The upstream has a name and it is not Chromium's tracker.**
`MicrosoftEdge/WebView2Feedback` on GitHub is Microsoft's own feedback and issue
repository for WebView2 and already carries accessibility issues, including one
titled "A11Y: WebView2 control is completely inaccessible with screen readers
(NVDA, JAWS and parcially with Narrator too)" as issue 2330. A WebView2 consumer
files there; filing at `crbug.com` is the wrong door even though the deeper
upstream is Chromium.

**5. Two of the five can be reasoned about and three cannot.**
`Chrome_WidgetWin_1` is the Win32 window class Chromium uses for its host window
and `BrowserRootView` is a Chromium Views class. Both are produced by the Edge
WebView2 runtime's own accessibility tree. **This is an inference from the names
and from the changelog line's own claim, not a verified fact**, and the research
marks it as an assumption. Confirm it against the artifact rather than repeating
it.
