<objective>
One window for everything that has come due, each row saying what kind of
thing it is, with the answers a person needs for one row and for all of them,
and a model shaped so that the fourth kind, a mail message somebody asked to
be told about later, can arrive after version 1 without a migration.

Purpose: Pratik's widening of 06-05's answer on 2026-09-14. In his words:
"there should be an indication that a task is due, a calendar event is coming
up, or a reminder. In other words, I'm reconsidering a single window for
multiple types. What happens if there is a reminder, a task due, and a
calendar event in the same window? Perhaps the same infrastructure can be used
but there can be indications of each type: event, task, or reminder. We also
need to plan for future expansion of this functionality (post version 1)
which will enable us to set notifications for mail that will let the user
decide to tackle individual mail later on."

Today events and tasks raise nothing at all: `raise_what_is_due` reads
`s.reminders` only. So this plan is the first time a calendar alert or a task
due date reaches a person here, and the two decisions underneath the feeds
are put to Pratik before they are wired.

Output: `Due` with a kind and an identity; one window; three feeds; a hold
table; the two decisions recorded; and the seam for the mail kind written
down where the next milestone's planner will find it.
</objective>

    date is a date and never a time, on purpose: both providers send a time

    | Option | What happens | What it costs |
    |---|---|---|
