  <name>Checkpoint: what shape should the per-event panel take</name>
  <decision>
    Sixteen events, three answers each, on a page somebody meets in order with
    a screen reader. How should they be laid out?
  </decision>
  <context>
    **The recommendation is option 1, a Choice of the sixteen with three
    controls beneath it.** Everything else here is the reasoning and the cost of
    the other answers.

    **Why this is being asked rather than decided.** The comment above
    `build_feedback_tab` today argues against a grid of events and says the
    per-event overrides "are not worth forty checkboxes here". Somebody wrote
    that on purpose. It is right about the grid and wrong to conclude that the
    answer is to offer nothing, because that leaves a setting the model holds
    and no screen can reach, which is the rule this whole phase exists to
    enforce. Reversing part of somebody's stated position is not a planner's
    call.

    | Option | What the page holds | What it costs |
    |---|---|---|
    | **1. A Choice, then three controls and a button** | Five controls, always, whatever the event count becomes. Pick an event, set its three answers, or press "Use the default for this event" | Somebody has to move to the Choice, change it, and come back, for each event they want to change. Sixteen events means sixteen trips. The controls reload underneath the cursor when the Choice changes, which is a live-region shaped problem nothing here can prove is announced well |
    | 2. A grid | Forty-eight checkboxes in sixteen rows of three, all visible | One trip for everything, and forty-eight controls met in order by somebody who cannot skim. This is what the existing comment argues against and the argument is good |
    | 3. A separate dialog behind a button | The Feedback tab stays as it is and gains one button. The dialog holds either shape | One more window to open and close, one more thing to find, and it moves a setting off the tab it belongs on |
    | 4. A Choice, three controls, and a fourth row that sets one answer for every event at once | Option 1 plus a way to say "sounds for everything" in one move | The extra row is a control whose state is ambiguous when the sixteen disagree, which is its own accessibility problem |

    **What option 1 inherits.** The Reading tab already uses a Choice with
    controls that reload beneath it, so this is an existing pattern rather than
    a new one.

    **The combination worth considering.** Option 1 for the page, with option 4's
    extra row only if a listening pass later says the sixteen trips are the
    problem. That defers the ambiguous-state control until there is evidence it
    is needed, and adding it later costs one row.

    **What none of these settle.** Whether any of it reads well. That is
    `WINDOWS.md` material either way and this plan records it.
  </context>
  <options>
    - 1: a Choice of the sixteen events, three controls and a reset button beneath it. Recommended.
    - 2: a grid of forty-eight checkboxes.
    - 3: a separate dialog behind a button on the Feedback tab.
    - 4: option 1 plus a row that sets one answer for every event at once.
    - a combination, which is the usual answer here.
  </options>
