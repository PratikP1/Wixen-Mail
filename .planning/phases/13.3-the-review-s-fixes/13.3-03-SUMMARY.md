# Phase 13.3 Plan 03: the folder tree's counts follow whatever drew the tree Summary

The folder tree's unread count now changes at once after a mark, delete, move or copy made
here for anyone with two or more accounts whose labels differ, and a check no longer puts
back the count of a mark still waiting for the server (review items 2 and 7).

## What changed

- **Item 2.** `folder_tree::rows_that_read_differently(held, fresh)` answers
  `Vec<(usize, String)>`: for each held row whose fresh row of the same identity reads
  differently, its position among the rows held and its new words. A row only in one
  reading is left out. `folder_tree::the_first_label_shown(rows)` answers the id of the
  first `WhichRow::Label` held. In the window, `say_the_folder_counts_again` reads the tree
  again for the account `the_account_whose_labels_are_shown` names (the first label's
  `Tag::account_id`, else the open account), compares the items on screen with the rows
  held, writes each answered item's words, then changes those rows' words in `tree_rows`
  and `folders` in place. The held rows are never replaced.
- **Item 7.** `MessageCache::set_folder_counts` writes, in one statement,
  `MAX(?1 - (count of waiting_flag_changes joined to messages where which_flag = ?4 and
  changed_to = ?5 and the message is in this folder, reads as read and is not deleted), 0)`,
  with `WhichFlag::Read.as_stored()` and `true` bound as `?4` and `?5`. Read and quoted:
  the statement's text holds no flag word or value. `mail_sync.rs:2064-2068`'s comment still
  says what is true and was not edited.
