# Phase 13.3 Plan 11: A note changed during a notes read keeps what was done Summary

A notes read that fetches a newer copy from the backend no longer writes it over the note as it
found it before the fetch. The store now reads the note again inside one immediate transaction
and answers: gone (deleted or moved meanwhile, nothing written), changed here (an unsent edit,
nothing written, held for a choice), or written (one `UPDATE` by id that keeps the folder and
the pin). Reached in the running program through `spawn_notes_sync`, which calls
`notes_backend::sync_the_notes_of` and so `sync_notes` and `take_what_has_arrived`.

## What changed

- `src/data/message_cache/notes.rs`: `WhatTheNoteHereWas` and `the_backends_words_over`, which
  takes the note as first read and the backend's title, body, name and marker as plain values.
  `holds_words_nobody_has_sent` decides "changed here": the note is waiting, its words differ
  from the backend's, and they were waiting when the read found it or were typed since.
- `src/application/notes_sync.rs`: `take_what_has_arrived` sends a note the first read held
  through the store method: `Written` counts `stored`, `Gone` counts nothing, `ChangedHere`
  holds the two copies with the note as it stands. A note the first read did not hold still goes
  to `write_it_down`, narrowed to making a new note. The comment above the decision keeps its
  reasoning and says why the decision moved. The test service gained `while_it_is_read`.
- `src/data/message_cache/mod.rs`: re-exports `WhatTheNoteHereWas`.

## Deviations from Plan

1. **[Plan] The pinned case followed the behaviour, not the decision.** The decisions block says
   a note "edited or pinned" during the read, whose backend copy changed, is held as "today's
   rule applied to the note as it now stands"; the behaviour says a note pinned and not edited
   takes the backend's words with `pending` 0 and keeps its pin. Today's rule keys on the
   waiting flag, which a pin sets, so the two disagree. The behaviour was built: holding the pin
   would ask somebody to choose between their own unchanged words and the backend's, a question
   with one answer (the principle of `test_a_note_changed_only_at_the_backend_is_taken_and_is_not_held`),
   and the notes seam carries no pin, so nothing is lost. The pin keeps its value either way.
2. **[Rule 2] A third guard record** for that decision, "a note pinned while a read fetched it
   is not held for a choice", since nothing else reddens if the distinction goes.
3. **[Scope] `src/data/message_cache/mod.rs`**, not in the plan's file list, re-exports the
   answer type beside `MovedWhatTheBackendHolds`. No record anchors there.
4. **[Reading] The move case.** The plan's behaviour says a moved note leaves "exactly one row
   with its backend name, the moved one". The moved copy carries no backend name: the move
   drops it on purpose (`move_a_note_the_backend_holds`). The case asserts one note on the
   account, in the new folder, none in the old, and `stored` 0.
5. **[Name] `the_backends_words_over`** rather than the plan's example `the_backend_s_words_over`.
6. **[Count] Line numbers moved:** SCALE-06's and PIM-04's rows were at `REQUIREMENTS.md:8229`
   and `:8240`, not `:8082` and `:8093`. Nothing else the plan cited had moved.
7. **[Brief] One read-only command carried a do-nothing shell assignment named after a banned
   tool** (`sed_unused=0;`), the slip 13.2-20 recorded. No sed or awk ran; every tracked file was
   changed with Edit or by `cargo fmt`, and every break was taken and undone with Edit.
