# Phase 13.3 Plan 01: the check suite measured, and the scoped run reads once and calls once Summary

The registry scan is now compared with Python's TOML reader on every commit that stages the
registry, a scoped commit reads the registry once and starts the library tests in one cargo
call, and the check suite's slowdown is measured: most of it is this machine, where a process
started from Git's bash costs about a tenth of a second, and the suite's own cuts bought 8 s.

## What works now

- A guard record whose red names are indented other than four spaces, or carry a comment, is
  read; a record spelled any way the scan still misses is refused by the check suite at the
  commit that adds it. Over today's registry the scan prints the same 1,640 lines before and
  after the green and they match `tomllib` record for record (0 differences).
- `bash scripts/check.sh --scoped-runs-for guards/guards.toml src/application/sent_copy.rs`
  now prints one library line, where 13.2-26 printed three lines (a third filter,
  `data::message_cache::messages::the_dispatcher_is_what_keeps_the_two_numberings_apart::`,
  arrived after 13.2-26):

  ```
  --lib -- --test-threads=4 application::mail_controller::against_a_server_that_answers:: application::sent_copy:: data::message_cache::messages::the_dispatcher_is_what_keeps_the_two_numberings_apart::
  ```

  and the same `--test` line as before.
- `--suites-for guards/guards.toml src/presentation/wx_managers.rs` answers the same ten

  nothing and prints no error.
- One real call, `cargo test --lib -- --test-threads=4 help_page::
  presentation::what_the_scans_can_judge::`, ran 20 tests from both modules in one program.
  No commit of this plan staged a source file, so its own hook runs made no library call;

## Deviations from Plan

1. **[Rule 1] The covered-filter pruning stays.** The plan said the `covered` loop goes,
   since libtest runs a test matching two filters once, and also that every rewritten case
   still says the same thing. Three cases assert a change answers exactly its own module's
   filter ("adds no library run"); without the pruning they would have read a second filter.
   The pruning moved into `the_library_line_for`, in bash, at no process cost.
2. **[Plan] The library line's shape is cargo's arguments:** `--lib -- --test-threads=4
   <filters>`, so the builder keeps "one invocation's arguments to a line" and the runner
   hands it as `cargo test --lib "${arguments[@]:1}"`, which `house_style`'s
   one-failing-target reading accepts (one `--lib` word).
3. **[Plan] A ninth case:** a Python that does not answer fails the comparison and says so,
   through a stand-in `python`; the plan named the behaviour without a case.
4. **[Rule 3] `tar -xf C:/...` read `C:` as a remote host;** the archives were unpacked with
   the `/c/...` spelling of the same path.
5. **[Plan] The probes ran from scratch scripts timed with `$EPOCHREALTIME`,** after a first
   take timed with `date`, which put a process inside each interval; the first take is not
   quoted.
6. **[Process] Two baseline runs of the suite (332 s and 183 s) were taken** before task 1,
   one while another `cargo build --release --timings` was running on this machine; neither
   is quoted as a figure.

No changelog entry: nothing a person using the program sees changes. No pull request: nothing

## Question for Pratik

The measurement points at Git's bash starting programs slowly (about a tenth of a second
each, three to five times what PowerShell pays), not at the suites. The usual cause on
Windows is the antivirus checking each start, and Defender's real-time and behaviour
monitoring are on. Nothing was changed. A test would be a Defender exclusion for Git's
programs (`C:\Program Files\Git\usr\bin`), tried for ten minutes and then taken off: it
would show whether the check suite goes back to about a minute, and it would mean Defender
does not scan those programs while it is on. Recommended: try it once, so ledger 803 can say
what the cause is; keep it only if the suite's time halves.
