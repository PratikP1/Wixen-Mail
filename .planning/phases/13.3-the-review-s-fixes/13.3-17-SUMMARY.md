# Phase 13.3 Plan 17: A deletion stays in the calendar it was made in

A meeting or one day of it deleted in one calendar no longer hides, freezes or calls off the
same meeting in another calendar of the account (review item 22, ledger 825). Every calendar
read, each Google calendar, the Outlook calendar, a calendar server's and a subscribed feed's,
now asks only the deletion notes of the calendar it fills, plus notes naming no calendar and
notes in a calendar made on this computer. Whatever was deleted in the calendar being read
still stays deleted. The store's four single-event lookups read the first row through
`optional()`, the shape the sibling store modules use (item 40). Nothing is spoken or shown
differently, so the branch was not pushed.

## Deviations from Plan

1. **[Rule 2] A note in a calendar made here masks every read.** Moving the Google read onto
   the narrowing turned `test_a_deletion_in_a_calendar_made_here_holds_across_three_syncs` red.
   Moving a Google event into a calendar made on this computer keeps Google's name for it and
   files it under the local calendar, so deleting it there writes a note naming a calendar no
   read fills, while Google's copy is still in the calendar it left. Narrowed as the plan
   wrote, that note masked nothing and Google's read wrote the event back. The threat model's
   T-13.3-17-02 asks that the cases already held stay green, so the condition keeps a note in a
   calendar made here, as it keeps one naming none. A calendar counts as made here when its
   row exists and its provider is none of Google, Outlook, a calendar server or a feed; a note
   whose calendar no longer exists is narrowed like any other. Its unit case was seen red by
   hand and went in with task 2's green rather than as a red commit of its own, and it has a
   guard record. The plan's premises read what the note's calendar column is read for and not
   every path that writes it.
2. **[Shape] The calendars are looked up by id, not by account.** The calendar in that case's
   fixture belongs to account `test` while its event is in `acct`, so the set is built from
   `get_calendar` for each calendar a note names rather than from the account's calendar list.
3. **[Count] Four records rather than two.** The plan named one new record per task. Task 2
   added three: the made-here clause of deviation 1, and one each for the Google and Outlook
   reads passing their own calendar, since the task 1 record's break reaches neither alone.
4. **[Shape] Task 1's feed case runs twice,** once with the moved day deleted in the calendar of
   one's own and once with the series, and reads the feed's calendar rows directly rather than
   through `the_series_and_its_moved_tuesday`, whose drawn-days check counts every calendar.
5. **[Brief] One read-only command reached for sed** in a pipeline; the project's hook refused
   it before it ran. No sed or awk ran; every tracked file was changed with Edit or Write, by
   `cargo fmt`, or by `scripts/guards.sh`.
