# Phase 13.3 Plan 24: The handover quits and the words are true Summary

Answering Yes to installing an update now closes Wixen Mail through `really_quit`, the one
function Quit closes through, so with "Keep Wixen Mail running in the notification area" on
the handover no longer hides the window and says Wixen Mail is still running: the Trash is
emptied where that is set, sessions are signed out of, the icon is taken away and the window
is destroyed, as Quit does. The New versions control names the installer as about 15 MB,
held by a case to the privacy page's measured 15,725,012 bytes. The update comments, the
privacy page and the release page say what the code does now. Nobody can reach the handover
until an installer passes the signer check, so its end state stays unrun (ledger 335).

## What works now

- `really_quit(really_quitting, frame)` (`wx_app.rs`, beside `handle_update`) sets the flag
  and then calls `frame.close(false)`. The Quit arm, which the tray's Quit reaches too, calls
  `really_quit(&really_quitting, &frame)`; the `AnUpdateIsReady` arm's success branch calls
  `really_quit(really_quitting, frame)` and holds no `.close(` of its own. `UpdateTargets`
  carries `really_quitting: &'a std::cell::Cell<bool>`, a clone of the `Rc` captured by the
  timer closure. Read with the Grep tool after the green: `really_quit(` at the Quit arm, the
  function and the handover arm, and `frame.close(true)` nowhere in `wx_app.rs`.
- `application::closing` holds `whether_the_handover_quits_the_way_quit_does`, a reading of
  `wx_app.rs` through `what_ships` with `\r\n` taken out. Its doc says it reads source because
  the handover's arm takes a `Verified`, which only `update_download::verify` makes. Its
  companion shows it a right window, one whose handover closes on its own, and one whose
  shared function closes before it sets the flag. `closing` holds 11 tests (9 before).
- `hand_over_to`'s doc says the window then closes the way Quit closes it.
- `WHICH_UPDATES_DESCRIPTION` says "about 15 MB of it", its other sentences untouched. The
  case reads the privacy page's "Downloading an update" section, whitespace joined, for a
  figure with thousands separators followed by " bytes", and the description's "about N MB",
  and passes when N is within 0.5 of bytes / 1,048,576. Its companion: 15,725,012 bytes,
  wrapped across a line, beside 12 MB refused and beside 15 MB passed; a page with no byte
  figure refused, while a byte figure in the next section is not read. `update_check` holds
  32 tests (30 before).
- The size, measured with `ls -l dist/` on 2026-10-23; nothing was built and nothing in
  `dist/` or `target/` was run:

  ```
  -rwxr-xr-x 1 prati 197609 15536146 Oct  6 07:44 Wixen-Mail-Setup-1.0.0-alpha.1+1118.gd3455792.exe
  -rwxr-xr-x 1 prati 197609 15725012 Oct 20 06:02 Wixen-Mail-Setup-1.0.0-alpha.1+1403.g6fd465c6.exe
  -rwxr-xr-x 1 prati 197609 14116838 Sep 20 08:57 Wixen-Mail-Setup-1.0.0-alpha.1+351.g5f363255.exe
  ```

  15,725,012 / 1,048,576 = 14.997, which File Explorer shows as 14.9 MB. `ls -l
  target/release/wixen-mail.exe` the same day answered 50,291,200 bytes, built 2026-10-23
  05:31, a later build than the one 1403 packs (50,268,160 on 2026-10-20 by the plan's
  premise 3). 300 MB is 314,572,800 bytes: 20.0 times the installer and 6.3 times the
  executable, which `MOST_BYTES_ACCEPTED`'s doc now says.
- `docs/privacy.md` gives the measured size with its date, build, command and what File
  Explorer shows, and says it grows as the program does. `docs/BETA_RELEASE.md` names the
  installer `Wixen-Mail-Setup-<version>.exe` and describes Check for Updates and the New
  versions setting, linking the privacy page.
