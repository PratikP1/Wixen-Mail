every message.

its deadline. Pratik answered yes to fixing both on 2026-10-20.

**2. Why the session may answer from its last SELECT, and the one place it must not.** RFC
3501 section 2.3.1.1 says a message's unique identifier must not change during a session, so
a numbering read by the SELECT that opened a folder holds while that folder stays open on
that session; a reconnect is a new `ImapSession` with nothing kept. `select_folder` keeps
always asking, because the check's own SELECT at every check is how a numbering changed
between checks is seen, and a record pins it: "a second SELECT of an already-open folder
still asks the server", anchored on the first two lines of `select_folder`, reddening
`test_a_second_select_of_the_same_folder_reports_a_changed_uidvalidity` (`imap.rs:4484`). So
the kept numbering is read by a new `the_numbering_of` only, and refreshed by every SELECT.

The place it must not answer: a SELECT the server refuses. RFC 3501 says a failing SELECT
leaves no mailbox selected, and today `selected` keeps naming the folder opened before, since
it is set only on success. Every command already trusts that field, so that hole exists now
for them; the plan closes it rather than build on it, by clearing `selected` and the kept
numbering before the SELECT is sent. Without that, `the_numbering_of` would answer for a
folder the server had closed, where today's always-SELECT `numbering_of` reopened it by
accident.
