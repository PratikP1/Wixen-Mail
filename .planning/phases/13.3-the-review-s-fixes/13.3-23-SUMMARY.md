# Phase 13.3 Plan 23: The update check fetches only what it can run Summary

While this project's certificate profile identifier is empty, a newer version is no longer
downloaded to be refused: the person is told it has been published, that Wixen Mail cannot
install updates by itself until its installers are signed, and where to download it by hand.
A check at start says what it found once, on the status line at normal priority, with a
sentence naming Check for Updates on the Help menu, and opens no window. One check runs at a
time, each download goes in a folder of its own that goes with its file, and the check and the
download give up on a host that stops answering. No package changed. Nothing here has been
heard (ledger 944), and the paths a published release reaches cannot be heard until one exists.

## Task 1: Pratik's answer

The brief carried it, in these words, and no agent gave it: on 2026-10-20 Pratik said yes to
option (c): do not use ship-shape, fix the five gaps in Wixen Mail's own update code with no

The plan's checkpoint text said moving wxDragon "breaks the build in one file". The research for

13.4, after 13.3 and before the sittings. That replaces the recommendation the checkpoint carried
for when wxDragon should move.

## What works now

- `whether_an_installer_could_be_accepted(profile)` (`update_download.rs`) asks the platform
  first, then refuses a blank or empty profile with `Refused::OurInstallersAreNotSignedYet`,
  whose sentence names no deleted file, says nothing was downloaded and nothing changed, and
  gives the releases page. `whether_that_signer_is_ours`'s line
  `if profile.is_empty() || !who.usages.iter().any(|usage| usage == profile) {` still appears
  once.
- `what_to_do_about_with_profile(answer, profile)` answers `SendThemToThePage { why, page }`
  for an offer nothing could pass, `FetchIt { version, page, files }` for one that could, and
  `JustSayIt` otherwise; `what_to_do_about(answer)` passes `THE_CERTIFICATE_PROFILE_IT_SIGNS_WITH`.
  `fetch` still asks the platform before `bring_it_down`.
- `ask_whether_there_is_a_newer_version` (`wx_app.rs`) takes `update_check::ONE_CHECK.begin()`
  after the channel is known and before `rt.spawn`; given none, by hand it sends
  `CommandAnswered` with `what_a_second_check_says`, at start it logs one line, and returns;
  given one, the task binds it as `_under_way`, so it is let go when the task ends. The worker
  matches `JustSayIt`, `SendThemToThePage` and `FetchIt` by name; the fetch is
  `fetch_the_installer`, new, which sends `AnUpdateIsReady` or `AnUpdateDidNotHappen`.
- `UIUpdate::AnUpdateDidNotHappen { said, page, asked }` (`ui_types.rs`), its doc rewritten. The
  arm in `handle_update` matches `asked`: `AtStart` writes the sentence and
  `WHERE_THE_PAGE_IS_OFFERED` to the status line and `s.status_message` and says them at Normal
  on `"new version"`; `ByHand` does what the arm did before, High on `"command"` and the
  Yes/No dialog with Enter answering No. `open_help`'s doc is back above `open_help`.
- `update_check::ask` is `ask_at(endpoint, channel, A_CHECK_HAS_THIS_LONG)`, 30 seconds through
  `ClientBuilder::timeout`; a client that cannot be built with the limit answers
  `CouldNotBeFetched { why: NoAnswer }`.
- `bring_it_down` is `bring_it_down_within(.., A_DOWNLOAD_HAS_THIS_LONG_TO_CONNECT,
  A_DOWNLOAD_MAY_GO_QUIET_FOR)`, 30 seconds each through `connect_timeout` and `read_timeout`,
  and no `.timeout(` on that builder. The folder, `updates/<Uuid::new_v4()>/`, is made only after
  a success status; `write_it_down` writes the body, and any failure after that removes the
  folder whole. `throw_it_away` (reached from `verify`'s refusal) and `say_no` call
  `its_folder_goes_too`, which uses `remove_dir`, so only an empty folder goes, and a folder that
  cannot be removed is logged. `clear_the_waiting_room` is unchanged.
- Counts at the end, taken by the guard runner and the hook: `service::update_download::` 59
  tests (47 before), `service::update_check::` 30 (23 before), `presentation::wx_app::` 199,
  unchanged. Every one passed in the guard runner's whole-library baseline before task 3's green.
- `git diff 7157c7e7 -- Cargo.toml Cargo.lock` is empty. `uuid` with `v4` was already a direct
  dependency (dependency-audit: nothing added).
