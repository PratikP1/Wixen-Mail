<objective>
After a refused account save, make the window hold what the store holds, make a refused new
account leave no secret behind, and make a refused removal say one plain sentence.

Purpose: ledgers 922, 923 and 924, opened by 13.3-07 on 2026-10-21 as `todo` rows for Pratik
to schedule, and Pratik's "yes to 3" of 2026-10-22, which puts all three in phase 13.3 before
its close. 922: `handle_account_mgr` keeps the list the Account Manager handed back even when
the store refused it, and starts the first syncs of an account that was never saved, so until
a restart the window works with an account the store does not hold. 923: a browser sign-in in
the Add Account window stores the new account's tokens before OK, so a save refused after it
leaves them under an id no row names, which neither removing an account nor the uninstall
erases. 924: a refused removal is spoken as "Security error: This account has not been
removed, because Windows would not let go of its saved password (Security error: Could not
remove ...)", the layer's name twice and the store's own words in the middle.

Output: the read-back and the handler that uses it, with a reading; the shared forgetting, the
refused account's secrets forgotten and the plain sentence, with their cases; the guard
records; the changelog; ledgers 922, 923 and 924 closed and two rows opened; MAIL-04's dated
line; the four marks; the pull request.

  when the table cannot be read either (premise 1), logged. A call with a case each way rather
  than logic in the handler, which only a reading could reach.
- **Everything the handler works out after the save comes from what the store holds:** sign-offs,
  stopped watches, first syncs, the active account and the default, the last through
  `default_after_change` as startup does. The dialog's list is moved into the call, so the
  compiler refuses any later use of it.
- **A refused account no stored row names has every secret forgotten,** the password and the
  directory password as well as its browser sign-ins, through the one function
  `delete_account` uses (premise 2). Ledger 923 named the tokens; the password left by a save the
  table refuses is the same defect on a sibling path. An account already stored whose edit is
  refused keeps everything.
- **The refusal names the account,** so `delete_account` takes its name (premise 3), and the
  sentence is one sentence: "{name} was not removed, because Windows would not let go of {what
  was kept}; try again, and see When something goes wrong in Help if it keeps happening." Each
  kind is named once, in this order and these words: "its saved password", "its directory
  password", "its browser sign-in", joined as "A and B" or "A, B and C". "This account" when the
  name is blank. The store's reasons go to the log by the account's name, never a password or a
  token.
- **The sentence of a save the credential store refuses is ledgered, not changed** (premise 6).
- **Pushed with a pull request** under Pratik's standing OK of 2026-09-23: what a refused removal
  says changes, and what the window lists after a refusal changes.
