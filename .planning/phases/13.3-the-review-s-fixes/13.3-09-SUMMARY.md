# Phase 13.3 Plan 09: A feed names only its host, and reads past a byte order mark

A calendar feed that cannot be fetched, for any reason, now says so naming its host and never
its whole address, so a private token in the address reaches neither the log nor what a
followed link speaks (review item 10). A feed, an opened calendar file or an opened contact card
that starts with a UTF-8 or UTF-16 byte order mark reads again, and a feed whose host declares a
character set such as windows-1252 is read in it, as reqwest's `text()` read feeds before 13.2-14
(review item 11). No package was added: the charsets come from `mail-parser`, already a direct
dependency.

No requirement names subscribed calendar feeds, opened calendar files or contact cards (premise
5), so no requirement line is written and the completion marks are three.

## What was done

- **Task 1, red then green (tracer).** `why_the_feed_did_not_arrive` takes the error by value;
  the timeout keeps its sentence, and every other failure answers `Error::Network` reading
  "{layer} at {host}: " and reqwest's words through `without_url()`. Both `map_err` calls pass
  the error as received. Red at `5ff2ba72`, green at `704f5db9`; the tracer's verify passed end
  to end before task 2.
- **Task 2, red then green.** `a_calendar_or_card_as_text(bytes, declared_charset)` takes a
  UTF-8 mark off and reads the rest as UTF-8, otherwise decodes through
  `mail_parser::decoders::charsets::map::charset_decoder` for a charset it knows, otherwise lossy
  UTF-8. `the_charset_in` reads `charset` off a `Content-Type`, without case and without quotes.
  `fetch_ics` reads the header after the status check and before its chunk loop, which with the
  cap line is as it was, and decodes `arrived` through the reading. `opening::text_of` decodes
  through the same function with no charset. Red at `fafd6943`, green at `878edaf3`.
- **Task 2, a second pair (deviation 1).** A UTF-16 mark, either way round, has the bytes read
  through `mail-parser`'s `utf-16` decoder, which reads the order off the mark and drops it. Red
  at `79940984`, green at `671d8771`.
- **Task 3.** The changelog's two entries under `[Unreleased]`, `### Fixed`, and the dated
  correction of 13.2-14's known limitation; ledger 926 in both halves with the header counts;
  the three marks.

## Deviations from Plan

1. **[Rule 2] A UTF-16 byte order mark is read too.** The plan's truth is that a feed starting
   with a mark refreshes as it did before 13.2. Read in reqwest 0.13.4's `text_with_charset`,
   `text()` decoded through `encoding_rs`'s `decode`, which sniffs UTF-16 marks as well as
   UTF-8's, so a feed saved as UTF-16 read then and would not have read after the plan's fix.
   One more red and green pair and one more record; `mail-parser`'s `decoder_utf16` reads the
   mark, read in its 0.11.5 source.
2. **[Addition] A loopback case for the declared charset,**
   `test_a_feed_served_in_windows_1252_arrives_with_its_accents`, because no case of the
   reading alone shows that `fetch_ics` hands the header over. `common::answering` sends text
   only, so the module's tests gained `answering_in_bytes`, a host that sends bytes.
3. **[Pin] `test_a_feed_declared_in_utf_8_reads_as_utf_8` was green on arrival,** as the plan
   foresaw; the red commit says so and does not name it.
4. **[Process] The UTF-16 red was first refused by the hook,** because `STATE.md` on disk,
   unstaged, already counted this plan's summary, which did not exist yet: the planning-files
   check reads the disk (ledger 325's hole). The count went back to 310 until this summary was
   written; nothing in the commit changed.
5. **[Count] Three new guard records rather than two,** the third for deviation 1.

Dependency verdict: nothing added. The route taken is a public API of a package already pinned
and audited, `mail_parser::decoders::charsets::map::charset_decoder`, so no new trust
relationship and no change to the threat register's supply chain line. `encoding_rs` stays under
reqwest.

No schema change. No key, control or setting added, so no letter spent and nothing to scan for a
name. What a failed feed says changes: "ICS fetch failed at calendar.example.com: error sending
request" in place of the same words ending "for url (" and the whole address.
