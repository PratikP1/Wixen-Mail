<objective>
Make removing an account and adding one back on the same address save, by doing the removals
before the saves and letting no single refusal stop the rest.

Purpose: item 6 of the review of 13.2 (must), and Pratik's "yes" of 2026-10-20 to fixing all 42.
Since 13.2-06 a save refuses an address another stored row uses, and `replace_accounts` saved
before it removed, so the account just removed still held its address: the new account was
refused, nothing was removed, the person was told to edit the account they had removed, and
after a restart the old account was back and the new one gone.

Output: `replace_accounts` corrected with its cases, the guard records, the changelog, the
ledger, the four marks. The branch is not pushed: nothing said or shown changes but the order of
writes, and the sentence that can now be heard instead is one `delete_account` already says.
</objective>


`replace_accounts` (`:152-167`) works out `gone` from `load_accounts()`, runs `save_account(account)?`
for every account, and only then `delete_account(id)?` for each gone one. `save_account` refuses
first, through `who_already_uses` (`src/application/one_address_one_account.rs:66-81`, addresses
compared ignoring case and spaces), against a table that still holds the removed row. The Account
Manager's own check passes, because `delete_selected` takes the account out of its working list
(`wx_account_manager.rs:869`) and `refusal_for` reads that list (`:535`, `:1812`), and a new
account gets a fresh id (`:1892`). All six checkers stood the finding.

**2. The proposed fix does not work alone, as the checkers found.** The schema holds `email TEXT
NOT NULL UNIQUE` and `save_account`'s statement is `INSERT ... ON CONFLICT(id) DO UPDATE`
(`:35-61`), which does nothing for a clash on the address, so skipping the code's own check
would fail at SQLite while the removed row exists, after `credentials::store` had already kept
the new account's password. The removed row has to go before the save that reuses its address.
And the removals must not end on a bare `?`: `test_one_account_that_will_not_go_does_not_throw_away_the_other_edits`
(`:887-917`) holds that one refused removal does not throw the other edits away.

**3. The shape chosen.** Every removal first, each refusal kept and none stopping the rest; then
every save, likewise; the answer is the first refusal, and any later one is logged. Removing
first was set aside in 13.2 only because it stopped at the first refusal (the doc at
`:148-151`); with nothing stopping, it is the order the table's address rule needs, it needs no
split of the removals into two kinds, and checker 6's "smallest fix that works" is this. A
removal refused for an address the new list reuses leaves that address held, so the account
reusing it is refused by `refuse_an_address_another_account_uses` before `credentials::store`,
and no password is kept for it; the answer is the removal's own sentence (`:349-353`), which
says what was not removed and why.

**4. What this plan leaves, read and ledgered.** `handle_account_mgr` sets `s.accounts = new` and
starts `bring_what_a_new_account_holds` for added accounts even when the save refused
(`wx_app.rs:23236-23264`), so the window can work with an account the store does not hold until a
restart. With this fix the commonest way there is gone; a credential store that refuses remains.
A browser sign-in stores the new account's tokens before OK (checkers 3 and 4), so a refused save
after it leaves them with no row to name them, the class ledger 847 records. Neither is one of
the 42; task 2 ledgers both with recommendations.
