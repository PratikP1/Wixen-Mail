# Phase 13.3 Plan 24.7: The Test Suite job restores its caches and saves none

The CI Test Suite job's three cache steps now use `actions/cache/restore@v4` with the path and
key text they had, so a run that misses the cache no longer spends about ten minutes packing a
save GitHub refuses; Clippy still saves the same keys. A reading in `tests/house_style.rs` that
was red on the old file holds it, with two guard records. On the way, the green's whole gate met
a new advisory, RUSTSEC-2026-0387, which Pratik accepted as a known risk; it is in
`.cargo/audit.toml` with its reason and exit condition, in the changelog, and in ledger 954.

Branch `13.3-24.7-the-test-suite-restores-its-caches`, cut from `main` at `a6b43184`, not
merged (merge train: a merger merges it) and not pushed, since nothing the program says or
shows changes.

## What works now

- **The Test Suite job.** In `.github/workflows/ci.yml`, inside the Test Suite job alone, the
  steps "Cache cargo registry", "Cache cargo index" and "Cache cargo build" use the restore half
  of the action at the same tag, which declares no post step. Name, `with`, `path` and `key`
  lines and the space-only lines between steps are byte for byte as before. A comment above the
  first step says why and names the test. Every other job, and every other workflow, is
  unchanged. Nothing has run on a runner; ledger 955 asks the first pull request run after the
  merge for its step list and minutes.
- **The reading.** `the_job_named` and `the_cache_steps_of` in `tests/house_style.rs`, with
  `test_the_test_suite_job_saves_no_cache_and_restores_what_another_job_saves` over the real
  file and its companion `test_the_cache_reading_can_see_a_step_that_saves` over strings. Red
  on main's `ci.yml` naming the three steps; green after the change. The file went from 78
  tests to 80.
- **The audit.** `.cargo/audit.toml` accepts RUSTSEC-2026-0387 (crypto-bigint 0.5.5, dated
  2026-10-23, operations meant to be constant-time that can branch on secret values, patched in
  0.7.6, nothing on the 0.5 line). `cargo tree -i crypto-bigint@0.5.5` reaches it only through
  pgp 0.20.0's elliptic-curve 0.13 family (k256, p256, p384, p521, their ecdsa and primeorder,
  cx448). pgp 0.21.0, the newest on crates.io on 2026-10-24 by `cargo search pgp`, still asks
  for elliptic-curve, k256 and p256 at 0.13 in its own manifest, read that day, so no lock move
  clears it. `rsa` 0.9.10 uses num-bigint-dig, not this crate. `scripts/audit.sh` by hand after
  the acceptance: exit 0, all 6 accepted advisories still reported, none outside the list.
