# Phase 13.3 Plan 18: A contact changed during a sync is kept

A contact Google, Outlook or a CardDAV address book has just made or changed is now read again
before the address book's answer is written down (review item 23). Unchanged, the copy sent is
written as before. Edited meanwhile in the window, the edit stays and waits for that address
book under the name and version marker it just gave, so the next sync sends it as a change
rather than making a second contact. Deleted meanwhile, that address book is owed a deletion
under that name, so the contact does not come back here and is deleted there at the next sync.
The Contact Manager saves over the contact as it stands, so a name a sync gave while the window
was open is kept. Google's and Outlook's refusal to make a contact names its id in the sync's
errors, and so in the log, never its name (item 25). Nothing is spoken or shown differently, so
the branch is not pushed.

## Deviations from Plan

1. **[Rule 1] The Contact Manager asks "did this row change" against the copy it opened with.**
   The plan had the re-read row answer both questions. Read that way, a row nobody touched whose
   contact a sync had changed while the window was open would differ from the re-read row and be
   written back over what the sync wrote, marked waiting. So `holds_a_change` still compares with
   the copy the window opened with, which is what the editor's row started from, and only
   `to_stored`'s carried fields come from the contact as it stands.
2. **[Shape] A contact edited while an address book made it takes the address book's word for
   where it came from.** `source_provider` is the sync's to say. Kept from the row, an edit to a
   contact typed here would sit with no source while the setting that sends a change only to
   where it came from is on, and never leave.
3. **[Shape] `write_down` kept its name.** The plan said it goes if nothing calls it; it took the
   new shape instead of a second helper beside it, and the plain save it held went.
4. **[Plan] `data/message_cache/mod.rs` re-exports `WhatTheAnswerCameTo`.** Not in the plan's
   file list.
5. **[Test] The CardDAV case stores an unmoved change marker.** Without it, the read that follows
   the push takes the contact off for a card the test server never holds, and the case would
   test the removal pass instead.
6. **[Plan] Three ledger rows, not two.** 937: the Contact Manager's failures go to the log
   through `report()` with the contact's name, the class item 25 fixed for the sync. Not
   changed here; for Pratik.
7. **[Count] Two re-measure calls in each task, not one,** for the five records above.
8. **[Brief] Two tooling slips, both refused before anything ran.** One read-only pipeline
   reached for `sed`, which the project's hook refused. And the first re-measure call was handed
   names with a carriage return on each, written by Python in text mode, and `guards.sh` refused
   all 122 as unknown before measuring any; the file was written again with `\n` endings. No sed
   or awk ran; every tracked file was changed with Edit or Write, by `cargo fmt` or by
   `scripts/guards.sh`.
9. **[Brief] Task 2's red was committed without running the count check by hand first.** Its hook
   ran it and accepted the red naming it.

No package added; `git diff main -- Cargo.toml Cargo.lock` is empty. No schema change: the new
