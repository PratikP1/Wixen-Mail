# Phase 13.3 Plan 24.6: A broken restore stops the guard run, and a fast path for --remeasure

The guard runner now reads back every file it puts back and stops with a sentence when one
does not come back; `--remeasure` asks a record flagged only by added tests a fast question,
its named tests and every test added since it was last measured, and falls back to the whole
run under the same break on any other answer; the Defender exclusion of 2026-10-22 is on the
measurements page and in ledger 803, which stays open.

Branch `13.3-24.6-a-broken-restore-stops-the-run`, cut from `794deee8`, 13.3-24.5's branch tip,
not yet merged into `main`. Every comparison below with the tree before this plan is against
`794deee8`.

## What works now

- **Ledger 927.** `measure`'s `finally` goes through `put_the_file_back`, which writes the
  copy back, reads the file back and compares bytes. When the write raises `OSError` or the
  bytes differ, the copy is kept in `target/guards-left-broken/` and `TheTreeWasLeftBroken`
  stops the run with `what_a_failed_put_back_says`: the file, what went wrong, where the copy
  is, the `cp` command that puts it back, and that nothing was written to `guards/guards.toml`
  and no later record was measured. `measured_and_said` lets it through ahead of its two
  handlers; `main` prints it and returns 1 before any count is written. `the_verdict_on` reads
  its first line as could not be measured and `verdicts_in` drops the name, so a resume measures
  that record again once `why_a_resume_is_refused` sees the file clean. Where the `OSError(22)`
  of 2026-10-21 arose is still not diagnosed.
- **The fast path.** Under `--remeasure` without `--named-only`, after the pre-read and before
  any break: each suite's `--list` and `--list --ignored`, the working tree's id, one
  `git blame --porcelain` over the selected records' lines, one `git cat-file --batch` kept
  open, and per commit blame names, its records and its parents' records and the test names of
  every differing `.rs` file then and now. `the_question_for` answers a `FastQuestion` or the
  reason for the whole run, in the plan's order. `judged_under_the_break` asks the fast filters,
  and on anything but a clean answer prints `path: whole, <why>` and asks the whole suite under
  the same break. Each block says its path; the fast agreement has its own shape, read as agreed;
  `the_closing_verdict` says how many took each path and what the fast path did not ask. A plain
  run, the sweep, `--touched-by` and `--named-only` reach none of it.
- The module docstring names the four places the script reads git, and says it read three while
  saying two from 2026-09-23. `run_the_whole_suite`'s docstring and `scripts/guards.sh`'s
  `--remeasure` comment say what the fast question is.
