# Phase 13.3 Plan 02: a delete made here leaves at once, and conversation rows follow changes that erase their names Summary

A message deleted on this computer now leaves the list in the same call as the delete, so a
conversation reopened after a Delete inside it no longer lists the message, and a second
Delete can no longer find it in the Trash here and erase it unasked. Under conversation
view, a conversation's row now changes at once after a take-off, a POP delete into the Trash
this computer keeps, or a move into another account's folder, for one message and for a set.

## What works now

- `delete_these`'s arm for `DeletedHere::Left` takes the row out with
  `take_row_out_of_the_list` and asks for the counts with `the_folder_counts_moved`, the way
  `complete_here_then_tell_the_server` does. `delete_if_local` no longer sends
  `MessageLeftTheFolder`, and the variant and its arm are gone: `git grep -n
  "MessageLeftTheFolder" -- src tests` names nothing.
- `ASetLeaving` carries `conversations`, read with `cache.conversations_holding` when the set
  is remembered, before the state is locked and before anything changes. `the_set_leaving`
  takes the state and the store; the Delete arm, `remember_the_set_leaving` (the move arm,
  Report as Junk, the runner's move) and `remember_these_rows_leaving` (the runner's delete)
  hand it their store. The two reads: `wx_app.rs:463`, where a set is remembered, and
  `wx_app.rs:28146`, the catch-up's own.
- The catch-up is split: `bring_the_conversation_rows_up_to_date` names from the store after
  the change and hands the names to `bring_the_named_conversation_rows_up_to_date`, the
  listing. `take_row_out_of_the_list` at the last row of a set and
  `a_refusal_ends_the_wait_for_a_set` hand the set's names to the listing; every other caller,
  the marks, stars and labels among them, keeps reading after its change.
- On the built list, six cases that were red first: one message taken off, moved to the other
  account, and moved into the Trash here, each leaving A's row out with B's as it was; b1 and
  b2 taken off, and moved to the other account, leaving B's row out with A's kept; and a1 and
  b1 remembered, a1 taken off and a refusal for b1, leaving A out and B reading "2 messages,
  2 unread". 13.2-02's mark and delete cases pass unchanged.

   `"fn delete_these("` as the sixth entry, the planter wrote it after the
   `MessageDeletedFromCache` arm, and an arm is read to the next arm, so the arm's text
   swallowed the function and `test_the_reading_can_see_a_change_that_does_not_ask` failed
   for the wrong reason. The planter now writes the functions first, then the arms. In the
   red commit.

   to `remember_these_rows_leaving`; the Delete arm calling it reddened
   `every_command_acts_on_the_selection`, which requires `a_set_leaving` in that arm. The arm
   keeps its block and calls `the_set_leaving(&state, message_cache.as_deref(), &leaving)`,
   which reads the store itself.
3. **[Plan] Two cases beyond the plan's four:** a set taken off and a set moved to another
   account, so the set path is held by a take-off and a move, not only the refusal.
4. **[Rule 2] One more record than the plan named,** for the refusal arm's use of the names,
   since nothing else would go red if that arm read after the change again.
5. **[Plan] The cases assert a row that leaves, not a row reworded.** Every message in the
   target's mailbox has a copy in the account's All Mail, and whether a row that loses one of
   two messages rewords under the whole-account reach with that copy beside it was not
