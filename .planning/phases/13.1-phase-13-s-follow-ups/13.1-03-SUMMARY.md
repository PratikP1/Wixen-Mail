## On or fast (D-13), read before the red

SQLite's `PRAGMA secure_delete` section, fetched from sqlite.org/pragma.html
on 2026-10-03: "When secure_delete is set to "fast", SQLite will overwrite
deleted content with zeros only if doing so does not increase the amount of
I/O. In other words, the "fast" setting uses more CPU cycles but does not use
more I/O. This has the effect of purging all old content from b-tree pages,
but leaving forensic traces on freelist pages."

Taken: `on`. A page a write frees goes to the freelist. Under fast it keeps
its old bytes, its last image sits in the write log, and a checkpoint copies
that image into the file, where it stays until the page is reused. Under on
the page is zeroed, the zeroed image goes through the write log into the file
at the next checkpoint, and the next check's truncating checkpoint
(`empty_the_write_log`) drops the older frames. So on settles the file, and
the write log is settled by the truncation the next check already runs, not by
either setting. The same section says secure delete scrubs "ordinary tables"
only and that a virtual table's shadow tables may keep traces, which is why
13-44.8's compaction of the search index stays.
