<objective>
Give the program the two pieces of judgement it needs before it can tell anybody
about a new version: how to put two versions in order, and how to decide whether
a published release is an offer for the person in front of it.

Purpose: the first half of success criterion 2, and the part of D-07 that is pure
reasoning. Nothing here fetches anything, stores anything or draws anything.
Plan 07-05 does the asking, the settings and the saying; plan 07-09 does the
downloading.

There is no version comparison anywhere in this tree. `src/common/version.rs`
only formats, and `semver` is not a dependency of this crate. So the ordering is
new, and it is the piece with a clear test surface and no network in it, which
is why it goes first and on its own.

**What changed since this plan was first written.** It used to hold the settings
as its second task, and recommended in the same breath that they move to the plan
that gives them a reader. They have moved, to 07-05, for the reason that
recommendation gave: `every_setting_is_acted_on` asks whether anything outside
`config.rs` and `wx_settings.rs` reads a field, and nothing in this plan could.
In their place is the decision D-07 created, which is pure, has no reader problem,
and is the thing 07-05 and 07-09 both call.

Output: an ordering with tests for every case the release workflow can produce,
and a channel-aware answer to "is this release an offer" that the two plans
downstream call rather than re-deriving.
</objective>

**1. D-07 adds a second thing this file has to know, and it is not a setting.**
`.planning/decisions-2026-09-06.md` decision 7 says the program will "offer a
choice of public releases or development releases". The setting that stores that
choice is 07-05's; the meaning of the two words is this plan's, because it is
entirely a question about versions.

The two words decide two different things and both belong here:

- **Which release is even asked for.** GitHub's `/releases/latest` "retrieves the
  most recent non-prerelease, non-draft release"; `/releases` lists everything.
  So the channel selects an endpoint, and 07-05 makes the request. This plan owns
  the type that says which.
- **Whether a candidate is an offer.** On the public channel a prerelease is
  never an offer even if the ordering says it is newer. On the development
  channel it is. Both channels offer `0.6.0` to somebody running
  `0.6.0-alpha.1`, because it really is newer. That is a decision with a clear
  test surface and no network in it.

Put `ReleaseChannel` in `src/common/version.rs`, not in `src/service/`. Plan
07-05 stores it on `AppConfig`, and `src/data/` reading a type out of
`src/service/` would be a layer inversion. `common` is where both can see it.
`CLAUDE.md` asks for a typed value rather than a stringly-typed one wherever a
fixed set of strings is stored, and this is that case exactly.

**1a. D-16 makes the choice one thing with three answers, and that is a second
type rather than a third variant on this one.** Decision 16 of
`.planning/decisions-2026-09-06.md` settles the shape: "a single control with
three values: off, public releases, development releases", and it gives an
accessibility reason rather than a tidiness one. A dependent control that greys
out when its parent is off "is skipped in the tab order, so for somebody moving
by keyboard it does not read as unavailable, it simply is not there".

So this plan owes two types, not one.

- `ReleaseChannel` keeps exactly two values. Every value of it is a real channel,
  so the offer decision stays total and no arm of it has to answer a question
  with no answer. "Is `0.6.0-alpha.1` an offer for somebody who is not looking
  for updates" is not a question with a true answer, and a three-variant channel
  forces every caller to pretend it is.
- A second type carries what somebody chose. Three values: not looking, public
  releases, development releases. Its whole job is to be stored by 07-05 as one
  top-level `AppConfig` field, and to answer one question: which channel, if any.

The mapping is one small function from the three-valued type to an optional
channel, and the off value maps to nothing. Write it here, test it, and let 07-05
and 07-09 call it rather than matching on the setting themselves. Two callers
matching on three values independently is how one of them ends up treating off as
public by accident.

**Name it for what somebody is choosing, not for the machinery.** `UpdatePolicy`,
`UpdateChecking` and `WhichUpdates` are all defensible; pick one, run
`naming-review` on it and on its three values, and say in the summary which was
chosen, because 07-05 stores that spelling and 07-09 reads it.

**The stored spelling of all three values is fixed here for the same reason the
channel's is.** `CLAUDE.md`'s rule about never renaming what shipped applies to a
stored settings value, and once one settings file on one machine holds a spelling
it is permanent. Round-trip all three.

**3. The `[D]` line asks for SemVer ordering and the release workflow can really
produce a prerelease, so the comparison is more than splitting on dots.**
`.github/workflows/release.yml:9-25` offers `patch`, `minor`, `alpha`, `beta`,
`rc` and `release` as levels, and lines 95 to 97 already distinguish a
prerelease tag from a release tag with `-(alpha|beta|rc)`. `CLAUDE.md` says a
prerelease suffix stages a release about to go to people. Under SemVer a
prerelease sorts **below** the release it stages, so `0.6.0-alpha.1` is older
than `0.6.0`, and a comparison that ignored the suffix would tell somebody
running `0.6.0` that `0.6.0-alpha.1` is newer.

No prerelease has ever been cut: `git tag` returns zero tags, so the tag list is
empty outright. This is untested territory in the real world and the tests are
the only thing holding it.

**D-07 turns that from a defensive case into the main one.** Before the decision,
prerelease ordering mattered only so that a stray prerelease could not be
mistaken for an upgrade. With a development channel, a prerelease is the thing a
tester is meant to be offered, so `0.6.0-alpha.10` being newer than
`0.6.0-alpha.9` is now a feature somebody depends on rather than a guard against
a mistake. Every prerelease case in the behaviour list is load-bearing.

**4. `semver` is in `Cargo.lock` and is not a dependency of this crate, and the
difference matters for a dependency-audit argument.**

```
grep -n '^name = "semver"' Cargo.lock                       # 1.0.28
awk '/^\[\[package\]\]/{p=""} /^name = /{p=$3} /^ "semver/{print p}' Cargo.lock | sort -u
```

The only package listing it is `rustc_version`, which is a build dependency, so
`semver` is compiled for the host at build time and is not in the binary. Adding

dependency rule and the `dependency-audit` skill both point the same way for
something this size. **Write the ordering here.** Say the measurement in the
summary rather than the assertion, and say what would change the answer, which is
this needing full SemVer with build-metadata precedence rules rather than
`0.x.y` plus three prerelease words.
