Checked against the working tree on 2026-09-06, command first.

**1. The gate hole is real and the research's reason for it is wrong, which
matters because the wrong reason points at the wrong fix.** The research says
"Neither `house_style` nor `wired` reads the `.iss`". `house_style` does:
`ours()` in `tests/house_style.rs` calls
`collect(Path::new("installer"), &["iss"], &mut found)`. So a prose rule in
`house_style` already reads the installer script on every commit.

The hole is real for a different reason. `scripts/which-checks.sh` answers
`affected` for an `installer/*.iss` change, and `check.sh`'s
`run_the_tests_that_reach_what_changed` maps only `src/*.rs` to `--lib module::`
and `tests/*.rs` to `--test target`. An `.iss` path matches neither arm, so no
scoped target is chosen, and what runs is formatting, clippy, the suites
`guards/guards.toml` couples to a changed source file (none, see below), and
`guards_that_read_the_whole_tree`, which `scripts/check.sh:15` sets to
`(house_style wired)`.

Verify both halves rather than trusting this:

```
sed -n '33,50p' tests/house_style.rs          # ours() collects installer/*.iss
sed -n '363,385p' scripts/check.sh            # the src/*.rs and tests/*.rs arms
sed -n '15p' scripts/check.sh                 # guards_that_read_the_whole_tree
```

**The correction changes the options.** A test placed in `tests/house_style.rs`
would already run on an `.iss` commit, so widening `which-checks.sh` is not the
only way. It is still the right way, for two reasons given in task 1.

**2. The three existing installer-reading tests, located by symbol.**

```
grep -rn "Wixen-Mail-Setup.iss" src/ tests/ --include=*.rs
```

returns exactly three call sites: `src/application/forget.rs:555`,
`src/application/running.rs:228`, `src/presentation/first_run.rs:409`. All three
are unit tests in `src/`, so all three are invisible to an `.iss`-only commit.
Widening the gate fixes all four at once, which is the second reason to do it
that way.

**3. No guard record mentions the installer, checked several ways.**

```
grep -niE "installer|build-installer|\.iss" guards/guards.toml
```

returns one hit and it is a false positive: the string `frame.iconize(false)`
inside an unrelated record's `before` block, matching on "icon". So no suite is
coupled to the installer script through `guards.toml` either.

**4. `which-checks.sh` already has the rule to copy, with its reasoning written
out.** Lines 132 to 157 make `Cargo.toml` and `Cargo.lock` answer `all`, and the
comment above says why: a manifest reaches every target, something reads it as
data, and a manifest change answering `affected` ran no tests at all because no
module maps to it. That is the same sentence with `installer/*.iss` substituted,
and the file says so itself: "it is the markdown rule at the top of this file
read the other way round."

The existing case matches `Cargo.toml | Cargo.lock | */Cargo.toml | */Cargo.lock`.
An installer case is `installer/*.iss` or `*.iss`; decide which and say why. An
`.iss` anywhere in the tree is a setup script and there is only one, so the wider
pattern costs nothing and cannot miss a second one added later.

**5. The suite that holds `which-checks.sh` exists, and a case in it can be
committed red.** `scripts/which-checks.test.sh` sources
`scripts/shell-suite.sh`, reports each case through `suite_case_passed` and
`suite_case_failed`, and ends at `suite_verdict`. The name a red commit carries
is `which-checks::<the case description>`, and `shell-suite.sh` refuses a
description that is empty, that holds ` ... `, or that holds a comma. Read
`CLAUDE.md`'s paragraph on this before writing the descriptions; the comma rule
was found by a commit that tried to name a case with one in it.

The existing manifest cases are the shape to copy:

```
expect all "Cargo.toml" gsd/x Cargo.toml
expect all "a manifest beside a source file" gsd/x src/lib.rs Cargo.toml
```

**6. The shortcuts are not iconless today, and the change is smaller than the
requirement's title suggests. Say so rather than claiming a fix.**
`build.rs:34` calls `res.set_icon("assets/icon.ico")`, so `wixen-mail.exe`
carries the icon in its resources. Inno's own help for the `[Icons]` section:
"If this parameter is not specified or is blank, Windows will use the file's
default icon."
[CITED: jrsoftware.org/ishelp/topic_iconssection.htm] So both shortcuts already
show that icon.

**7. There is no `.ico` installed to `{app}` today, which the research does not
say and which decides what `IconFilename` can point at.**

```
grep -n "ico\b|\.ico|assets" installer/Wixen-Mail-Setup.iss
```

returns one line, `SetupIconFile=..\assets\icon.ico` at line 49, and that is the
wizard's own icon, compiled into the setup executable rather than installed. The
`[Files]` section installs `wixen-mail.exe`, `LICENSE`, `README.md`,
`docs\*.md`, the search handler DLL, the search handler setup and the search
handler README. No image at all.

So there are two readings of "IconFilename to the bundled icon" and they differ:

| | what it means | what it buys | what it costs |
|---|---|---|---|
| point at the executable | `IconFilename: "{app}\wixen-mail.exe"` | nothing. It names the same icon Windows already uses by default, so the picture is identical and the line is a comment that compiles | one line, no new file |
| ship the image | a `[Files]` line for `..\assets\icon.ico` and `IconFilename: "{app}\icon.ico"` | the shortcut keeps its icon if the executable ever loses its resource, which has happened here before: `build.rs:30` records "The executable had no icon at all, so Windows drew the generic one" | one file in `{app}`, removed by uninstall with everything else |

**Take the second.** The first is honestly worth nothing and should not be
written up as a fix. The second is testable from a Rust test in the way the
first is not, because a test can assert the installer ships the file the way
`first_run.rs::test_the_installer_ships_the_page_beside_the_program` already
asserts it ships the docs, and no test in this repository can assert the
executable's resource table.

**There is no drift risk in shipping a second copy**, which is the obvious
objection. `build.rs` embeds `assets/icon.ico` and the installer would ship
`..\assets\icon.ico`. One source file, two consumers, nothing to disagree.

**8. `tests/installer.rs` does not exist and costs nothing.** Measured on
2026-09-06 by parsing `tests_last_seen`: no record fingerprints a file that does
not exist, so a new target starts at zero and the count check does not fire.
Compare `tests/house_style.rs`, which 18 records fingerprint. With
`which-checks.sh` widened, an `.iss` commit answers `all` and the whole suite
runs, so the new target is picked up without being named anywhere.

**9. `Cargo.toml` in this plan's file list makes every commit answer `all`.**
That is the manifest rule from premise correction 4 working as intended, and it
means each version-bump commit runs the full gate. Warm, `CLAUDE.md` measures
that at around five minutes; on a cold tree it can exceed a ten minute cap. Run
those commits detached.

**10. `cargo test --lib a --lib b` does not run.** "the argument '--lib' cannot
be used multiple times". The form that runs is `cargo test --lib -- a b`.
