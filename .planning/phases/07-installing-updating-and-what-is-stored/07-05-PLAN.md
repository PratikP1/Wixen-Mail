<objective>
Ask GitHub whether there is a newer version, when somebody asks for it, say the
answer, and give them the one setting that decides whether and what they are
told.

Purpose: the rest of success criterion 2 except applying. Plan 07-04 built the
ordering and the channel-aware judgement; this builds the settings, the asking,
the saying, and a way to reach the releases page. Plan 07-09 builds the
downloading, after signing lands.

Output: one setting a person can find, a check that can be asked, five answers
it can give, a menu item that asks it whatever the setting says, and a privacy
page that is still true afterwards.

answers, rather than argues, the question the earlier version of this plan asked

release before 07-09 exists, and afterwards it is the path 07-09 falls back to

**4. The channel decides which endpoint is asked, and the two endpoints behave
differently enough that this is not a parameter.**

`GET /repos/{owner}/{repo}/releases/latest` "retrieves the most recent
non-prerelease, non-draft release, sorted by the `created_at` attribute", and
lists 200 and 404 as its statuses.
[CITED: docs.github.com/en/rest/releases/releases]

So the **public** channel asks that endpoint and gets prerelease exclusion for
free from GitHub. The **development** channel cannot use it, because it would
never see an alpha; it asks `GET /repos/{owner}/{repo}/releases`, which lists
releases including prereleases, and takes the newest by 07-04's ordering rather
than by trusting the list order.

Three consequences, all of which have to be handled rather than discovered.

**Today both would find nothing**, because there are no releases at all:
`git tag` returns zero tags in this repository. So the very first answer this
feature can give is "nothing is published yet", and if that is mapped to an error
or to "you are up to date", the feature is wrong on the only case that exists
right now.

**On the public channel, 404 does not mean there is nothing.** It means there is
no full release. If the repository holds only prereleases, the public channel
gets a 404 while the development channel would find something. So the
"nothing published" sentence must differ by channel: on the development channel
it can say nothing has been published; on the public channel it must not deny the
existence of prereleases, and should name the setting that would show them. This
costs a wording rule rather than a second request, and a second request is the
wrong answer because it doubles what goes to GitHub for a case nobody is in.

**The list endpoint is paginated and ordered by creation, not by version.**
Do not take element zero and call it the newest. Sort by 07-04's ordering, refuse
the entries it cannot read rather than dropping them silently, and say in the
summary how many entries were considered and what bounds that.

**5. An unauthenticated request is rate limited per IP address, and that is the

unauthenticated requests is 60 requests per hour" and "Unauthenticated requests
are associated with the originating IP address, not with the user or application
that made the request."
[CITED: docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api]

`docs/privacy.md`, in its opening paragraph at lines 6 and 7, currently says
there is "no analytics, no telemetry, no crash reporting service and no update
check that says who you are". A check that sends no account and no identifier
does not say who you are, and it does put an IP address and a rough
version-to-user mapping in front of GitHub. **D-07 settles the direction rather

page says plainly what is sent and what GitHub keeps." The remaining judgement is
the wording, and the summary has to quote what was written and say why it is
honest against GitHub's own sentence.

Rate limiting is also a real outcome. Sixty requests an hour from one IP is
generous for one person and is reachable from an office or a shared connection,
and GitHub answers it with a 403, the same status as a bad User-Agent. Decide
whether the two are told apart and say how.
