<objective>
Let somebody act on "there is a newer version": download the installer, verify it
is really from this project, and run it.

Purpose: SHIP-02's title, "Check for and **apply** updates", and
`.planning/decisions-2026-09-06.md` decision 7, which chose a real self-updater
over the browser link plan 07-05 recommended.

**This is the largest single increase in attack surface in the milestone**, in
D-07's own words: it makes this program fetch an executable and run it. The
decision says so and takes it knowingly, and it says how to make it worth doing:
sign first, then update. That ordering is in `depends_on` rather than only in
prose, and it is structural rather than cautious. Without plan 07-08 there is no
publisher name to expect, and a signature check with nothing to compare against
accepts an installer signed by anybody at all.

**D-16 makes that dependency heavier, not lighter.** The fetch is now unattended:
with a channel chosen, the program checks, downloads and verifies on its own, and
asks only before running. So the bad file is already on somebody's disk before any
person is involved. There is no moment where somebody looks at a URL and thinks
better of it. The whole of what stands between a stranger's installer and a run is
a comparison against a name that only exists because 07-08 bought a certificate.
Say that where the dependency is declared, and say it in the summary too.

Output: a download that is verified before anybody is asked about it, a refusal
that is louder than the success, a named place the file lives and a rule for
clearing it, and a privacy page that says both where the bytes come from and that
they arrive unasked.
</objective>

Checked against the working tree on 2026-09-06, command first. The external
facts about the `windows` crate were read out of the vendored source this
session rather than recalled.

**1. Verifying a signature is not the check. Verifying whose signature it is, is
the check.** This is the mistake this whole plan is arranged around.
`WinVerifyTrust` answers "is this file validly signed by somebody a trusted root
vouches for". Millions of files pass that. The question worth asking is "is this
file signed by the certificate subject plan 07-08 signs with", and it needs a
second call to read the signer's name out of the certificate.

**A verification step that stops at `WinVerifyTrust` is worse than no
verification**, because it produces a program that says "verified" before running
an executable somebody else signed. If only one of the two checks can be made to
work, nothing runs and the plan says so.

**2. Both APIs are already available and no new dependency is needed. Measured,
not assumed.** The `windows` crate is a dependency at `0.62.2`, pinned in
`Cargo.toml` under `[target.'cfg(windows)'.dependencies]` with six features
enabled. The two needed here are not among them and do exist:

```
grep -n '^Win32_Security_WinTrust\|^Win32_Security_Cryptography' \
  ~/.cargo/registry/src/*/windows-0.62.2/Cargo.toml
grep -rn 'pub unsafe fn WinVerifyTrust' \
  ~/.cargo/registry/src/*/windows-0.62.2/src/Windows/Win32/Security/WinTrust/mod.rs
grep -rn 'pub unsafe fn CertGetNameStringW\|pub unsafe fn CryptQueryObject' \
  ~/.cargo/registry/src/*/windows-0.62.2/src/Windows/Win32/Security/Cryptography/mod.rs
```

On 2026-09-06 those returned the two feature lines, `WinVerifyTrust` and
`WinVerifyTrustEx`, and both certificate functions. `WINTRUST_ACTION_GENERIC_VERIFY_V2`,
`WTD_CHOICE_FILE`, `WTD_UI_NONE`, `WTD_REVOKE_WHOLECHAIN`, `WTD_STATEACTION_VERIFY`
and `WTD_STATEACTION_CLOSE` are all present in the same module.

**Re-run those greps before writing the code** rather than trusting this. The
pinned version could move, and a feature that exists at one version is not a
feature that exists at another.

**Why this matters beyond convenience.** The three ways to get this capability are
not equivalent on trust. A new crate adds a maintainer to trust and a supply chain
to audit. Shelling out to `powershell Get-AuthenticodeSignature` adds a process
boundary and a parse of another program's output, which changes format when
Microsoft decides it does. Two feature flags on a crate already vendored, pinned
and audited add compiled code from a source already accepted.
`CLAUDE.md`'s dependency rule and the `dependency-audit` skill both point at the
third. **Say the measurement in the summary rather than the conclusion.**

**3. This must compile where `WinVerifyTrust` does not exist, and the non-Windows
path is the most dangerous three lines in the phase.** `CLAUDE.md`: platform
code sits behind `#[cfg(target_os = "windows")]` with a fallback that keeps the
crate building. Plan 07-06 builds this crate on Linux and macOS, so the fallback
will really be compiled.

**The fallback must refuse.** On a platform with no way to check a signature,
nothing is downloaded and nothing is run, and the reason is said. A fallback that
returns "verified" so the code path stays uniform is the single worst line that
could be written in this phase, and the shape of the code invites it, because
every other platform fallback in this tree returns a harmless nothing. Write a
test that the non-Windows path refuses, and say in the summary that it was
written for that reason.

**4. The single-instance mutex is what stops the installer, and it makes the
handover order a real question.** `installer/Wixen-Mail-Setup.iss` sets
`AppMutex`, and `src/main.rs` holds a named mutex and a hand-over pipe so a second
start hands over to the copy already running. Its comment at line 212 calls the
mutex the uninstaller's stop and the rest the backstop.

So a running Wixen Mail blocks its own installer. Two orders, both with a real
failure:

- **Launch the installer, then close.** The installer may reach the mutex check
  before this process has gone, and refuse. Whatever waiting is done has to be
  bounded and has to say something if it runs out.
- **Close, then launch.** The process doing the launching is the one closing, so
  the launch has to be detached and survive its parent, and if it fails there is
  nothing left running to say so.

**Read `src/main.rs`'s mutex handling before choosing**, decide, and say what the
rejected order would have cost. Say what somebody hears in the moment between the
two, because that is a moment where the program they were using disappears.

**4a. Verify before asking, and it is a rule about who is asked what rather than
an order of steps.** D-16 settles the shape: with a channel chosen the program
"checks, downloads and **verifies** the installer on its own, then **asks before
running it**", so the fetch is unattended and the install is not.

**State it as a rule, because an ordering can be reordered and a rule cannot.**

> Nobody is ever asked to approve a file that is already known to be bad.

The reason, which belongs in the code beside it: a question implies the answer
could reasonably be yes. Offering somebody "this installer could not be verified,
run it anyway?" moves a decision the program is equipped to make onto a person who
is not, at the exact moment they are most likely to say yes, because they asked
for an update and this is the thing standing between them and having one. A
program that has already established the file is not from this project has all the
information the person would have and more.

**Carry it in the types rather than in the sequence.** The function that asks
takes the verified outcome as its only argument, exactly as the run path does.
Then there is no ordering to get wrong, no later edit that can move the question
earlier, and no code review that has to notice. Task 2's test about there being no
path from an unverified file to the run path covers the asking as well as the
running, and it must say so.

**4b. The unattended fetch changes what the person is asked, and it is one
question, not two.** Before D-16 the shape was: tell somebody there is an update,
ask whether to fetch it, fetch it. Now the fetch has already happened, verified,
by the time anybody is involved, so the only question is whether to run it now.
Ask that one question. Do not add a second one about downloading, and do not ask
again after verifying; a person who is asked twice about one thing learns to
answer without reading.

**4c. The Help menu path runs whatever the setting says, and it takes the same
route.** D-16: "the update can also be started by hand from the Help menu,
whatever the setting says", and it is the deliberate path criterion 2 asks for.
Plan 07-05 built that item and decided that with the setting on not looking it
asks the public channel. This plan extends what happens after its answer; **it
does not add a second menu item**. One id, one item, one route, and the route is
the same for the automatic and the manual case, which is also why there is only
one thing to test.

**5. Where the file is written is a security decision, not a housekeeping one,
and D-16 makes it a promise as well.** A downloaded executable placed in a
directory other local users can write is a file another user can replace between
the verification and the run. Put it somewhere only this user can write, under
this application's own directory rather than a shared temporary one, and verify
the file at the path it will be run from rather than verifying one path and
running another.

**Add it to `src/common/paths.rs` as an accessor, and adding it is the RED half
for free.** Plan 07-01 task 3 builds a check that every path `paths.rs` hands out
is named in both `docs/installing.md` and `docs/privacy.md`, by calling each
accessor against a temporary root rather than by grepping the source, so it cannot
miss one. Adding the accessor therefore reddens 07-01's check on arrival, and the

RED commit's trailers, by the name `07-01-SUMMARY.md` records. `src/common/paths.rs`

**Under the application's own root, and one of the reasons is a sentence already
on the page.** `docs/privacy.md`'s "Uninstalling" section says uninstalling
"removes everything: the program, your accounts, your settings, the downloaded
mail, and your saved passwords and sign-in tokens". A downloaded installer under
the root goes with the rest and that sentence stays true. One in a temporary
folder does not, and would need the sentence weakening. **Confirm by reading what
the uninstall really removes** rather than assuming the root is cleared wholesale,
and say in the summary which it was.

**Three rules for clearing it, and the third is the one that gets forgotten.**
Delete it after a successful handover. Delete it on refusal, because a rejected
installer left on disk is a file somebody may find and run by hand having been
told the program would not run it. And **clear the directory at the next start**,
because the process can die between downloading and handing over, and neither of
the first two rules runs then. Say where each of the three happens, and say what
the directory holds at most, which should be one file.

**6. The response has to be bounded and the redirect has to be watched.** A
release asset URL redirects to a content host. Follow redirects, but bound how
many, refuse a redirect to a scheme that is not HTTPS, and bound the total bytes
read so a hostile or broken response cannot fill the disk. Say in the summary what
the bounds are and what happens at each.
