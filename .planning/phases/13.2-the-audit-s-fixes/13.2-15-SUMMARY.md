# Phase 13.2 Plan 15: A browser sign-in's token goes only to its provider and is kept only for the account asked for

A Google or Microsoft sign-in is now refused before any token is fetched when the account names a server the provider does not run, every browser sign-in tells the provider which address to use, and a Google sign-in made as somebody else keeps nothing.

## Deviations from Plan

**1. [Premise] Google's page says "usually".** Premise 4 said the primary calendar's id is the signed-in address. Google's "Calendars and events" page, last updated 2026-09-03, says it "usually matches the user's primary email address"; `calendars.get`, last updated 2026-05-12, lists the calendar scope both sign-ins ask for. So a Workspace account entered under an alias is refused with its main address named. The changelog and Help say so, and ledger 869 asks Pratik.

**2. [Rule 2] A plus suffix on a Gmail address is ignored too**, beyond the plan's rows, since Gmail delivers `me+x@gmail.com` to `me@gmail.com`; a row holds it, and an organisation's domain keeps the plus.

**3. [Rule 2] A Google sign-in Google says nothing about is refused**, with a sentence pointing at the Calendar API in Help, rather than kept unchecked. Help's page gained a line for it and for the wrong-account refusal, and step 7 names the address to choose.

**4. [Rule 2] The Account Manager's log line after a sign-in named the address**; it names the account's id now (T-13.2-12-05).

**5. [Shape] The separate sign-in's answer carries the address**, `SignsIn { key, address }`, so its sentence can name it; three existing assertions changed with it in the red. The census reading `.authorize()` in `who_holds_the_calendars` reads `.authorize(` since the call takes an argument.

**6. [Rule 2] The one-check census names the new caller**, `a_server_its_provider_does_not_run`, as its header asks of a plan that adds one; `tests/one_check_says_who_runs_the_mail.rs` was not in the plan's file list.
