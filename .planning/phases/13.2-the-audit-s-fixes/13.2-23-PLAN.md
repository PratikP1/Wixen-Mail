<objective>
Write the settings the way the mailbox export already writes its files:
beside the target, flushed, then renamed over it. Today `fs::write` empties
`app_config.json` and then writes it, so a power cut, a crash of Windows or a
forced reset in that moment leaves an empty or zero-filled file, and from
then on every load fails: Allow Changes answers nothing for every account,
the theme, columns, mute and kept mail read as defaults, and the setters that
load first refuse to save.

Purpose: audit finding #7, unreported to Pratik, verdict "should"; his
request of 2026-10-14 is every item that needs fixing.

Output: the helper, its cases, the guard record, the changelog, a ledger row
for what the verdict left out, and the completion marks. No requirement in
`.planning/REQUIREMENTS.md` covers how settings are written (FOUND-12 is how
fast Settings opens, FOUND-17 the spelling language), so this plan names
none and adds no requirement line.
</objective>

**2. Who saves, and from which thread.** `git grep -n '\.save()' main -- src`
outside `config.rs`'s tests names `wx_account_manager.rs:1524`, `:1574`,
`:1775` and `wx_app.rs:36040`, and `load` saves the default itself when no
file exists (`config.rs:1157`), which a worker's `load_stored` can reach on
a first run. The executor lists every caller with the thread it runs on,
reading each in context, and says whether two saves can run at once; if
they can, the writes are serialised with one process-wide lock rather than
by unique file names, which would leave a trail of unfinished files.

**3. Where the audit was wrong, from its verdict.** A normal Windows shutdown
flushes its cache, so the empty file needs a hard power loss, a crash of
Windows or a forced reset within seconds of a save, not "the window closes
while Windows shuts down". The first-run question is skipped, not asked
again (`wx_app.rs:36026`). The read during a save on another thread is real,
lasts one read and fails safe. The account files are rewritten only where
`load` found them, since nothing in `src` adds to `account_configs`. And
`sync_all` before the rename is required: a rename without it can still
leave a zero-filled file after power loss on NTFS.

**4. What the verdict left out.** Nothing on screen says the settings could
not be read; only the log does, and Settings then opens on defaults and
writes over the file. The verdict calls telling the person "a separate,
larger change". With this plan the file can no longer be left half written
by a save; it can still be unreadable for other reasons (a disk fault, a
hand edit). A ledger row records that, for Pratik to schedule.
