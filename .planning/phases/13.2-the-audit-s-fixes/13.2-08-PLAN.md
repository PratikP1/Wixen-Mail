<objective>
Make every new message reach the rules once: all of a large arrival is
fetched and sorted by the check, and a message a rule files into another
folder is one row there, not two.

Purpose: finding #12 (reported as R8) and finding #10 (reported as R7).
The check keeps only the newest 500 of what arrived, and on a resumed folder
the next check starts above the new top, so the rest come in through the
download, which runs no rules: after a week away, a blocked sender and a
filing rule miss everything but the newest 500, and the count says 500.
And a rule's move leaves its row at a reserved number marked as filed here,
which the next read of the destination never matches, so every message a
rule files shows twice there for good.

Output: the bounded fetch corrected, the moved row settled, the cases, the
changelog, the ledger, the four marks, and the pull request.
</objective>

**1. The bound on a check's fetch.**

```
git show main:src/application/mail_sync.rs | grep -n -E "pub const INITIAL_FETCH_LIMIT|^fn uids_to_fetch|let wanted = uids_to_fetch|apply_rules\(cache, rules, &arrived\)|WhatToAskFor::TheUidsAbove\(highest\)"
  -> :49 INITIAL_FETCH_LIMIT = 500; :389 uids_to_fetch (newest first, cut at limit, :401-403)
  -> :1860 the call in sync_folder; :1878 the rules over what that call stored; :568 the resume above the highest held
```

The verdict traced the rest: every check that went through asks for the
download (`wx_app.rs`, the end of `spawn_mail_sync`), and the download's
chunk calls `sync_folder(..., None, MoreOfWhatIsAlreadyThere)`
(`wx_app.rs:29995-30008`), which runs no rules; on Gmail, which reports no
modification sequence, the download takes the gap the same way straight
after the check. The check's "N new messages" and `WhatArrived` count only
what the check fetched. The fix changes `uids_to_fetch` alone: when
anything is held, every missing uid above the highest held is taken, and
`limit` bounds only the missing uids below it; when nothing is held the
newest 500 stay the bound. `fetch_headers` already splits a uid set into
pieces a server takes (`sequence_set::chunks`). The six existing cases at
`:6550-6584` keep their answers under the new rule; the executor runs them
to show it.

**2. The cost the verdict named, and the choice taken.** A bulk copy of
tens of thousands of messages into one folder from another client now
arrives in one check as one fetch and one insert. The verdict offers a loop
of fetch, store and rules in batches of 500 within the check if that is too
much. This plan takes the single fetch: every message above the newest
held one is one the person has not seen, the rules have to see all of them,
and `upsert_messages` already writes a batch in one transaction. If a run
shows otherwise, the batching is the way, not the cap; the summary says
what was seen.

**3. The rule's move.**

```
git show main:src/application/mail_sync.rs | grep -n -E "^async fn carry_out_the_moves|Moved::Moved\) => \{\}|cache.move_message\(moving.message_row, into.id\)"
  -> :1300 carry_out_the_moves<M: Mailbox>; :1347 Moved::Moved; :1370 the row moved here and nothing more

git show main:src/application/moves_waiting.rs | grep -n -E "async fn settle_the_row|trait ReplaysAMove|async fn where_it_is"  -> :931, :524, :534
```

`move_message_from` gives the row a reserved number and the filed-here
marker; `stored_uids` leaves marked rows out and `forget_message` refuses
them (`messages.rs:2113-2137`), so the next read fetches the message under
its new uid as a second row. The manual move's replay settles its row in
`settle_the_row`; the rule's path never did. The fix is the verdict's: the
bound becomes `M: Mailbox + ReplaysAMove`, which `sync_folder` already
carries (`:1719`), and after `Moved::Moved` and `cache.move_message`, the
row is settled the way `settle_the_row` settles one. The audit's claim that
the reserved-number row cannot be opened was not traced by the verdict and
is not relied on here.

**4. One settling function.** `settle_the_row` (`moves_waiting.rs:931-962`)
takes an `AWaitingMove`. Its body, from "a row already gone here" to the
two outcomes, is moved into a function of the row, the destination path
and the account, which `settle_the_row` and `carry_out_the_moves` both
call, so the two cannot come to settle differently. No anchor lies in
`:920-963` (premise 7).

**5. The test that seemed to lock the duplicate in.** The verdict says
`messages.rs:3209`,
