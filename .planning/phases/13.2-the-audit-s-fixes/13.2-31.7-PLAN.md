**5. Why the names break.** zip 7.2.0 kept entries keyed by the decoded name
(`zip-7.2.0/src/read.rs:40`, `IndexMap<Box<str>, ZipFileData>`) and decoded a name with the
UTF-8 flag through `from_utf8_lossy` (`:1456-1464`); 9.0.4 keys them by the raw bytes
(`zip-9.0.4/src/read/zip_archive.rs:31`, `IndexMap<Box<[u8]>, ZipFileData>`), `by_name` and
`index_for_name` look up `name.as_bytes()` (`:545-547`), and `name()` answers the bytes as
UTF-8 when they are, and otherwise reads them in code page 437, the old DOS alphabet
(`types.rs:122-131`). So a name that is not UTF-8 comes back as text whose bytes are not the
key. Measured on 9.0.4 directly: an entry named `Entw` 0x81 `rfe.mbox` with no UTF-8 flag
comes back as `Entwürfe.mbox`; `by_name` with that answers `FileNotFound`; `by_index(0)`
reads it. Three archives, each also on 7.2.0 as the control:

- The existing fixture (`mailbox_archive.rs:2314-2333`, `W\u{f6}rk` with the letter replaced
  by 0xFF 0xFE): 7.2.0 names it `W\u{fffd}\u{fffd}rk.mbox`, two stand-in characters, and reads
  it; 9.0.x names it `W\u{a0}■rk.mbox` and cannot read it by that name.
- `Entw` 0x81 `rfe.mbox`, no UTF-8 flag, written with an ASCII stand-in and the stand-in byte
  replaced where the whole name occurs, in the local header and the central directory: both
  versions name it `Entwürfe.mbox`; 7.2.0 reads it, 9.0.x does not. This is the case people
  have.
- Two names that differ only in bytes that are not UTF-8 (`W` 0xFF 0xFE `rk.mbox` and `W` 0xFE
  0xFF `rk.mbox`): 7.2.0 makes them one entry, `len()` 1, so one folder's mail is left out
  without a word; 9.0.x holds both and can read neither by name.

With each entry read from its place (`by_index`) rather than its name, all three read their
mail on 9.0.4 in the probe. That is the advice in zip-rs/zip2 issue 1080, open, filed
2026-10-16, which reproduces the round trip on 8.6.0 and 9.0.4; its pull request 1085, a

**6. Why the lying size is refused, and how the refusal is told apart.** zip 9.0.1 added
"fail reads that exceed the declared uncompressed size" (#1022). In 9.0.4 the reader of every
entry is `Crc32Reader` (`zip-9.0.4/src/crc32.rs:7-52`), which counts what comes out and, once
it passes the recorded size, fails the read with
`std::io::Error::new(std::io::ErrorKind::InvalidData, "File is larger than its declared uncompressed size")`
(`:43-52`). There is no `ZipError` variant for it: measured with the archive the test builds
(200,000 bytes written, the recorded size changed to 10 with the real checksum),
`ZipArchive::new` and `by_index` both succeed on 9.0.4, whichever version wrote the file, and
the first read past ten bytes fails with that `io::Error`, kind `InvalidData`. On 7.2.0 and
9.0.0 the same read succeeds. In `mailbox_archive.rs` the failure arrives in
`a_zip_looked_over` (`:357-362`), where `how_it_begins` reads the first 64 KB of each entry;
it is counted by `one_could_not_be_read` (`:484-487`), and when no entry could be read,
`WhatWasFound::nothing_at_all` (`:495-503`) answers `stops_partway_through` (`:276-282`).

The zip error does not let the size case be told apart by type: its payload is a private
string. The kind does tell apart what the sentence needs. Measured on 9.0.4, three damaged
archives each fail with kind `InvalidData`: the lying size ("File is larger than its declared
uncompressed size"), a stored entry with one byte changed ("Invalid checksum", `crc32.rs:66`)
and a packed entry with sixteen bytes of its compressed data changed (also "Invalid
checksum", after 528,887 bytes came out). On 7.2.0 the second and third give the same kind
and the first reads whole. So `std::io::ErrorKind::InvalidData` from reading an entry means
"what came out does not match what the archive records", whichever check caught it, and the
sentence is worded for both: damaged or changed after it was made, never cut short. A file
that is cut short fails earlier, at `ZipArchive::new` (`:310-316`), and keeps its own
sentence. On 7.2.0 the checksum case already reaches `nothing_at_all` and says "stops partway
through" today, which is the red this plan's first task starts from.
