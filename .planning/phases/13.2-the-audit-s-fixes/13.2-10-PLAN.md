<objective>
Run one check per account at a time, so new mail is announced once and
the rules run once, and make a check's flag pass read the account once
instead of once per message.

Purpose: finding #15 (reported as R19) and finding #14 (not reported).
Only the schedule reads `last_checked`; F9, start-up and a watch waking each
start a worker regardless, and two workers on one account take turns on its
session command by command, both read what is held before either writes,
both fetch the same messages, both run the rules, and both say what
arrived: "1 new message" and the new-mail sound twice. And on a server with
no modification sequence every check reads the flags of every held message
and makes about six statements per message, re-reading the account and its
labels each time.

Output: the per-account turn, its reading, the lighter flag pass, the
duplicate lookup gone, the changelog, the ledger, the four marks, and the
pull request.
</objective>

The four callers are F9 (`:5186`), start-up (`:6657`), the schedule
(`:27698`) and a watch waking (the MailboxChanged arm). The audit's fix, a
set of accounts in flight with a "check again" mark cleared by the worker,
is not taken: the worker leaves an account by about eight `continue` paths
and one early return, and missing one blocks that account for the session.
The verdict's fix is taken: a per-account `tokio` mutex beside
`the_sessions_being_held`, its owned guard taken with
`handle.block_on(lock.lock_owned())` at the top of each account's pass
(before the POP branch, so a POP account is checked one at a time too), and
held to the end of that pass. It releases on every `continue`, return and
panic. Every caller passes accounts in list order and nothing else is
taken inside it, so it cannot deadlock; a crossing uses the other account's
session, not its turn.

**2. Why a second check then says nothing.** It reads `stored_uids` after
the first has written (`mail_sync.rs:1770`, `:1871`), fetches nothing, and
`what_arrived` gives `None` when nothing arrived, so no `WhatArrived` is
sent and the arm at `wx_app.rs:23218` signals and announces nothing.

The verdict corrected the audit twice. The contention claim is wrong: with
WAL, `synchronous=NORMAL` and a five-second busy timeout (`mod.rs:1443-1445`)
an autocommit statement holds the write lock for one indexed update and a
no-change update writes nothing, so the interface's writes are not queued
behind the pass. And the audit's fix, one transaction around the loop,
would make that worse, holding the write lock for the whole pass of every
held message; it is not taken. What is taken: the account and its labels
that carry a keyword read once per folder, the row looked up once per
message, label matching skipped when no label carries a keyword, and the
two per-message statements prepared once (`prepare_cached`). That takes a
message from six statements to two, three where keyword labels exist. This
is a cost change with the same results, so the existing cases are its
guard, and the new form of label matching is a new function written test
first.

**4. folder_account.** Its callers are `mail_sync.rs:1613` and `:1991` and
