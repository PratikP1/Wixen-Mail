# Phase 13.2 Plan 25: The gate tests the commit it judges Summary

A commit made through the hook is now refused, before rustfmt, when a file the build or the
tests read differs on disk from what it stages or sits untracked, with the files named and the
two ways forward. A red commit whose test program crashed part way is refused with a line
saying how many binaries stopped, rather than read as clean. Both suites are green in the hook
on this branch, and every commit after the first green ran under the new refusal.

## What works now

- **Finding #40.** `scripts/check.sh` asks, when `--message-file` is given and after the mode
  is settled, `git diff --name-only` and `git ls-files --others --exclude-standard` over
  `:(top)` less `.planning`, `docs`, `guards` and `:(top,exclude,glob)*.md`. Either answer
  refuses with exit 1, up to five paths and a count, the mode it would have run, and "stage
  them, or `git stash --keep-index -u`". By hand nothing is refused. Eleven cases in
  `check.test.sh`, each from a repository of its own: a tracked `src/` file changed, the
  refusal's words, untracked files under `src/`, `tests/`, `locales/` and a `src/notes.md`
  (refused); changes under `docs/`, `.planning/`, `guards/` and a root `README.md`, and a run
  by hand (not refused, reaching `== rustfmt ==`).
- **Finding #44.** `verdict` in `scripts/red-commit.sh` counts `     Running ` and
  `test result: ` lines in its reading loop and adds a problem when more started than
  finished. Six cases in `red-commit.test.sh`. A real scoped log (`--lib
  application::allowed::` then `--test installer --test house_style`) read 3 started and 3
  finished, so no ordinary run trips it.

## Deviations from Plan

**1. [Rule 1] The binaries are counted in the reading loop, not with `grep -c`.** The plan
said `grep -c` on the right of an assignment. Under `set -euo pipefail` a count of nought
makes `grep -c` exit 1 and stopped the script; the first green turned four existing cases
red ("exactly the named tests failed" among them). Counting inside the loop that already
reads every line avoids both that and an or-true.

**2. [Plan] Only the cases that fail were named in each red.** Five of the eleven `check`
cases (the four exclusions and the run by hand) and three of the six `red-commit` cases (every
binary reported, shell lines, the name that never ran in a crashed binary) hold today's
behaviour and were green on arrival, so `red-commit.sh` would have refused naming them. Each
red message says which.

**3. [Plan] Dated 2026-10-18, not 2026-10-14.** The plan asked for CLAUDE.md's sentence dated
2026-10-14, the day it was written; the change landed 2026-10-18, so CLAUDE.md, the ledger
line, FOUND-23's line and the scripts' comments say that day.

**4. [Plan] STATE's plan number is 27.** As 13.2-23 and 13.2-24 record, it counts the plans
done; `completed_plans` moved from 283 to 284.

**5. [Plan] CLAUDE.md also names the crash count.** One sentence beside the refusal, since
the same paragraph is where somebody looks to learn why the gate refused a red.

No changelog entry: nothing a person using the program sees changes. No pull request: nothing
spoken or shown changed. No guard record names these scripts, read 2026-10-14; the suites are
the guard. Nothing installed.

## What an unstaged change outside the refusal can still do

A change left unstaged under `docs`, `.planning`, `guards` or in a root Markdown file is still
read from disk by the document-reading targets and by the whole-tree readings of planning
files, so it can still turn a commit red that does not hold it, or green over a document the
commit does not carry. That is ledger 325's question and stays open.
