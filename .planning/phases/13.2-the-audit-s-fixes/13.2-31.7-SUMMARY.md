# Phase 13.2 Plan 31.7: zip 9.0.4, entries read from where they were found, a damaged archive said plainly Summary

zip moved from 7.2.0 to 9.0.4 so the audit names no zip advisory; every zip entry is read
again from the place it was found, so a folder named in the old DOS alphabet still brings its
mail in; and an archive whose contents do not match what it records is refused with its own
sentence rather than told it stops partway through.

## What works now

- Cargo.lock holds zip 9.0.4 alone. `.cargo/audit.toml` accepts five ids, none of them zip's.
  The move's commit ran the full gate through the hook, and its audit said: "All 5
  advisory(ies) this project accepts are still reported." and "No advisory outside
  .cargo/audit.toml, and nothing is being held open."
- An archive whose only entry fails its check, or whose recorded size is smaller than what
  it holds, is refused when it is looked over with: "{file} is damaged or was changed after
  it was made. What is inside it does not match what the file records about it, so nothing
  was imported from it." (the format in `does_not_match_what_it_records`; the case asserts the
  path, "is damaged", "changed after it was made", "nothing was imported" and the absence of
  "stops partway through" and "another copy"). A cut-short archive keeps "stops partway
  through".
- A zip holding `Entw` 0x81 `rfe.mbox`, no UTF-8 flag, brought in with `an_archive_brought_in`
  lands as `Entwürfe` under Imported with both its messages, on zip 7.2.0 before the move and
  on 9.0.4 after it.
- Two entries whose names differ only in bytes that are not UTF-8 are two entries, each read
  to its own mail; zip 7.2.0 made them one.
- A name not written as UTF-8 logs one warning: "the name {named} in {archive} was not written
  as UTF-8, so it is read in the old DOS alphabet and may not say what its writer meant".
- Every archive limit holds on 9.0.4: in the move's hook run the library passed 9,323 tests
  with 5 ignored, and no target failed; `service::mailbox_archive::` 46, `application::importing_messages::` 52,
  `sound_scheme_import::` 17, `what_an_export_holds::` 5, `exporting_mail::` 7 and
  `outlook_data_file::` 56, 183 in all, pass.

The reason is decided by the error's kind alone (`23c0bbbc`):

```rust
impl From<&std::io::Error> for WhyAnEntryWasNotRead {
    fn from(why: &std::io::Error) -> Self {
        match why.kind() {
            std::io::ErrorKind::InvalidData => Self::ItDoesNotMatchWhatTheArchiveRecords,
            _ => Self::ItCouldNotBeRead,
        }
    }
}
```

## Deviations from Plan

1. **[Shape] One guard record for the read from the found place, not two.** The plan asked for
   one record per read, each going back to `by_name(named)`. Both reads now open an entry
   through one function, `the_entry_opened`, which also takes over the old `holds` check, so
   there is one `by_index` site and one record whose red list holds the import reading.
2. **[Premise] A newer zip, 9.0.5, was published.** `cargo update -p zip --precise 9.0.4` from
   9.0.5 also rewrote spellbook 0.4.2's dependencies (hashbrown 0.17.1 to 0.15.5, foldhash
   0.2.0 to 0.1.5), which the move did not explain. The lock was restored, the requirement
   set to `=9.0.4` for one resolution and then back to `9.0.4`, and cargo wrote the lock both
   times; the delta above is the result. Ledgered for no one: it is how the lock was written.
3. **[Shape] A shared fixture builder, `mailbox_archive::for_tests`.** The import reading in
   `importing_messages.rs` and the module's own cases build zips whose names another tool
   wrote through one `a_zip_whose_names_another_program_wrote`, and `tests::an_archive` in
   `importing_messages.rs` became `pub(super)` for the reading.
4. **[Shape] The damaging of a stored entry became a helper**, `damaged_at_its_first`, used by
   the existing one-damaged-entry case and the new one.
5. **[Rule 2] Two folder-walk log lines now carry the error.** Typing the reason in `walked`
   needed the error where it was dropped; the "something in" and file-type lines say it.
6. **[Wording] The changelog's third Fixed line** is about a name marked UTF-8 whose bytes are
   not, which 7.2.0 showed with stand-in marks; a name an older tool wrote without the mark,
   such as Entwürfe, read as letters on 7.2.0 too, so it is named as arriving as it did.
7. **[Brief] A banned text tool was typed once, read-only,** as a do-nothing stage on a grep
   pipe while composing a search of `importing_messages.rs`; its output was empty and nothing
   was written. Every tracked file was changed with Edit or Write, by `cargo fmt`, by cargo
   writing the lock, or by `scripts/guards.sh`.

No version moved. No schema change, no setting, no key, no label and no mnemonic letter.
Installed: zip 9.0.4 and nix 0.31.3 from crates.io, the crate and version Pratik confirmed
(T-13.2-31.7-SC).

## Known edge, not fixed

zip 9 keeps entries by the bytes of their names. Two entries whose different bytes read as the
same letters, one written as UTF-8 and one in the old DOS alphabet, are one name to the import,
and asking for it reads the first. The comment on `the_entry_opened` says so; no case builds
it, and no archive met here has it.
