# Phase 13.2 Plan 08: Every new message reaches the rules once Summary

A check after a long gap now fetches every message that arrived, runs the rules over all of them and counts all of them, and a message a rule files into another folder is one row there at the number the server gave it, or comes back once on the next read.

## What changed

**Finding #12.** `uids_to_fetch` partitions the missing uids at the newest one held: everything above it is taken, however many, and the limit cuts only the older mail below it and a first look at a folder holding nothing. The early return for a limit of nothing stays. `sync_folder` and the download's chunk call it unchanged, so the rules in `sync_folder` now see everything the check stored and `FolderSync::fetched` counts it. The six older cases (`:6733-6766` today) pass unchanged.

**Finding #10.** `settle_the_row`'s body is `moves_waiting::settle_a_moved_row(server, cache, message_row, account_id, destination)`. `settle_the_row` keeps only "a delete outright has nowhere to hold it" and calls it. `carry_out_the_moves` is bound `Mailbox + ReplaysAMove` and, after `cache.move_message`, settles the row the same way; when the server will not say where the message is, the row is let go and the failure is logged with the two folder names and the server's words, never a subject. The move still counts as done. The undo (`undo_here`) and the crossing (`settle_the_crossed_row`) keep their own calls, which are about other rows.

`git grep -n settle_a_moved_row -- src`: the definition at `moves_waiting.rs:960`, the call in `settle_the_row` at `:939`, the call in `carry_out_the_moves` at `mail_sync.rs:1398`, the import at `mail_sync.rs:15`, and the dated sentence in the comment of `messages.rs`'s case (premise 5).

## Deviations from Plan

**1. [Rule 1 - Bug] An existing case asserted the duplicate's half.** `test_a_rule_that_files_mail_reaches_the_server_and_this_computer` checked that Invoices held one row after a rule's move, against a server that could not say where it put the message, so the row it counted was the one at the reserved number. Under the fix that row goes, so the case's server now says where it put the message (`finds_it_at: Ok(vec![3])`), with a dated comment. Its meaning, the move reaching the server and this computer, is unchanged. Commit `fb694c7b`.

**2. [Shape] A refused question lets a rule's row go, outside the shared function.** The plan's behaviour line wanted the row gone on an error; the replay's `settle_the_row` propagated one, and its waiting row asks again at the next check. Making the shared function drop the row on an error would have changed the replay. So the shared function hands the error back, and `carry_out_the_moves`, with nothing waiting to ask again, lets the row go. The function's doc says why the two callers differ there and only there.

**3. [Shape] The plan's third `uids_to_fetch` behaviour was already a case.** "Nothing held, a server of 10,000, a limit of 3: the newest three" is `test_a_first_look_at_a_large_folder_takes_the_newest`, unchanged, so it was not written a second time and the red named three tests, not four.

**4. [Rule 1] A stale record found by the re-measure** (above), written 2026-09-28 and short by a test from 2026-10-01; corrected in task 1's green.
