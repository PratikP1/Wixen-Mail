# Phase 13.2 Plan 20.1: An event changed during its push is kept Summary

An event edited while a sync is sending it to Google, Outlook or a calendar server now keeps the
edit on this computer and sends it at the next sync, an event made here and deleted while it is
first being sent is deleted at the other end at the next sync instead of coming back, and one
moved to another calendar meanwhile stays where it was put.

## What works now

- **Finding #1 (R17), events half, as the verdict corrects it.** The three settles,
  `settled` in `application/calendar.rs` (Google and Outlook) and `settled_here` and
  `settled_here_for_an_occurrence` in `caldav_sync.rs`, no longer save the row the push read.
  Each calls `MessageCache::the_provider_holds_the_event`, which reads the row inside one
  immediate transaction and then:
  - unchanged or edited: writes the provider's name, address and version, fills in the
    calendar only when the row has none, and sets
    `pending = CASE WHEN updated_at = ?6 THEN 0 ELSE pending END` with the `updated_at` the
    push read, leaving `updated_at` alone;
  - gone: gives the deletion note written while the event had no name the provider's name,
    calendar and address (`provider_event_id`, `calendar_id`, `event_url`, existing columns);
  - moved to another calendar during its create: leaves the row alone and writes a deletion
    of the provider's copy under a fresh identifier.
- Reached in the running program through `spawn_calendar_sync` in `wx_app.rs`, which runs
  `sync_google_calendar` and `sync_microsoft_calendar` (each pushing through `push_to_google`
  or `push_to_microsoft`, then `create_*_event` or `update_*_event`, then `settled`) and the
  calendar server pass `push_to_the_calendar_server`, then `send_one_change`, then the two
  `settled_here` functions.
- The store's sent-marker for events, `mark_calendar_event_sent`, is gone; its one test is now
  the new write's case. `git grep -n 'mark_calendar_event_sent' -- src tests` prints nothing,
  where `main` printed two lines, and `git grep -c 'save_calendar_event(&settled)'` over the
  two application files prints nothing, where `main` printed 1 and 2.
- **The move case, as the plan asked to report:** the move survives. Under the old code the
  case failed with the calendar written back (`left: Some("cb686a97-...")`, the provider's
  calendar, `right: Some("cal-home")`); it now passes, for Google and Outlook and for a
  calendar server. No ledger row was needed for it.
- Counts, taken 2026-10-17 on the branch: `cargo test --lib data::message_cache::calendar::`
  58 passed (unchanged, one test rewritten); `application::calendar::` 209 (204 plus five);
  `application::caldav_sync::` 80 (74 plus six). Whole library 9,259 passed, 5 ignored.
  Integration targets reading the calendar store, all green:

## Deviations from Plan

**1. [Rule 2] The move during a create is kept and fixed here, not ledgered.** The plan allowed
either. The write can carry it in its own files: a move is detected when the push read no
provider name and the row's calendar differs from the one read, and it is settled the way
13.2-20 settled a task or note move, with the provider's copy owed a deletion under a fresh
identifier so a later deletion of the event cannot replace it. No waiting column was added,
since `deleted_calendar_events` has none and an event's two halves need no order: the next
push deletes the old copy and makes the moved one.

**2. [Rule 1] One existing test handed the push an event the store never stamped.**
`test_editing_a_caldav_occurrence_exception_sends_if_match_with_the_fetched_tag` saved an edit
and then passed its in-memory copy, whose `updated_at` was the helper's fixed value rather than
the store's. A real push always reads the row from the store, so the conditional clear left
the day waiting. The test now reads the row back before sending, as the push does; its
assertions are unchanged.

**3. [Scope] `src/data/message_cache/mod.rs`, a file the plan did not list,** re-exports the two
new types, `WhatTheProviderHolds` and `TheProvidersVersion`, beside `DeletedCalendarEvent`.

**4. [Shape] `settled` hands back the row as stored, or, when the event was deleted meanwhile,
the copy that was sent under the provider's name.** The only caller that reads it,
`push_to_microsoft`, takes the provider's name off it; the gate's proof test sends an event
the store never held and needs an answer, not an error.

**5. [Plan] `STATE.md`'s plan number is 22, not the plan's 20.1.** The convention since 13.2-01
counts the plans done, and the roadmap row and the planning check agree with it, the reason
13.2-20's deviation 7 gives.

**6. [Plan] The summary was written before the green commit,** because the documents' marks
were already in the tree and the hook's planning check reads it, the refusal 13.2-20's
deviation 9 records.

**7. [Brief] `awk` ran once for real in a read-only count of the test totals the register
records for `caldav_sync.rs`, and a do-nothing `sed_free=0;` assignment sat in one read-only
pipe.** Nothing was written by either. Every tracked file was changed with Edit or by
`cargo fmt`, and the three breaks were taken and undone with Edit.

**8. [Finding] Ledger 883.** `delete_calendar_event` writes its note and removes the row in two
statements with no transaction, so a settle landing between them leaves a provider copy that no
note names. Not seen and not driven by a test; recommended for a later plan.

No version moved and nothing was added to `Cargo.toml` (T-13.2-17.1-SC). No schema change:
every write uses existing columns. No setting, no label, no key and no mnemonic letter. Nothing
spoken or shown changed, so the branch was not pushed.
