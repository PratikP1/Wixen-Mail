**Where the audit and the verdict were wrong.** The finding said pin the
leaf key or its hash; the verdict said that refuses every genuine
release because Artifact Signing issues a fresh three-day certificate
each day, and proposed requiring the "durable identity" EKU
`1.3.6.1.4.1.311.97.<identity validation id>`. Microsoft's page on
Artifact Signing certificate management, read 2026-10-14
(learn.microsoft.com/en-us/azure/artifact-signing/concept-certificate-management),
corrects the second half: certificates "are renewed daily and are valid
for only 72 hours"; the durable value is a custom EKU with the prefix
`1.3.6.1.4.1.311.97.` that "is associated with the certificate profile,
not with the subscriber or identity validation resource"; and "if you
delete the certificate profile and create a new one, Artifact Signing
assigns a new EKU". So the rule requires the certificate profile's EKU,
whose value exists only once Pratik's Artifact Signing account and
certificate profile exist (ledger 329). The constant ships empty, and an
empty constant refuses everything, which changes nothing a person sees
today: no release is signed, so every installer is already refused as
unsigned. The executor reads the page again and quotes it with its date.

**3. What recreating the profile would do.** Once a release ships with
the identifier set, every installed copy accepts only installers carrying
it. A profile deleted and made again gets a new identifier, and every
copy already installed would then refuse every update until somebody
installs a new version by hand. That is a one-way cost for the plan that
sets the value, written into the constant's comment and the ledger
entry here, not decided here.
