# Phase 13.2 Plan 20: A task or note changed during its push is kept Summary

A tick, a due-window completion, a pin or a note edit made while a sync is sending that task
or note now waits and goes up at the next sync, a task or note made here and moved or deleted
while it is first being created stays moved or deleted at the other end, and the notes
editor's Save marks the note waiting so the edit reaches the backend.

## What works now

- **Finding #1 (R17), tasks half, as the verdict corrects it.** `mark_task_sent` takes the
  `updated_at` the push read, always writes `remote_updated` and `remote_status`, and clears
  `pending` only when the row still carries it, in one statement
  (`pending = CASE WHEN updated_at = ?4 THEN 0 ELSE pending END`). `settle` passes
  `was.updated_at`. `rename_task` reads the row inside one immediate transaction: unchanged is
  renamed as before; ticked or completed keeps the local content under the provider's id with
  the provider's stamp and word, still waiting; moved into another list stays as it is and the
  provider's copy is owed a deletion waiting for it; deleted leaves the provider a deletion of
  the copy it made. Reached in the running program through `spawn_tasks_sync` in `wx_app.rs`,
  which calls `sync_google_tasks` and `sync_microsoft_tasks`, both of which run `push_tasks`.
- **Finding #1, notes half.** `a_backend_took_the_note` takes the note as the push read it and
  reads the row inside one immediate transaction: the name and marker always recorded and the
  flag cleared only when unchanged; moved to another folder keeps the move and no name, with a
  removal owed for the copy in the old container, waiting for the moved note; deleted names the
  deletion the window wrote, so the push removes what the backend made. All four callers pass
  the note they hold. `keep_what_the_backend_could` leaves a note whose `updated_at` moved since
  the push read it. Reached through `spawn_notes_sync`, which calls
  `notes_backend::sync_the_notes_of` and so `sync_notes`.
- **The editor gap.** The notes editor's Save calls `the_person_changed_the_note`, one
  statement writing the title, the body, the stamp and `pending = 1`, and no longer reads and
  saves the whole row. `git grep -c 'cache.save_note(&note)' HEAD -- src/presentation/wx_app.rs`
  prints nothing, where `main` printed 1. Its announcements are as they were.
- **The Move command stamps** a task and a note beside `pending = true` in `file_under`.
- How the push's deletion loop reads the column a deleted note gains, quoted from
  `send_the_deletions` in `notes_sync.rs`: `let Some(named) = gone.known_as.clone() else {
  continue; };`, then, where `waiting_for_note_id` is set, `cache.get_note(waiting_for)
  .map(|found| found.is_some_and(|copy| copy.pending)).unwrap_or(true)` holds the removal while
  the copy still waits. `known_as` is the `provider_note_id` column, so a deletion named there
  is sent at the next sync, and the moved note's removal waits for the note to be made. No
  column was added.

## Deviations from Plan

**1. [Rule 2] A move during a create is settled as a move, not written as an update.** The plan
asked for the move to be kept like a tick. Kept that way, the row would carry the provider's
id in the list it was moved to, and the next update would ask the provider for a task in a
list it never put it in, refused on every sync, while the copy in the old list stayed for ever.
So `rename_task` and `a_backend_took_the_note` compare the list or folder too, and a moved row
stays as it is with the provider's copy owed a deletion that waits for it, the state the
existing move of a held task or note already leaves and the push already handles. Held by a
store case and a sync case for each kind and their records.

**2. [Shape] The settle compares the list or folder whatever the stamp says.** So the Move
command's stamp is not what keeps the move; it is held by its own assertion in each sync-level
move case and its own record, which reddens that assertion alone.

**3. [Shape] The deleted-during-create task writes the deletion directly.** The plan said to
write the provider's copy and delete it through `delete_task`. `owe_the_provider_a_deletion`
writes the same deletion note in one statement and also serves the moved arm, so the
provider's copy is never written down only to be removed.

**4. [Shape] The note's removal for a move during its create is under a fresh identifier.**
Under the note's own id, a later deletion of the note would write its own record under that
id and replace this one, leaving the old container's copy named by nothing.

**5. [Shape] The move cases live in the sync modules, not in `managers.rs`.** A test added to
`managers.rs` flags 60 records. `tasks_sync.rs` already drives the Move command through
`file_under` (`move_it`), and the notes case does the same, so the stamp is exercised through
the real command without touching `managers.rs`'s test count.

**6. [Scope] Two doc comments in `src/data/message_cache/mod.rs`**, a file the plan did not
list: `waiting_for_task_id` and `waiting_for_note_id` said they were set only by the moves, and
`known_as` on a deleted note said a nameless record is never work the push owes. All three
now say what this plan adds.

**7. [Plan] `STATE.md`'s plan number is 21, not the plan's 20.** The convention since 13.2-01 is
"Current plan N of 35" naming the next plan, and 13.2-19 left it at 20 with 13.2-20 next; the
roadmap row reads 21/35.

**8. [Brief] Five do-nothing shell assignments named after the banned tools** in read-only
commands (`sed_unused=1`, `awk_free=0 cat`, `sed_unused=;`, `sed_x=0`, `sed_never=1 cat`), the
slip 13.2-19 recorded. No banned tool ran and nothing was written by them; every tracked file
was changed with Edit or by `cargo fmt`, and every break was taken and undone with Edit.

**9. [Brief] A first attempt at the second green commit was refused by the hook** on
`the_planning_files_agree_with_themselves`, because the documents commit's edits to

summary was written and the commit made again.
