<objective>
Stop a stranger's deeply nested HTML from overflowing a thread's stack
and killing the whole program, by checking depth once where the markup
is parsed and reading anything deeper than the limit as its words alone.

Purpose: Pratik's request of 2026-10-14, "I want all of the items that
need to be fixed as a phase including the ones not reported to me",
carries R4 of the audit, finding #17. A body of a few thousand nested
`div` elements arrives from anybody and passes every filter. Selecting
it overflows the window's 1 MB stack, which is not a panic: the process
aborts with no log line, and does it again every time the message is
selected. An HTML-only body does the same on the sync worker when it is
saved, through the snippet, so the message never even reaches the list.

Requirements: LIST-25 (an HTML message read says what the sender showed;
`hidden_text` and the reader's own structure were built under it) and
FOUND-03 (the snippet and the index of an HTML-only message are its
words; `read_markup` is their reader). A dated line under each, adding
no `[D]` clause and touching no box.

Output: the helper and its constant, the three checks with their
fallbacks, the sentence, the 1 MiB proofs, the rewritten and re-measured
guard records, the measurement row, the changelog, the ledger, the pull
request.
</objective>

**4. What the limit is checked against.** The verdict says confirm 512
"in a debug build on a 1 MB stack". Tests run in a debug build, whose
frames are larger than a release build's, and the window's thread is
the smallest stack the program runs on (Tokio's workers and
`spawn_blocking` threads are 2 MiB). So the limit is the largest value
for which markup exactly that deep is walked whole by every walker on a
1 MiB thread in a debug build: 512 if it holds, halved until it does if
not, and the summary quotes the deepest that passed and the first that
did not.

**5. The parse itself is quadratic in depth, and that is not this
finding.** html5ever checks the open-element stack for a `p` in button
scope on every `div` start tag, so parsing n nested `div` elements costs
about n squared steps. The check here runs after the parse and cannot
remove that cost. Task 3 times the audit's message in a release build
and ledgers the figure as found and left, so it is a number on the
record rather than a guess.
