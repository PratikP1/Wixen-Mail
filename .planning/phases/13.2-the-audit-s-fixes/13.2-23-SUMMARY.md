# Phase 13.2 Plan 23: Settings are written whole Summary

The settings file and each account file are now written beside themselves as
`<name>.partial`, flushed with `sync_all` and renamed over the old file, so a power cut or a
crash during a save leaves the old settings or the new ones and never an empty file. A save
that cannot finish returns its error, takes its partial file away and leaves the old file
byte for byte as it was. Audit finding #7 is closed on the tree's side.

## What works now

- **The write.** `save_app_config` and the account loop in `save` call `written_whole` in
  `src/data/config.rs`, which creates `<name>.partial`, writes, calls `sync_all`, drops the
  handle and renames over the target. On any failure after the create it removes the partial
  file and returns the first error, with a failure to remove said beside it, the shape of
  `mailbox_archive.rs`'s `finish`. A comment says why the rename and why `sync_all`.
- **The lock.** `ONE_SAVE_AT_A_TIME`, a `Mutex<()>` taken with `unwrap_or_else(PoisonError::into_inner)`,
  so a panic in one save never stops the next.
- **The load.** Unchanged: it reads only `account_*.json`, and a case holds it to passing
  over half an account file left as `.partial`.
- **Acceptance check.** `git show HEAD:src/data/config.rs | grep -c -E 'fs::write\((self\.app_config_path\(\)|path, content)'`
  answers 0 at the green, 2 on `main`. `cargo test --lib data::config::` passes 73, 68 before
  this plan.

And `load` saves the defaults when no file exists, reached from any `load_stored`, several of
them on workers (`allowed.rs:1059`, `describing_pictures.rs:102`, `html_renderer.rs`,
`managers.rs`). `main.rs:115` loads first at start-up, so the file normally exists before a
worker reads it, but if that first save failed, or the file went away while the program ran, a
worker's default write could meet the window's save. So two saves can run at once, and the
write takes one process-wide lock, with a case: eight threads of forty saves each, red three
runs in three with the lock taken out.

Two copies of the program can also run side by side (`ThisCopy::BesideAnother` in `main.rs`),
and a lock inside one process does not reach the other. Two copies saving in the same
millisecond could still truncate each other's partial file before its rename. Not fixed here;
the window is one save wide and both copies would be writing the same person's settings.

## Deviations from Plan

**1. [Plan] Five records rather than one.** The plan asked for one, whose break puts
`fs::write` back. The two writes are two places and a record breaks one, and the three pins
(nothing unfinished left, a partial account file not read, saves taking turns) were each taken
red by hand, so each has a record.

**2. [Premise] One flagged record disagreed, and is kept as it was.** "a settings file
written before reading was a setting still loads" also reddened
`application::mail_controller::against_a_server_that_answers::test_a_command_that_names_a_different_folder_opens_that_one_first`,
three runs in three. That test reaches `allowed_for`, which reads the real profile, and the
profile on this machine, read with Python, is stamped `0.1.0-alpha.22` and its
`allowed_changes` has no `reading` field, so the break reads it as false. On a runner the
profile is written fresh with the field. The record's own comment says the test was taken off
its list on 2026-09-15 for staying green on the runners. So the list is unchanged, the count
for `config.rs` was written by hand to 73 with a dated comment, and ledger 890 recommends
running the guard measurements with `WIXEN_MAIL_DATA` pointed at an empty folder. This plan
did not cause it: the break is in `allowed.rs` and reads a file this plan's write never
touched.

**3. [Plan] `STATE.md`'s plan number is 25, not 23.** The plan says "`current_plan` and
`Current Plan:` at 23"; the convention since 13.2-01 counts the plans done, which 13.2-22's
summary records and the roadmap's 25/35 agrees with. `completed_plans` moved from 281 to 282.

Settings opens, FOUND-17 the spelling language), so the marks are three and no requirement box
