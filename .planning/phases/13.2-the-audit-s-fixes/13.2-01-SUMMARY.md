# Phase 13.2 Plan 01: Enter opens a message alone in its conversation Summary

Under conversation view, `Enter` on a row whose conversation holds one message among the open
folder's loaded rows opens the row's own message, found by id the way Space finds it and read
from the store when it is filed in another folder; two or more still open the conversation
window on the row's message; and when neither holds it, `Enter` says "That message is no
longer on this computer, so it could not be opened." rather than nothing. Pratik's first
report of 2026-10-14.

## What was done

- **Task 1.** The conversation arm's choice became `what_enter_opens_on_a_conversation_row`
  (`wx_app.rs`, beside `conversation_nodes`), answering `WhatEnterOpens::TheMessage`,
  `TheConversation` or `Nothing`, first as a green extraction with no change in behaviour.
  Three cases in `tests/a_conversation_row_stands_for_one_message.rs` build the rows through
  the store, `MessageItem::from_row` and `apply_threading`: a lone message, a conversation split
  between INBOX and Sent, and a conversation of two with a lone row beside it. The first two
  were red against the extraction (`Nothing` against `TheMessage(1)`), the third green before
  and after. The fix finds the row's message by id through
  `the_loaded_message_the_row_stands_for`, then through `the_stored_message`, one row by
  `message_rows_for`.
- **Task 2.** The activation reading requires the chooser and a `send_refusal(` on its
  `Nothing` arm, with a planted fault for each in the existing complain test; red against the

  page's Conversations table gained two rows and the Thread View row says what `Enter` does

- **Task 3.** The changelog's Fixed entry, ledger 831 to 833, LIST-06's dated line and

## Deviations from Plan

1. **[Rule 2] The split case has two halves.** As written in the plan, the case's row stood
   for the INBOX message the loaded rows already hold, so it went red without reaching the
   store read the green adds: removing the store read alone left it green. The case now also
   builds the conversation with the originator read, so the row stands for the reply in Sent,
   and asserts that `Enter` opens it from the store. Still one test function. The second guard
   record pins that branch. Observation 1008.
2. **[Shape] `TheMessage` holds a `Box<MessageItem>`.** Clippy's `large_enum_variant` refused
   the unboxed item under `-D warnings`.
3. **[Shape] The extraction commit's store parameter was `_cache`,** unused until the fix
   used it, so the red's cases could call the three-argument chooser against an unchanged
   behaviour.
4. **[Shape] The conversation's name is worked out only when a conversation opens.** The
   old arm called `how_a_conversation_reads`, a settings read and a query, before it knew
   whether one or several messages would open; the handler now asks it in the conversation
   arm alone. Nothing it says changes.
5. **[Scope] The re-measure found a sixth record to correct,** the row-message ordering one
   above, which the plan's count of five flagged records could not foresee.
6. **[Shape] Case 3 finds its rows by conversation id** rather than assuming row 0, because the
   listing's order puts the lone row and the conversation of two in an order the case does not
   fix.
7. **[Rule 1] The changelog's first wording was refused by `house_style`.** "The fault dates
   from conversation view becoming the default for a folder you have never set" read to
   `test_nothing_says_a_new_installation_changes_nothing_while_it_changes_contacts` as a
   sentence about what a new installation changes; it now says the fault began when folders
   started showing conversations on 20 September 2026, the date of `478f5885`.
8. **[Wording] The changelog says "about half the rows or more"** where the plan's purpose
   says 47%: REGRESSIONS.md derives 47% as a lower bound from one day's log, so "most rows",
   the first draft, claimed more than the evidence.
