<objective>
Stop the Account Manager deleting an account and undoing the order, and
stop an account that was removed or switched off from being watched and
checked until the program closes.

Purpose: finding #3 (reported as R3) and finding #33 (not reported).
`save_account` writes with `INSERT OR REPLACE`, which deletes any row that
clashes on the unique address before it inserts, and resets the account's
place and the day it was added on every save. Adding the same mailbox
twice silently deletes the first account on the next start and leaves its
password and sign-in tokens in the credential store with nothing able to
name them. And the Account Manager never stops the watch of an account it
removed or switched off, so a switched-off account goes on being checked,
its rules run and its waiting changes sent.

Output: one rule for addresses, the store and the dialog using it, the
order kept, the watches stopped, the readings, the changelog, the ledger,
the four marks, and the pull request.
</objective>

The insert names every account column but `tree_order`, so a replace sets
it NULL and `created_at` to now. Nothing has a foreign key to `accounts`,
so no cascade hides the delete. The audit overstated one thing: pressing OK
with no change saves nothing, because `show_account_manager_dialog`
returns `AccountManagerAction::None` unless something changed
(`wx_account_manager.rs:171-187`). Any add, edit, delete, Set Default or
Set Active does save.

**2. The finding's fix leaves a hole, and the verdict closes it.** With
`ON CONFLICT(id) DO UPDATE` alone, a second account on a taken address
would write its password with `credentials::store` (`:17`) and then fail on
the unique address, leaving a secret with no row, and the spoken error
would be SQLite's own words. So the refusal comes first, before the
credential store, in a person's words. The audit's case compares addresses
exactly; addresses are compared here ignoring case and surrounding spaces,
since `Pratik@x` and `pratik@x` are one mailbox and the column's UNIQUE is
case sensitive.

**3. Two places refuse, one rule decides.** The Account Manager holds the
working list and refuses at Add and at Edit, before `run_oauth_flow`
(`wx_account_manager.rs:533-575` for Add, `:594-640` for Edit), so a
refused account stores no sign-in tokens either; and `save_account`
refuses as the backstop for any other writer. Both ask one function in a
new module, `application::one_address_one_account`, so the two cannot
come to disagree. The store gives it the stored ids and addresses with one
light query, never `load_accounts`, which reads every password
(`accounts.rs:175`). `show_edit` (`:1782`) shows its window once and
validates nothing; its title is Edit Account whenever an existing account
is passed (`:1955-1958`), so showing the typed values again needs a way to
open the Add window filled in, which this plan adds.

**4. The order.** `move_the_chosen_account` (`wx_app.rs:11243-11287`)
writes `tree_order` and reads the tree back from the store, and never
touches `s.accounts`, which is assigned only at start-up (`:970`) and in
`handle_account_mgr` (`:22225`). The sidebar reads the store
(`the_accounts_in_the_tree`, `:14351`), so once the save keeps
`tree_order` the sidebar keeps the order; the Account Manager is opened
with `s.accounts` (`:22132-22152`), so it would still list the old order
until a restart. The window's list is put in the new order in the same
step.
