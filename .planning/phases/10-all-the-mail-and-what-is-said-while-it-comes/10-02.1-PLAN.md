<objective>
Read All Inboxes, a label view and a saved search's results in the sort that
was chosen, the way a folder is read. With All Inboxes open, choosing a sort
from View, Sort Messages re-sorts the rows on screen and saves the choice;
moving to a folder and coming back reads All Inboxes in a fixed newest-first
order, because `load_every_inbox` calls `unified_inbox`, whose query carries
`ORDER BY m.date DESC, m.uid DESC` and takes no order, while a folder is read
through `get_message_list_sorted` with the stored sort in the query (#69).
The label view and the saved-search listing have the same shape.

Purpose: the tester reported #69 on 2026-09-17 against `1.0.0-alpha.1`
(`59c5b6a4`) with the cause diagnosed from the source. The list already
sorts in the database rather than in memory, for the reason
`get_message_list_sorted`'s doc gives: sorting in memory is fine at five
hundred rows and wrong at forty thousand, and the list now holds everything
the folder holds (10-02). So the fix is the order in the query for the three
views that lack it, from the same `the_sort_as` the folder uses, and a
measurement of what a chosen sort costs the combined view, whose fixed order
an index served.

Output: three cache methods taking an order, three loaders asking for it, one
new integration target coupled to four files by measured records, an All
Inboxes series in the scale harness with ten rows on the measurements page,
a changelog entry, a ledger entry, and #69 closed from the merge commit with
what the readings proved and what only the tester's ear settles.
</objective>
