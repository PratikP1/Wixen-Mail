<objective>
Decide, in code that runs without a window and without a server, what
"everything" means for one account and what happens when a provider says no:
which folder's next chunk of headers comes next, which messages' text comes
next, how big a chunk is, in what order, when to stop, and how long to wait
before asking again. Nothing here reaches a person yet; 10-05 wires it and
10-06 asks the same wait rule for the inbox watch.

Purpose: #20 and #23 are one download with one progress story, and #37's
restart needs the same bounded retry the download does. The model comes first
so that every later plan builds on decisions that are tested against the
scripted mailbox rather than discovered in `wx_app.rs`, where a test costs 57
guard records to add.

Output: two new application modules, a chunk-bounded text pass with a stop and
a read of the provider's answer, and the guard records that hold each rule.
</objective>

`sync_folder` pages by uid, not by sequence number: `uids_to_fetch` takes the
newest `limit` uids the cache does not hold and `fetch_headers` (`imap.rs:1156`)

(`mail_sync.rs:401-409`) is the arm that reaches further back; the resumed
listing under `WhateverHasChanged` asks only above the highest uid held, so a
chunk of older mail has to be asked for as `MoreOfWhatIsAlreadyThere`, which
`spawn_whole_folder_fetch` already does (`wx_app.rs:21657-21667`).

**2. The text pass is one message at a time, unbounded, with no stop but the
reading gate, and it reads the provider's answer per message only.**

```

So a provider that starts refusing after two hundred messages is asked for the

**4. The body cache evicts at the end of every folder sync, above half a

A download of every message's text on a mailbox whose text exceeds that would
be evicted by the next folder's sync, and `messages_with_no_text_here` would
list the evicted rows as missing again, so the runner and the eviction would
chase each other forever. That is why 10-03 makes the budget a setting before
10-05 wires the runner, and why this plan's `what_to_do_next` takes the budget
as an input rather than reading a constant.

**5. One retry rule exists in the tree, for the Google and Microsoft HTTP
clients, and it cannot serve a wait of minutes; the mail paths have none, and
the only reconnect there is one immediate sign-in when a command finds the
connection gone.**

```

  -> src/service/google_api.rs:877 `pub async fn with_retry<F, Fut, T>(max_retries: u32, mut f: F)`: 500 ms doubling per attempt, at most max_retries, `tokio::time::sleep(delay).await` inside; seven callers, all in microsoft_graph.rs; nothing under the mail vocabulary

`with_retry` is not reused, and the module doc says why: it sleeps inside an
async call on a runtime thread, for at most a few seconds, and it decides its

server is served by the main timer (10-05, 10-06) from a value handed back,
so the rule here answers a `Duration` and never sleeps. Ledger 64 records that
the single immediate sign-in is proved against a loopback server and has met
no provider. A growing wait for the mail paths is new code, so it is a new
module with its own tests, and both long runs ask it.
