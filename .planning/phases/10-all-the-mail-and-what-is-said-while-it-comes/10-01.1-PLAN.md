A Ctrl+Tab becomes a page change only in `MSWProcessMessage`, which the
event loop calls on a message it pulled from the queue before dispatching it,
and which reads the Control key from the physical keyboard state, not from
the message. A `WM_KEYDOWN` sent to a window procedure, which is what `press`
in `the_settings_tab_row_says_each_tab_once.rs:166-182` does and what reaches
`answer_the_arrows_on` for an arrow, goes to `HandleKeyDown` and changes no
page (`window.cpp:3326` lists `VK_TAB` among the keys for which no char event
is even made). Everything after that translation is wx's code ending in
`SetSelection`, the same call the arrow handler makes at `wx_settings.rs:128`.
So the reading puts focus on a General control and calls
`notebook.set_selection(THE_COMPOSE_TAB)`, which is exactly the fault's
precondition (`notebook.cpp:364-391`: the notebook visible and not holding
focus); the arrow companion uses `press` as before. The diagnosis's "pump the
loop" is not needed either: `SetSelection`, `SetFocus` and `WM_SETFOCUS` are
synchronous on the calling thread, and `GetFocus()` answers as soon as
`set_selection` returns. Injecting a real Control key with `SendInput` would
change the machine's keyboard state under a test and is not done.
