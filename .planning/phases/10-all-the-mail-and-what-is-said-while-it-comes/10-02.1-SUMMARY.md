# Phase 10 Plan 02.1: All Inboxes, a label view and a saved search read in the sort that was chosen Summary

**All Inboxes, a label view and a saved search's results are read in the sort that was chosen,
the way a folder is: `unified_inbox`, `messages_with_label` and `message_rows_for` take the
order from `Sort::order_by_clause` and put it in the query with `m.uid DESC` after it, one
shared default for the person who never chose a sort, and the window's three loaders ask
`the_sort_as` for it as `load_folder_messages` has since the layout carried a sort, so leaving
a row and coming back finds the order that was left (#69). The test that holds each listing to
every menu sort, both ways, against a hand-sorted fixture found one more thing: the menu's
Unread First was stored as `m.read DESC`, read first, and every folder re-read after choosing it
put the read rows on top; it stores unread first with newest first beneath now, the order the
setting of the same name has always meant. What a chosen sort costs the combined view is ten
rows on the measurements page at 12,872 and 200,000: at 200,000 with no `LIMIT` the fixed order
reads in 500.31 ms and the chosen orders in 499.98 to 570.93 ms, because reading every row is
most of the cost and the sort adds a few percent; at 12,872 every order sits between 21.02 and
23.96 ms. Closed #69 from the merge commit `c0505f68` with what the tests proved and what only
the tester's ear settles.** Nothing pushed.
