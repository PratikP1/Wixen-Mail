<objective>
The separate Wixen Mail window a link can open in, as the one shape
that gives it a profile of its own.

Purpose: #80's third route and its third menu item. 11-11.1 established
from the tree that every WebView in a process shares one WebView2
environment under wxdragon 0.9.17 and that nothing clears it, so a

and storage, which is the thing the issue's item 3 exists to prevent. A
process of its own with an application name of its own is the isolation
the toolkit can reach, and this plan builds it, wires the route 11-11.1
left pointing at the browser with a status line, and closes the issue.

Output: the page process and its window, the command, the route, the
erase, the scan target for the window's names, the readings, the pages
and the changelog. Closes #80 on the tree side.

A page process is a `Command` of its own, answered where Help and
Version are, before the data folder, the log file, the claim and the
handover: it opens no database, holds no mutex, and is not the copy a
later start hands its link to. Its log goes to stderr and its panics to
the crash file, which the hook already writes before anything else.


So the app name set in the page process's `on_init`, before its WebView
is built, decides where WebView2 puts that process's profile, and the
main process's name is the executable's. Two names are tried, in this
order, and the summary says which held: `wixen-mail\pages`, which would
put the profile at `%LOCALAPPDATA%\wixen-mail\pages\EBWebView` under the
one root the paths module promises, so the erase and the uninstaller
reach it without learning a second place; and, if wx refuses a
separator in an application name, `wixen-mail-pages` as a second root
that `erase_all_data` removes by name and the paths module's doc names.
The tester's profile shows `EBWebView` beside `cache` and `config`, so
the main process's profile is already under the root and has never been
named in the doc; this plan names it.
