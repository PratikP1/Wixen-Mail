# Phase 11 Plan 06.1: After a delete the cursor lands on the next message, and Delete says one word Summary

**After a delete the cursor is on the next message, or on the previous one when the last
was deleted, on the list control itself, with the focus event a screen reader reads the
row from; a re-read of the folder, which the watch makes after every delete on an IMAP
account, keeps the cursor on the same message by its identity and moves it only when its
row changed; and Delete says the one word "Delete" and then nothing, the landed row being
the confirmation, with the fuller line written to the status bar for the eye and a
refusal still spoken. The rules are `presentation::landing_after_a_removal`, held by
twelve cases; the control follows them through two public helpers in `wx_app.rs` that a
built virtual list calls in a target. That list corrected the plan's premise before the
fix was written: a shrink that leaves the focused index in range keeps the cursor where it
was, so a landing that only set the state the control already held would have raised
nothing, and only a shrink that puts the index out of range, the last row deleted with the
cursor on it, leaves the control holding no row at all, which is the top the tester met.
So the landing clears and sets the row's states, and the reading counts the focus event.
`UIUpdate::Shown` is a third channel, written and never spoken, and whether an outcome
rides it follows whether the row left. Nobody has heard the landed row or the one word.**

## What 11-06.2 and 11-07 need to know

- **`landing_after_a_removal` is where the cursor lands on the list.** 11-06.2's
  `where_to_land_on_arrival` joins it, on the README's decision 27; its three functions
  are pure over indices and ids, and the module has two records on the library, so a test
  added there names the count check.
- **`put_the_cursor_on` clears before it sets, on purpose.** A landing on a row the control
  already holds raises no focus event otherwise, and NVDA reads the landed row from that
  event; 11-06.2's landing on arrival, which lands only when no item is focused, can use
  the same setter and inherits the event. It also runs the selection handler, which loads
  the body into the preview and refreshes the Mark as Read words.
- **`land_the_cursor_after(list, removed, len_after)` takes a set.** 11-07's delete of a
  set calls it with every removed index and the count after, and `where_to_land` answers
  the row after the set, else before it, else the last row left; no rule is added. The
  helper is `pub` and the target calls it on a list it built, which is how a set's landing
  can be proved without the window.
- **The load arm remembers the cursor's message before the rows are replaced**, and only
  under the flat view; a set's delete followed by the watch's re-read keeps the cursor on
  the row it landed on by identity, since that row's message survives.
- **`Shown` is the third channel and `show_or_say_what_happened_next` is its sorter.**
  A set's success lines from `spawn_server_change` ride it one by one as each server
  answer arrives, quiet; the one sentence a set says is at the key, through
  `say_the_one_word` or a `StatusUpdated` naming the count, the way the conversation row's
  arm does. An outcome that left the row where it was is spoken; a refusal is never on
  `Shown`. `tests/progress_is_shown_and_results_are_said.rs` and the target hold the
  sorting, and `quiet_on_purpose` holds the arm.
- **11-07.1 inherits the one word.** A move or a delete that completes here first still
  says "Delete" or "Move" at the key and shows the fuller line; its success shown, its
  refusal undone and spoken.
