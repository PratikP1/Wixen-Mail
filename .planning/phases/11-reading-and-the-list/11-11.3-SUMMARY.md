# Phase 11 Plan 11.3: A Markdown marker counts at the start of any line Summary

**A Markdown block marker typed with its space now makes its structure on any line of the
message, not only the first: on a line of the quoted text in a reply to plain text, after
Shift+Enter and after Enter on the empty first line, where since 2026-07-29 the page refused
it before reading it with nothing said. A refusal that met a marker is written to the log so
the next report can say which path refused. The first character typed after `**bold**`, a
code span or an italic is plain, where it and every line after it used to keep the style.
A test types into the real editor page in the hosted WebView and holds the document after
each of twelve steps. The pages say the space in words and the guide lists the markers for
the first time. #79 is closed on the tree side; which of the two states the tester was in is
his ear's, and the steps to check are ledger 565. Nobody has heard any of it.**

## The reading over the real page really types

Yes, and it says so when it cannot. Each character goes as a `WM_CHAR` posted to the window
`GetFocus()` names, which the browser sets to its `Chrome_WidgetWin_1` when the page takes
focus; Enter, Down and End as `WM_KEYDOWN` and `WM_KEYUP`; Shift+Enter, which a posted
message cannot carry because the engine reads the Shift state from the keyboard, as
`insertLineBreak` from script, the command the key runs. The page's `input` events are
counted, so a run where no key arrived is told from one where the rule refused. The first
red run showed steps 2, 3, 4 and 7b red for the intended reason and 1, 5, 6 and 7a held,
quoted in the red commit; the green run held all eight, then all twelve.

hand were three red: `<h2>Hing</h2>` for `## Heading`, `bold**` for `**bold**`, `<em>bold*`
for the same, each two or three characters short right after an Enter or right after a
marker had made its block, with every key posted to the same window handle (recorded per
key and printed on failure). Waiting for each character's own `input` event before posting
the next, with a re-post after a second and a line printed when one is needed, gave twenty
runs green with no character posted twice. Two re-posts happened later in the green run of
task 2, both a `d` three characters into a fresh page, both printed, both right afterwards.
A person's keys go through the input method's own queue and a posted message does not;
what the engine does with a message posted before the last one's event has fired is not
diagnosed, and the wait is what makes the reading believable rather than an explanation.
