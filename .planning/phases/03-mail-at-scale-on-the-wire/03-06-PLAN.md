<objective>
Hold one authenticated session per account open across a run of mail actions,
reconnect once when it drops, and put a number on how many connections this
program opens.

Purpose: criterion 2, and the argument is the worst case verified in
`03-RESEARCH.md`. Marking one message read (`wx_app.rs:17509-17534`) builds a
`MailController`, calls `connect_imap`, issues one `set_flag`, and disconnects: a
full TLS handshake, CAPABILITY, LOGIN and SELECT per starred message. Twelve
sites do this. There is no reconnect or retry anywhere in `mail_controller.rs`,
`imap.rs` or `mail_sync.rs`; searching finds two hits and both are prose comments
about a user retrying by hand.

Output: a session with a lifetime, a reconnect that happens once, a sentence when
the retry also fails, and a budget that counts the IDLE connection.
</objective>

<premise_corrections>
**1. The lock does not need replacing.** `MailController` already holds
`Arc<Mutex<Option<ImapSession>>>` with `require_imap` (`mail_controller.rs:278`)
as the single unwrap point. `03-RESEARCH.md` is explicit: what is missing is
lifetime and reconnect, not structure. A plan that rebuilds the locking is
solving a problem that is already solved and will produce a second answer to
where the session lives.

**2. The budget starts at two, not one.** `watch_folder` (`mail_sync.rs:1165`)
opens its own client and session for IDLE, is reached from `wx_app.rs:17212`,
and is dispatched at the end of every mail check (`:18897`). Any budget test
that counts only the fetching connections is wrong by one before it starts, and
that one is long-lived.

**3. Twelve sites, and the list is in a test now, not in this plan.** Plan 03-02
put the count in `tests/one_sign_in_per_piece_of_work.rs` for exactly this
moment. Use the census as the arbiter of when this plan is done, and do not
write a new census that happens to agree with the new code. If a thirteenth site
appears during the work, the census will say so.

**4. The shapes are not identical.** The twelve sites were read individually
during research and they differ: some disconnect on every path, some do not, some
build the controller inside a closure. Converting them by pattern-matching on the
first one read is how eleven get converted correctly and one gets converted
wrongly. Convert in small groups with a commit per group, and let the census
count down.

**5. Reconnect once, and once means once.** Criterion 2 says "reconnects once and
says so if the retry also fails". A loop that retries until it succeeds is a
different thing and is worse: against a server that is rate-limiting, it is the
behaviour that gets an account locked. Gmail allows fifteen connections per
account and punishes more, which the requirement's evidence records.

**6. None of this can be proved against a real server here.** `CLAUDE.md`
requires network code to be tested against parsing and error mapping rather than
live servers, and `03-RESEARCH.md` names the connection budget as one of the
things that cannot be settled: what a provider does with a session idle for
minutes, and whether a reconnect after a drop is accepted or rate-limited, is
untestable in this repository. Ledger entry 11 already records the same gap for
the bulk body fetch. Expect this plan to close criterion 2 structurally and to
leave an `unrun-verify` ledger entry for what only a live account settles.

**7. Sixty-one guard records name `src/presentation/wx_app.rs` and twenty-seven
name `src/application/mail_controller.rs`.** Every RED commit in this plan will
fire the count check. Name it each time, and treat the remeasure as an overnight
job after the merge rather than as part of the branch.
</premise_corrections>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a held session -> every piece of work using it | one session shared across the program means one failure can affect all of them, and one close can strand all of them |
| this program -> a provider's connection limit | Gmail allows fifteen per account and punishes more, and nothing here has ever counted what is really opened |
| a dropped connection -> a retry loop | a retry that does not stop is the behaviour that gets an account rate-limited or locked |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-23 | Denial of service | a retry with no bound | high | mitigate | exactly one reconnect, proved by a server that drops every connection and counts the attempts |
| T-03-24 | Denial of service | connections opened per account | high | mitigate | a named budget counting the IDLE connection, with a test asserting both an upper bound and a non-zero count |
| T-03-25 | Denial of service | a lock held across a server round trip | high | mitigate | the session handle taken and released around the call, not held across it, with the reason recorded from the database-lock precedent at `mail_sync.rs:1029-1032` |
| T-03-26 | Repudiation | a bare protocol error shown to somebody | medium | mitigate | a sentence saying what happened, that a retry was made, and what to do next, said by ear as well as shown |
| T-03-27 | Spoofing | a session reused across accounts | critical | mitigate | the holder is keyed by account and a test drives two accounts and asserts two sign-ins; `a_session_at`'s existing rule that the account's own id goes with the session is kept |
| T-03-28 | Information disclosure | credentials in a test transcript | medium | mitigate | the existing loopback harness already takes a whole sign-in line off before recording it, per the comment in `mail_session.rs`'s tests, and the counting test asserts on the count rather than the line |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | no dependency added; `Cargo.toml` changes only its version line |
</threat_model>
