<objective>
Put the conflict choice where the conflicting state can actually happen, and stop
the losing copy being written over and apologised for afterwards.

Purpose: criterion 6. SCALE-06's evidence was corrected on 2026-09-03 because
"no conflict resolution path in `src/`" is wrong and getting it wrong would have
had this phase write a second conflict model beside a working one, with the two
disagreeing about who wins. Contacts already resolves: `whose_copy_wins`
(`contacts_sync.rs:988`) returns a four-armed decision built from whether local
work is unsent and whether the address book's version marker moved, with two
production call sites reached from the interface, and the losing case counted and
spoken rather than silent. What is missing is that the losing case is told after
the fact rather than asked before it.

Output: a held conflict, a choice made from the keyboard, a calendar path that
asks the same question, and mail's real defect fixed as itself: a flag change
made with no server is kept and sent later rather than quietly undone.
</objective>

<premise_corrections>
**1. Settled on 2026-09-03: contacts and CalDAV get the conflict choice, and
mail's real bug gets fixed too.** `03-RESEARCH.md` asked whether the choice
should be built where the state exists rather than where the requirement points.
Pratik answered both: build the choice for contacts and CalDAV, tasks 1 to 3, and
add mail's actual defect as task 4.

The argument for not building a mail conflict chooser is in the requirement's own
corrected text: mail flags are optimistic-local with revert-on-failure, nothing
queues a mail flag change, so the "both changed" state this requirement describes
largely cannot arise there. Building a mail conflict chooser would be a surface
for a state that does not occur.

**What mail has instead is worse and simpler.** A flag change is applied locally,
pushed on a connection, and reverted when the push fails
(`wx_app.rs:17381-17404`). Every failure takes that same path back, including the
one where the server was never reached. So starring a message with no network
stars it, un-stars it a moment later, and says why. Task 4 makes the unreachable
case keep the change and send it later, and leaves the refused case reverting,
because a server that answered and a server that was not there are different
facts and only one of them means the change was rejected.

**2. Do not write a second conflict model.** `whose_copy_wins` decides who wins
and it decides correctly, comparing markers rather than clocks on purpose
(`contacts_sync.rs:977-982`). This plan changes what happens in one of its four
arms. If the work starts to look like a new decision function, stop: that is the
duplicate `03-RESEARCH.md` warns about, and the two would disagree the first time
either changed.

**3. Guard record counts, measured 2026-09-03. A hundred and thirty-five records
name `src/application/contacts_sync.rs`.** That is the most expensive file in
this tree for the count check by a wide margin: `src/service/protocols/imap.rs`
is next at sixty-eight, then `src/presentation/wx_app.rs` at sixty-one,
`src/application/caldav_sync.rs` at thirty-three and
`src/data/message_cache/mod.rs` at eighteen. Neither new module,
`conflict_choice.rs` nor `flag_changes_waiting.rs`, is named by any record.
Adding test functions to `contacts_sync.rs` flags all hundred and thirty-five,
and a remeasure at a build and a full library run each is an overnight job. **So
the new types, the held conflict, the decision and the waiting flag changes go in
the two new modules**, and `contacts_sync.rs`, `caldav_sync.rs` and `wx_app.rs`
gain as few test functions as the work allows. That is not tidiness, it is hours, and it is written here so the next
person does not move the module for tidiness. The count for
`contacts_sync.rs` is quoted in the summary before and after so the cost of what
was added is visible.

**4. The telling already works and is the model.**
`SyncResult::sent_over_a_newer_copy` (`:335`) becomes a sentence at `:1674-1690`
and reaches the user through `what_the_contacts_sync_did` at `wx_app.rs:15289`.
The asking should arrive the same way rather than through a new channel.

**5. CalDAV has the markers and not the choice.** `etag` and `If-Match` are at
`caldav_sync.rs:870`, `:1028`, `:3424` and `:3716`, and it resolves automatically
showing the user nothing. So the second half of this plan is wiring an existing
disagreement to an existing question, not building detection.

**6. Mail's real defect is adjacent, is not a conflict, and is fixed in task 4
rather than only recorded.** A flag change made while the server is unreachable
is silently reverted (`wx_app.rs:17381-17404` reverts per flag kind with a
sentence). That is not a both-changed conflict and it must not be built as one:
it needs a queue and a distinction between two kinds of failure, not a chooser.
Task 3 restates the requirement so the defect is named as itself; task 4 fixes
it.

**7. Task 4 carries the same trap plan 03-08 carries, and the two must answer it
the same way.** A flag change reaching the server is a write at the provider, so
guardrail 7 applies: it happens on purpose. Wiring "the network came back" to
sending waiting flag changes is the same mistake as wiring it to `flush_outbox`,
and it is easier to make here because a flag feels smaller than a message. It is
not smaller: it is a write at somebody else's server. Waiting changes go when a
sync that was going to talk to that server anyway does, or when somebody asks.

**8. Which queue, decided by reading rather than by assuming.** `outbox_queue`
(`mod.rs:1749-1762`) holds `to_addr`, `subject` and `body`, all `NOT NULL`, plus
`attempt_count`, `last_error` and `created_at`. A flag change has none of the
first three. Reusing that table means either writing values that are not true
into three required columns, or adding nullable columns that mean nothing for a
message, and then teaching `flush_outbox` to skip rows that are not messages. The
two also mean different things: an outbox row is a thing to send once, and a
waiting flag change is a state to reconcile, which is why two changes to one flag
collapse to one and two messages never collapse. **So flag changes get their own
table**, and its comment names `outbox_queue` and says why it was not used. Task
4 asks the executor to confirm this reading before acting on it.

**9. The five `*_sync.rs` files total over 38,000 lines and none has met a live
account.** Everything here is proved against divergent local states driven through
the same code path the sync uses, which is what SCALE-06's fourth deliverable
asks for and is all that is possible.
</premise_corrections>
