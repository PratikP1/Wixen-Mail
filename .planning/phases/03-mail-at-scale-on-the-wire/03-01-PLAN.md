<objective>
Put a type where the doc comment is, so that a listing covering part of a mailbox
cannot reach the code that deletes cached mail, and make a folder the server
renumbered say that it discarded what it held.

Purpose: this is the only work in phase 3 that can destroy the user's mail, and
it has to land before anything changes how a folder is listed. `sync_folder`
calls `list_uids` unconditionally at `src/application/mail_sync.rs:1014`, its
result feeds `uids_to_forget` at `:1025`, and that feeds `cache.forget_messages`
at `:1026`. The doc comment at `:286` already states the constraint in words:
the server list must be the whole mailbox, not the page just fetched, because
comparing against a page would delete everything outside it. Plan 03-07 exists
to stop that listing happening. A comment does not survive that change; a type
does.

Output: a whole-mailbox witness the forget path is the only consumer of, a
census holding the call count at one, a spoken sentence when a folder is
renumbered, and two guard records measured by hand.
</objective>

<premise_corrections>
**1. This plan is first because of an ordering constraint, not a size one.**
`03-RESEARCH.md` names the hazard as the single most important finding in the
phase and says the tests that would catch it have to be written before the
change rather than after. A test written after 03-07 lands would be a test
written against code that had already had the opportunity to delete somebody's
mail on their first sync. So this is red-first in the strong sense: the guard is
red against a shape of code that does not exist yet, and 03-07 is the plan that
would otherwise create it.

**2. Nothing here is decision-dependent.** None of the four questions
`03-RESEARCH.md` leaves for Pratik changes any of this. Whichever answer QRESYNC
gets, the forget path needs the same witness.

**3. The second destroying path is `forget_folder_messages` on a UIDVALIDITY
change**, at `mail_sync.rs:1004-1012`, and it is not a defect to be removed: a
server that renumbers a mailbox has made every UID held here name a different
message or none, so discarding is correct. What is wrong is that it is silent
apart from `tracing::info!`, which nobody sees. Criterion 1 asks for the
announcement in as many words: "a `UIDVALIDITY` change announces the resync
rather than doing it quietly".

**4. The renumber test has a narrow arm worth writing.** The condition at
`:999-1002` is a `matches!` over `(status.uid_validity, cache.folder_uid_validity(folder_id)?)`
requiring both to be `Some` and different. That is already right, and it is
right by one pattern that a later edit could widen without anything noticing.
A server answering no UIDVALIDITY at all must discard nothing, and that arm has
no test today.

**5. The source-reading census goes in `mail_sync.rs`'s own test module, not in
`tests/`.** `scripts/check.sh` runs `cargo test --lib application::mail_sync::`
on any commit changing `src/application/mail_sync.rs`, so a unit test there runs
on exactly the commits that could break it, with no `guards/guards.toml` coupling
needed for reachability. A guard in `tests/` would need that coupling, per
`CLAUDE.md`. Five guard records name `src/application/mail_sync.rs`, so adding
tests to it flags five records on the count check, which is the cheap end of that
cost: `src/presentation/wx_app.rs` would flag sixty-one and
`src/application/contacts_sync.rs` a hundred and thirty-five. That is a real
reason to prefer this file and it is stated so the next person does not move the
census for tidiness.

**6. The count check will go red in this plan's RED commits and must be named in
them.** Adding a test function to `src/application/mail_sync.rs` or to
`src/presentation/wx_app.rs` changes the number
`test_every_guard_record_says_how_many_tests_the_files_it_names_held` compares
against, and `CLAUDE.md` records that there is no ordering that avoids this. Name
it in the same `Fails-until-green:` block as the real failures, with the reason
in the message body. The counts are written down again afterwards with
`scripts/guards.sh --remeasure`, and every record whose red list turns out short
is corrected by hand first.

**7. `MailController::list_uids` is not the only reader of the answer.**
`uids_to_fetch` at `:1028` and `still_to_check` at `:1077` also take
`on_server`. Those two are safe against a page: fetching fewer messages than
exist is a smaller sync, not a deletion. Do not force them through the witness;
that would make the witness mean "a listing" rather than "the whole mailbox",
which is the entire distinction being drawn.
</premise_corrections>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the mail server's UID listing -> the only copy of somebody's cached mail | an answer from a stranger's server decides what gets deleted from this computer |
| the mail server's UIDVALIDITY -> a whole folder's cached mail | one changed integer discards every message held for that folder |
| a future plan's change to `sync_folder` -> this deletion path | 03-07 exists to remove the listing this deletion currently depends on |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Denial of service | `uids_to_forget` fed a page | critical | mitigate | a coverage-carrying type the forget path is the only consumer of; the partial variant answers with nothing |
| T-03-02 | Tampering | a second call to `forget_messages` added later | high | mitigate | a source census in `mail_sync.rs`'s own tests holding the count at one, with a companion proving it reads rather than asserts |
| T-03-03 | Denial of service | `forget_folder_messages` on an absent UIDVALIDITY | high | mitigate | a test for the absent arm and a guard record measured by widening the `matches!` |
| T-03-04 | Repudiation | a discard nobody was told about | medium | mitigate | the sentence on its own announcement topic, plus the retained `tracing::info!` |
| T-03-05 | Information disclosure | the sentence naming what was discarded | low | accept | it carries a folder name and a count, never a subject or a sender, which is the rule the neighbouring refusal at `:1017-1023` already follows |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | no dependency added; `Cargo.toml` untouched; no package manager runs in this plan |
