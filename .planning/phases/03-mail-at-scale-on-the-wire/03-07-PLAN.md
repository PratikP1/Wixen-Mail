<objective>
Stop re-listing a folder that was synced before, keep finding the messages
somebody deleted elsewhere anyway, and let somebody ask for a whole folder
without pressing a key once per five hundred messages.

Purpose: criteria 1 and 3. The sync state SCALE-01 asks for already exists and is
already read: `folders.uid_validity` and `folders.highest_modseq` are additive
columns, written and read by four functions, and `sync_folder` already detects a
UIDVALIDITY change and already passes the stored modseq to `fetch_flags` as
`changed_since`. What is missing is the one thing the requirement is named for:
stopping the unconditional `list_uids` at `mail_sync.rs:1014` when the stored
state says it is not needed.

Output: a resume, a named seam over how a folder learns what was deleted with the
UID comparison behind it and VANISHED declared beside it, a bound somebody can
state, a whole-folder request that continues in the background, and progress
somebody hears once.
</objective>

<premise_corrections>
**1. QRESYNC is decided and the decision is final. Build the seam, take the UID
comparison now.**

Pratik settled this on 2026-09-03. The decision is not "the fallback for now,
QRESYNC maybe later", which is the shape that gets re-argued every time somebody
opens this file. **The decision is that how a folder learns what was deleted is a
seam with more than one implementor, and the UID comparison is the one that gets
built.** His condition was that he should not have to revisit it, so this plan
has to make the design final and leave only implementation work behind the seam.

**What the seam is, concretely.** A named type in
`src/application/finding_what_was_deleted.rs` standing for the ways a folder can
learn what the server no longer has. Two members. The first is the UID set
comparison and it is implemented here. The second is VANISHED and it is
**declared and not implemented**, so it exists as a name in the code, is
documented as unbuilt, and is never selected. A probe over the server's
capabilities chooses between them, and today it always answers the first because
the second is never offered.

**What adding QRESYNC later then costs.** One implementor, plus one arm of the
probe. It touches nothing that decides policy: not the bound, not the resume
decision, not `sync_folder`'s shape, not the deletion path. That is the property
this plan is buying and it is the whole reason the seam is worth building before
there is a second implementor.

**Do not build a seam with one member and call it a seam.** An enum with one
variant, or a trait with one implementor and no second name written down, is a
refactor waiting to happen rather than a decision that has been made. VANISHED
being present as a declared and unbuilt member is what makes this final: the
shape of the second answer is fixed now, while the first one is being written,
rather than being discovered later by the person who adds it.

**The performance context, recorded here so nobody re-litigates it.** Gmail
advertises no CONDSTORE. That is asserted and commented in this codebase at
`src/service/protocols/imap/abilities.rs:112`. QRESYNC requires CONDSTORE. So on
Gmail the UID comparison is the only available path whether or not QRESYNC is
ever built, and **the seam costs Gmail users nothing at all**: they were always
going to take the first implementor. Whoever reads this later and wonders
whether the fallback is holding Gmail back: it is not, and the assertion in
`abilities.rs` is the evidence.

**The library facts, recorded so the seam is designed against what is really
there rather than against the roadmap's version.** The roadmap recorded QRESYNC
as blocked because async-imap 0.11.3 exposes no helper, and it does not: there is
no `ENABLE`, no `select_qresync` and no VANISHED handling anywhere in it. But
`run_command` (`client.rs:1376`) and `run_command_and_check_ok` (`:1364`) are
public raw escape hatches, `imap-proto` 0.16.7 already parses
`Response::Vanished` (`rfc7162.rs:31`) and `ResponseCode::HighestModSeq`
(`rfc4551.rs:21`), and **this project already uses that escape hatch for
CONDSTORE**: `fetch_flags` builds `UID FETCH 1:* (UID FLAGS) (CHANGEDSINCE
{modseq})` by hand at `imap.rs:1154`. So the second implementor is reachable, and
its real cost is that a raw `SELECT x (QRESYNC (...))` returns a mailbox response
async-imap's own `select` parses, so going through `run_command` means rebuilding
that parsing. The seam's second member is designed against that cost: it is
declared as something that needs a select response of its own, not as something
that can borrow the existing one.

**2. The second assumption in this plan is still open and is Pratik's.**

**The announcement topic: use the superseding topic that already exists.** `Announcement::with_topic` (`announcements.rs:108`), superseding in
`push` (`:180-186`) and `announce_topic` (`accessibility.rs:310`) with roughly
twenty-five production call sites are all built, and `UIUpdate::StatusUpdated`
already goes through them. So criterion 3's superseding half is close to
satisfied and mostly wants measuring. **The open question this plan cannot settle
is whether a whole-folder fetch belongs on the shared `"status"` topic or its
own.** `"status"` carries every other status line and the queue keeps only the
newest of a topic, so a long fetch there would silence them. The precedent for
splitting is `"message text"` at `wx_app.rs:15174`, kept off `"status"`
deliberately for exactly this reason. Task 3 builds it on its own topic and says
so; if Pratik wants it on `"status"`, that is a one-line change and the reasoning
is recorded either way.

**3. Do not touch the forget path.** Plan 03-01 made the deletion path take a
value that says the server listed the whole mailbox. The resume built here skips
that listing, so it must not produce such a value. If this task finds itself
needing to construct one, something is wrong with the design and the answer is to
stop, not to construct it. That is the entire point of 03-01 landing first.

**4. Gmail never offers CONDSTORE.** `imap/abilities.rs:112-113` asserts and
comments on it. So on Gmail every sync takes the full re-read branch and
criterion 1 costs something different there than on a CONDSTORE server. Say that
in the changelog rather than promising a saving nobody with a Gmail account will
see.

**5. There are two 500s and the requirement names one.**
`INITIAL_FETCH_LIMIT` (`mail_sync.rs:38`) bounds what is fetched from the server,
applied in `uids_to_fetch` (`:263-279`). `FOLDER_LIST_PAGE_SIZE`
(`wx_app.rs:6346`) bounds what is read out of the cache into the list. A change
to one alone appears to do nothing because the other still binds. Get Older
Messages moves both, at `wx_app.rs:5929`; SCALE-03's evidence gives that as line
5245, which has moved, and this is another instance of the staleness plan 03-02
exists to stop.

**6. Guard record counts, measured 2026-09-03.** Five records name
`src/application/mail_sync.rs`, sixty-one name `src/presentation/wx_app.rs`, one
names `src/presentation/message_rows.rs`, and none names
`src/service/protocols/imap/abilities.rs` or the new
`src/application/finding_what_was_deleted.rs`. **The seam module having no
records is a reason to put the comparison's tests in it rather than in
`mail_sync.rs`**, and it is a smaller saving than the same move buys elsewhere in
this phase because five is already cheap. The bigger reason is that a policy
named in its own module is a policy the next implementor can read on its own.
The count check fires on every RED commit here.
