<objective>
Stop re-listing a folder that was synced before, keep finding the messages
somebody deleted elsewhere anyway, and let somebody ask for a whole folder
without pressing a key once per five hundred messages.

Purpose: criteria 1 and 3. The sync state SCALE-01 asks for already exists and is
already read: `folders.uid_validity` and `folders.highest_modseq` are additive
columns, written and read by four functions, and `sync_folder` already detects a
UIDVALIDITY change and already passes the stored modseq to `fetch_flags` as
`changed_since`. What is missing is the one thing the requirement is named for:
stopping the unconditional `list_uids` at `mail_sync.rs:1014` when the stored
state says it is not needed.

Output: a resume, a bounded comparison that still finds deletions, a whole-folder
request that continues in the background, and progress somebody hears once.
</objective>

<premise_corrections>
**1. This plan rests on two assumptions Pratik has not confirmed. Both are
written here so that if either is wrong, the plan is wrong visibly rather than
quietly.**

**Assumption A, QRESYNC: take the recorded fallback.** SCALE-01's own text
specifies deletions being found by a periodic UID set comparison, bounded so it
does not run on every folder open, and the roadmap records that as accepted. So
this plan builds the comparison and does not build QRESYNC.

**That is a choice, not a limit, and the roadmap's reason for it turned out to
be wrong.** The roadmap recorded the dependency as blocking because async-imap
0.11.3 exposes no QRESYNC helper, and it does not: there is no `ENABLE`, no
`select_qresync` and no VANISHED handling anywhere in it. But `run_command`
(`client.rs:1376`) and `run_command_and_check_ok` (`:1364`) are public raw escape
hatches, `imap-proto` 0.16.7 already parses `Response::Vanished`
(`rfc7162.rs:31`) and `ResponseCode::HighestModSeq` (`rfc4551.rs:21`), and **this
project already uses that escape hatch for CONDSTORE**: `fetch_flags` builds
`UID FETCH 1:* (UID FLAGS) (CHANGEDSINCE {modseq})` by hand at `imap.rs:1154`.
A `Response::Vanished` arm in an existing closure is the same shape of work.
The real cost is that a raw `SELECT x (QRESYNC (...))` returns a mailbox response
async-imap's own `select` parses, so going through `run_command` means rebuilding
that parsing, and `Abilities` has no `qresync` field
(`imap/abilities.rs:26-49`). If Pratik would rather have QRESYNC, this plan is
the wrong plan and should be replanned rather than amended.

**Assumption B, the announcement topic: use the superseding topic that already
exists.** `Announcement::with_topic` (`announcements.rs:108`), superseding in
`push` (`:180-186`) and `announce_topic` (`accessibility.rs:310`) with roughly
twenty-five production call sites are all built, and `UIUpdate::StatusUpdated`
already goes through them. So criterion 3's superseding half is close to
satisfied and mostly wants measuring. **The open question this plan cannot settle
is whether a whole-folder fetch belongs on the shared `"status"` topic or its
own.** `"status"` carries every other status line and the queue keeps only the
newest of a topic, so a long fetch there would silence them. The precedent for
splitting is `"message text"` at `wx_app.rs:15174`, kept off `"status"`
deliberately for exactly this reason. Task 3 builds it on its own topic and says
so; if Pratik wants it on `"status"`, that is a one-line change and the reasoning
is recorded either way.

**2. Do not touch the forget path.** Plan 03-01 made the deletion path take a
value that says the server listed the whole mailbox. The resume built here skips
that listing, so it must not produce such a value. If this task finds itself
needing to construct one, something is wrong with the design and the answer is to
stop, not to construct it. That is the entire point of 03-01 landing first.

**3. Gmail never offers CONDSTORE.** `imap/abilities.rs:112-113` asserts and
comments on it. So on Gmail every sync takes the full re-read branch and
criterion 1 costs something different there than on a CONDSTORE server. Say that
in the changelog rather than promising a saving nobody with a Gmail account will
see.

**4. There are two 500s and the requirement names one.**
`INITIAL_FETCH_LIMIT` (`mail_sync.rs:38`) bounds what is fetched from the server,
applied in `uids_to_fetch` (`:263-279`). `FOLDER_LIST_PAGE_SIZE`
(`wx_app.rs:6346`) bounds what is read out of the cache into the list. A change
to one alone appears to do nothing because the other still binds. Get Older
Messages moves both, at `wx_app.rs:5929`; SCALE-03's evidence gives that as line
5245, which has moved, and this is another instance of the staleness plan 03-02
exists to stop.

**5. Five guard records name `mail_sync.rs` and sixty-one name `wx_app.rs`.**
The count check fires on every RED commit here.
</premise_corrections>
