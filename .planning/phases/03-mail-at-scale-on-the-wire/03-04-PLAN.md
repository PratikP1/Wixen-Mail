<objective>
Stop a Gmail conversation disappearing from the list because one of its messages
was archived without a label, by counting messages by their identity rather than
by excluding a folder.

Purpose: phase 1 deferred this here and the roadmap carries it as "Gmail mail
archived with no label vanishes from a conversation count, because D-08 excludes
All Mail by folder rather than by message identity. One extra predicate in one
query." The size in that sentence is wrong in two ways and `03-RESEARCH.md` says
so: the `here` CTE has no join to `folders`, so a per-message predicate needs one
added, and there are two queries carrying the exclusion rather than one.

Output: identity-based counting in both queries, a test holding them to each
other, and an entry saying what changed for somebody using Gmail.
</objective>

<premise_corrections>
**1. `DEFER-1-01` is an identifier minted by this plan.** The roadmap carries
phase 1's three deferrals as prose under "Inherited from phase 1" with no
requirement identifiers, and `REQUIREMENTS.md` has no entry for them. Phase 2.1
minted `CRIT-2.1-NN` the same way. The three are numbered in the order the
roadmap lists them: `DEFER-1-01` is this one, `DEFER-1-02` is the conversation
root merge in plan 03-05, `DEFER-1-03` is the UID wrap, closed by plan 03-03's
task 3.

**2. Two queries, not one, and they are deliberately coupled.**
`MESSAGES_IN_ONE_CONVERSATION` (`messages.rs:127-146`) and `conversations_query`
(`:148-208`) carry the same `reach` and `here` construction with the same three
parameters in the same order, and the doc comment at `:117-126` states why:
D-07 needs the number named before a deletion to be the number of messages that
actually go, and two queries agreeing today would drift the first time somebody
changed one. Changing one of them here would create exactly that drift, in the
path that tells somebody how many messages a delete is about to take.

**3. The identity column is `gmail_msgid`, not `gmail_message_id`.** It is added
by `ensure_column_exists` at `mod.rs:2297` as an `INTEGER` and is therefore
absent for every message that did not come from Gmail, and null for some that
did.

**4. This codebase already deduplicates by that identity, in one place, and that
is the pattern to follow.** `searching.rs:539` groups by
`COALESCE(m.gmail_msgid, m.id)`. The `COALESCE` half is the whole reason it is
safe: a message with no Gmail identity falls back to its own row id, so it is
never merged with another message. Reusing that expression rather than inventing
a second one also means one place to change if the identity ever moves.

**5. The `here` CTE has no join to `folders`.** It reads `messages m` and bounds
by `m.folder_id IN (SELECT id FROM reach)`. A per-message rule that has to know
whether a message's folder is the All Mail one needs that join added, which is
the sentence in the deferred note that understated the work.

**6. Nothing here has ever run against a real Gmail account.** No account has
been used with this program at all. `03-RESEARCH.md` records that Gmail has never
offered CONDSTORE and that `imap/abilities.rs:112-113` already asserts and
comments on it. So the tests here drive the queries over a cache built by hand,
which is real evidence about the SQL and no evidence at all about what Gmail
actually sends. Say that in the changelog rather than implying the case is
closed.

**7. Twenty-six guard records name `src/data/message_cache/messages.rs`.** The
count check will fire on both RED commits. Name it, and run
`scripts/guards.sh --remeasure` after the merge, in the background.
</premise_corrections>
