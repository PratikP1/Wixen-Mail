<objective>
Make a conversation root that arrives after a message already naming it join that
message's conversation, and make the fix visible on mail already stored.

Purpose: phase 1 deferred this here and the roadmap carries it as "A conversation
root arriving after a message that already names it is not merged, so three of
six arrival orders over such a set merge. One table, one index, one writer." It
is also broken windows ledger entry 7, and entry 9 records that plan 01-13's
order-independence criterion was unsatisfiable with the lookup's current
signature. `threads_holding_any_of` (`messages.rs:1151-1225`) matches on
`m.message_id IN (...)` and nothing else, so it cannot see a stored message whose
`refs_header` names the arriving one.

Output: the table, the index, the writer, the lookup, the backfill the deferred
note does not mention, and a root-choice rule that survives more merges firing.
</objective>

<premise_corrections>
**1. "One table, one index, one writer" leaves out the backfill, and without it
the change is invisible.** `03-RESEARCH.md` states this: a new identifier table
starts empty, so without a backfill every conversation already stored stays
split, which reads to somebody using this program as the fix not working. There
is a precedent for exactly this shape in the same file:
`backfill_message_identifiers` is named in the comment at `messages.rs:1170-1183`
and runs when the database is opened, non-fatally.

**2. `rejoin` always makes the arriving message's own root the winner, and that
is not always the true root.** `thread_identity.rs:195-219` returns
`winning_root: the_arriving_conversation`. Its doc comment argues that the chain
is oldest first so the arriving message's conversation is the chain's earliest
identifier. That holds for a message carrying a full `References` chain and does
not hold for a message naming only its parent, which is common: many clients send
`In-Reply-To` alone. More merges firing makes that rule matter more, which is
exactly what this plan causes.

**3. The writer and the call site are already single and in the right place.**
`merge_what_this_message_connects` (`messages.rs:961-992`) runs on every arrival
through `upsert_message` (`:943`), and its doc comment says one call serves a
sync's batch, a POP download, a copy of something sent and an imported mailbox,
with no second copy to come to differ. Do not add a second path. Add a table the
existing path writes and the existing lookup reads.

**4. The two spellings problem is live and this change must not narrow it.**
`threads_holding_any_of` asks about each identifier bare and in angle brackets,
and the comment at `:1163-1195` explains that narrowing the question would make
bracketed rows stop joining, which is mail dropping out of a conversation. The
new table has to store identifiers in whatever form the existing
`thread_identity::bare` normalisation produces, and the lookup has to keep
answering for rows a backfill has not reached. This is broken windows ledger
entry 8's territory and it is marked fixed; do not reopen it by accident.

**5. Schema changes are additive.** `CREATE TABLE IF NOT EXISTS` for the table,
`CREATE INDEX IF NOT EXISTS` for the index. Nothing shipped is dropped or
renamed.

**6. This plan changes what somebody sees in the message list, so it needs a
changelog entry and it needs the version bumped.** A behaviour change is what the
versioning rule names as needing a bump in the same commit as the change. The
Gmail fix in 03-04 was a bug fix and did not; this merges conversations that were
separate, which is a behaviour change.

**7. Twenty-six guard records name `messages.rs` and none names
`thread_identity.rs`.** The count check will fire. Name it in each RED commit and
remeasure after the merge, in the background.
</premise_corrections>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a stranger's `Message-ID` and `References` headers -> a table this program writes | every identifier stored here was written by somebody outside, and none of it is interpolated into SQL |
| a merge -> a conversation's identity | one of the two conversations is renamed and there is no merge without that, so the rule deciding which must be stable |
| a backfill -> the only copy of somebody's mail | a migration that moves conversations must not move mail |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-18 | Tampering | identifiers from an arriving message | high | mitigate | every value bound as an anonymous parameter, following the reasoning already written at `messages.rs:1191-1200`; the 64-identifier cap and the corrected parameter-count arithmetic keep it inside SQLite's limit |
| T-03-19 | Denial of service | a backfill over a large mailbox on every open | medium | mitigate | either idempotent and cheap, or gated by a cheap check, stated in a comment; non-fatal either way so the database still opens |
| T-03-20 | Tampering | a backfill that merges by deleting | critical | mitigate | the message count asserted equal before and after, in a test |
| T-03-21 | Repudiation | a conversation whose identifier depends on arrival order | medium | mitigate | the stability test over every arrival order, plus the widened winner rule and its guard record |
| T-03-22 | Information disclosure | a `Message-ID` in a log line | medium | mitigate | the existing rule at `messages.rs:981-984` logs a count and a number of conversations and never an identifier; the new writer and backfill follow it |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | no dependency added; `Cargo.toml` changes only its version line |
