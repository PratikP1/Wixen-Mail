<premise_corrections>
**1. Do not build the split. It is built.** The requirement's old sentence is
corrected in `REQUIREMENTS.md` already, and `03-RESEARCH.md` gives the file and
line for every tier. A plan that reads the old sentence and builds a second body
cache beside the working one is the failure phase 2.1 existed to remove.

**2. The migration is permanent, not one-off, and that is the point of the
test.** `messages.body_plain` and `messages.body_html` are in the original
`CREATE TABLE` at `mod.rs:1407-1408`, added by no `ensure_column_exists`, so
they exist in every database this program has ever written and cannot be dropped
under this project's additive-schema rule. `migrate_inline_bodies`
(`bodies.rs:609`) therefore runs on every cache open, forever, non-fatally
(`mod.rs:1226`). Any path that still writes those columns reintroduces the
problem the migration exists to clear.

**3. Do not test the migration against a database this program wrote today.**
That database has already been migrated, so the test would assert that a
migration of nothing loses nothing, which is true and worthless. The fixture has
to be a database whose `messages` rows carry text in the inline columns and whose
body table is empty or absent, built by writing that schema directly.

**4. The wrap is real, is unreachable, and is guarded by something outside
itself.** `messages.rs:752` saturates on `i64` and then casts to `u32`, and
`FIRST_RESERVED_UID` is `u32::MAX` (`messages.rs:14`) with no filter in the
query, so one reserved row would make the next call answer zero. It does not
happen because `numbering_in` (`:628`) dispatches by folder path and a folder
either counts up or counts down, never both. The two direct callers are a
`#[cfg(test)]` helper (`local_delete.rs:289`) and a local POP folder
(`pop_sync.rs:268`). So the test belongs on the dispatcher: one new direct caller
pointed at a server-numbered folder makes the wrap reachable with one row rather
than four billion.

**5. Do not "fix" the wrap by filtering the query or widening the type.** That
would make the function safe and leave the dispatcher unguarded, and the
dispatcher is the thing that actually decides. `next_reserved_uid`'s doc comment
at `:756-767` explains what goes wrong when a locally-filed row is given a number
a server is about to issue, and that reasoning is what the test has to hold.
If the executor finds a cheap way to do both, the extra safety is welcome and
does not replace the dispatcher test.

**6. This plan changes no behaviour if everything it checks is already true.**
That is the expected outcome and it is a result, not a wasted plan. If a guard
turns something up, that finding goes in the summary and, if it is user-visible,
in `docs/changelog.md`. If nothing is found, `docs/changelog.md` is not touched
and the summary says so.

**7. Twenty-six guard records name `src/data/message_cache/messages.rs`, two name
`bodies.rs` and the count check will fire.** Name
`test_every_guard_record_says_how_many_tests_the_files_it_names_held` in each
RED commit alongside the real failures, with the reason in the body, and run
`scripts/guards.sh --remeasure` after the merge rather than before it.
</premise_corrections>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a database written by an older version -> this version's cache open | the migration runs on every open forever and is the only path between the two schemas |
| a folder path -> which numbering a row gets | the wrong numbering makes a real message invisible and overwrites a sent one, per `next_reserved_uid`'s own comment |
| a sync -> the attachment content store | an attachment fetched without being asked for is bandwidth and disk somebody did not agree to spend |
