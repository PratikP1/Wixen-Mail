<premise_corrections>
**1. Do not build the split. It is built.** The requirement's old sentence is
corrected in `REQUIREMENTS.md` already, and `03-RESEARCH.md` gives the file and
line for every tier. A plan that reads the old sentence and builds a second body
cache beside the working one is the failure phase 2.1 existed to remove.

**2. The migration is permanent, not one-off, and Pratik decided on 2026-09-03
to attack the cost of that rather than accept it.** `messages.body_plain` and
`messages.body_html` are in the original `CREATE TABLE` at `mod.rs:1407-1408`,
added by no `ensure_column_exists`, so they exist in every database this program
has ever written and cannot be dropped under this project's additive-schema rule.
`migrate_inline_bodies` (`bodies.rs:609`) therefore runs on every cache open,
forever, non-fatally (`mod.rs:1226`). Any path that still writes those columns
reintroduces the problem the migration exists to clear.

**What it really costs today, measured by reading it.** The function opens with

    SELECT id, body_plain, body_html FROM messages
    WHERE body_plain IS NOT NULL OR body_html IS NOT NULL

and there is no index on either column, so this is a full scan of `messages` on
every open of every database forever, in front of the user, before anything is
shown. On a two-hundred-thousand-message cache that is the whole table read to
find nothing. Task 2 measures it rather than assuming the size; the shape is not
in doubt.

**3. There is no settings table to put a marker in, and that was checked rather
than assumed.** Every `CREATE TABLE IF NOT EXISTS` in `mod.rs` was read. The two
that sound like candidates are not: `sync_state` (`mod.rs:1841`) is keyed
`UNIQUE(account_id, sync_type, provider)` and holds sync tokens and delta links,
so it is account-scoped and provider-scoped where this fact is neither; and
`tree_state` (`mod.rs:2090`) holds whether a tree row is collapsed. There is no
key-value or metadata table, and `PRAGMA user_version` is used nowhere in
`src/data/message_cache/`. So the marker is a new additive thing, and task 2
decides which shape, with the constraint that it is `CREATE TABLE IF NOT EXISTS`
or `ensure_column_exists` and never a dropped or renamed column.

**4. The marker must be safe in the conservative direction, and the way to get
that is ordering rather than care.** A marker that says "already migrated" when
a body is still inline would lose that body, since nothing else moves it. So the
marker never gates the *question*, only the *work*: a cheap probe asking whether
any inline body exists runs on every open regardless of the marker, and the
marker only skips the expensive scan-and-move that follows a positive answer.
Made cheap by a partial index over exactly the probe's condition, the probe is a
constant-time lookup against an empty index rather than a table scan, so paying
it unconditionally costs nothing worth saving. A marker found wrong by the probe
is corrected, and the summary says how many times that happened in testing.

That ordering is the entire safety argument and it is why this is safe to add to
a database holding the only copy of somebody's mail: **the only thing a wrong
marker can cost is a probe that was already free.**

**5. Do not test the migration against a database this program wrote today.**
That database has already been migrated, so the test would assert that a
migration of nothing loses nothing, which is true and worthless. The fixture has
to be a database whose `messages` rows carry text in the inline columns and whose
body table is empty or absent, built by writing that schema directly.

**6. The wrap is real, is unreachable, and is guarded by something outside
itself.** `messages.rs:752` saturates on `i64` and then casts to `u32`, and
`FIRST_RESERVED_UID` is `u32::MAX` (`messages.rs:14`) with no filter in the
query, so one reserved row would make the next call answer zero. It does not
happen because `numbering_in` (`:628`) dispatches by folder path and a folder
either counts up or counts down, never both. The two direct callers are a
`#[cfg(test)]` helper (`local_delete.rs:289`) and a local POP folder
(`pop_sync.rs:268`). So the test belongs on the dispatcher: one new direct caller
pointed at a server-numbered folder makes the wrap reachable with one row rather
than four billion.

**7. Do not "fix" the wrap by filtering the query or widening the type.** That
would make the function safe and leave the dispatcher unguarded, and the
dispatcher is the thing that actually decides. `next_reserved_uid`'s doc comment
at `:756-767` explains what goes wrong when a locally-filed row is given a number
a server is about to issue, and that reasoning is what the test has to hold.
If the executor finds a cheap way to do both, the extra safety is welcome and
does not replace the dispatcher test.

**8. Tasks 1, 2 and 4 change no behaviour if everything they check is already
true.** That is the expected outcome for them and it is a result, not a wasted
plan. Task 3 does change behaviour, because a repeat open stops doing work, so
that one carries a changelog entry and a version bump and the other three do not.
If a guard turns something up in the other three, that finding goes in the
summary and, if it is user-visible, in `docs/changelog.md`.

**9. Guard record counts, measured 2026-09-03.** Twenty-six records name
`src/data/message_cache/messages.rs`, eighteen name
`src/data/message_cache/mod.rs`, and two name `src/data/message_cache/bodies.rs`.
The count check fires on every RED commit here. Name
`test_every_guard_record_says_how_many_tests_the_files_it_names_held` in each RED
commit alongside the real failures, with the reason in the body, and run
`scripts/guards.sh --remeasure` after the merge rather than before it.

**The marker work added by task 3 changes the arithmetic and is worth stating.**
Its tests want to live in `bodies.rs`, which two records name, rather than in
`mod.rs`, which eighteen name, even though the marker's schema statement goes in
`mod.rs`. (Task 3 is the marker.) Put the schema statement where its neighbours are and the tests where
the behaviour is, which is both the cheap answer and the right one. If a test
genuinely needs to be in `mod.rs`, that is nine times the remeasure cost of the
same test in `bodies.rs`, so say in the summary why it had to go there.
</premise_corrections>
