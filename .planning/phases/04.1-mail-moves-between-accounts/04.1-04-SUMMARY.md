# Phase 4.1 Plan 04: The bytes kept while a move is in the air Summary

## Does it work

**Yes, and a test that kills the run is what says so rather than a source read.**
`test_a_move_in_flight_outlives_the_run_that_started_it` opens a cache, writes a
move, drops the connection by letting the cache fall out of scope so SQLite
closes the file, opens the same database the way the next start of the program
opens it, and finds the move with its message byte for byte. That is the only
test here that could prove the store survives the process that wrote it, and
without it every assertion would be inside one run where a field on a struct
would pass just as well.

**The store is reached by a non-test path.** `say_what_did_not_finish` runs from
`wxdragon::main`'s on_init callback, after the window is shown and after the
alpha question, and reads the leftover moves with a local read that touches no
server. That wiring is the whole reason task 1 was a tracer: this cache has no
sweep and nothing that ever looks at what a previous run left, so a store built
on `signed_original`'s shape would have been cleared on the happy path and read
by nothing after a restart, which is the one case it exists for.

**What does not work, said plainly.** No process has been killed mid-move
against real accounts and restarted, so the thing this plan is for has never
happened outside a test. Nothing here has been heard. The question put on the
next start has never been read out by NVDA and nobody has checked that it does
not sound like an error. Those are the plan's fourth task, and it was not run.

`scripts/check.sh all` passed on the branch head before the merge, including the
release build, and it exited 0 rather than being read off a pipe. Merged into
`main` at `a8de443`, whose tree is byte for byte the branch that was gated,
confirmed with `git diff --quiet`. **Not pushed**: guardrail 7 says publishing
happens on purpose.

**One gate run failed before that one, and it was my doing rather than the
code's.** `.planning/WINDOWS.md` was being edited while the gate was reading
it, so `test_both_halves_of_the_ledger_say_the_same_thing` saw two table rows
whose JSON objects had not been written yet. Both halves agree now and the

already warns that nothing else may be building while a tool reads the tree.

## What the kept bytes buy, in one sentence

**They protect no message.** A move is append then remove and the source server
holds the message at every point where the program can die, so dropping these
bytes loses no mail. What they buy is that an unfinished move can be completed
when the *source* account is the one that is not answering, and that a large
message is not fetched a second time.

No document says otherwise, and `docs/privacy.md` says the negative outright.

### What to do

With two real accounts set up, and after `04.1-03`'s checkpoint has been done:

1. **Start a move** of a message from account one to a folder on account two,
   and **kill the program while it is in flight**. End the process from Task
   Manager rather than closing the window: closing the window may let the move
   finish, which is a different case and not this one.
2. **Start the program again.** What are you told? Write the words down. Do they
   name the message, the account and the folder it was going to, and say where
   the message still is?
3. **Is it read out**, or does it only appear on screen? Listen with NVDA. Can
   you reach both answers by keyboard, and does focus land somewhere sensible?
4. **Does it read as something that went wrong, or as something unfinished?**
   Nothing was lost. If it sounds like an error, that is worth changing.
5. **Answer it, choosing to finish.** Check both servers. Is the message at
   account two **exactly once**, and gone or marked for removal at account one?
   Once is the answer that matters.
6. **Do it again and choose to leave it.** Check the message is still at account
   one and that you are not asked about it again on the next start.
7. **Repeat step 1 with the source account signed out or its password wrong**
   when you come back, and try to finish. This is the case the kept bytes exist
   for and the only one that tells them apart from doing nothing at all.

Write down what was heard and seen, not whether it seemed fine.

### What each outcome means

- **Nothing said at all at step 2:** the store is written and read by nothing.
  That stops the phase; it is the failure this plan's second premise correction
  is entirely about.
- **The message at account two twice at step 5:** the resume appended without
  asking. That also stops the phase, and it is the one way this store can do
  harm that not having it would not.
- **The message once at account two and gone from account one:** working as
  built.
- **Step 7 finishing the move with the source unreachable:** the kept bytes
  earning what they cost.
- **Step 7 failing because the source cannot be reached:** expected and correct
  for the removal half. The append should still have gone. Say which half
  failed.
- Anything that reads wrongly is a ledger entry with the spoken words in it.

## Findings

### A test that reads a store after the operation cannot see when it was written

The first version of `test_a_message_too_large_to_keep_still_moves` asserted,
after the crossing, that the store held nothing. It passed against the wrong
implementation, and it always would have: the clear runs on the way out of every
move, so "nothing was ever kept" and "something was kept and then let go of" are
the same answer by then. It reads the store from inside the append now, through
the same witness `04.1-03` built for the ordering, and only then can it fail.

This is the third time in this phase that trying to break a test, rather than
reading it, is what found something.

### The obvious place for a backstop is the place that makes it do nothing

The natural shape is a public `forget_the_moves_nobody_answered_about` beside
the other eviction functions. Written that way it has no caller, exactly like
`evict_signed_originals_over` and `keep_signed_originals_within_budget`, which
are public, documented, and called by nothing that ships. There is no sweep in
this cache to hang one on, and `moves_that_did_not_finish` is the only place a
leftover row is ever looked at, so that is the only place a backstop can live.
The RED half wrote it the natural way on purpose so the test that caught it is
recorded rather than assumed.

### An eviction rule copied from a cache is backwards for a queue of offers

`signed_original` drops the least recently read, which is right for a cache of
content. Here the oldest row is a move somebody has not been asked about yet and
the newest is one that will be over in seconds, so dropping the oldest takes
away the only offer they will ever get in order to make room for bytes that will
be released almost immediately. Dropping the newest also has a property worth
naming: the sweep can only ever drop the row it was called about, so nothing
here can drop a row it is about to read.

### A guard grew because a second caller arrived, and the count check did not know

Re-measuring the four records the first RED commit flagged found that "an append
the destination never answered is counted as one that landed" now reddens three
tests it did not name. The resume calls the same question, so a version of it
answering yes to everything sends somebody's message to a destination that
already has it. The count check could not have found that: it compares test
counts per file and says nothing about which rule a new test reaches. The record
was corrected by hand with the reason beside it, and the run afterwards agreed
in both directions.

## Deviations from the plan

### [Rule 2 - missing correctness requirement] The date is stored beside the flags

- **Found during:** Task 1, writing the row.
- **Issue:** The plan's behaviour list says the row carries "the destination
  account, the destination folder, the flag list the append will send, the bytes
  and their size". The append also sends the date the source server filed the
  message, which `04.1-02` added deliberately because without it a five year old
  message sorts to the top of the destination folder. A resumed append built
  from a row with no date would file the message as arriving today, and the
  defect would surface only on a resume, which is the path nobody exercises.
- **Fix:** an `arrived` column beside `flags`, carrying the same already
  formatted value the append takes.
- **Files modified:** `src/data/message_cache/mod.rs`,
  `src/data/message_cache/moves_in_flight.rs`,
  `src/application/mail_across_accounts.rs`
- **Commit:** `56ea95c`

### [Rule 3 - blocking] The store is optional at the boundary

- **Found during:** Task 1, wiring `spawn_folder_move`.
- **Issue:** `MessageCache` holds a `rusqlite::Connection`, which is not `Sync`,
  so the `Arc<MessageCache>` the window holds cannot cross into
  `rt.spawn_blocking`. Every other worker in this file opens its own connection
  to the same database, and that can fail.
- **Fix:** `TheMoveAsThisProgramRecordsIt.cache` is `Option<&MessageCache>`, and
  the worker opens its own. When it cannot, the move goes ahead and keeps
  nothing, with the reason at the field: the keeping is a safeguard on top of the
  ordering, and refusing to move somebody's message because a second copy of it
  could not be written would make things worse than not having the store at all.
- **Files modified:** `src/application/mail_across_accounts.rs`,
  `src/presentation/wx_app.rs`
- **Commit:** `56ea95c`

### [Rule 2 - a duplication about to be created] `asking::which_of_the_two`

- **Found during:** Task 1, writing the window's question.
- **Issue:** Reading a two-answer dialog's answer was about to be written a
  second time. `one_question_at_a_time::what_they_said` already does it, but its
  enum names another question's answers, so reusing it would have read

- **Fix:** `asking::which_of_the_two` and `Answered`, beside the flag that

> ### A message being moved to another account is kept until the move ends
>
> Moving a message to a folder on a different account means fetching it from one

> the message stays there until you answer the question you are asked the next
> time you start it, and at most seven days. Answer it either way and the copy
> goes immediately. Say nothing, and it goes on its own after the seven days.
>
> A message larger than 25 MB is not kept at all, and the move happens exactly as
> it would have. If several interrupted moves add up to more than 64 MB, the
> newest one is not kept, so a move you have not been asked about yet is never
> dropped to make room for one happening now.
>
> **This copy does not protect your message, and nothing else here should be read
> as saying it does.** A move puts the message at the second account first and
> only takes it off the first afterwards, so at every point where the program can
> stop, the first account still has it. What the copy buys is narrower: the move
> can be finished even when the account the message came *from* is the one that
> is not answering, and a large message does not have to be downloaded a second
> time. Deleting the copy loses nothing.

The two real numbers are 25 MB and 64 MB, in one sentence, the way the
attachments sub-section gives its two, and the third number is the seven days.

## Accessibility

**What was done.** The words are announced through
`presentation::accessibility::screen_reader` at high priority as well as being
shown, so somebody whose reader was mid-sentence on something else still hears
them. The question is a `MessageDialog` with Yes and No, and Enter answers **No**
through `asking::yes_no_where_enter_answers_no`, because Yes here speaks to two
servers and may take the message off one of them. Closing the window is neither
answer: nothing is written and nothing is sent, and the question comes back next
time.

**What was not done, and why.** The dialog carries no name set through
`set_accessible_name_and_description`. It is a `MessageDialog`, which the
binding builds from a title and a body and offers no accessible-name seam, and
this is the house pattern: `ask_about_the_folders_that_have_gone` does the same.
What a screen reader reads for a message box is its title and its text, and both
are written here.

**Nothing has been heard.** Whether the announcement and the dialog say the same
thing twice over, whether the focus lands sensibly, and whether the words read
as unfinished rather than broken are all questions only NVDA can answer. Ledger
191.
