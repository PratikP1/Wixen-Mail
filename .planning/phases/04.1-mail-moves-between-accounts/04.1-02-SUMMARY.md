# Phase 4.1 Plan 02: A copy that crosses accounts Summary

## Does it work

**Yes, against a loopback server, and no message has crossed between two real
accounts.** That distinction is the whole of what this summary is careful about.

**The window can now name the account you chose, and a test with two accounts
sharing a folder path proves it.** Accounts `a` and `b` in
`tests/one_hierarchy_two_views.rs` both hold a folder at the path `Archive`.
`test_the_folder_the_message_is_in_is_taken_out_of_its_own_account_and_no_other`
asserts that moving a message out of `a`'s `Archive` takes `a`'s out of the
offering and leaves `b`'s in it, and it reads each folder off **the branch it is
drawn under** rather than off the place's own account. Those two agree in working
code, which is exactly why `04.1-01` found a test that read the place and passed
against a build that drew every row under the wrong heading. The guard record
whose break puts the narrowing back reddens all three of the new tests, measured.

**A message copied into another account's folder really arrives there.** The
bytes are fetched from the source with `BODY.PEEK[]` and appended at the
destination with `APPEND`, over that account's own held session. The destination
server's transcript holds exactly one `APPEND`, naming the folder that was
chosen, carrying `\Seen` and carrying `01-Aug-2026`. The source server's
transcript holds no `STORE`, no `EXPUNGE` and no `COPY`.

**The sentence afterwards names the account.** `Copied to Archive in Personal:
Lunch` rather than `Copied to Archive: Lunch`, and a refused copy says
`Nothing was copied. Personal refused it. Lunch is still in INBOX: ...`.

**The window opens with one account showing and the rest closed**, and it is the
one the message is in. Asked of a live control with three accounts, where the
answer is in the third.

**What does not work, said plainly.** Moving a message to another account is
refused in words. It is an append and then a removal at the source, and the
removal is `04.1-03`. Sending `MOVE` at the source would name a folder path on a
server that does not have it.

`scripts/check.sh all` passed on the branch head before the merge, including the
release build. Merged into `main` at `8c21a02`, whose tree is byte for byte the
branch that was gated. **Not pushed**: guardrail 7 says publishing happens on
purpose.

## Three findings

### The plan's test approach could not be built, and the reason is a global

The plan says to write the two-server tests "on the model of `mail_session.rs`'s
test module: two `Conversation`s, two `Account`s pointed at them". That model
cannot assert an append landed, and `mail_session.rs`'s own test module says why
in a comment at line 324: whether a session may write is decided at sign-in by
reading the account's setting out of the profile of whoever is running the suite,
"so an assertion about an append succeeding through one of these would pass on
one machine and fail on another". It tests only the sign-in for that reason.

Measured rather than assumed: `MailController::connect_imap` calls
`allowed::allowed_for(account_id)`, which reads `ConfigManager::load_stored`,
which resolves through `AppPaths::resolve` to `dirs::data_local_dir()` unless
`WIXEN_MAIL_DATA` is set. The default written there has `mail: false`, so on CI
every one of these tests would have failed on the refusal.

So the crossing is written over two traits and the tests drive them with
`ImapSession`s built through `signed_in_to` and `reading_only_on`, which set the
permission explicitly and read nothing. Both traits are the shape
`MailController` already has, so its implementations forward and decide nothing;
everything decided is in `copy_it_across`, which both sides share. The source is
given `reading_only_on`, which proves the crossing needs no write permission at
the account the message is in.

### A refusal test passes when its fixture fails earlier for a different reason

`test_a_source_that_says_nothing_about_the_message_is_not_a_copy_with_no_flags`
asserts that a source naming no message is refused rather than appended blind.
Its first fixture was a generic loopback server answering neither the header
fetch nor the body fetch. The body fetch failed first, so the function returned
an error whatever it did about the headers, and taking the entire UID check out
left the test green.

The fixture now hands the bytes over and names a different UID, which is what a
folder looks like when the message has been taken out from somewhere else between
one command and the next. With the check removed it fails, measured.

The general shape, and it is not about this test: **an assertion that something
comes back as a failure is satisfied by the first failure on the path, not by the
intended one.** A fixture for a refusal test has to be permissive everywhere
except the one place under test. It was found by taking the red by hand rather
than by reading the test, which is the only thing that would have found it.

### A stub that fails everything is a weaker red than a stub that is wrong

The first RED stub for `copy_it_across` returned an error saying a crossing was
not built, which was true of the program. It reddened eight tests of thirteen. It
also did not compile under `-D warnings`, because its collaborators went unused.

The stub that shipped is the crossing somebody writes without thinking: fetch,
fetch, append, carrying nothing. Five tests, and every one of the five fails
because of the thing it is named after. The three the refusal reddened and this
one does not all failed under it for the same unrelated reason, that the copy
never happened at all.

**The count looked better and the measurement was worse.** The eight remaining
reds were then taken by hand, one break at a time, which is where the finding
above came from.
