# Phase 4.1 Plan 01: A destination is a folder in an account Summary

## Does it work

**Yes, and one real defect that shipped is closed.** Moving a message from All
Inboxes used to offer the folders of the account you had open and send the move
to the account the message is really in. Those are routinely different accounts,
which `spawn_folder_move`'s own comment has said in those words since the last
time this fault was fixed. It now offers the folders of the account the message
is in.

**The sidebar and the move window genuinely come from one builder.**
`where_mail_can_go` asks `folder_tree::rows` for the sidebar's answer and
translates it. It decides nothing about which folders exist, which account owns
one, how deep it sits or what an account is called, because all four already had
an answer.

**The test that proves it is green by construction and I am saying so plainly.**
Once the picker really sources from the sidebar's builder, "they agree" cannot
fail: they are one call. What defends the sourcing is three guard records whose
breaks take it away, each measured, and `tests/one_hierarchy_two_views.rs` is
what goes red when they fire. The instrument is the test; the measurement is the
record.

**Nothing here has been heard.** The window now draws a nested tree and names
accounts the sidebar's way, and no screen reader has met either. Ledger 180.

`scripts/check.sh all` passed on the branch before the merge. Merged into `main`
at `4e3ae9a`, whose tree is byte for byte the branch that was gated, so the run

## The finding worth more than the fix

**A guard measurement caught a test that could not see the defect it was written
for, and the mechanism was the test's own projection rather than its fixture.**

`where_mail_can_go` returns a grouped answer: branches, each holding places, and
each place also carrying the account it belongs to. The new target flattened the
branches and compared the flat list of places. The guard record whose break puts
every folder into the first account's branch reddened **nothing at all**, because
every place still carried its own correct account, so the flattened list came out
identical.

Those are two different facts and the window uses both. The branch decides which
heading a row is drawn under, which is what somebody hears above it. The place's
own account is what travels back with the answer and decides which server the
command goes to. In working code they are equal, which is exactly why a test can
read either one and look right.

The target now reads the branch, and
`test_a_place_says_the_account_of_the_branch_it_is_drawn_under` holds the two
together. The break then reddens four tests, and five after a later test in the
same session reached it.

The generalisable form: **a `flat_map` in a test throws away the structure the
code under test was responsible for building.** The question that finds it is
"what would this assertion say if every element were moved into the wrong
group?"

**What the plan got wrong.** Task 2's action says "Every existing caller passes
nought for every place, so the shape those callers produce does not change". That
is false and the plan's own premise correction 3 says why: `where_a_folder_can_go`

therefore changed the folder move's window from a flat list into a tree, which is
an improvement and is not what the sentence forecast.

It also brought a defect with it, which is the second thing the plan did not
foresee. Places attach to the row above them, so a list has to arrive parent
before child, and `where_a_folder_can_go` emitted them in stored order, which is
`ORDER BY id`. A folder made inside another one after a folder was made beside it
gives `Archive`, `Work`, `Archive/2026`, and drawn in that order `Archive/2026`
hangs under `Work`: a folder read out under the wrong parent, which is exactly
what this dialog must not do. It now sorts on the chain of folders each one sits
inside, which is the same bounded walk that answers how deep it is, so
`how_far_in` and the ordering are one walk rather than two. `how_far_in` itself
is deleted, having no caller left.

## The second finding, in the settings census

The record "the move window stops asking where the last one went" was written to
redden the census that asks whether every stored setting is read by something.
Measured, it stayed green, and that exposed a real hole.

The census reads each setting's name in the files that act. `last_filed_into` now
has a reader and a writer, so its name appears nowhere but `config.rs`, and the
census called it ignored. Widening it to follow one hop through a function of
`config.rs` fixed that, and then counted the **writer** as evidence: taking the
read out of the whole program left the census green, which is a setting written
on every move and looked at by nothing, and that is precisely the shape the
census exists to catch.

A function taking `&mut self` is no longer a reader. Rust says which is which in
the signature, so nothing is guessed from the body. Both halves of the reading
are now proved inside the test: that a name this file never writes yields no
reader, and that a pair offers the reader and not the writer. Its limits are
ledger 181 rather than narrowed away.

## The fixture, and why each of its three properties is load-bearing

```rust
AccountInTheTree { id: "a", name: "Work",     address: "ada@example.com" }
AccountInTheTree { id: "b", name: "Work",     address: "grace@example.com" }
AccountInTheTree { id: "c", name: "Personal", address: "katherine@example.com" }

folder("a", 1, "INBOX",             None)
folder("a", 2, "Archive",           None)
folder("a", 3, "Receipts",          None)     // before its own nephew, on purpose
folder("a", 4, "Archive/2026",      Some(2))
folder("a", 5, "Archive/2026/June", Some(4))
folder("b", 6, "Archive",           None)     // two accounts, one path
folder("b", 7, "Old",               None)     // and the server has stopped listing it
folder("c", 8, "INBOX",             None)
```

Two accounts share a label, so the naming rule has both of its answers to give in
one fixture. Two accounts hold a folder at one path, so something has to know
which account a folder belongs to. One folder sits two deep, so the depths do not
agree vacuously. `test_the_fixture_can_tell_the_two_views_apart` asserts all
three, because a fixture without them makes every other test in the file pass
while measuring nothing.

**Task 3's fixture is the other way round on purpose and the summary is asked to
say why.** Its two accounts hold *different* folders, because the question there
is which account was asked, and a fixture whose accounts held the same folders
would answer the same either way. In tasks 1 and 2 the question is whether the
account is consulted at all, and there the paths have to collide. Same principle,
opposite fixture: make the thing under test the only thing that decides.

## Deviations from the plan

**Rule 2, a missing correctness requirement.** `where_a_folder_can_go` had to be
made to emit parents before children, which the plan does not mention. Honouring
depth without it draws a folder under the wrong parent, which is worse than the
flat list it replaces. Written up above.

**Rule 3, a blocking issue.** The two existing guard records on
`wx_destination.rs` both stopped applying: one's `after` no longer compiled and
one's `before` no longer matched. Both were corrected and re-measured.

**A judgement the plan left open, taken the other way.** The plan said to write
`where_mail_can_go` over `&[AccountInTheTree]` and `&[FolderInTheTree]`, taking
the naming from `folder_tree` and the depth from `parent`. It calls
`folder_tree::rows` instead. Two reasons. A depth computed from `parent` does not
agree with the sidebar's for a folder whose parent is missing from the branch or
sits in a cycle, and the sidebar puts both at the top of the branch while a walk
up the parents does not. And nothing needed making public: the whole translation
is written against the existing public API. The cost is that the agreement test
is green by construction, which is written into the target's own module doc.

**Four tests declined, and why.** The plan asks for the account resolution case
in `tests/one_hierarchy_two_views.rs`. It is there, but the decision it tests had
to be extracted into `whose_folders_a_move_is_about` first, because the thing
that could fail is which account is chosen, not a filter given an account.
`owner_of` now resolves through it, so both halves ask one rule.
