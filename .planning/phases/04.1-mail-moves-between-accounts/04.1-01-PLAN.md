<objective>
Make a destination a folder in an account, and build the picker's tree and the
sidebar's tree from one hierarchy.

Purpose: the move and copy window is already a tree of accounts, and three
things inside it compare a folder by its path alone. That is harmless while every
caller passes one account and wrong the moment two arrive, and it is wrong in a
way no fixture in this tree can see, because every one of them gives its two
accounts folder identifiers that could not collide. Sourcing both trees from one
builder comes before widening the picker, because widening doubles the surface on
which the two can disagree.

Output: a picker whose answer names the account, one builder feeding both trees,
and the All Inboxes defect that ships today closed. The picker still receives one
account at the end of this plan. Nothing a person does changes except that moving
a message in All Inboxes stops offering the wrong account's folders.
</objective>

needs a change, it is the return type, and it is task 1.

mail.** `wx_app.rs:8221` is `move_the_chosen_folder`, which moves a folder inside
its own account with `RENAME`, and RFC 9051 gives that command no way to cross an
account. It must not be widened, and this phase leaves it alone except for the
return type. `wx_app.rs:17227` is `move_or_copy_message`, which is the mail one.
`managers.rs:6403` is the PIM one and belongs to phase 5.

one heading, and two comments say otherwise.** `Destination.depth` is computed by
`how_far_in` for a folder move, hardcoded to `0` by the mail and PIM callers, and
read by nothing. `build_destination_dialog` appends every place as a direct child

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored config to picker | `last_filed_into` is read from a file on disk that an older build, or a person with an editor, wrote. Its value now carries two facts in one string. |
| cached folder rows to picker | folder names and paths come from mail servers and are stored, then read back as row labels and as identifiers. |
| picker answer to server command | the value the window answers with becomes a mailbox name in an IMAP command. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-4.1-01 | Tampering | `last_filed_into` stored value | low | mitigate | Read through one pair of functions, and a value that does not parse is read as the account it is keyed under, which is where it always was. Nothing about it reaches a server without first matching a folder that is on offer. |
| T-4.1-02 | Spoofing | account naming in the picker | medium | mitigate | Two accounts that read alike is the failure `so_no_two_accounts_read_alike` exists for. Task 2 makes the picker use its answer rather than a second rule, so a person choosing a destination can tell two accounts apart by ear. |
| T-4.1-03 | Tampering | folder path as an identity across accounts | high | mitigate | Task 1 makes the comparison a pair, so a path from one account cannot resolve to a folder in another. This is the phase's central threat and the reason the identity change comes before the widening. |
| T-4.1-04 | Information disclosure | a message filed into the wrong account | high | mitigate | The All Inboxes defect in task 3 is this exactly: a path chosen in one account sent to another account's server puts somebody's mail in a mailbox they did not name. | T-4.1-05 | Denial of service | stored folder parents holding a cycle | low | mitigate | Depth comes from a bounded walk, `AS_DEEP_AS_A_TREE_GOES`, the bound `how_far_in` and the sidebar already use. No second walk is written. |
