<objective>
Offer every account in the move and copy window, and make a copy across accounts
really put the message at the other server.

Purpose: copy first, because nothing is deleted. A copy that fails leaves the
message exactly where it was, so the whole of the fetch, the append, the flags,
the two sessions and the permission gate on the destination account can be built
and proved before anything is asked to remove the original. The move is
`04.1-03` and it is the same path with one command on the end.

Output: a picker that shows every account, a copy that crosses, the outcome
decided in the one place that decides the others, and a tree that opens on the
account the message is in rather than on all of them at once.
</objective>

<premise_corrections>
**1. The primary safeguard is an ordering, not a store, and the phase context
says otherwise.** The context says the local cache safeguard Pratik chose for the
provider task move applies here in the same shape. It does not, and the
difference decides what this plan has to build.

A provider task move is a delete on one list and a create on the other, and the
failure is between them, which is what `05-07-PLAN.md` is built around. A mail
move is an append at the destination and then a removal at the source, and the
source copy is untouched until the append has answered. So the safeguard for mail
is an ordering, and the ordering already exists in this tree:
`imap.rs:1374`'s no-MOVE path is copy, then flag, then expunge, with a doc
comment saying the copy goes first so a failure leaves the original alone.

The one case an ordering does not cover is an append whose answer never arrives,
where the message may or may not have landed. **That was put to Pratik and is
answered.** Decision 17 of 2026-09-07: both halves are built. The destination is
asked whether it holds the message, in `04.1-03`, and the raw bytes are kept so
recovery does not depend on the server behaving, in `04.1-04`. Neither is this
plan's work, because this plan copies and deletes nothing, and a copy that fails
leaves the message exactly where it was.

Verify: `sed -n '/^## Phase 4.1, answered/,$p' .planning/decisions-2026-09-06.md`,
then `sed -n '1358,1405p' src/service/protocols/imap.rs`, then
`awk 'NR==1&&/^---/{p=1;next} p&&/^---/{exit} p' .planning/phases/05-the-other-five-modules-keep-up/05-07-PLAN.md`.

**2. The cache cannot supply the bytes an APPEND needs.** `message_bodies` holds
`body_plain` and `body_html`, which are a parsed reading. Handing those to an
APPEND makes a different message: header order, folding, transfer encoding and
every attachment change or vanish. The only raw bytes kept anywhere are
`signed_original`, and only for mail that claimed a signature. So the fetch
reaches the source server every time and this plan does not try to avoid it.

Verify: `sed -n '2189,2200p' src/data/message_cache/mod.rs`, then
`sed -n '1,40p' src/data/message_cache/signed_original.rs`.

**3. This can be proved without a live account, and phase 5's equivalent could
not.** `imap::against_a_server_that_answers` gives a loopback IMAP server that
records every line said to it. Two of them are two accounts. So "the append
reached the second server before anything was said to the first" is an assertion
over a transcript rather than a source read or a promise.

Verify: `sed -n '/mod against_a_server_that_answers/,/^    }$/p' src/service/protocols/imap.rs | head -60`,
then `grep -n "pub async fn transcript" -B 2 -A 4 src/common/answering.rs`.

**4. The window opens every account it is given.** `tree.expand(&account)` at
`wx_destination.rs:196` is inside the loop and has no condition. That is correct
for one account and is the accessibility question this plan has to answer,
because it is the first time the window will hold more than one.

Verify: `sed -n '178,199p' src/presentation/wx_destination.rs`.
</premise_corrections>
