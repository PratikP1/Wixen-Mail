# Mail moves between accounts, and it validates the reminder move

Decision of 2026-09-06, Pratik: "I see the mail move/copy issue from account to
account only in tests. We need to address that in a future phase so as to
validate the reminder moving."

Recorded here rather than in `.planning/` because an executor holds the checkout.
Moves in with the phase 5 re-split.

## What is actually true, measured 2026-09-06 at `ad4a49b`

Not "missing". **Built, and never offered.**

- `Branch` at `src/application/destinations.rs:149` carries `account_id`,
  `account_name` and `places`. It is a per-account group of destinations, so the
  type was designed for several.
- `offer()` takes a `Vec<Branch>`.
- The tests below `#[cfg(test)]` at `destinations.rs:306` build one branch at
  `:320` and two at `:354`, so the picker is exercised against more than one
  account and handles it.
- Both production callers build exactly one, hardcoded to the account the item
  is already in: `wx_app.rs:8057` uses `chosen.account.id`, and `wx_app.rs:16794`
  uses `account_id`. `managers.rs:6403` is the PIM equivalent and does the same.

So the work is passing the other accounts' folders into a picker that already
knows what to do with them, plus whatever the move itself needs when the source
and destination servers differ, which is the part that is genuinely new: a
cross-account mail move is a fetch from one server and an append to another,
not a server-side move, so it has the same delete-then-create failure the task
move has.

**I claimed a precedent that does not exist.** When the reminder question was put
to Pratik it said moving a reminder between accounts works "exactly as moving
mail between accounts already works". Mail does not move between accounts. The
answer stands, the stated cost was wrong, and this entry is the correction.

## Why it goes first

Pratik's reasoning, and it is right: a reminder move would otherwise be the
first cross-account move in the program, inventing the pattern and proving it at
the same time. Mail is the case people expect, has the most existing machinery,
and is where a mistake is most visible. Build it there, then the reminder move
follows an established path instead of setting one.

## Where it goes

Proposed: **phase 4.1, "Mail moves between accounts"**, two or three plans,
inserted before phase 5, following the `02.1` precedent for an inserted phase.

Reasoning for that placement rather than folding it into phase 5: phase 5 is
titled "The other five modules keep up" and is explicitly the non-mail modules.
Mail work under that heading fights the title, and a phase is a unit of
judgement. This is a mail verdict.

It must land before phase 5's move and copy work, since that is what it exists
to validate.

## What it must carry

- The same failure shape as the task move: source and destination are different
  servers, so it is a fetch and an append, and something has to survive the gap.
  The local cache safeguard Pratik chose for the task move applies here and
  should be designed once for both.
- A copy across accounts is safer than a move and should probably ship first.
- Nothing may delete at the source until the destination has confirmed. The
  precedent is `one_day_kept_out_of_the_series`, which writes two rows in an
  order chosen so a failure between them leaves a visible duplicate rather than
  an invisible loss.
## The picker is already a tree, and already shared. Measured 2026-09-06.

Pratik proposed a tree view in a dialog for move and copy, sourced from the main
folder list, applying to every move and copy. **Two thirds of that already
ships**, and saying so is cheaper than building it twice.

`src/presentation/wx_destination.rs`, 348 lines, module doc: "One window for
every move and copy: a message into another folder, a task onto another list, an
event into another calendar. A tree of accounts with their places under them,
because two accounts can both have an Archive and a flat list of names makes
those two rows that read identically."

- It builds a real `TreeCtrl`, `HasButtons | LinesAtRoot`, at `:140`.
- It sets accessible names and descriptions, not `set_name`.
- Its own Keyboard section says arrows move, Left and Right collapse and expand,
  typing jumps to a name, Enter chooses, Escape leaves, and that nothing here
  needs a mouse or a drag.
- It is already the single window for every module's move and copy.
- `Destination`'s doc comments were written for it: `name` is the leaf only
  "because the tree says the rest", and `depth` exists "so the tree can be built
  without a second pass".

So the earlier note in this file worrying about a two-level list and screen
reader skimming was solving a problem somebody already solved. Withdrawn.

**What is left is exactly one thing**: the callers pass one `Branch`, hardcoded
to the account the item is already in, at `wx_app.rs:8057`, `wx_app.rs:16794`
and `managers.rs:6403`. Feed the tree every account and the window needs no
change at all.

## The third part of Pratik's suggestion is a real improvement and is not done

"Possibly pull the list of accounts and folders from the main folder list."

There are two shapes for one hierarchy today: `FolderInTheTree` built in
`src/presentation/folder_tree.rs` for the sidebar, and `Destination` built by
`destinations::where_a_folder_can_go` for the picker. They are assembled
separately from the same underlying folders.

That is a divergence waiting to happen: a folder the sidebar shows and the
picker does not, or the two disagreeing about which account a folder belongs to,
would be invisible until somebody moved mail into the wrong place. Sourcing both
from one builder is the fix, and it belongs in the same phase, before the
picker starts showing several accounts and doubles the surface where they could
disagree.
