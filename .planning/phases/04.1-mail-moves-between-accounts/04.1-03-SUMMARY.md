# Phase 4.1 Plan 03: The move that crosses accounts Summary

## Does it work

**A copy across accounts lands, and a move now lands and then leaves, both
against loopback servers. Neither has touched a real account.**

**An upload with no answer really is resolved by asking**, and the asking is
narrower than the plan asked for on purpose. The destination folder is read
before the message is sent as well as after, and only something carrying the
message's identifier that is there now and was not there before counts as an
arrival. Without the before-reading, a folder that already held a message
carrying that identifier would confirm an arrival that never happened, and the
source copy of a message that never left would be removed. That is exactly the
failure the ordering exists to prevent, arriving through the back door.

**Nothing at the source is touched until the destination has answered**, and the
proof is behavioural rather than a source read. Hoisting the removal above the
append makes a named test fail and print the source's transcript with the
removal already in it:

```
the source had already been told to give the message up before the destination
was handed it: ["A0001 LOGIN", "A0002 CAPABILITY", "A0003 SELECT \"INBOX\"",
"A0004 UID FETCH 4 (UID FLAGS RFC822.SIZE INTERNALDATE BODYSTRUCTURE
BODY.PEEK[HEADER.FIELDS (...)])", "A0005 UID FETCH 4 BODY.PEEK[]",
"A0006 UID STORE 4 +FLAGS (\\Deleted)", "A0007 UID EXPUNGE 4"]
```

**What does not work, said plainly.** Nothing in this phase has met a real mail
server. The ambiguous append, which is the case the plan is mostly about, has
never happened against one either: both tests that drive it script the answer
through a hand-written destination, for a reason given below. A message moved
into a folder somebody has turned syncing off for is at the server and never
appears in this program, and only the changelog says so.

`scripts/check.sh all` passed on the branch head before the merge, including the
release build. Merged into `main` at `f944af7`, whose tree is byte for byte the
branch that was gated, confirmed with `git diff --quiet`. **Not pushed**:
guardrail 7 says publishing happens on purpose.

### What to do, part one: two real accounts

Set up two accounts on **different providers** if you can. One provider on both
sides hides the cases that matter, because a provider is consistent with itself.
Then, in this order:

1. **Copy** a message from account one into a folder on account two. Check at
   account two, in webmail or another mail program, that the message is there,
   that it is the same message with its attachments intact, and that it is read
   or unread as it was at account one. Check at account one that the message is
   still there and is not marked for removal.
2. **Look at the date account two shows for it.** If it reads as arriving today
   rather than when it originally arrived, the internal date is not being
   carried. Say so: an archive that sorts wrongly is worth knowing about before
   somebody moves a thousand messages.
3. **Move** a message from account one into a folder on account two. Check both
   ends: at account two it is there, at account one it is gone or marked for
   removal, and the sentence the program said matches what both servers show.
4. **Move a message with an attachment of a few megabytes.** A real upload of a
   large message is the case a loopback server cannot answer at all.
5. **Try a move into a Gmail account** if you have one. Gmail turns a copy into
   a label rather than a second message, and what it does with a message
   uploaded from another account is not known here.
6. **Pull the network out part way through a move**, if you can, and say what the
   program said and where the message ended up. That is the ambiguous append and
   asking the destination is what this plan does about it. **Leave the program
   running while you do this.** Closing it mid-move is a different case, it is
   what 04.1-04 is for, and its own checkpoint asks about that.

**What each outcome means.**

- The message at account two and gone from account one, with a sentence saying
  it moved: working as built.
- The message at both accounts, with a sentence saying it is in both places and
  the row still in the list: **also correct**, not a bug. It means the second
  server took it and the first would not let go. The row staying is deliberate:
  a list that dropped it would be claiming something the server has not done.
- The message at account one only, with a sentence saying nothing was moved:
  correct. The destination refused and nothing was made.
- The message at **neither** account: this is the failure the whole phase exists
  to prevent and it stops the phase. Do not start 04.1-04 on it. Say what the
  program said, and say which step it happened on.
- A sentence naming only the folder and not the account: a defect. Two accounts
  can both have an Archive.

### What to do, part two: a screen reader on the picker

Set up **three or more accounts**, ideally with two of them sharing a label. In
the message list, press `Ctrl+Shift+V` for Move to, and answer these:

1. When the window opens, what is read out? Does it say which folder the cursor
   is on **and** which account that folder is in, or only the folder?
2. Arrow to an account row. Does it read as an **account**, as a collapsed
   branch, and as one of however many? Or does it read as a folder?
3. Press Right on a closed account. Is it announced as opening, and are the
   folders under it reachable?
4. With three or more accounts, is the list of accounts something you can move
   through quickly, or does it still feel like one long list?
5. Two accounts with the same label. Do they read differently? They should carry
   their addresses.
6. A folder nested inside another. Does the tree say how deep it is, and does the
   row read as its own name rather than as a whole path?
7. Choose a folder in an account you are not in. Does what is said afterwards
   tell you **which account** the message went to?
8. Press Enter on a folder. Does it choose that folder? This has never been
   pressed and was read off the code; it is ledger 185.

NVDA first, then Narrator. **Write down what was heard, not whether it seemed
fine.** Anything that reads wrongly is a ledger entry with the spoken words in
it.

**What each outcome means.** Question 2 is the one that stops the phase: a row
that reads as a folder rather than as an account means the tree is being heard as
the flat list it used to be, and the whole of 04.1-02's branch work is not
reaching anybody. Question 7 failing means the account naming this plan built is
not arriving. Everything else is a ledger entry rather than a stop.

## Findings

### An ordering assertion across two servers cannot be made after the fact

The plan says to take both transcripts, find the position of the destination's
`APPEND` and the position of the source's first `STORE` or `EXPUNGE`, and assert
the append was recorded first. **That assertion cannot fail.** Two transcripts
are two independent lists with no shared clock, so an index into one says
nothing about whether it happened before an index into the other. Written that
way, the test passed against a build with the removal hoisted to the top.

It was caught by trying to break it, not by reading it, which is the second time
in this phase that has been the only thing that found something.

The witness has to be taken at the moment that matters. The destination in that
test reads the **source's** transcript from inside `take_this_message`, so what
it records is what the source had been told at the instant the message was
handed over. Anything in that snapshot that changes the source means the removal
went first. Two further assertions keep the snapshot honest: that the
destination really was given the message, and that the source really was told to
remove it afterwards, so an empty snapshot cannot pass for a correct order.

### A stub that asks the question wrong is a better red than one that never asks

04.1-02 found that a stub failing everything reddens more tests and measures
less. This plan is one turn further on. The first stub considered was the naive
move that uses `?` everywhere and never asks anything. It would have reddened
six of the seven. But `-D warnings` made it impossible: `which_messages_carry`
would have had no caller in the library and `dead_code` is a build failure, and
there is no ordering that splits that.

The stub that shipped asks and asks wrongly, in four ways at once: it cannot
tell a refusal from an answer that never came, it searches for an empty
identifier, it reads a message that was already there as one that just arrived,
and it throws the removal's answer away. Seven tests red, each for the thing it
is named after. **The constraint produced a better stub than the free choice
would have.**

### The ambiguous append cannot be produced by a loopback server, and the tests say so

`Turn::HangUp` closes the connection without answering, which is what an
unanswered append looks like from the client. But the connection is then dead,
and the whole point of this plan is that the destination is **asked again**
afterwards. A dead connection cannot be asked. The test double `ADestinationThat`
exists for that reason and its doc says so where somebody meeting it will read it.

What is proved is what the code does with an `Error::Network`. What is not
proved is that a real dropped connection and a real timeout both arrive as one.
Both do in this tree, by reading: `with_timeout` maps a timeout to
`Error::Network`, and `connection_failed` maps `Io` and `ConnectionLost` to the
same. That is a source read and it is ledger 188.

### A retry that is right for a read is a duplicate for a write

`MailController::append_message` goes through
`once_more_if_the_connection_went!`, which signs in again and runs the work over
when the connection went. For a fetch that is correct. For an `APPEND` it means
a server that took the message and lost its answer on the way back is sent the
whole message again, and the account ends up with two copies with nothing saying
so.

`append_message_once` is the same command with no second attempt. **The copy path
from 04.1-02 now uses it too**, which is a fix to shipped code rather than only
to what this plan added, and it is recorded as a deviation below.

The removal keeps the retry, and that asymmetry is stated at the function: the
mark is the same mark whether it is set once or twice, and an expunge of a
message that has already gone finds nothing to do.

## Deviations from the plan

### [Rule 2 - missing correctness requirement] The question takes a before-list

- **Found during:** Task 1, while writing the doc for
  `whether_the_destination_has_it`.
- **Issue:** The plan asks for a function "taking the folder and the identifier
  and answering with three states". A `Message-ID` is a header a stranger wrote,
  and a destination folder can already hold a message carrying it: an earlier
  copy of this same message, or one somebody else put there. With only the
  folder and the identifier, either confirms an arrival that never happened, and
  the source copy of a message that never left is removed. That is the exact
  failure the ordering exists to prevent.

**One thing the threat model did not name, found while building it.** T-4.1-14
and T-4.1-15 both treat the identifier as an input to a command. Neither names
it as an input to a **decision**: a message carrying the identifier being present
at the destination is what authorises the removal, and a stranger who can put a
message into the destination folder chooses what that identifier is. Quoting the
value does nothing about that. The before-list is what closes it, and it is the
reason that parameter exists.
