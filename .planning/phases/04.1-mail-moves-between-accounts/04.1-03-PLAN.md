<objective>
Move a message to a folder on another account, with nothing removed at the source
until the destination has it.

Purpose: this is the phase's point and the only part of it that can lose
somebody's mail. Everything it needs was built and proved in `04.1-02` without
deleting anything: the picker offers every account, the fetch and the append
work, the flags travel, the outcome is decided in one place. What is added here
is the one command on the end and the rule about when it may be sent.

Output: a move that crosses, an outcome for every way it can end, two-server
tests that witness the order, and the documents saying what a person now has and
what has never been tried against a real account.
</objective>

<premise_corrections>
**The decision this plan used to wait on is taken, and this plan builds the
first of its two halves.** `04.1-02` used to end with a decision checkpoint
asking what a move does when the append's answer never arrives. It was put to
Pratik and answered on 2026-09-07, decision 17: "a combination of 1 and 2 by
using the cache". Both halves are built. Do not re-ask it.

**This plan builds the asking half.** After an append whose answer never
arrived, the destination is asked whether it now holds a message with that
identifier, through `uids_with_message_id`, which already exists. It needs no
schema change and writes nothing to anybody's disk, so it is the half that can
ship on its own and the half that makes the other half safe.

**`04.1-04` builds the keeping half**, the raw bytes written before the append so
a move interrupted by the program closing can be finished without going back to
the source server. It is second for a reason that is not sequencing convenience:
**the kept bytes are not actionable without the question.** After a restart you
would hold the bytes and have no way to know whether the append landed, so you
could neither safely re-append, which risks a second copy, nor safely remove,
which risks removing the only one. The question is what tells the resume path
which of those to do. Build the question first and the bytes have something to
join; build the bytes first and there is nothing to read them with.

Verify: `sed -n '/^## Phase 4.1, answered/,$p' .planning/decisions-2026-09-06.md`.

**One thing about the local cache that holds whichever option was chosen.** The
message row in this program's cache is not carried into the destination account.
An appended message has a UID only the destination server knows, and no reply
gives it to us on a server without UIDPLUS, so there is nothing to write. The
source row is marked deleted, the way a same-account move already marks it, and
the destination account's next sync of that folder brings the message in. Say so
in the summary, because "the message is at the server and is not in this
program's list yet" is a thing somebody will notice and should have been told.

Verify: `sed -n '17355,17372p' src/presentation/wx_app.rs`, then
`sed -n '600,640p' src/data/message_cache/messages.rs`.

**And a limit worth finding before somebody else does.** If the destination
folder is not one that account syncs, the message will be at the server and will
never appear in this program until it is. Read `folder_choices` and
`cached_folder_syncs` and settle whether the move should say so, or should turn
the folder's syncing on, or should do neither. Whichever it is, it is a decision
with a sentence, not something to be discovered by a person whose mail has
apparently vanished.
</premise_corrections>

  <name>Task 4: Two real accounts, and a screen reader on the window</name>
  <what-built>
    A message can now be moved to a folder on another account. Nothing is removed
    at the source until the destination has answered that it holds the message,
    and where the answer never arrived the destination is asked again before
    anything is removed. Every way the move can end has one sentence and one
    answer about the row, decided together in `server_delete.rs`. The window
    offers every account and opens on the one the message is in.

    All of that passes its tests against two loopback IMAP servers whose
    transcripts witness the order the commands go in. Nothing in this phase has
    met a real mail server and nothing in it has been heard.
  </what-built>
  <how-to-verify>
    Two things need Pratik and neither can be done from here.

    **A real move between two real accounts.** Set up two accounts on different
    providers if possible, because one provider on both sides hides the cases that
    matter. Then, in this order:

    1. Copy a message from account one to a folder on account two. Check at
       account two, in another client or in webmail, that the message is there,
       that it is the same message with its attachments intact, and that it is
       read or unread as it was at account one. Check at account one that the
       message is still there and is not marked for removal.
    2. Look at the date the destination shows for it. If it reads as arriving
       today rather than when it originally arrived, say so: that is the internal
       date not being carried and it is worth knowing before somebody's archive
       sorts wrongly.
    3. Move a message from account one to a folder on account two. Check both
       ends: at account two it is there, at account one it is gone or marked for
       removal, and the sentence the program said matches what both servers show.
    4. Move a message with an attachment of a few megabytes, because a real
       `APPEND` of a large message is the case a loopback server cannot answer.
    5. Try a move to a Gmail account if there is one. Gmail turns a copy into a
       label rather than a second message, and what it does with an `APPEND` from

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| destination server answer to the removal decision | whether the source copy may be removed rests entirely on what the destination server said, or on what a second question to it said. |
| source server to this program | the message bytes, fetched once, held in memory across a second server's round trip. |
| stored `Message-ID` to a search command | an identifier that came from a stranger's message becomes a `SEARCH` key at the destination server. |
| two accounts, two permissions | the source's Allow Changes governs the removal and the destination's governs the append, and they are different answers. |
