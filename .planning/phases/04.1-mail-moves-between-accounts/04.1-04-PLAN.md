<objective>
Keep the bytes of a message being moved across accounts, so a move interrupted by
the program closing can be finished, and make something read them on the next run.

Purpose: decision 17 of 2026-09-07 chose both halves of the safeguard. `04.1-03`
built the asking half. This is the keeping half, and the thing that makes it real
is not the write. It is the read: a store justified by an interruption is worth
exactly as much as the code that runs after the interruption, and there is no
sweep in this cache to hang that on.

Output: one additive table, bytes that live for seconds on the ordinary path, a
person who is told when a move did not finish, a resume that asks before it acts,
and a privacy page that says what is on the disk while a move is in the air.
</objective>

<premise_corrections>
**1. What the kept bytes buy is smaller than the decision note makes it sound,
and the documents must say the smaller true thing.** The options table this
decision answered said the bytes mean "a move interrupted by a crash can be
finished later", and that reads as though the message would otherwise be at risk.
It would not be. A mail move is append then remove, and nothing is removed at the
source until the destination has confirmed, so at every point where the program
can die the source server still holds the message. **The bytes protect no message.
They save going back to the source server for it.**

That is still worth having, and it is worth having for one reason that is not
convenience: the source account may be unreachable when somebody comes back to
an unfinished move. Credentials revoked, the account signed out, the network
down, the provider having a bad day. With the bytes the append can still be
completed; without them the move waits on a server that is not answering. The
second reason is that a large message is not re-fetched.

Write that, and not more than that, in the changelog and on the privacy page. A
sentence claiming the bytes keep the message safe would be an overclaim in the
one document whose whole job is telling somebody what is on their disk and why.

Verify: `sed -n '/^## Phase 4.1, answered/,$p' .planning/decisions-2026-09-06.md`,
then read the ordering in `04.1-03-SUMMARY.md` and confirm the removal is last in
every ending.

**2. There is no sweep in this cache, so nothing will find a leftover row unless
this plan makes it.** The obvious model, `signed_original`, evicts only inside
its own write: `keep_signed_original` calls `stay_within_the_budget_after_keeping`
and that is the whole of it. `evict_signed_originals_over` and
`keep_signed_originals_within_budget` are public and have no caller in shipped
code outside that module. There is no startup pass, no periodic maintenance and
nothing that ever looks at rows a previous run left behind.

So copying that shape gives a table that is written, cleared on the happy path,
and read by nothing after a restart. **The one case the store exists for would be
the one case nothing reaches**, every test would pass, and a whole message would
sit unencrypted on the disk in exchange for a capability that does not exist.
That is why task 1 is a tracer that runs from the table through to something the
person sees, rather than a data-layer task with the wiring deferred.

Verify:
`grep -rn "evict_signed_originals_over\|keep_signed_originals_within_budget" src/ --include=*.rs`
and confirm every hit outside `signed_original.rs` is inside a `#[cfg(test)]`
module.

**3. A guard will fire, its message will name the wrong fix, and it is right to
fire.** `how_it_arrived.rs` holds two guards over the pair of facts recorded when
a message arrives. One asserts that nothing shipped outside
`src/data/message_cache` calls `.keep_signed_original(` directly, and its failure
message tells the reader to call `note_the_form_it_arrived_in` instead. The other
asserts the exact list of four files that do call it:
`importing_messages.rs`, `mail_sync.rs`, `pop_sync.rs` and `wx_app.rs`.

The bytes this plan keeps are not an arrival. The message arrived long ago and is
already in the cache; these are bytes held for a move. So **do not follow the
first guard's advice**, because doing so reddens the second by adding a fifth file
to a list of arrival paths that this is not one of. Give the new store its own
named function in its own module, and call that. Neither guard should fire at
all if the naming is right; if either does, the naming is wrong.

Verify: `sed -n '400,446p' src/data/message_cache/how_it_arrived.rs`.

**4. This plan adds no setting.** The ceilings and budgets in `signed_original`
and `attachment_content` are constants, `AppConfig` holds no cache-size field, and
the two checks in `config.rs` that would bind, `every_setting_is_acted_on` and
`test_every_setting_somebody_can_change_is_offered_by_a_screen`, read `AppConfig`.
Adding a knob for how long an unfinished move is kept would be a setting, would
have to appear on the settings screen, and is not wanted: the number is a
backstop, not a preference. Use a constant and say in its doc that there is no
measurement behind it, which is the shape `SIGNED_ORIGINAL_BUDGET_BYTES`'s own doc
uses.

Verify: `grep -n "budget\|_bytes\|cache_size" src/data/config.rs`, which returns
nothing today.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a whole message written to disk | the raw bytes of somebody's mail, unencrypted, in a place that did not hold them before. |
| a row surviving a process | state written by one run and acted on by another, with nothing in between to say what happened. |
| resume to destination server | an `APPEND` that may be a second copy of a message already there. |
| resume to source server | a removal decided on the strength of a question asked in a different run of the program. |
| two accounts, two permissions | the append needs the destination's Allow Changes answer and the removal needs the source's, and a resume asks both again. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-4.1-19 | Information disclosure | a whole unencrypted message in a new place on disk | high | mitigate | The row lives for the length of the move, which is normally seconds, and is cleared at every ending. A leftover row goes when the person answers, and on its own after a bounded time. `docs/privacy.md` names the table, what it holds, its ceiling and budget, and when it is cleared, in the same commit that creates it. |
| T-4.1-20 | Tampering | a resume appending without asking | critical | mitigate | The resume asks the destination first, through the same function the move uses, and appends only where the answer is that the message is not there. A guard record's break removes the question so this cannot regress silently. This is the one way the store can do harm that not having it would not, and it is the only threat here rated critical. |
| T-4.1-21 | Repudiation | a row left behind after a finished move | medium | mitigate | The clearing is written so it cannot be forgotten arm by arm, a test asserts no row survives any ending, and a guard record's break leaves the row behind. |
| T-4.1-22 | Denial of service | the table growing without bound | medium | mitigate | A per-message ceiling, a total budget with the newest row giving way, and an age backstop. All three drops are cheap because the source server holds the message throughout, which is the difference from `signed_original` and is written in the module doc. |
| T-4.1-23 | Elevation of privilege | a resume writing to an account whose permission changed | medium | mitigate | Both permissions are asked again on the resume, through each account's own session, because the answer may have changed between the run that started the move and the run that finishes it. |
| T-4.1-24 | Spoofing | a leftover row pointing at an account that no longer exists | medium | mitigate | The destination account id is resolved before anything is sent, and a row naming an account that has been removed is reported and cleared rather than acted on. |
| T-4.1-SC | Tampering | npm, pip and cargo installs | high | mitigate | No package is installed by this plan. If one is proposed, the package legitimacy gate applies and a blocking human checkpoint comes before the install. |
