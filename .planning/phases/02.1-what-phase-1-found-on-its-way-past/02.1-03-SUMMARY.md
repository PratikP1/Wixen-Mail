# Phase 2.1 Plan 03: The pages say folder management is built Summary

Both pages now read true, and two checks would catch the next capability filed
under a heading or a tick that has stopped being true of it. The plan's premise
correction was right and mattered: `docs/IMPLEMENTATION_STATUS.md` was false
through where a paragraph sat, not through anything it said, so a grep for the
sentence that used to be wrong found nothing and any check searching for a claim
of absence would have passed on the day the defect was live.

## The premise, verified rather than taken

Measured before anything was built:

| claim | result |
|---|---|
| every sentence in the Folder management paragraph describes it working | true, `:74-85`, present tense, with its real limits |
| the paragraph sits under `## What does not work` | true, heading at `:72` |
| `grep -n "cannot be created\|cannot be renamed\|not built" docs/IMPLEMENTATION_STATUS.md` | no match, exit 1 |

**One refinement to the plan's premise 1.** It says to move the threaded view
"if the search finds it filed the same way". It is not. `**Threaded view.**` is
at `:62`, under `## What works`, and has been since 01-12. Only folder
management was misfiled on that page.

## What the pages say now

`docs/IMPLEMENTATION_STATUS.md`: the Folder management paragraphs moved out of
`## What does not work` and into `## What works`, after Receiving. Not a word of
the paragraph changed. Every limit it stated is kept: server folders only for
making, renaming, moving and deleting, local folders a fixed set, the two
settings deciding how far emptying and marking read reach, and nothing on the
server side yet run against a real mail server.

**Two headings changed with it, and this went beyond moving a paragraph.** The
deferred entry that recorded this defect said the page needs one answer to what
its headings mean rather than a paragraph moved, and it was right. Moving the
folder paragraph on the reading "this heading means not built" leaves "Anything
that writes, against a real account" under that heading while its own first
sentence says all of it is built. That is the same defect, and encoding the
"not built" reading in a check while the page contradicts it would have been
building on a premise known to be false. So that paragraph now sits under
`## Built, and never run against a real account`, and `## What does not work`
holds only the one item that genuinely is not. This is the smallest edit that
makes the check's reading true of the page.

`docs/roadmap.md:58` is ticked, with what it covers and its limits on the same
item. `_Last updated_` moved to 2026-09-02 on both pages.

## The checks, and how each was proved it can fail

Two guards, one capability table, one code probe. `CLAUDE.md` requires a
companion for a guard that reads documents, because such a guard passes when it
finds nothing to read, and 02.1-02 closed exactly that fault on the version
guard.

**Guard 1**, `test_no_capability_the_code_has_is_filed_under_a_heading_denying_it`,
red on arrival:

```
docs/IMPLEMENTATION_STATUS.md:74: "Folder management" is described under
"What does not work" at line 72, and src/service/protocols/imap.rs holds
fn create_mailbox, fn rename_mailbox, fn delete_mailbox
```

**Guard 2**, `test_no_capability_the_code_has_is_unticked_on_the_roadmap`, red
on arrival:

```
docs/roadmap.md:58: "CREATE, RENAME and DELETE" is unticked, and
src/service/protocols/imap.rs holds fn create_mailbox, fn rename_mailbox,
fn delete_mailbox
```

Five by-hand breaks, each with what it did to which test:

| what was done | guard | companion |
|---|---|---|
| `described_under` stubbed to answer nothing | red, but "stopped reading the page" | **FAILED**: "Folder management" is not introduced anywhere in `docs/IMPLEMENTATION_STATUS.md` |
| the code probe pointed at a file without the mailbox verbs | **went green while the page was still wrong** | **FAILED**: the mailbox verbs are in `src/common/version.rs`, and the probe says they are not |
| the code probe stubbed to answer `true` | red | **FAILED**: the probe found a symbol this client has never had |
| `on_the_roadmap` stubbed to answer `Ticked` | **went green while `:58` was still unticked** | **FAILED**: left `Ticked`, right `Unticked(5)` |
| `on_the_roadmap` stubbed to answer `NotFound` | red, "stopped reading the page" | **FAILED**: no checkbox line says "CREATE, RENAME and DELETE" |

The two rows in bold are the fault criterion 7 was about, reproduced on the new
guards: a reading that has stopped reading makes the guard green, and the
companion is the only thing standing between it and that.

The code probe is a real read of `src/`, and the second row is the measurement
that says so. A true rename of `create_mailbox` was not used, because the
library has to compile for an integration test to run at all; pointing the
probe at a file that does not hold the verbs is the same question asked of the
same reading. The committed companion asks it in both directions on the real
file: `the_code_has` says yes for the mailbox verbs and no for a verb this
client has never spoken.

**The heading matcher was measured against text that is already correct**,
following what 02.1-02 found when a three-word co-occurrence rule named sixty
places almost all asserting the opposite. Asking only that a heading hold a
refusal and a working word calls `## Known gaps in verification` and
`## Which tests would fail if the code were wrong` refusals, and both sit over
things that work. Requiring the refusal within two words of the working word
takes it to exactly one. The companion asserts that, over the real page's own
headings, rather than only asserting that the denying heading is caught. The
new heading added by this plan, "Built, and never run against a real account",
holds "never" and is tested by that same assertion.

The roadmap reading matches a wording only on a line carrying a box. A wrapped
item's continuation line carries none, and matching anywhere would have read
the second line of the ticked thread-view item as an item of its own. Asserted
both ways in the companion.

## The by-hand demonstration found a hole in the check

The plan's acceptance criterion said to move the corrected paragraph back under
the old heading and watch the check fail. **It passed.**

`described_under` answered with the first section that introduces a capability
and stopped, and after the correction the right mention comes first. So a page
that says a capability works in one section and does not work in another was
approved. That is not a hypothetical: moving a paragraph is a deletion and an
insertion, and a hand that makes the insertion without the deletion leaves both.

Closed as its own red/green pair, `36516a5` and `9dc8787`. The reading now
answers with every section, the check complains about each one under a denying
heading, and the companion additionally asserts the real page introduces each
capability exactly once. Repeating the demonstration afterwards:

```
guard:     docs/IMPLEMENTATION_STATUS.md:87: "Folder management" is described
           under "What does not work" at line 85, and
           src/service/protocols/imap.rs holds fn create_mailbox,
           fn rename_mailbox, fn delete_mailbox
companion: "Folder management" is introduced 2 times in
           docs/IMPLEMENTATION_STATUS.md, and it should be once
```

This is the argument for doing the demonstration rather than reasoning about
it. Every automated assertion in the committed companion passed against the
hole, because each fed the reading a page with one mention.
