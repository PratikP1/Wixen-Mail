# Phase 2.1 Plan 05: The two dialogs that leaked a registry entry per row Summary

The leak is gone, and it is gone in a way a test can see: the destination picker
and the conversation view leave nothing in wxdragon's process-global item
registry, counted before and after, and both still resolve a chosen row to the
same answer they gave before.

## What was wrong, measured rather than described

`set_custom_data` and `append_item_with_data` do not put data on a tree row.
They put it in `wxdragon::widgets::item_data::ITEM_DATA_REGISTRY`, a static
`HashMap` behind a `LazyLock`, keyed from a monotonic counter, and store the key
on the row. Nothing takes anything out again.

Before this plan, opening the two dialogs left:

| dialog | fixture | entries left after the dialog was destroyed |
|---|---|---|
| destination picker | one account, two folders | 2 |
| conversation view | three messages | 3 |

One per row, for the life of the process.

## The premise corrections

**The upstream defect is worse than the plan recorded, and worse than the guard
said.** Both said `cleanup_all_custom_data` "returns early on any item with no
children and so never clears a leaf". It does return early on a leaf, and that
is not the reason nothing is cleared. `clean_item_and_children` calls
`remove_item_data` **nowhere at all**, for a leaf or for a branch: it walks the
tree and releases nothing. So the escape hatch clears nothing for any tree, and
the same walk is what runs automatically when the control is destroyed. Recorded
as ledger entry 41 rather than absorbed, and the sentence corrected in
`folder_tree.rs` and in `guards/guards.toml`.

**The plan's premise 5 was wrong, and it was the load-bearing one.** It said
neither dialog can be built in a test process, because the budget is one live
window per process and `theme_reach.rs` and `checkbox_labels.rs` have each spent
theirs, and concluded that the pairing could only be proved by pure tests plus
the source read, with the summary saying plainly that no window was opened.

The budget is per process. `cargo test` gives each file under `tests/` its own
process. `tests/tree_selection_raises.rs` already spends a second one. So a new
test file buys another live window for the cost of a file, and this plan opened
two of them. That matters because the leak has no assertion a pure test can
make: without a live window the plan's own success criterion could only have
been met structurally.

**The record's claim that the leak has no observable behaviour was wrong.** It
said so as the reason the guard is a source read, and the reasoning had stopped
at the widget API, where there is indeed nothing to see. The registry's own
surface is enough: `store_item_data` and `get_item_data` are both public and the
keys are monotonic, so a throwaway entry either side of a build fences exactly
the keys that build issued, and asking the registry for each of them counts what
is still live. The narrower claim that is true has replaced it: the folder tree
is drawn inside a running application, so nothing can fence a build of it, and
the source read is what stands between it and the leak.

## The test that would have caught it

`tests/tree_rows_leave_no_registry_entry.rs` builds both dialogs in one live
window, fences each build, and counts what is still in the registry after the
dialog is destroyed. Against the tree as it stood it failed with the two numbers
in the table above. Against the tree now it passes.

It carries its own proof that the counting works, sequenced as the first act of
the same test function rather than written as a companion beside it: a companion
`#[test]` runs on another thread and would issue registry keys inside the
fences, so its own planted entry would be counted as a dialog's leak. The
planted entry is stored, fenced, counted as one, and removed. A fenced count
that always answered zero would pass the assertion at the bottom of the file
without having looked at anything, and this is what says it does not.

`tests/tree_dialogs_resolve_the_row_somebody_is_on.rs` is the other half.
Extracting the resolution into a function a pure test can call moved the
untested part to the line that calls it rather than removing it, so this file
drives the real thing: it builds each dialog, selects every row in turn the way
a person arrows through the tree, and reads the answer out of the same place the
dialog reads it. Its picker fixture gives both accounts the same name and both
an `Archive`, which is what a label chain cannot tell apart.

That test settled something nobody had written down as an assumption. The
conversation view resolves inside its own `EVT_TREE_SEL_CHANGED` handler, so it
asks `is_selected` while handling a selection change. Whether that sees the new
selection or the old one was not known. It sees the new one: the conversation
half of the live test passed on the commit where the picker half was still
deliberately wrong.

## What I broke by hand, and what happened

Four breaks, each applied by hand, run, and reverted, then written into
`guards/guards.toml` so the run can take them again.

| break | what went red |
|---|---|
| `set_custom_data` back in the conversation view | the source-read guard names `wx_thread_view.rs calls set_custom_data`; the registry count says "the conversation view left 3" |
| `append_item_with_data` back in the destination picker | the guard names `wx_destination.rs calls append_item_with_data`; the count says "the destination picker left 2" |
| an account row pushing the first folder under it | the live resolution test reddens in three places at once, the vector's contents and both account rows, and names each |
| the conversation view reading the row after the one chosen | the same test names all three conversation rows |

Two more reds were taken as committed red halves rather than by hand, and both
were deliberately wrong reachable answers rather than absent ones, because the
lint denying dead code refuses an unreachable stub:

- the conversation view's ordering function answering the order the nodes arrive
  in, which is what the append loop did before. Five of the six new tests failed
  against it. The sixth, `test_the_root_means_the_whole_conversation`, passed,
  and honestly so: it is about what a selection means, not about the ordering,
  and it goes red under the fourth break in the table above.
- the picker's resolution answering the row after the one chosen. Two of the
  three new pure tests failed against it, and so did the live test.

**The fixture guards itself.** The conversation fixture's third message replies
to the first, so the order the nodes arrive in and the order the tree is walked
are different sequences, and
`test_the_fixtures_two_orders_really_do_differ` asserts that difference. A
fixture whose two orders agreed would let the arrival order pass as the walk
order and every ordering test in the file would have read as green on arrival.

## The guard's exception list

Empty. It now reads as:

```rust
// Nothing is excepted. Two files were, the destination picker and the
// conversation view, and both were fixed in 02.1-05: they hold their
// rows in a vector beside the control now, the way this tree does. So
// every `.rs` file in the layer is read, and a file that starts doing
// this is what the check is for.
```

Emptying it makes the guard read two more files in `src/presentation`, and it
named neither. **There is no third instance.** A grep over both dialogs for the
six row-data calls returns one match each, and both are backticked mentions
inside comments explaining why the calls are not there; the guard matches
`.{call}(` and sees zero.

## Guard records

Four added, two per dialog, taking the file to 556 records (192 swept on
2026-08-12, 364 arrived since). Each names the break in the table above and the
target it reddens. They are what makes the two new integration targets run on
the commits that could break them rather than only on the commits that change
the test file, which is the rule 02.1-04 wrote into `CLAUDE.md`. Verified:

```
$ bash scripts/check.sh --suites-for guards/guards.toml \
      src/presentation/wx_destination.rs src/presentation/wx_thread_view.rs
tree_rows_leave_no_registry_entry
tree_dialogs_resolve_the_row_somebody_is_on
```

The count check stayed quiet, as the plan predicted: no existing record names
either dialog, so the six and three tests they gained flagged nothing, and no
`--remeasure` command was printed or run. `tests_last_seen` for the four new
records was measured on 2026-09-02 with the same reader `house_style` uses.

**One gap, reported rather than fixed.** A record couples the commit gate only
through its `suite`, and a `suite` names one integration target, so the
source-read guard in `folder_tree.rs` still cannot be coupled to anything: it is
a `--lib` test, and it runs on commits that change `folder_tree.rs` and on
nothing else. Emptying its exception list widened what it reads without widening
when it runs. The two behavioural targets cover the same defect on the same
commits, which is why this is a note rather than a task.

## Deviations from Plan

### 1. [Rule 2] Two live-window test files the plan said were impossible

**Found during:** reading premise 5 against `tests/tree_selection_raises.rs`.

**Issue:** the plan specified pure tests plus a source read and required the
summary to say plainly that no window was opened. The phase's own CONTEXT says
"every criterion here is a defect being closed, so each gets a test that would
have caught it", and no pure test can see a leak.

**Fix:** two new integration targets, each with its own process and its own live
window. The leak is counted; the resolution is driven end to end.

**Files:** `tests/tree_rows_leave_no_registry_entry.rs`,
`tests/tree_dialogs_resolve_the_row_somebody_is_on.rs`.

**Commits:** 64e4b50, 380d431.

### 2. [Rule 2] A shared walk module rather than the walk written twice

**Found during:** task 1, on realising task 2 needs the same thing.

**Issue:** the plan describes the walk in both tasks and names no home for it.
Writing it twice is the defect this plan removes, in a new place.

**Fix:** `src/presentation/tree_walk.rs`, used by both dialogs and by both live
tests. It is not testable in `--lib` (every function needs a real control) and
its doc says where its tests are.

**Commit:** 8c5c10c.

### 3. [Rule 1] Two false sentences about the upstream defect

**Found during:** reading `wxdragon-0.9.17/src/widgets/treectrl.rs` to confirm
premise 1.

**Issue:** the guard's doc comment and its record both said the cleanup returns
early on a leaf and so never clears a leaf. It clears nothing for anything.

**Fix:** both corrected, and the ledger entry states the mechanism.

**Commit:** ba63125.

### 4. [Rule 2] A row that cannot be appended closes the conversation dialog

**Found during:** task 1.

**Issue:** the plan does not say what happens when `append_item` returns `None`.
With a parallel vector, one row short leaves every row after it resolving to the
message before it.

**Fix:** the builder returns `None`, which is what it already does for a missing
root, and `show_thread_dialog` maps that to Cancelled. Not tested: an FFI null
cannot be forced from a test.

**Commit:** c98d1af.

### 5. Both builders return one more value

`build_destination_dialog` returns the destinations vector, which `ask` needs.
`build_thread_dialog` returns the tree, which `show_thread_dialog` does not need
and the live test does: choosing a row is the whole of what the dialog does and
there is no way to choose one without the control. `tests/theme_reach.rs` was
updated at both call sites.
