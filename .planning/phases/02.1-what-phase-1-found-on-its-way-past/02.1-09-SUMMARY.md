# Phase 2.1 Plan 09: A dialog refuses a value it cannot show Summary

**A rule carrying a field this build has never heard of now survives a trip
through the dialog, because it never takes one.** Both editors refuse to open
it and say why, and the stored rule is untouched.

## What somebody is told

Selecting such a rule and pressing Edit brings up a box captioned "Not opened",
saying:

> This condition cannot be shown: it asks about the sender_name of a message,
> which this version does not understand.
>
> Nothing has been lost: it is still in the list, exactly as it was stored. You
> can delete it and write a new one here. If a newer version of Wixen Mail
> wrote it, it still works there.

The first clause is the same sentence a saved search says when it cannot run,
taken from `NotUnderstood::why` rather than written a second time. The filter
manager's box says "This filter cannot be shown", because that is the word its
own rows are called everywhere else in that window.

The rule stays in the list, still showing the words it was stored with, and
Delete still removes it. That is asserted twice: `what_a_condition_row_says`
gives back the stored name in a unit test, and a real `ListCtrl` holding one is
still emptied by `delete_selected` in `tests/manager_delete_stays_open.rs`.

## Both doors, and how each was traced

The plan's premise 6 said one function is reached by the saved-search condition
manager and the filter manager alike, citing 02-07's collapse of two calls into
one. **It is wrong, and following it would have fixed one window and reported
two.**

- `grep -rn "show_rule_edit" src/ tests/` returns one call site,
  `wx_managers.rs:3101`, inside `show_rule_manager_dialog`.
- What 02-07 collapsed was the **Add and Edit pair inside one manager loop**,
  not the two managers. `run_manager_loop` calls `open_one(dialog, None)` for
  Add and `open_one(dialog, Some(&current))` for Edit. Add has no stored word
  to fail on, which is why the plan's fifth behaviour holds by construction.
- The filter manager reaches `show_filter_edit` through its own
  `run_manager_loop` call, and that function has its own
  `build_filter_edit_dialog` and its own pair of `unwrap_or_default` reads at
  what were lines 3443 to 3449. The same defect, written out again.

So the doors are: `show_rule_manager_dialog` to `run_manager_loop`'s Edit branch
to `show_rule_edit`, and `show_filter_manager_dialog` to `run_manager_loop`'s
Edit branch to `show_filter_edit`. Both now refuse. The check that holds them
there names both functions and both builders, so neither can be fixed while the
other is reported as fixed.

## What I broke by hand, and what happened

Two breaks, each applied by hand and run against the whole 6,060-test library.

**Emptying `what_stops_this_being_shown`,** which is what the code did before
this plan: five tests red, all written here, nothing else in the library
noticed. That is the guard record. `scripts/guards.sh` then agreed with the
hand measurement.

**Taking the pre-open refusal out of `show_rule_edit`,** so the dialog really
does open on a condition it cannot show: **exactly one test red**, the source
read. That is thin, and it is written into the guard record rather than left
for somebody to find. It is thin for a reason the phase already knows: every
path that tells a refusal from an opening ends at `show_modal`, which blocks
with nobody to answer it, so a test that opened the editor would hang the
commit gate rather than fail it. 02.1-07 recorded exactly this about the
vanished-folders window, and a test that hangs on the failing case is weaker
than the weak one it replaces.

The source read has a companion that puts the same reading to five made-up
bodies: one that refuses at both ends, one that never asks, one that opens
first and complains after, one that refuses the open and not the write, and one
whose ask is commented out rather than deleted. Each is reported. Without it a
reading that found nothing would pass and look identical to one that found
everything, which is criterion 7's whole subject.

## Is criterion 10 worth what it costs

**No, and I would say so before starting rather than after.** The decision
record already called it the lowest-value criterion in the phase; what I can
add is the measured cost and one thing the cost bought that the criterion did
not ask for.

The refusal itself is about thirty lines of production code. Around it: 721
lines added across six files, four commits, two whole-library runs to measure
the breaks by hand, nine guard-record runs, and roughly three hours, most of it
waiting for cargo.

The subject is unreachable. It needs somebody running a newer build to write a
rule using a field a later version added, then opening it in an older build,
and there has been no public release. I went looking for a second way in and
found one: a condition emptied by the pre-02-04 read-back holds `field: ""`,
which this refusal also catches. That case is reachable in principle and
unreachable in practice for the same reason, since only a developer's own
database can hold one.

What it bought that was not on the list is worth more than what was:

- **A second editor nobody had counted.** `show_filter_edit` carried the same
  defect and was not in the plan, the criterion, or D-2.1-02.
- **One reading where there were about to be three.** `what_it_cannot_read` was
  the search's own; both dialogs were going to grow their own if anything else
  ever asked.
- **A sentence with a hole in it, fixed.** `why()` on an empty word read "it
  asks about the  of a message", which is reachable today from data the
  pre-02-04 bug wrote.

That is a real return on three hours. It is not the return the criterion
promised, and none of it needed criterion 10 to be found: a survey of what the
two editors do with a stored word they cannot read would have found all three
in twenty minutes. **If the trade comes up again, spend the twenty minutes and
skip the criterion.**

## Deviations from the plan

### Wrong premises, reported rather than built on

**1. `show_rule_edit` is not shared by both managers.** Premise 6. Traced
above. The consequence is that the fix is in two functions rather than one, and
that "both doors" means two managers rather than Add and Edit.

**2. The reading already existed at a coarser grain.** Task 1 said to write one
function over a whole condition. `SavedSearch::what_it_cannot_read` at
`saved_searches.rs:1088` already asked exactly this over a search's whole
question list, field before way of matching, using the same two vocabularies.
The plan's `read_first` named `NotUnderstood`, `SAVED_BY_ANOTHER_VERSION`, the
filters vocabulary and `Question`'s fields, and not the method that already
answered the question. What was actually needed was the per-condition grain,
with the existing method delegating to it.

**3. Five records name `wx_managers.rs`, not four.** The plan said four for
`wx_managers.rs` and three for `saved_searches.rs`, measured 2026-09-02. The
count check flagged **five** for `wx_managers.rs`; three for
`saved_searches.rs` was right. All eight were re-measured with the
`--remeasure` command the check printed, and all eight redden exactly the tests
they name. Only the counts moved: 70 to 76 and 36 to 44.

**4. `files_modified` was short by two.** `tests/manager_delete_stays_open.rs`
is in the plan's own `<verify>` command and not in its file list, and
`.planning/WINDOWS.md` was needed for the screen reader gap the plan's own
instructions ask for.

### Auto-fixed

**[Rule 2 - missing critical functionality] `NotUnderstood::why` on an empty
word**

- **Found during:** Task 1, working out what the write-path refusal would
  actually say.
- **Issue:** `format!("it asks about the {field} of a message, ...")` with an
  empty field gives "it asks about the  of a message", a sentence with a hole
  where the answer belongs. The empty string is exactly what the pre-02-04
  read-back stored, so this is reachable from stored data today, and it is the
  only word the new write-path refusal can meet.
- **Fix:** two arms saying what is true when there is no word: "it does not say
  which part of a message it asks about" and "it does not say how the message
  is to be compared". Not a second wording of the same fact; the right words
  for a different fact.
- **Files:** `src/application/saved_searches.rs`, `docs/changelog.md`.
- **Commit:** a5d0689.

**[Rule 1 - bug] The refusal's advice was false for one of its two causes**

- **Found during:** Task 2, after the first draft was already committed to in
  the guard record.
- **Issue:** the sentence ended "Delete it if you no longer want it, or open it
  in the version of Wixen Mail that wrote it." A word this build has never met
  arrives two ways: from a version that has met it, or from something that
  wrote the word wrong. **This program is on the second list.** A condition the
  pre-02-04 read-back emptied was written here, so that advice sends somebody
  back to the build they are already using.
- **Fix:** "Nothing has been lost: it is still in the list, exactly as it was
  stored. You can delete it and write a new one here. If a newer version of
  Wixen Mail wrote it, it still works there." The newer version is offered
  conditionally rather than asserted, and a test on the empty-word case asserts
  that.
- **Files:** `src/presentation/wx_managers.rs`, `guards/guards.toml`,
  `docs/changelog.md`.
- **Commit:** ced6f8b.

**[Rule 3 - blocking] The sweep census at the top of `guards/guards.toml`**

## Upstream, not absorbed

`wxdragon 0.9.17`'s `ListCtrl::get_item_text` answers `"sender_nam\0"` for a
cell holding `"sender_name"`: one character short, with a NUL in its place.
Windows ledger 28, met again here. `tests/manager_dialog_labels.rs` carries a
helper that allows for it, and copying that helper into a second test file
would be a second copy of a workaround for somebody else's defect, so the new
real-widget check asserts removability and leaves what the row says to the unit
test. The comment in the test says so rather than reading as an omission. The
ledger still records it as unreported upstream.

## What the phase leaves undone, from here

This is the last plan of 2.1, so what follows is what I can see from inside it
rather than an audit.

**Nothing in this phase was confirmed by ear, and the phase added to the
backlog rather than drawing it down.** The ledger holds 42 open entries, 27 of
them `unrun-verify`, and most of those are somebody needing to hear a window.
Entry 49 is mine. Guardrail 2 says accessibility is not done until a screen
reader confirms it, and by that measure a good deal of what this phase and
phase 2 built is structurally right and experientially unmeasured. That is the
phase's largest standing debt and it is not a defect in any plan; it needs a
session with NVDA rather than another plan.

**The guard sweep after this branch has not been run.** `CLAUDE.md` takes
re-measurement off the critical path and asks for
`scripts/guards.sh --touched-by <the commit the branch left main at>` after
merging. I ran the nine records the count check named, which is the net rather
than the sweep: a test added in a module a record has never named can still
redden it, and only the sweep sees that.

**Mutation testing has not been run over anything this phase added.** The rule
in `CLAUDE.md` is `scripts/mutants.sh --since <a real commit or tag>`, and no
plan in 2.1 that I can see ran it. What this plan added is exactly the shape
mutation testing keeps finding gaps in here: a function that switches on a
string and returns one of several sentences. My tests walk both vocabularies in
both arms, which is the lesson from the `filters` passes, but that is a belief
rather than a measurement until a run says so.

**Two things the scope note deliberately parked are still parked, and one of
them is getting older.** The `wxdragon` `ListCtrl::get_item_text` defect is now
worked around in one test file, met and refused in a second, and still
unreported upstream. Guardrail 9 says the goal is a better ecosystem; carrying
an upstream defect in a ledger for a second phase without filing it is the part
of that guardrail nobody is doing. The `said_and_shown` census floor in
`wx_managers.rs` was noted by 02-06 as slack by nine and has still not been
measured, and a census that is slack is a guard that has quietly stopped
guarding, which is the exact shape `CLAUDE.md` warns about two paragraphs
before it.

**One thing this phase proved about itself.** Every one of the nine plans found
a check or a claim green while defending nothing, and every one corrected at
least one premise. Nine for nine is not a run of bad luck in the planning; it
is what a re-check against the tree finds when the notes are a day or two old.
The phase's own working rule, that a record is a measurement with a date and it
perishes, applies to plans as well as to guard records, and the cheapest place
to spend the next hour is probably making that re-check something the planner
does rather than something the executor discovers.
