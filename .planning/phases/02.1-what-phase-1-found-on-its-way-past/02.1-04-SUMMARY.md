# Phase 2.1 Plan 04: A guard in tests/ runs on the commits that could break it Summary

**It works, and it was proved by hand rather than by its own suite.** A commit
changing `src/presentation/wx_managers.rs` now runs `--test manager_dialog_labels`
alongside the unit tests beside that file, because `guards/guards.toml` says the
two are coupled and `scripts/check.sh` now reads it. Two guards that had no
record, so the gate could not find them, have one.

## Does a guard in tests/ now run on a commit that could break it

Yes. Staged a comment into `src/presentation/wx_managers.rs`, ran the gate
unmodified, and it printed:

```
== the tests that reach what changed ==
-- presentation::wx_managers
-- manager_dialog_labels (coupled to what changed by guards/guards.toml)
-- the guards that read the whole tree
```

That middle line is the whole plan. Before this, `manager_dialog_labels` ran
only when `tests/manager_dialog_labels.rs` itself changed.

The negative half came free from the commits themselves. Both task commits
touched `scripts/*.sh` and `guards/guards.toml` and no `src/*.rs`, so
`which-checks.sh` answered **`affected`** and the scoped Rust run was **the
tree-reading guards only**, with no `(coupled ...)` line. That is what the
mapping should do for a change with no source module in it, and it is what it
did.

And the mapping answers the two new couplings:

```
$ bash scripts/check.sh --suites-for guards/guards.toml src/presentation/wx_item_form.rs
checkbox_labels
$ bash scripts/check.sh --suites-for guards/guards.toml src/presentation/wx_managers.rs
manager_dialog_labels
manager_delete_stays_open
```

## What was broken by hand, and what happened

Four breaks, each reverted after.

| break | what went red |
|---|---|
| the already-run filter removed from the mapping | 3 cases: `wx_app.rs` answered `wired`, `draft_copy.rs` answered `house_style`, and the mixed fixture answered `alpha house_style` |
| the `src/*.rs` filter removed | 3 cases: a record breaking a test file, a script and a workflow all answered their suite |
| the scan unanchored from column 0 | 1 case: a record's `before` block answered `      suite = "ghost` instead of `alpha` |
| the wiring, tested by staging a real source change | not a break: the positive run above, which no case in the suite covers |

That last row is the point of the exercise. **Every case in `check.test.sh` was
green while the wiring was untested**, because the suite asks the mapping
questions and never asks whether `run_the_tests_that_reach_what_changed` calls
it. The mapping and its call site are two things, and only the staged run
proves the second.

## Two things the by-hand run found that were not the job

**The gate had a fork bomb in it.** `check.sh` runs every `scripts/*.test.sh`,
and `check.test.sh` runs `check.sh`. Before the `--suites-for` dispatch existed,
that argument was read as a mode, fell past every branch, and ran the whole
gate, which ran the suite, which ran the gate. It had to be killed by hand. An
unrecognised argument is now refused with a usage line before anything with a
side effect, and a case in the suite asserts both halves: that an unknown
argument is refused, and that each of the five modes `which-checks.sh` can
answer is not.

**A tree-reading guard run could hide half of itself.**
`cargo test --test house_style --test wired` ran two targets and stopped at the
first that failed, so a red `house_style` meant `wired` never started. That is
exactly the defect `test_one_failing_target_does_not_hide_the_rest` exists for,
and it was silent, because its exemption is `line.contains("--test ")` and that
is true of a line naming two targets as much as one. Moving the targets into an
array took the literal flag out of the text and the guard spoke. Fixed with
`--no-fail-fast`. The over-wide exemption is left as it is and recorded, because
narrowing it is a change to a different guard: **windows ledger 40**.

## The red half could not be committed, and that is a real limit

The plan asked for the failing suite to be committed with a `Fails-until-green:`
trailer, and said to report it as a finding if the gate could not hold a shell
suite to a named failure. It cannot. Measured by hand: one case in
`check.test.sh` was broken, staged, and the gate run with a message naming that
case. The run printed

```
== the scripts that decide what runs ==
FAIL [the manager window's dialog-label guard is coupled to the window]: ...
check: 1 case(s) failed
```

and stopped there. `check.sh` runs the suites under `set -e` before it branches
on the mode, so the `red` branch is never reached and `red-commit.sh verdict` is
never consulted. Past that ordering there is a second wall: `verdict` reads
cargo's `test NAME ... FAILED` lines, which a shell suite never produces, so a
named shell case would report as never having run.

Recorded as **windows ledger 39**, and written into `CLAUDE.md` beside the
red-commit rules, because that is where somebody looks. Until it is fixed, a new
shell suite and the code that makes it pass arrive in one commit that says which
cases were red and what they said. That is what the task 1 commit does.

## Premises checked, and three of them wrong

**Premise 1 was short by three.** It lists four couplings from a source module
to an integration target. Measured today there are seven distinct source files
carrying a `suite`:

| source file | suite | in premise 1? |
|---|---|---|
| `src/presentation/wx_managers.rs` | `manager_dialog_labels` | yes |
| `src/presentation/wx_app.rs` (5 records) | `wired` | yes |
| `src/main.rs` | `wired` | yes |
| `src/application/draft_copy.rs` | `house_style` | yes |
| `src/presentation/managers.rs` | `house_style` | no |
| `src/presentation/wx_settings.rs` | `house_style` | no |
| `src/presentation/wx_folder_choice.rs` | `house_style` | no |

The three missing ones are all `house_style`, which the gate already runs
unconditionally, so the conclusion survives untouched: the only coupling this
change makes real today is `wx_managers.rs` to `manager_dialog_labels`. But the
enumeration was wrong, and it mattered enough to check, because three more
source files now take the "already run, drop it" path.

**Premise 2 was right.** Neither `tests/checkbox_labels.rs` nor
`tests/manager_delete_stays_open.rs` appears anywhere in `guards/guards.toml`.
Checked before building on it.

**Premise 3 was wrong about the second file.** It says
`tests/manager_delete_stays_open.rs` "checks a delete that leaves the list empty"
and suggests breaking whatever makes such a delete close the window. That
decision exists, as `what_it_still_needs` and `nothing_stops_this_closing` in the
modal loop, and **nothing in that file reaches it**. The file's one test is
`test_delete_removes_the_right_row_against_real_widgets`, and it is about
`delete_selected` and `delete_selected_contact` removing the right row, marking
the state changed, repainting, and saying the right sentence. The plan's
suggested break would have reddened nothing. The break used came from what the
file asserts.

Premise 3's other half was right: each suite holds exactly one `#[test]`
function for the one-live-window-per-process budget, and both new records say so
the way the existing `manager_dialog_labels` record does.

**Premise 4 was right.** `which-checks.sh` answered `affected` for both task
commits and `run_the_tests_that_reach_what_changed` has no case for
`scripts/*.sh`, so the Rust half was the tree-reading guards only. That is
correct: what changed is the gate, and the gate's own suite is what judges it.

## The two records, and what the whole library said

Both breaks taken by hand, one at a time, with the whole library run as well as
the suite.

| record | break | red, at the suite | red, in the library |
|---|---|---|---|
| a check box carries its own label | `CheckBox::builder(parent).with_label(field.label)` loses its label | `test_every_check_box_in_a_form_carries_its_own_label` | none, 5,997 tests pass |
| a delete says how many rows are left | `left` read before the row is removed instead of after | `test_delete_removes_the_right_row_against_real_widgets` | none, 5,997 tests pass |

**The whole-library run found nothing the suite run did not, for either break.**
`house_style` and `wired` pass through both, and `manager_dialog_labels` passes
through the second. That is not a weak pair of breaks, it is what these two
guards are for: a check box's accessible name only exists once the platform
builds a real control, and the delete count is computed in the caller that the
sentence builder's own tests never run.

`scripts/guards.sh` then measured both records by name, one build and one run
each, and both came out clean in both directions: "the one test named went red,
and nothing else did". No unfiltered sweep was run, as the plan asked.

**A limit of the record format, found while writing these.** `scripts/guards.py`
runs only the record's own suite, and resolves every name in a `red` list to
`tests/<suite>.rs` when a `suite` is given. So a record with a `suite` **cannot**
record that its break also reddens library tests: naming one would report it as
never having run. For these two breaks that costs nothing, because neither
reddens anything in the library. For a future break that does, the record will
be silent about half of what it reaches, and only the summary beside it will say
so.

## The suite's own assertion shape had to change

Four cases in `check.test.sh` pinned the exact set of suites the real registry
couples to `wx_managers.rs`. Task 2 added a record for that file, and those four
cases went red for having done their job. They now ask whether a suite is among
the answer. The exclusions stay exact, because those are genuinely claims about
the whole answer: a file no record names, or one coupled only to a target the
run already ends with, must answer nothing at all.

Worth stating plainly, because the plan's own ordering produced it: an assertion
that pins the contents of shared, growing data fails on every addition to it, and
a suite that reddens when somebody adds a guard record teaches people not to add
guard records.
