# Phase 2.1 Plan 08: A menu per kind of folder tree row, and two accounts of one name Summary

Six context menus for twelve kinds of row, decided by one pure function, and
account branches that stop reading their email address aloud unless two of them
share a name.

## What each kind of row now offers, and how somebody reaches it

The menu key is the Applications key or `Shift+F10`, on the row the cursor is
on in the folder tree. Nothing else changed about reaching it, and no
accelerator was added, so `docs/KEYBOARD_SHORTCUTS.md` is untouched.

| Row kind | Menu | Why |
|---|---|---|
| `Folder` | mail folders, unchanged | it is a folder |
| `Pinned` | mail folders, unchanged | a copy of a folder (D-30); every command reaches the folder it copies |
| `SavedSearch` | saved search, unchanged | 02-07 |
| `Account` | account branch | its own branch: where its folders live and where the reordering gesture moves it |
| `PinnedIn` | account inside a group | names the account, but is not the branch its folders live in |
| `SavedSearchesIn` | account inside a group | same shape as `PinnedIn` |
| `Labels` | labels | the group of labels, and the manager is the only route to any of it |
| `Label` | labels | one of them, edited in the same one place |
| `AllInboxes` | none | names no account, holds nothing of its own |
| `Favourites` | none | as above |
| `OnThisComputer` | none | as above |
| `SavedSearches` | none | as above |

**Account branch**, five entries, and every one acts on the account the row
names: check this account for mail, new folder, folders to keep up to date,
move this account up, move this account down. The first three read whichever
account is open. That is safe here and only here among branch rows, because the
selection handler sets the open account from the row's own identity through
`the_account_a_row_belongs_to` (`wx_app.rs:2552-2563`). Move up and down act on
the row directly through `what_the_gesture_moves`.

**Account inside a group**, two entries: check this account for mail, folders to
keep up to date. New folder is left off because a folder made from there appears
in the account's own branch and not under that row, so the entry would name the
wrong place. Move up and down are left off because `what_the_gesture_moves`
answers `Nothing` on those rows, so the entry would be a line that refuses.

**Labels**, one entry: the label manager. Short and true, rather than longer and
borrowed. Nothing in this program acts on a single label from the tree.

**Four rows get no menu.** All Inboxes, Favourites, "On this computer" and the
saved searches heading. Nothing this program does acts on one of them: each is a
group of other rows, none names an account, and every command that could go
there reads whichever account is open, which on those rows is whichever account
somebody came from. That is T-2.1-25 exactly.

No command was invented. All five new actions raise ids the menu bar already
raises: `ID_CHECK_MAIL`, `ID_NEW_FOLDER`, `ID_MOVE_UP`, `ID_MOVE_DOWN`,
`ID_TAG_MGR`. `tests/wired.rs`'s `test_every_context_menu_line_has_a_handler`
covers them, and `test_no_two_entries_in_one_menu_share_a_mnemonic` walks all
sixteen focuses.

## What criterion 12 actually fixed, which is not what it asked for

**Both halves of the plan's premise about criterion 12 were wrong.** Reporting
them rather than building on them changed what got built.

**`where_a_row_sits` is live production code.** The plan measured it as having
no production caller and prescribed "wire it or remove it". It has one:
`wx_app::the_row_on_screen` (`:13793`) compares each row's chain of words
against the chain walked up from the control, and `which_row` calls that on
every folder tree selection. The premise was scoped to the defining file and to
`tests/`, and never to sibling source files. Acting on it would have deleted the
function on the main control's selection path. It is kept, and its doc comment
now names its caller.

**Two accounts of one name did not draw rows that read alike.** Not because of
anything in `folder_tree.rs`, which has no defence and whose test helper built
two same-named accounts freely. `the_accounts_in_the_tree` filled each name from
`Account::display_name`, which is `"{name} <{email}>"`, and the accounts table
declares `email TEXT NOT NULL UNIQUE`. Two facts in two other layers, neither
mentioned where the defect was filed.

So the property was real and **unowned**: a change to the caller would have lost
it in silence. And the way it was held cost something the criterion never
mentioned. Because the address went on unconditionally, **every account branch
read a full email address aloud, every time**, to serve a case that has never
happened.

What was fixed: `so_no_two_accounts_read_alike` decides from the set of accounts
being drawn, before anything is worded, so an account nobody else is named after
reads as its name and nothing more, and two that share a name both get their
addresses. Names are compared by how they are spoken, so "Work" and "work" count
as one name. The caller passes the name and the address apart and lets the tree
decide. Row identities are untouched, and a test pins that, so a tree collapsed
before this opens the same way after it.

### Departures from the plan's design, taken deliberately

**3. Four rows get no menu, where D-2.1-03 says every branch kind gets one.**
The plan told me to give a row with nothing true of it "a focus whose list is
honestly short rather than borrowing another kind's". An existing test,
`test_everything_that_can_hold_focus_offers_something`, forbids a focus with an
empty list, and weakening it would make `Focus` mean two things. So the decision
function answers `Option<Focus>` and `wire_context_menu` takes a closure
returning one. `Focus` keeps meaning "a place with a menu", the existing test
stays load-bearing, and absence is a decision the type carries.

The precedent was already in the codebase, in a comment inside
`tests/wired.rs`'s `test_the_menu_key_is_given_to_every_list_and_tree`: the
reminders sidebar "holds buckets rather than containers somebody made, and there
is nothing to do to one, so it has no menu rather than an empty one".

D-2.1-03's reasoning is kept. It rejected no menu on a branch row for losing
genuinely useful per-account commands, and none is lost: every row that names an
account keeps its own menu.

**4. Choosing which folders are kept up to date moved onto the account menus
rather than off them.** The plan's acceptance criterion called it one of "the
two folder-only commands". It is not: its handler reads `active_account_id` and
never the row, and its own wording asks about this account's folders as a set.
Excluding it from the account branch would have removed exactly the kind of
per-account command D-2.1-03 refused to lose. The test written for it is the
general rule instead: a command that reads the open account is offered only
where landing on the row set the open account from the row.

**5. `wx_app.rs` changed more than the closure.** Eleven `wire_context_menu`
call sites gained `Some`, the helper's bound changed, and
`the_accounts_in_the_tree` stopped composing the address. The invariant behind
that acceptance criterion holds: **`wx_app.rs` gained no test function**, so
none of the thirty-two guard records naming it was disturbed, and
`git diff main -- src/presentation/wx_app.rs | grep -c "^+.*fn test_"` is 0.

## Breaking what was built, by hand

**The menu decision.** Making `which_menu_a_row_offers` answer the mail folders
focus for everything that is not a saved search, which is the code as it stood
from 01-14 until this plan, was applied by hand and run against the whole
6,039-test library: five tests red, and all five written in this plan. Nothing
else in the library notices a folder tree that offers a folder's commands on a
heading, which is what the fault having been live for a phase and a half already
said. Recorded as `guards/guards.toml`'s "a row that is not a folder is not
offered a folder's commands", and `scripts/guards.sh` then agreed.

**The disambiguator.** Removing it is what the RED commit e6a2250 measured: five
tests red with the disambiguation absent, held to that list by
`scripts/red-commit.sh`, which also required that nothing else failed.

## Accessibility

The menus are reached by the Applications key or `Shift+F10` and every entry
carries a mnemonic, held apart per menu by
`test_no_two_entries_in_one_menu_share_a_mnemonic` and, on the menu bar side, by
`test_no_two_items_on_one_menu_claim_the_same_letter`. No accelerator was added,
so `docs/KEYBOARD_SHORTCUTS.md` needed no change.

Two things need hearing and are recorded in `.planning/WINDOWS.md` rather than
claimed:

- Whether the new entries are announced, and whether the menu key doing nothing
  on four rows reads as "nothing to do here" rather than as a key that failed.
  That is the risk this design takes on purpose: silence teaches as little as an
  item that does nothing, and only a real run says which is worse.
- Whether the shorter account branch labels are an improvement by ear, and
  whether an address on two branches and not on a third reads as a
  disambiguator rather than as an inconsistency.

No window was opened in a running build for this plan. The whole of both
criteria is decided by pure functions over a row's identity and over the set of
accounts, which is why they are testable without one, and the one integration
test that does build a control,
`tests/folder_tree_rows_pair_with_the_control.rs`, was run and passes.
