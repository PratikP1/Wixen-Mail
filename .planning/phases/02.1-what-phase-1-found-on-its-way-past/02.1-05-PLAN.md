Stop the destination picker and the conversation view hanging row data off
their tree controls, and hold the rows beside the control instead.

`delete_all_items` does not clear, and whose cleanup returns early on any
childless item, which is every row these two put data on. So each opening of

Output: two dialogs holding their own rows, and a guard with nothing left on
its exception list.
</objective>

<premise_corrections>
**1. The leak is confirmed upstream and the mechanism is exactly as recorded.**
`wxdragon 0.9.17`'s `cleanup_all_custom_data` walks from the root through
`clean_item_and_children`, and that function's first act is to return when
`get_children_count(item, false) == 0`. Every row these two dialogs put data on
is a leaf. So `wx_destination`'s `tree.cleanup_custom_data()` at `:87` clears
nothing at all, and `wx_thread_view` never calls it, which means the second
dialog leaks unconditionally and the first leaks despite appearing to clean up.
That is an upstream defect and this plan works around it rather than fixing it:
record it in `.planning/WINDOWS.md` beside the `ListCtrl::get_item_text` entry
the ledger already carries, because guardrail 9 says a gap papered over here
should stay visible.

**2. The criterion says a parallel vector "which is what `collect_rows` already
does", and the hard half is not the vector.** Building a list alongside is
trivial. Reading the selection back off it is the part with no obvious answer,
because `wxdragon`'s `TreeItemId` has no equality and its pointer is not public,
which `folder_tree.rs:765-780` states as the reason `where_a_row_sits` walks
label chains.

**There is a better answer than label chains and it was found by reading the
API.** `TreeCtrl::is_selected(&TreeItemId) -> bool` exists at
`wxdragon-0.9.17/src/widgets/treectrl.rs:739`. So a depth-first walk that asks
each item whether it is selected gives the selected row's index without ever
comparing two items, and `wx_app.rs:13749` already records the property that
makes the index meaningful: the build appends depth first and `collect_rows`
walks depth first, so the two line up by position. Use that. Do not use label
chains here: they carry criterion 12's ambiguity, two accounts with one name
collapse to one row, and importing that into a dialog that decides where mail
is moved would trade a leak for a silent wrong destination, which is the exact
failure `wx_destination.rs:146-150` warns about.

**3. That warning comment is about to become false and goes with the change.**
It says matching rows by position would be one list and one tree that have to
stay in step and that the failure is silent. It is the reason the item data was
used. What makes the position answer safe here is that neither tree changes
after it is built: nothing is inserted, removed or re-sorted while the dialog is
open. Say that in the comment that replaces it, because it is the load-bearing
condition and the next person needs to know what would break it.

**4. `wx_thread_view` already builds a parallel vector and does not use it for
this.** `items: Vec<Option<TreeItemId>>` at `:193` exists to find each node's
parent. Its order is `nodes` order, which is not the control's depth-first walk
order, so it cannot be indexed by walk position. The ids must be produced by a
depth-first traversal of the node structure, which is a pure function over
`nodes` and is where this criterion's real test lives.

**5. Neither dialog can be built twice in one test process.** The budget is one
live wxWidgets window per process, and `tests/theme_reach.rs` and
`tests/checkbox_labels.rs` have each spent theirs. So the pairing is proved by
pure tests over the ordering functions plus the source-reading guard, and the
summary says plainly that no window was opened, which is what
`.planning/WINDOWS.md` is for.
</premise_corrections>
