# Phase 2.1 Plan 07: The question nothing asked, and the marker read as the wrong kind Summary

A one-letter forward marker is now read as a forward marker, so a reply to one
says it is a reply and a forward of one does not stack a second marker. The
window that asks about vanished folders is still not exercised at run time, and
what it is asked is now read from its source with a companion proving the
reading works.

## Whether it works

**Criterion 13 works, end to end, and the values were measured.** Before this
plan, `format_reply_subject("I: Ebéd")` returned `"I: Ebéd"` and
`format_forward_subject("I: Ebéd")` returned `"Fwd: I: Ebéd"`. Now they return
`"Re: I: Ebéd"` and `"I: Ebéd"`. Those two functions are what the compose box
puts in the Subject box when somebody presses Reply or Forward, so the fix is on
a path a person reaches, not only in a predicate.

Every marker `mail-parser 0.11.5` knows is now read as the kind it is, checked
by a sweep over both of its prefix sets: 22 forward, 18 reply. One is excluded
and the test says why, below.

**Criterion 6 does not work in the sense of the window being exercised, and the
plan did not claim it would.** The four things
`ask_about_the_folders_that_have_gone` decides before it opens anything are read
out of its source and asserted one by one. The window has still never been
opened in a running build. Ledger entry 42 records that.

## Premise corrections

**1. Criterion 13's stated symptom is not the one this defect has, and the plan
was right about that.** Verified here rather than taken on trust:
`is_a_forward_marker` is read only by `opens_with_a_reply_marker` and
`opens_with_a_forward_marker`, and a grep of `src/` and `tests/` for either name
returns exactly two call sites, `src/presentation/wx_compose.rs:174` and `:188`.
Nothing in threading reads either. The roadmap says a forwarded Hungarian
message joins the conversation it is a reply to; no code path can produce that.
The mechanism is real and reproduced exactly. The observation log already
carries this as 141.

**2. The plan's reason for not using a live window is wrong, and its conclusion
is right.** Premise correction 3 says the budget of one live wxWidgets window
per process has been spent by `tests/theme_reach.rs` and
`tests/checkbox_labels.rs`. That is not how the budget works: a file under
`tests/` is its own process and gets its own window, which is what 02.1-05
established when it bought the test that counted a registry leak after its own
plan had said no window was available.

So the availability claim was checked rather than accepted, and the strong test
was traced. Every argument of the function is public and constructible;
`WxUIState`, `UIUpdate`, `Pending` and `OneAtATime` are all `pub`. The blocker is
elsewhere. To tell a correct argument from a constant you have to reach the
branch where the two disagree, and every one of those ends at
`MessageDialog::show_modal`, which blocks until somebody answers and in a test
nobody does. The one branch that returns early on both a right and a wrong
argument is the `cache.as_ref()` guard, which returns before anything
observable happens either way. So the live test would **hang** on a broken call
site rather than fail on it, and a check that hangs the commit gate is one that
gets deleted.

The correct reason is written into the test's own comment, in place of the
plan's. Recorded in the observation log as 168.

**3. Seven guard records name `tests/wired.rs`, not six.** The plan's premise 5
predicted six. The count check named seven, and printed a `--remeasure` command
scoped to exactly those. All seven were re-measured: each still reddens exactly
the test it names, and no red list had grown. The seventh is "the main window is
read whole rather than cut at its first test module", whose `file` is
`tests/wired.rs` itself rather than a `src/` module, which is probably why the
count of six was taken from the `src/`-guarding ones.

**4. Two numbers in `conversations.rs`'s comments were wrong.** The module doc
said `mail_parser` carries nineteen reply markers, and `opening_marker`'s doc
said forty-one words in total. `mail-parser 0.11.5` has eighteen and
twenty-two, so forty. Corrected, and the count now has a home where something
checks it: the two arrays in the tests are `[&str; 18]` and `[&str; 22]`, and
the compiler counts them. The count of languages appears in four places, was not
measured here, and was left alone rather than restated.

## What was built

### Task 1: the vanished-folders question

`tests/wired.rs` gained two checks and three helpers, 264 lines.

`what_the_vanished_folders_question_asks` reads one body and answers four
things: that the decision is handed the one-question gate's answer, that the
typing answer reads both ways somebody can be typing, that nothing opens when
the decision answers with nothing, and that the question is written down before
the window opens. It reads the argument list of the `what_to_raise` call by
counting brackets rather than finding the first `)`, splits it on top-level
commas only, and follows each argument to the `let` that binds it. Both the
argument and its binding are read, because `turn` is taken from the gate on one
line and asked `is_none()` on another, and reading either half alone misses
what the other says.

`test_the_question_about_vanished_folders_is_put_at_a_moment_that_is_free` puts
that reading to the real body, with a distinct message per assertion.
`test_the_reading_of_the_vanished_folders_question_can_see_a_missing_argument`
puts it to six made-up bodies: one written the way the real one is, and one per
break.

**Taken red by hand, three times.** The gate's answer replaced by `true` at the
call site: one test red in `wired`, and its message named the gate assertion.
The typing answer replaced by `false`: one test red, and its message named the
typing assertion. The whole library was run against the first break and noticed
nothing, which is why the record names the `wired` suite rather than `--lib`.
Then the reading itself was made to answer an empty string, and the companion
failed on three of its four fields.

Guard record: "the vanished-folders question is put at a moment that is free",
`suite = "wired"`, one test in its red list.

### Task 2: the one-letter forward marker

`is_a_forward_marker` now asks two ways and takes either yes as a yes. The
trailing probe is unchanged. The bracketed probe hands `thread_name` the word
and one other inside square brackets: inside brackets `mail_parser` treats a
forward prefix and a reply prefix differently rather than alike, so the answer
is the other word alone for a forward prefix of any length, and the whole
subject for anything else.

Neither probe knows a marker. Both ask the dependency about one word, which is
the property the old doc comment existed to protect and which the fix keeps.

The tests carry `EVERY_FORWARD_MARKER` and `EVERY_REPLY_MARKER`, read out of
`mail-parser 0.11.5`'s `parsers/fields/thread.rs` on 2026-09-02, with that
provenance in the doc comment. A dependency upgrade that changes either set
fails the sweep rather than changing a subject line quietly.

**Taken red by hand.** The bracketed probe removed and the whole library run:
four tests red, exactly the four the RED commit named, two on the
classification and two on what a person sees. Written into the guard record
"a one-letter forward marker is read as a forward marker", on `--lib`.

`test_no_list_of_markers_ships` was green on arrival, so it was taken red
separately by hardcoding `if word == "i" { return true; }` into the shipping
half, which is the shape of the defect it is about. It failed and named the
word. The hand grep for a quoted marker in the shipping half with comments cut
returns **0**.

## Known limitations

- **The vanished-folders window has never been opened in a running build.** The
  four decisions before it opens are read from source, which says the call is
  written correctly and does not say the window behaves correctly. Ledger 42.
- **Arabic's forward marker is two words and takes a marker it does not need.**
  `opening_marker` hands everything before the first colon over as one token,
  and `thread_name` reads only the first word of it, finds `إعادة` is neither
  kind of marker, and gives the subject back. So the token is not a marker at
  all and neither probe is ever put to it. The test names it, asserts it is read
  as no kind of marker, and explains why, so a change there fails rather than
  passing quietly. Not fixed: `opening_marker` taking a whole multi-word token
  is a change to what counts as a marker at all, which is wider than this
  criterion.
- **The count of languages in four comments is unmeasured.** Two counts of
  markers were wrong and are corrected; "seventeen languages" was not counted
  and is left as it was rather than restated with false confidence.
- **No screen reader has heard any of this.** Nothing here is spoken, but a
  subject line is read aloud, and no NVDA run has confirmed that
  `Re: I: Ebéd` reads sensibly.
