<premise_corrections>
Four things the criterion says that were re-checked against the tree on
2026-09-02, and three of them came out differently.

**1. There are sixteen readers, not ten, and they are of two kinds.** Twelve
test functions in `tests/wired.rs` hold the prefix cut, at lines 1788, 1837,
1902, 2180, 2205, 2823, 2880, 2919, 2952, 2984, 3127 and 3167, one per function.
A thirteenth reader, `without_test_modules` at `:2580`, walks lines and drops
test modules at the margin; it has four call sites, at `:1358`, `:2484`, `:2551`
and `:2773`. Its own doc comment says a file with production code between two
test modules loses that code, "which makes it blind rather than wrong", and
`src/common/what_ships.rs`'s module doc names that same routine as the fourth of
the four answers it was written to replace. So this plan converts sixteen sites
and deletes one helper, and the criterion's "ten" is the count somebody wrote
down rather than the count in the tree.

**2. The comment at `tests/wired.rs:1352` is itself stale in the same
direction.** It says "Two other guards still cut that way and between them
cannot see about eight thousand lines." There are twelve, and they are blind to
6,863 lines each. That comment goes with the change rather than being left to
contradict it.

**3. `common::what_ships` already exists and is already the one answer.** It is
`pub mod what_ships` at `src/common/mod.rs:19`, gated `#[cfg(test)]`, so
`--lib` tests reach it and integration tests in `tests/` do not, because those
link the library built without `cfg(test)`. The criterion frames this as a
choice between shipping it, moving it to a test-support crate, or duplicating
it; D-2.1-01 settles that, and what is left is the mechanism.

**4. The mechanism was measured rather than assumed, in a throwaway crate, on
2026-09-02.** With a `[features]` section holding `what-ships` and a
dev-dependency of the package on itself requesting that feature:

- `cargo test` passes `--cfg 'feature="what-ships"'` when building the library
  for every dev target, so an integration test reaches the gated module.
- `cargo build --release` passes no feature cfg at all. The only occurrence of
  the feature's name in a verbose release build is rustc's `--check-cfg`
  declaration, which announces that the name is spelled correctly and enables
  nothing.

So D-2.1-01's condition, that the feature cannot reach a public release, holds
by construction. `scripts/check.sh`, `scripts/build-installer.sh` and
`.github/workflows/ci.yml` need no change, and none is in this plan's file list.
Clippy's `--all-features` still lints the gated code, so it cannot rot behind
the flag.

**What this plan is allowed to find and not allowed to fix.** The phase context
says anything newly surfaced is in scope to report and may not be in scope to
fix. Task 4 is where that is decided, and it is a blocking checkpoint rather
than a judgement made while converting a reader.
</premise_corrections>
