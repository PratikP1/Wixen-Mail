**Gathered:** 2026-09-02

<domain>
## Phase Boundary

Thirteen recorded defects and stale documents that belong to no other phase.
This phase adds no capability. It closes things that were found while building
something else, written down rather than fixed, and would otherwise stay
written down.

**Where the thirteen came from, because the provenance is the argument for
doing them at all.** Six were routed here on 2026-08-31 from phase 1's deferred
items, after three others went to phase 3 and two to phase 6. Three came from
phase 2's own deferrals. Three came from the observation log, which is where
this project records friction it had no room to fix at the time. One came from
`.planning/WINDOWS.md`, the ledger of things known and unproven.

**Each was re-checked against the tree on 2026-09-02 rather than trusted from
the note that recorded it, and two came out worse than logged.** The doc
comments claiming a test cannot build a wxWidgets window are five places, not
three, and one states it flatly. The version guard is not historically
disarmed, as `CLAUDE.md` describes it: it is disarmed now, reading two files
that between them name no version at all, so it iterates over nothing and
passes unconditionally.

The full criteria are in `.planning/ROADMAP.md` under Phase 2.1. This file
records the decisions the criteria left open.

<decisions>
## Implementation Decisions

### The three that were genuinely decisions rather than fixes

- **D-2.1-01:** `common::what_ships` goes **behind a cargo feature that dev and
  test builds turn on**, and criterion 4's ten checks in `tests/wired.rs` call
  it instead of cutting at the first `#[cfg(test)]`.

  Chosen on the condition that it cannot reach a public release, and that was
  verified rather than assumed on 2026-09-02: every `cargo build --release` in
  the tree passes no feature flags, in `scripts/check.sh`, in
  `scripts/build-installer.sh` for both crates, and in `ci.yml`. So a
  non-default feature is absent from every shipped binary. `--all-features`
  appears only in clippy invocations, which produce no artifact.

  Two consequences that are wanted rather than tolerated. Clippy's
  `--all-features` means the gated code is still linted, so it cannot rot
  unnoticed behind the flag. And if the feature is ever off when the tests run,
  `tests/wired.rs` fails to **compile** rather than quietly reading nothing,
  which is the correct failure direction for a criterion that exists because
  six checks passed in silence while reading 77% of a file.

  `Cargo.toml` has no `[features]` section today, so this introduces the first
  one. The alternatives were a separate crate, rejected as a workspace member
  and a build unit for sixty lines of string handling, and a plain `pub mod`,
  rejected for putting a source-slicer in the library's public surface where it
  invites use it was never meant for.
  — **Reversibility:** reversible, and cheaply. The feature can become a plain
  module or move to a crate later without changing what the ten checks read.

- **D-2.1-02:** A rule naming a field this build has never heard of is
  **refused with a sentence naming the field**, rather than opened and silently
  rewritten. Nothing is stored that the dialog could not show.

  **This is the lowest-value criterion in the phase and is planned last.** The
  case needs somebody running a newer build to write a rule using a field a
  later version added, then opening it in an older build. There has been no
  public release, so nobody has an older build. 02-04 already closed the half
  that was reachable, where the dialog could not show five of the eleven fields
  it does know about.

  It is kept because a silent rewrite of a stored rule is the shape behind
  every data-losing bug this project has found, and refusing costs a sentence
  and a guard. It is the first thing to cut if the phase runs long, and the
  plan must not make anything else depend on it.

- **D-2.1-03:** **Each branch kind gets its own context menu.** An account
  branch offers what is true of an account, a group heading offers what is true
  of the group, and neither offers folder commands.

  Today `wire_context_menu` answers `Focus::MailFolders` for everything that is
  not a saved-search row, so account branches, the Favourites branch, the
  Labels heading and "On this computer" all offer "Get older messages" and
  "Folders to keep up to date" on rows that are not folders. True since 01-14
  and D-29; 02-07 gave only the saved-search row its own focus, which is the
  mechanism to follow.

  The work is deciding, per branch kind, what belongs, which is why this was a
  decision rather than a fix. The alternatives were no menu at all on a branch
  row, rejected for losing genuinely useful per-account commands, and one
  shared branch menu, rejected as thin and certain to be outgrown.
  — **Reversibility:** reversible per branch kind.

### What the criteria already settle, recorded so the planner does not reopen them

- **Criterion 7** wants the version guard able to see a violation. `CLAUDE.md`
  already states the rule such a guard needs: one that reads documents needs a
  companion proving the reading can see a violation when one exists. Several
  guards here carry one. This is that pattern applied, not a new invention.

- **Criterion 8** corrects five doc comments, not three, and the correction is
  a budget rather than a prohibition: a library test can build one real
  wxWidgets dialog per process, and a second prints `initializing twice?` and
  hangs. 02-04 measured both directions.

- **Criterion 12** is about `where_a_row_sits` pairing by label chain, so two
  accounts called "Work" collapse to one row. The comment on that function
  already says so.

</decisions>

<constraints>
## Constraints

- **Every criterion here is a defect being closed, so each gets a test that
  would have caught it.** A fix without one leaves the phase having spent its
  time and learned nothing, and several of these were already written down once
  and not fixed.

- **Criterion 4 changes what ten existing checks read**, from 77% of
  `wx_app.rs` to all of it. Expect them to find things. Four of the ten already
  failed loudly when a test module moved mid-file; six passed in silence, which
  is the defect. Anything newly found is in scope to report and may not be in
  scope to fix.

- **Criteria 10, 11 and 12 all touch the folder tree and its menus**, which
  02-07 and 02-08 changed. Read those summaries before planning them together.

- No new capability, no version bump for the phase as a whole, and every
  user-visible change gets its `docs/changelog.md` entry in the same commit as
  the change.

</constraints>

<risks>
## Risks

- **Criterion 4 is the one that can grow.** Making ten blind checks see the
  whole file may surface violations they were never able to report. That is the
  point, and it is also unbounded until it is run. The plan should make the
  reading change first and separately, so what it finds is visible before
  anything is built on top of it.

- **Criterion 7 risks being satisfied without being fixed.** A guard that reads
  documents and finds nothing to read passes. Writing a companion that proves
  the reading works is the criterion; making the original guard green is not.

- The spellcheck flake, the `wxdragon` `ListCtrl::get_item_text` defect and the
  `said_and_shown` census floor are recorded in the roadmap's scope note and are
  deliberately **not** criteria. The first is diagnosed only as far as reading,
  the second is upstream and wants reporting rather than fixing here, and the
  third was noted rather than measured. None should be picked up in passing.

</risks>
