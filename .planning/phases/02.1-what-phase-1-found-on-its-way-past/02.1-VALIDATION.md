# Phase 2.1: Validation Strategy

> Per-phase validation contract for feedback sampling during execution.

**What is different about this phase.** It adds no capability. Every one of its
thirteen criteria is a defect being closed, and the phase context makes each
one's test a condition of closing it: a fix without a test leaves the phase
having spent its time and learned nothing, and several of these were written
down once already and not fixed. So the question this file usually answers, how
much of a new feature is sampled, is replaced by a narrower one: for each
defect, does something now fail that would have failed on the day the defect was
live?

Nine of the twenty-four tasks below are guards rather than features. Four of
those nine are red on arrival, which is the strongest form of the answer.

---

## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework** | Rust built-in `#[test]`, with `tokio-test` in dev-dependencies for the async paths this phase does not touch |
| **Config file** | None. `cargo test` reads `Cargo.toml`. Guard records live in `guards/guards.toml` |
| **Quick run command** | `cargo test --lib <module>::`, or `cargo test --test <target>` for a guard under `tests/` |
| **Full suite command** | `bash scripts/check.sh all`, which is the merge gate and is not any plan's to run |
| **Estimated runtime** | Quick: seconds to a minute. Whole gate: about 350 seconds warm, of which the suite is 239 and the release build 56 |
| **Scale** | 5,974 library tests as of `02-08-SUMMARY.md`, 2026-09-01, plus 22 files under `tests/` |
| **Guard records** | 544 as of `02-08-SUMMARY.md`, with the sweep header reading 192 + 352 |

Three things about this project change how those numbers read, and all three
bear on this phase in particular.

**Use `bash scripts/check.sh`, never `cargo test` alone, when a whole answer is
wanted.** Cargo shares build fingerprints between `check`, `build`, `test` and
`clippy`, so a clippy run following a build can report success without linting
anything. The script touches `src/lib.rs` first to force the work.

**No plan in this phase runs `scripts/check.sh all` or `scripts/guards.sh`
unfiltered.** The merge gate and the guard sweep are the orchestrator's. What a
plan may run is `scripts/guards.sh --remeasure "<name>"` scoped to exactly the
records the commit gate names, which is the printed remedy rather than a sweep.

**A green suite does not mean the tests would notice.** Red and green started at
commit 182 of 344, so many tests here describe the code rather than specify it.
Every code task below is RED-first, and every guard this phase adds is taken red
by hand at least once, because a test that has never been red proves nothing.

## Sampling Rate

- **After every task commit:** the scoped command in the map below. Seconds to a minute.
- **After every RED commit:** `scripts/red-commit.sh` holds the run to exactly the tests the message names, in all three directions.
- **After any commit that changes a file's test count:** the printed `--remeasure`, scoped, and nothing wider.
- **After every plan:** nothing extra. The merge gate is the orchestrator's.
- **Max feedback latency:** under 60 seconds for a per-task run, except the three that run an integration target that links the whole library.

**The one human gate is 02.1-01 task 4**, and it is blocking rather than
advisory. Making twelve blind checks see the whole of a 26,593-line file may
surface violations they were never able to report. The phase context says
anything newly found is in scope to report and may not be in scope to fix, and
the risk section says the growth is unbounded until it is run. So the plan stops
and the developer decides per finding: fix in this phase, record in the ledger,
or waive with a reason. Nothing is fixed before that decision.

**Two tasks carry no failing test of their own and both say why.** 02.1-02 task
3 is comment-only and is the GREEN half of the guard written in task 2. 02.1-03
task 2 is documents-only and is the GREEN half of the check written in task 1.
Both fall inside the exceptions `CLAUDE.md` lists. UI, CRUD and glue that
changes behaviour are not exceptions, which is why every other task here is
RED-first whatever layer it sits in.

**One task's RED is a measurement rather than a failure.** 02.1-07 task 1 writes
a check that should be green on arrival against a correct call site, so it is
taken red by hand by removing an argument. That measurement is the task, not a
formality: a guard that has never been red proves nothing.

## Wave 0 Requirements

Nothing in this phase needs a test framework or a harness that does not exist.
What does not exist yet is listed here so none is discovered late, and each is
created by the task that needs it.

- [ ] `common::what_ships` reachable from an integration test, which is criterion 4's whole mechanism and every later reading in `tests/wired.rs` depends on it (02.1-01 task 1)
- [ ] `scripts/check.test.sh`, which does not exist; `scripts/check.sh` already runs every `scripts/*.test.sh` in every mode, so creating the file is enough to have it run (02.1-04 task 1)
- [ ] A guard record for `tests/checkbox_labels.rs`'s coupling to `src/presentation/wx_item_form.rs`, and one for `tests/manager_delete_stays_open.rs`'s coupling to `src/presentation/wx_managers.rs`. Neither target appears in `guards/guards.toml` today, measured 2026-09-02, so reading the registry cannot reach them until the records exist (02.1-04 task 2)
- [ ] A pure ordering function over conversation nodes in `src/presentation/wx_thread_view.rs`, which is where criterion 1's real test lives (02.1-05 task 1)
- [ ] A pure function answering which menu a folder-tree row offers, in `src/presentation/folder_tree.rs`, which is what lets criterion 11 be tested without a window (02.1-08 task 1)
- [ ] A pure function answering what a condition holds that this build cannot show, in `src/application/saved_searches.rs` (02.1-09 task 1)
- [ ] Guard records for each new guard, measured by hand per `guards/guards.toml`'s own rule: take the break by hand first and write down all of what really went red, not what you expected

**The cargo feature mechanism was measured rather than left to Wave 0.** In a
throwaway crate on 2026-09-02, a `[features]` section plus a dev-dependency of
the package on itself made `cargo test` pass `--cfg 'feature="what-ships"'`
while `cargo build --release` passed no feature cfg at all. So criterion 4 needs
no change to `scripts/check.sh`, `.github/workflows/ci.yml` or
`scripts/build-installer.sh`, and none is in any plan's file list.

No framework installation is needed. No dependency is added anywhere in this
phase, and no plan bumps the version.
