<premise_corrections>
**1. Criterion 13's stated symptom is not the one this defect has.** The roadmap
says a forwarded message in Hungarian joins the conversation it is a reply to.
Traced 2026-09-02: `is_a_forward_marker` is read by exactly two functions,
`opens_with_a_reply_marker` and `opens_with_a_forward_marker`, and those two are
called from exactly one file, `src/presentation/wx_compose.rs:174` and `:188`.
Nothing in threading reads either. So the real cost is in composition, and it is
two things: replying to a message whose subject opens with that marker adds no
reply marker, because the subject is read as already having one, so the
recipient's client sees a reply that does not say it is one. And forwarding it
adds a forward marker in front of the one already there. The doc comment at
`src/application/conversations.rs:322-329` states the second and not the first.

**The mechanism is exactly as recorded and it reproduces.** `mail_parser
0.11.5`'s `trim_trailing_fwd` requires the parenthesised token to be at least
two characters, so the Hungarian one-letter forward marker fails the trailing
probe and the code concludes it is a reply marker, since the two sets do not
overlap and only the forward set can be asked about directly.

**An acceptance criterion written against the roadmap's symptom would be
unsatisfiable.** No code path can make a threading behaviour change here. The
criteria below are written against the composition symptom, which is what
exists.

**2. There is a second probe, and it was measured rather than reasoned about.**
`thread_name` handles a bracketed marker separately: inside square brackets, a
token followed by a colon sets a forward flag only when it is a forward prefix,
and a reply prefix inside brackets is ignored unless a forward prefix came
first. So `thread_name("[X: qzqz]")` returns `qzqz` when X is a forward prefix
and returns the whole subject otherwise.

Measured 2026-09-02 against `mail_parser 0.11.5`'s own two sets, all 22 forward
prefixes and all 18 reply prefixes:

- the trailing probe the code uses today is wrong on exactly one, the
  one-letter Hungarian marker, which it reads as not-a-forward;
- the bracketed probe is wrong on exactly one, the Arabic two-word marker,
  which it reads as not-a-forward;
- that Arabic marker is not recognised by `is_a_marker` either, because it
  contains a space and `opening_marker` takes a single token, so it never
  reaches this question at all;
- neither probe answers yes for any reply prefix, and neither answers yes for
  an ordinary word.

So the union of the two probes is right for all 22 forward markers with no
false positives, and it keeps the list inside the dependency, which is the
property the current doc comment exists to protect.

**3. Criterion 6 cannot be closed with a live window.** The budget is one live
wxWidgets window per process and `tests/theme_reach.rs` and
`tests/checkbox_labels.rs` have each spent theirs. `ask_about_the_folders_that_have_gone`
takes a `Frame`, a state mutex, a cache, a pending set, the one-question gate, a
channel and a slice of text controls, and opens a modal. Reading its body is
what `tests/theme_reach.rs`'s own file comment says is done for call sites it
cannot construct, and it says plainly that this is weaker than a live read. Say
the same here rather than presenting a source read as a behavioural test.

**4. Read the body, not the file.** `tests/wired.rs` already has `body_of` at
`:520`, which takes a signature and returns that function's body. A whole-file
grep for two names is answered by any line that mentions both, including an
import, which this project has recorded. A body-scoped read does not have that
hole, and after plan 02.1-01 the body is read out of the whole shipping half
rather than out of a prefix.

**5. This plan adds a test to `tests/wired.rs` again.** The six records naming
that file were re-measured in 02.1-01 and will be flagged again by the count
check. Run the `--remeasure` command it prints, scoped to exactly those six,
each of which is a build and a `cargo test --test wired`. Not a sweep.
</premise_corrections>
