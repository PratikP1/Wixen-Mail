<premise_corrections>
**1. Criterion 2 names the wrong half, and half of it is already fixed.** The
criterion says `MAX(m.safety)` returns the mildest verdict and that the
conversation expression's `CASE` is the answer. Measured 2026-09-02:
`MessageColumn::Safety`'s `conversation_sort_expression` at
`src/presentation/message_columns.rs:222` already spells the `CASE`, ranking
phishing above spam above suspicious above ordinary, with a comment explaining
why. What is still wrong is the message-level `sort_expression` at `:136`, which
answers with the bare column, so a message list sorted by Safety orders the
stored words alphabetically: ordinary, phishing, spam, suspicious. Descending
therefore puts the mildest of the three bad verdicts at the top and phishing
third.

**So the work is the message half, and the two halves must end up agreeing.**
The conversation view already ranks correctly and the message view does not,
which means one column sorts two ways depending on which view somebody is in.

**2. The check on that agreement must not read one constant on both sides.**
Pulling the ranking into a shared constant and asserting both expressions
contain it is a check that cannot fail: changing the constant changes both
sides. This project has recorded that shape as observation 104. The test has to
be behavioural: rows in a real database, sorted both ways, with the order
asserted.

**3. Criterion 3's premise holds and the write side is smaller than it
sounds.** There is exactly one production `INSERT INTO messages` that writes
this column, the upsert at `src/data/message_cache/messages.rs:832`; the only
other one, at `src/data/message_cache/attachment_content.rs:693`, is inside a
test module, measured today. So normalising on write is one call at one place,
not a sweep of writers.

**4. A normaliser already exists.** `src/application/thread_identity.rs:77`,
`fn bare`, trims whitespace and the angle brackets. It is private. Making the
store use it is the change; writing a second one beside it would be the defect
this criterion is about, in miniature.

**5. The widened query stays, and its comment changes.**
`threads_holding_any_of` at `:1061` asks about each identifier twice, bare and
bracketed, and its comment says the column was widened here rather than
rewritten because what shipped is not rewritten. After the backfill the second
form finds nothing, and there is a real decision to record rather than assume:
narrowing the query would make a database this backfill has not yet reached stop
joining, and the backfill is not fatal if it fails, so the query keeps both
forms and the comment says the second form is now a fallback for a database the
backfill has not finished rather than the normal case. Do not narrow it.

**6. The cost of touching `src/data/message_cache/messages.rs` is known before
starting.** Ten guard records name it in `tests_last_seen`, so the first commit
adding a test to it fails the count check and prints a `--remeasure` command
naming exactly those ten. That command is the remedy and a sweep is not. Both
criteria's tests live in that module, which is the reason they are one plan.
</premise_corrections>
