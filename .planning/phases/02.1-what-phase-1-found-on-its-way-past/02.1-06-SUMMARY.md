# Phase 2.1 Plan 06: Safety by severity, and one spelling of an identifier Summary

**Both work.** Sorting a message list by Safety now puts phishing at the top
descending and at the bottom ascending, and the message view and the
conversation view put the same four verdicts in the same order. A message this
program filed and a message it synced are now written with the same identifier,
so the import check that compares the two finds the pair it used to miss, and a
database written before this is corrected the next time it is opened.

## Criterion 2: does Safety sort by severity in both views

Yes, and it is asserted on row order in a real database rather than on a string.

| direction | before | after |
|---|---|---|
| descending | suspicious, spam, phishing, ordinary | phishing, spam, suspicious, ordinary |
| ascending | ordinary, phishing, spam, suspicious | ordinary, suspicious, spam, phishing |

The two views now agree, checked by sorting the same four rows each way in each
view and comparing the two orders. A word this build has never heard of sorts as
the mildest and is still listed, which is the safe end for a claim about how bad
something is.

## Criterion 3: does a join across the two spellings find what it should

Yes. The join that really missed is the import dedup: bringing mail in from a
file asks the folder what it already holds and compares that with what
`mail_parser` read, which is bare. A draft this program filed was listed as
`<draft-abc-123@wixen-mail.invalid>`, matched nothing, and came in again as a
second row. It now matches.

The conversation join across the two writers was already working, because
`threads_holding_any_of` asks about both spellings. That widening is what kept
the defect from being visible, and it stays, as a fallback for a database this
backfill has not reached.

## The plan's premise corrections, and one it did not make

**The plan's own corrections held.** `conversation_sort_expression` really did
already spell the `CASE` and `sort_expression` really did answer with the bare
column, so criterion 2's roadmap wording, which says `MAX(m.safety)` returns the
mildest, names the half that was already right. There is exactly one production
`INSERT INTO messages`, at `messages.rs:849`. The other two in the tree are both
inside test modules: `attachment_content.rs:693`, below the `#[cfg(test)]` at
line 448, and `messages.rs:6318`, the fixture this plan added for writing a row
the way an older database holds one.

**A fourth premise correction the plan did not make: it enumerated writers and
no readers, and one reader would have broken.** `message_uid_by_message_id`
compares the column to a value the caller supplies, and its one caller is the
draft filing path, which hands over the bracketed spelling because that same
value goes into the header. Normalising the write without normalising the
question makes that lookup answer "no such message" for every draft, so every
automatic save would take a fresh number and leave another copy in Drafts. The
fix for one duplication defect would have made a worse one, silently.

That is not hypothetical, and the guard record for it is the evidence: the break
that makes the write stop trimming reddens five tests, and the fifth is
`test_a_message_is_found_by_the_id_its_sender_gave_it`, written long before this
plan. It goes red in exactly the half-done state, which is what says the pairing
is real.

**Premise 5 held and is now written into the code.** `threads_holding_any_of`
keeps both forms and its comment says what is true after this change: the bare
form is the normal case, the bracketed one is a fallback for a database the
backfill has not finished, and narrowing the query would make those rows stop
joining.

| break | what went red |

The fourth is guardrail 1 made checkable. It leaves the code compiling and every

## A narrowing written twice could not be broken at all

The first draft of the backfill selected a superset in SQL and then skipped
unchanged rows in Rust. Removing either half alone reddens nothing, because
whichever one goes the other still answers, so there was no single edit a guard
record could apply and no way to record the rule.

The fix was to narrow once: a `WHERE` clause asking in SQL the question `bare`
answers in Rust, plus a test that asserts the two agree over nine shapes an
identifier can arrive in. Two of those shapes are the ones a careless clause
gets wrong. A leading `>` and a trailing `<` are not brackets round anything and
`bare` leaves them alone, so a clause that trimmed any angle from either end
would select them, rewrite nothing, count them anyway, and select them again on
the next open.

This is the sibling of the rule the plan quoted from observation 104. That one
is about two sides reading one source, so editing the source moves both. This is
about two filters each sufficient on its own, so deleting either is invisible.

## Where the backfill is reached from

`src/data/message_cache/mod.rs:1265`, in `MessageCache::open`, beside
`migrate_inline_bodies`, `merge_local_folders` and `backfill_thread_ids`, with
the same not-fatal handling and a comment saying why a failure there is not
fatal: the rows are still readable, `threads_holding_any_of` still asks about
both spellings and so still joins them, and the next open tries again.

The five properties `src/data/message_cache/shared_folders.rs` copied from
`migrate_inline_bodies`, and which of them apply here:

| property | applies | how |
|---|---|---|
| 1. the candidates are read into a `Vec` before anything is written | yes | a cached statement held open over `messages` while the same table is being written is a lock against itself |
| 2. each row lands somewhere new before the old one lets go | no | nothing moves between tables. One `UPDATE` per row, and the value it writes is derived from the value it read |
| 3. the count is the contract, the log line is not | yes | the count is returned and tested; the log line carries a number and never an identifier |
| 4. nothing is dropped | yes | values are rewritten; no column is dropped or renamed, which is what `CLAUDE.md`'s additive rule allows |
| 5. idempotent by its `WHERE` clause | yes, with one stated exception | a second run selects nothing. A value with whitespace inside its brackets, `<a b >`, takes two opens, because `bare` trims and then strips in that order. It converges rather than oscillating, and no writer here produces such a value |

## Deviations from Plan

### 1. [Rule 2] The lookup trims the question as well as the column

**Found during:** task 2, reading `wx_app.rs:13389` to see who calls
`message_uid_by_message_id`.

**Issue:** the plan applies the normaliser at the one production write and names
no reader. That lookup compares the column to a caller-supplied value and its
one caller hands over the bracketed spelling.

**Fix:** the lookup applies the same trimming to the question, so a caller can
hand over whichever spelling it has. Its doc comment says why.

**Files:** `src/data/message_cache/messages.rs`.

**Commit:** 0967567.

### 2. [Rule 1] The backfill narrows in one place rather than two

**Found during:** writing the guard record for task 3 and finding that neither
narrowing could be taken red on its own.

**Issue:** a redundant filter is not defence in depth, it is a rule that cannot
be falsified, and it also hides drift between the two spellings of the rule.

**Fix:** one `WHERE` clause asking exactly what `bare` answers, plus
`test_the_rows_the_backfill_selects_are_exactly_the_rows_that_change` asserting
the two agree over nine shapes. That test was written in the green half rather
than the red, and it is red against the stub, against break 3, and against a
clause that trims any angle from either end.

**Commit:** 0967567.

### 3. One red commit for three tasks

**Found during:** the first commit of task 1.

**Issue:** the guard-record count check fires on the first test added to the
messages module. Its remedy, `--remeasure`, applies each break and reads which
tests go red, so it needs a tree with nothing else failing in it, and a red tree
is not that. Meanwhile `red-commit.sh` refuses a commit where anything failed
that the message did not name. There is no ordering that satisfies both, so the
fingerprint can only be paid once, which means every test the plan needs has to
land in one commit.

**Fix:** the red half of all three tasks is one commit, naming eleven failing
tests and the count check, with the reason in the message. The green half is one
commit. The reopen test needed the migration to exist to compile, so
`backfill_message_identifiers` went in as a body returning `Ok(0)`: an absent
function is the weaker red, because a build that does not finish says nothing
about behaviour.

**Cost:** per-task commit granularity. Nothing else.
