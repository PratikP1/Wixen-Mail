<objective>
Give every kind of row in the folder tree a menu that fits it, and make two
accounts sharing a name two rows a person can tell apart.

answers with the mail-folders menu for everything that is not a saved-search
row, so account branches, the Favourites branch, the Labels heading and "On this
computer" all offer fetching older messages and choosing folders to keep up to
date, on rows that are not folders.

Output: a focus per branch kind, decided by a pure function, and account rows
that are not interchangeable.
</objective>

<premise_corrections>
**1. Criterion 11's premise holds exactly.** `wire_context_menu` at
`src/presentation/wx_app.rs:9237` takes a closure, and the folder tree's closure
at `:3034-3040` matches the selected row: a saved search answers
`Focus::SavedSearch` and everything else answers `Focus::MailFolders`.
`MAIL_FOLDERS` at `src/application/context_menu.rs:220` holds three entries, two
of which mean nothing on a branch. `WhichRow` has twelve variants, of which two
are folders and one is a saved search, so nine kinds of row are being offered a
folder's menu.

**2. Criterion 12's headline is right and its stated mechanism is not live.**
Measured 2026-09-02: `where_a_row_sits` at `src/presentation/folder_tree.rs:788`
is production code with no production caller. Every call to it is inside a test
module in that same file, and nothing under `tests/` calls it either. The folder
tree's real pairing is by position and by identity: `select_row` and
`land_the_folder_cursor` in `wx_app.rs` both work from `WhichRow::stored()`, and
two accounts sharing a name have different identifiers, so neither collapses.
`land_the_cursor`, which does pair by words, is used for the five personal
information sidebars and not for the folder tree.

**So the ambiguity `where_a_row_sits` carries costs nothing today, and something
else does.** Two accounts given the same name draw two rows that read
identically, and a person working by ear cannot tell which branch they are on or
which account a command is about to act against. That is the fault this codebase
keeps finding in lists, and it is what 02-07 fixed for condition rows and 02-08
fixed for saved searches. Task 3 is written against that, because it is the
symptom that exists.

**`where_a_row_sits` itself is then a separate question and it is task 3's to
settle**: a public function nothing calls is either wired or removed, and its
own doc comment already records the limitation. Do not leave it as it is with
the comment unchanged, which is the third option and the one this phase exists
to stop.

**3. A menu entry that does nothing is forbidden here, and that bounds the
work.** `src/application/context_menu.rs`'s module doc says a menu entry that
does nothing is a stop somebody lands on, hears, and learns nothing from, and
02-07 recorded that as the reason a saved search got its own list rather than an
extra entry on the folder list. So each branch menu holds only actions that
exist and that the row can carry out. This plan does not invent commands.

**4. `Focus::ALL` is a fixed-length array and tests walk it.** It is thirteen
today at `context_menu.rs:60`. Growing the enum means growing that constant, and
`entries_for` is a match with no catch-all, so a new variant is a compile error
until it has a menu. That is the compile-time half of this criterion and is
worth keeping: do not add a catch-all arm to make the growth easier.

**5. Where the new tests live is chosen on cost and said so here.** The decision
is a pure function over `WhichRow`, so it belongs in
`src/presentation/folder_tree.rs`, which can see both the row kinds and the
focus type; `context_menu.rs` is an application module and cannot see
`WhichRow`, which 02-07 already recorded. That placement also keeps every new
test out of `src/presentation/wx_app.rs`, which thirty-two guard records name.
`folder_tree.rs` is named by four and `context_menu.rs` by none, so the count
check will flag four records rather than thirty-two. `wx_app.rs` gains no test
function in this plan, only the closure change.
</premise_corrections>
