<premise_corrections>
**1. This is the lowest-value criterion in the phase and it is planned last on
purpose.** D-2.1-02 says so: the case needs somebody running a newer build to
write a rule using a field a later version added, then opening it in an older
build, and there has been no public release, so nobody has an older build.
Nothing in this phase depends on this plan, and it is the first thing to cut if
the phase runs long. It is kept because a silent rewrite of a stored rule is the
shape behind every data-losing bug this project has found, and refusing costs a
sentence and a guard.

**2. The mechanism was confirmed today and it is two values, not one.**
`show_rule_edit` at `src/presentation/wx_managers.rs:2915` reads both choices
back with `unwrap_or_default().to_string()` at `:2938-2944`, so an unreadable
field and an unreadable way of matching are both rewritten to the empty string.
`build_rule_edit_dialog` at `:2811-2820` selects nothing for either when the
words are unknown, and the comment there already describes exactly this failure
for the case 02-04 closed. So the criterion's "a field" is really either half of
a condition, and refusing on one and not the other would leave the same defect
behind a narrower door.

**3. The refusal already has a wording and a type.**
`application::saved_searches::NotUnderstood` at `:237` holds `Field(String)` and
`WayOfMatching(String)`, and `why()` at `:246` ends as a sentence naming the
word it could not read. That is what the search itself says when it cannot run,
so the condition editor refusing in the same words makes a condition behave the
same way whichever way somebody meets it, which is the argument 02-07 used for
`SAVED_BY_ANOTHER_VERSION`.

**4. `SAVED_BY_ANOTHER_VERSION` does not already cover this.** It is reached
when `Join::read` does not know the stored joining word, which is a different
part of a saved search. A search whose join this build understands and whose
field it does not is opened today, so the case is live.

**5. The row must stay visible and removable.** 02-07 records that a stored name
this build has no words for is shown as it is stored rather than blanked, so a
condition written by a later version is still a row somebody can see and remove.
Refusing to open it must not take that away, and a test on it is what keeps the
refusal from becoming a trap.

**6. Both doors, and the filter editor as well.** `show_rule_edit` is what both
Add and Edit call on `run_manager_loop`, for the saved-search condition manager
and for the filter manager alike, which 02-07 recorded when it collapsed the two
into one call. Check that both reach the refusal rather than assuming one
implies the other, and say in the summary which entry points were traced.
</premise_corrections>
