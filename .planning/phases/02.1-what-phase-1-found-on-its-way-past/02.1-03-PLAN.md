<premise_corrections>
**1. `docs/IMPLEMENTATION_STATUS.md`'s sentences were already corrected, and
that is not the defect.** Measured 2026-09-02: the Folder management paragraph
at `:74-85` describes, in the present tense, making a folder on the server,
renaming it, moving it, deleting it, marking a whole one read, and emptying one,
with the two settings that decide how deep those reach and the honest note that
none of it has run against a real server. Every sentence in it is true. The
paragraph sits under the heading `## What does not work` at `:72`. So the page
makes the false claim through position rather than through wording, and a grep
for the sentence that used to be wrong finds nothing.

**This changes what the check has to do.** A check searching for a claim of
absence would have passed against this page on the day it was wrong. The check
has to read which section a capability is described under.

**2. `.planning/intel/context.md` is wrong the way the criterion describes,
in five places**, all measured today: `:25` says a folder cannot be created,
renamed or deleted and that nothing groups the list by thread identifiers;
`:38` repeats the folder claim in a list of known-missing things; `:73` quotes
a user guide saying the thread-view toggle is not built and says so; `:134`
quotes the same about the View menu item; `:135` lists folder management's IMAP
verbs among unticked items. Phase 1 shipped all of it.

**3. Criterion 5's headline says every document, and its evidence names two.**
`.planning/intel/context.md:134` says its claim agrees with
`docs/IMPLEMENTATION_STATUS.md` and `docs/USER_GUIDE.md`, which means a third
page may carry it. Correcting a false claim by naming the two documents somebody
wrote down is how a claim survives in a third, so task 1 searches the tree
first and the file list above is the floor rather than the ceiling. Anything
found beyond the four files listed is added to the plan's own file list in the
summary.

**4. This plan is deliberately two commits with two different footprints.** The
check is Rust, so its commit is scoped to the tests it reaches plus the
tree-reading guards. The corrections are documents only, so their commit runs
the document-reading targets and nothing else, about 51 seconds against about
350. Do not fold them into one commit: that would buy nothing and cost the
document commit the whole gate.

**5. `tests/docs_links.rs` rather than `tests/house_style.rs`, on purpose.** No
guard record names `tests/docs_links.rs`, so adding a test to it trips no
count check, where `tests/house_style.rs` would trip seventeen. Both are in
`scripts/check.sh`'s documents-only target list, so the check runs on a
documents-only commit either way. That is the whole of the reason and it is
worth stating so the next person does not move it for tidiness.
</premise_corrections>

  <behavior>
    - For each capability in a small named list, the check finds the symbol in the code that has to exist for the capability to work, and finds the section of the status page the capability is described under.
    - A capability whose code is present and whose description sits under a heading saying it does not work is named, with the heading and the line.
    - A capability whose code is absent and whose description sits under that heading is not named, so the check does not force a page to lie in the other direction.
    - The section reading finds a real heading and a real paragraph for every capability in the list, so a page reorganised out from under the check fails rather than passing.
  </behavior>
  <action>
    Take RED against the page as it stands, which names folder management. That
    is the guard being red on arrival, which is the RED half; commit it with a
    `Fails-until-green:` trailer naming the test, on a branch.

    Build the check in three parts and keep them separable, because two of the
    three are where it can go quietly vacuous. First, read the status page into
    sections: a heading and the paragraphs under it, until the next heading of
    the same level. Second, for each capability in the list, find the paragraph
    introducing it by its bolded name. Third, ask the code whether the capability
    is there, by looking for the symbol it cannot work without.

    Keep the list short and name each entry's code-side symbol beside it, so the
    pairing is readable as a table rather than as two lists that have to be kept
    in step. Folder management pairs with the IMAP mailbox verbs phase 1 added.
    The threaded view pairs with the conversation grouping. Two entries is
    enough to close the criterion, and the shape takes a third without a second
    edit.

    Give it a companion, because this is a guard that reads a document and
    `CLAUDE.md` requires one. The companion feeds the section reader an invented
    page holding a capability under a heading saying it does not work and asserts
    it is named, and feeds it the same page with the paragraph moved and asserts
    it is not. It also asserts, over the real page, that every capability in the
    list was found in some section: a name the reader could not locate would
    otherwise pass as a capability with nothing to say about it.

    Do not check that the page uses particular sentences. The sentences here were
    already right while the page was wrong, and a check on them would have passed
    on the day this defect was live.
  </action>
