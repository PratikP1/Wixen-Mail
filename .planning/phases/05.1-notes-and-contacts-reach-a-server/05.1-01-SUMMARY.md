# Phase 05.1 Plan 01: A note's body comes back as it went in, Summary

**A note's body is proven byte-identical through storage, and the column that has
said "plain" on every note ever written now says in its own words why it stays,
with the literal replaced by a type so a second writer cannot spell it
differently.**

## Does it work

Yes, for what is testable on this computer, and nothing here reaches a server.

A note saved and read back is the same bytes, asserted through `save_note` and
`get_note` rather than through a formatter, for a body ending in a space, a body
with Windows line endings, a body holding a character outside the basic
multilingual plane, a body with a backslash before a newline, and an empty body.
A note with headings and lists in it is spoken as headings and lists after the
round trip, and a note with none is spoken exactly as it was written.

`NoteEntry.format` is a `NoteBody` rather than a `String`. The two production
write sites ask it instead of spelling a literal, a word this build did not write
survives being read and written back, and a row that does not carry the word at
all is read rather than refused.

`scripts/check.sh all` was run on the branch before the merge, not piped, and
reported all four checks passed. The merge into `main` ran it again and passed
again.

## The decision, which the plan required in writing

Three answers were on the table and one of them was never available. `CLAUDE.md`
says: "Schema changes are additive. `MessageCache` opens existing user databases,
so add tables with `CREATE TABLE IF NOT EXISTS` and columns with
`ensure_column_exists`. Never drop or rename a column that shipped." The one
exception taken so far was a table holding secrets nothing read, and arguing a
second exception is a decision for Pratik rather than a task. So dropping the
column was out before the work started.

**The column records why it stays.** The argument, which now lives in
`NoteBody`'s doc comment where the next reader of the schema meets it:

A note's body is text. `long_text.rs`'s module header already settled the
question this column pretends to ask, and it settled it before this plan was
written: "What is stored is exactly what was typed. Markdown is legible as it
stands, so keeping it means the text is never worse than it was, and anything
that is not markdown is simply text with no structure in it rather than an
error." The reading looks for whatever structure is there and finds none where
there is none. There is no fork here for a column to pick.

**What "give it meaning" would have cost, and this is why it lost.** The only
form of it that changes anything is a reader that consults the column. Every row
this program has ever written says `plain`. The note editor labels its box "Body,
in Markdown" and gives it the accessible description "Markdown headings and lists
are read back when this note is read aloud". `NoteItem::read_full` calls
`long_text::spoken` on the body unconditionally. A reader that took the column at
its word would therefore stop reading headings and lists in every note that
already exists, which is the accessible behaviour the product advertises, turned
off by a column nobody ever set on purpose. That is a loss dressed as a feature.

The other form of it, writing a different word for notes typed here, does not
help either: the reader still cannot obey it without the same loss for old rows,
so the column would carry a new word and still decide nothing.

**What "record why it stays" costs.** The next person to read the schema asks the
same question again unless the comment is good, which is the cost the plan named
and the only defence is that the comment argues rather than asserts. It is also
true that the column carries no information today: every row holds one value, so
the test for it can only assert a constant, and
`test_what_this_program_says_a_notes_body_is_written_in_is_one_word` says in its
own comment that this is what it is and why it is still worth having, which is
that a rename would orphan every note already on somebody's disk.

**What is not a judgement call, and was done under either answer.** The literal
stopped being repeated. `NoteEntry.format` is `NoteBody`, so the two production
writers cannot spell it differently: there is no string left to spell. That is
stronger than the shared constant the plan asked for, which would have left a
second writer able to type `"plain".to_string()` and nothing to notice.

## Each fixture and the wrong implementation it is aimed at

A fixture that is merely large tests nothing, so each names its target in the
test's own source:

| fixture | the wrong implementation it catches |
|---|---|
| a body ending in a space | a `trim()` somebody adds while tidying |
| a body with `\r\n` line endings | a line-ending normalisation |
| a body holding an emoji, outside the basic multilingual plane | a byte-length assumption cutting a character in half |
| a body with a backslash before a newline | an escape pass reading the backslash as an instruction |
| an empty body | a `NOT NULL` column with a default inviting somebody to fill it in |

## What `outlook_data_file.rs` said, and what it says now

Its production write carried a comment arguing for the literal: "Outlook's notes
are words and nothing else. Anything else here would send the markup reader at
text that is not markup."

**The column never did that job.** Nothing consults it, so the word protected
nothing. What really decides is `long_text::spoken`, which returns text with no
markup in it exactly as written, so an imported Outlook note that is words and
nothing else is spoken as words and nothing else whatever the column says.

The case the comment feared is real and the column never covered it either: an
Outlook line that happens to start with `#` or `-` is read as a heading or a
bullet. That was decided elsewhere and on purpose, in `long_text::from_markup`'s
doc comment, which says escaping it "would put a backslash into a box somebody
edits by hand, which is a worse fate than the rare line that reads oddly". The
comment now says all of that, so the file argues from the thing that decides
rather than from the thing that does not.

**Its test assertion now reads `assert_eq!(note.format, NoteBody::AsTyped)`.**
That is the plan's "read back a note written through each production path and
assert the stored value is the one the single source names", for the one
production path a test can reach. The other, `managers::store_new_item`, is
private and `managers.rs` may not gain a `#[test]` under this plan's cost rules;
what covers it is the type, which admits no second spelling, rather than a test.
That is stated here rather than papered over.

## The precedent followed for an unrecognised word

`AddressBook::Other(String)` in `src/data/message_cache/mod.rs`, whose doc
comment gives the reason: "`Other` exists so a word this code does not recognise
survives being read and written back. An address book named by a build that came
later, or by a provider added since, is still an address book, and forgetting its
name would silently join two of its contacts together." `NoteBody::Other` is the
same shape for the same reason and its doc comment names the precedent. That
closes T-05-17 in the plan's threat register, driven by a test that writes the
foreign word with raw SQL and reads it back.

## Deviations from the plan

**1. [Rule 2, missing critical] A null in the column is read rather than
refused.** Not in the plan's action, and it is inside the plan's own stated
behaviour: "A note read back from a database written by an older build, whose
column says something this build did not write, is still read and is still shown,
rather than refused." A null is a value this build did not write. It was the only
genuinely red test in the plan.

**2. [Deliberate] `NoteEntry.format` is an enum, where the plan asked for "one
place that answers what a note's body is written in".** A shared constant would
have satisfied the words and left every write site able to type the literal
anyway. `CLAUDE.md`'s elegant-code section asks for exactly this: "When a
database column holds a fixed set of strings, model it as an enum and convert at
the SQL boundary." The cost is that eleven construction sites changed, none of
which gained or lost a test.

**3. [Deliberate] One version bump for the plan, not one per task.** Task 1 and
task 2 each ask for a bump. Nothing user-visible changes anywhere in this plan,
and `CLAUDE.md` says a bump is for a feature, a schema change or a behaviour
change. What earns the single minor bump to `0.103.0` is `NoteEntry`'s shape
changing. Bumping twice would be using the version as a build counter, which this
project has already done twenty-five times and wrote a rule about.

**4. [Correction] Three guard records, not two.** The plan asked for one per
task. The second candidate break for task 2 was measured rather than assumed, as
`CLAUDE.md` advises, and it turned out to redden a different and larger set, so
both were written down.

**5. [Mechanical] `STATE.md`'s `last_activity` is a bare date now, where it used
to hold a paragraph.** Every `gsd-tools state` write normalises that field back
to the date, so a paragraph typed into it reverts on the next tool write, which
is the same trap `.planning/WINDOWS.md` sets for a hand-typed row. It was tried,
it reverted, and it is not being fought. The paragraph lives in the Current
Position section instead, which is where this project's own convention keeps it
and which was written in full. The old value was stale anyway: it described
05-04 while the phase had reached 05-08.

**6. [Correction] Task 1 made no RED commit**, which the plan explicitly allows:
"If none failed, do not commit a red half claiming otherwise: say so, commit the
tests as a green measurement, and let the break at the end carry the evidence."
All three of its tests were green on arrival and the commit message says so.

**What `toggle_note_pin` means for later plans, carried forward unchanged.**

`save_note` is bypassed by it. It does not bite here, because pinning does not
change a body. It bites in `05.1-03`, which puts a `pending` flag on a note.
