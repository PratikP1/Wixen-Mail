the first, and produce the list of everything the seam had assumed.

shaped like the one it was written for. That is why this one is not invented:

afternoon, rather than in the middle of a Graph client where it costs a phase.

honest statement of what a second implementation inside this crate cannot show.

<premise_corrections>
**1. The four axes, and where each comes from.** These were read on 2026-09-06
from Microsoft's own reference and each is quoted with its page in this phase's
`README.md`. They are the facts that make OneNote a different kind of
backend from CalDAV, and they are what this implementation is shaped from. Read
the pages again before starting: a documented API changes, and a fact taken from
a page in September is a fact with a date.

- **No version token.** `onenotePage`'s properties are `content`, `contentUrl`,
  `createdByAppId`, `createdDateTime`, `id`, `lastModifiedDateTime`, `level`,
  `links`, `order`, `self`, `title`. There is no `eTag`, and the update
  reference names no `If-Match`. So the marker is a timestamp the service owns
  and nothing else.
  (`learn.microsoft.com/en-us/graph/api/resources/onenotepage`)
- **No whole-document write.** The supported-actions table gives the `body`
  target `append: yes`, `replace: no`, `insert: no`. A page's body cannot be
  replaced in one call. The title can, with `target: "title"`.
  (`learn.microsoft.com/en-us/graph/onenote-update-page`)
- **Identifiers that move.** Most `replace` actions require the identifier the
  service generated, not one the client set, and the same page says generated
  identifiers "might change after a page update, so you should get the current
  values before building a PATCH request".
- **A container more than one level deep.** notebook, then section group, then
  section, then page.
  (`learn.microsoft.com/en-us/graph/api/resources/onenote-api-overview`)

CalDAV disagrees with all four: an ETag, a whole-document PUT with `If-Match`, a
URL the client chooses, and a flat collection. **That is the point.** A seam
that takes both takes most things.

**2. This is a fake and it is a serious one, and the difference matters.** It is
not a stub that returns canned answers. It implements the seam's trait fully,
holds its own state, enforces all four constraints as real refusals, and is
driven by the same `notes_sync` the CalDAV backend is driven by. If a test can
tell which backend it is talking to except through the seam's own vocabulary,
that is the finding.

**3. It exists only in tests, and PIM-08's last `[D]` line is why.** "Nothing in
this milestone ships a hosted client, a network call to one, or a setting
offering one. Preparing for it means the seam does not forbid it, not that
anything half exists. A switch that does nothing is the failure this project has
fixed repeatedly." So this implementation is behind `#[cfg(test)]` and nothing
in the settings screen names it.

**4. What that costs, said now rather than discovered later.** An
implementation inside this crate, behind `#[cfg(test)]`, cannot show that the
seam's trait and its types are `pub` enough for an implementation written
elsewhere, because it can see private items. **That is a real limit and the
summary states it.** Two ways to reduce it and both are decisions for the
executor to make and argue: write the implementation in an integration test
under `tests/`, which links the library as an outside consumer and therefore
sees only what is public, or keep it in the crate and add one integration test
that names every item an outside implementation would need. The first is
stronger and may not be possible if the trait is `pub(crate)`. Read what
`05.1-02` made public before choosing, and say in the summary which was chosen
and what the other would have proved.

**5. Read both summaries first.** `05.1-02-SUMMARY.md` says what the trait
became and what the contract document says. `05.1-03-SUMMARY.md` says what the
CalDAV implementation needed and whether anything in the trait changed to take
it. If `05.1-03` already had to change the trait, that is the first entry in
this plan's list and it was found a plan early.

**6. `TaskService` and its fake are the worked example.**
`pub(crate) trait TaskService` at `src/application/tasks_sync.rs:446` with ten
methods, and the fake the `push_tasks` tests drive. Read the fake in full before
writing this one, including how it is told to fail, because a second mechanism
for scripting failures is a second thing to keep working.

**7. `conflict_choice.rs` is the part most likely to have assumed CalDAV.**
`whose_copy_wins` in `contacts_sync.rs` compares markers rather than clocks, and
its doc comment says so deliberately. A backend whose only marker is a timestamp
the service owns cannot answer that question the same way. **This is the single
most likely place the seam turns out to have been written about CalDAV**, and it
is worth writing that test first.

**8. Guard-record cost.** Re-measure at the tree you are on with the awk in

`src/application/conflict_choice.rs` 0 records, `src/application/notes_backend.rs`
and `src/application/notes_sync.rs` not yet existing and therefore 0, and
`src/application/contacts_sync.rs` 77 records. **Add no `#[test]` to
`contacts_sync.rs`.** The new modules and a new file under `tests/` are free.

**9. Adding a record to `guards/guards.toml` changes the census at the top of
