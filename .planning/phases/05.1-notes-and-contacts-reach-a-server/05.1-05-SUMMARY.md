The parsing works and is tested. Nothing here runs in the product yet, and that
is the plan's shape rather than a gap it left: `05.1-06` builds the table, the

## What the requirement was pointing at, and why it could not have been reused

PIM-05's second `[D]` line asks that contacts sync both ways "reusing the
existing vCard reader and writer rather than a second one". The two functions it
points at are not a reader and a writer of a card.

`import_contacts_from_vcard` takes a whole file, reads every stored contact for
the account first, matches each card against cards already read in the same file
and against what is stored, and writes rows. `export_contacts_to_vcard` read
every contact for an account and appended `BEGIN:VCARD`, then each property,
then `END:VCARD` inline inside a `for` loop.

**There was no function that turned one contact into one card.** So the honest
reading of "reuse rather than write a second" was to lift one out, which is what
task 1 did. Anything else writes the second writer the requirement forbids.

The loop, before:

```rust
for c in contacts {
    output.push_str("BEGIN:VCARD\r\nVERSION:3.0\r\n");
    output.push_str(&Self::fold_vcard_line(&format!(
        "FN:{}",
        Self::escape_vcard_text(&c.name)
    )));
    // ... a hundred and sixty more lines ...
    output.push_str("END:VCARD\r\n");
}
```

and after:

```rust
for c in contacts {
    output.push_str(&Self::vcard_block_from_contact(&c));
}
```

The reader needed only its visibility decided and a doc comment saying who calls
it, because `contact_from_vcard_block` already was a per card reader.

## Which drop each escaping fixture would notice

The defect these exist to prevent is a hand lift that dropped a call. The plan's
premise was measured rather than believed, and it was right in three places and
overstated in one.

| Fixture | A dropped fold | A dropped escape |
|---|---|---|
| a value long enough to fold | caught, by asserting `\r\n ` is in the card | not applicable |
| a comma, plain text | invisible to the round trip, caught by asserting `\,` is in the card | as stated |
| a comma, structured | caught both ways | caught both ways |
| a semicolon, plain text | not applicable | invisible to the round trip on its own, caught on the card text |
| a semicolon, structured | not applicable | caught both ways: the street becomes two fields and the country falls off the end |
| a backslash | not applicable | caught both ways: `C:\new` comes back as `C:` then a line break then `ew` |
| a line break | not applicable | caught both ways: the card splits and the tail line is dropped |

Every one of them asserts on the card text as well as on the round trip, which
is what turns the two invisible cases into real fixtures.

The folding fixture puts a space exactly at the fold, which is the case that
once ran two words together: `NOTE:` is five octets, the first piece of a folded
line is seventy five, so seventy characters and then a space puts the space at
the join, where unfolding takes off exactly one whitespace and no more.

## The empty versus absent question, decided once for both markers

**An element that is there and holds nothing, and an element that is not there
at all, are one answer.** That is the decision, and it covers the address book's
change marker in task 2 and a card's version marker in task 3.

Three reasons. `extract_xml_value` ends
`if value.is_empty() { None } else { Some(value) }`, so the one extractor this
program has already collapses them, and every other reader in the tree takes its
values from it. A server sending an empty marker is sending no useful marker, so
both answers mean the same thing to whoever asks next: ask again in full. And a
second, differently shaped extractor would be a second thing to keep working, in
a file whose whole argument is that one answer to a question beats two.

Both criteria follow the decision and each has a test:
`test_a_change_marker_that_is_empty_and_one_that_is_absent_are_the_same_answer`
and `test_a_version_marker_that_is_empty_and_one_that_is_absent_are_the_same_answer`.

**The second of those was wrong when it was committed red, and is corrected in
the green half.** It was built with a marker whose value was two quotation marks
and asserted the value was kept, which is a marker with a value rather than an
empty one: the test's name claimed one thing and its body did another. Found
while writing the implementation. It now drives a genuinely empty element
against an absent one and asserts both come back as nothing.

## The refusal, and which of the two shapes it follows

**It follows `parse_report_events`: `Error::Protocol` with a fixed sentence
written for whoever reads it.** "That address did not answer with an address
book. Nothing was added here." and, for the cards, "That address did not answer
with the cards in an address book. Nothing here was changed."

**The other shape could not be followed, and the plan's correction was right
about why.** `parse_propfind_calendars` has no parser level refusal at all:
`response_blocks` splits on `<d:response`, so a captive portal page yields no
blocks and the function returns an empty vector as success. The refusal that
does exist there is `refused_with`, which takes a transport response and builds
an `Error::Api` from a status this file never sees. An acceptance criterion of
this plan is that nothing in `carddav.rs` names the transport, so that shape is
unreachable from here by construction.

**This diverges from `parse_propfind_calendars` deliberately and the doc says
so, so the next reader does not correct it back.** An empty list and a wrong
address are different facts, and a screen that cannot tell them apart says "no
address books found" to somebody whose address is wrong.

## What is shared with the calendar, and what is not

Shared: `response_blocks`, `extract_xml_value` and `resolved_against`, which
became visible to the rest of the crate with doc comments saying why. A copy of
each would be a second answer to where a response block begins, and the
namespace lesson written into the first of them, that a server repeating its
declarations on every block made a full home set read as empty, would have to be
learned again here.

Not shared: the types. `CardDavAddressBook` is its own rather than
`CalDavCalendar`, because the two will grow apart and a shared one makes each
carry a field the other never fills.

Improved on rather than copied: the address book element is matched on its local
name with the namespace prefix stepped over.
`names_a_calendar_collection` matches `<c:calendar` and `<cal:calendar` and its
own doc records that a third spelling reads as offering none. One fixture here
uses `CR:` and an unprefixed collection element for exactly that reason.

## Three limits written into the code rather than left to be found

**The `d:` prefix on the DAV elements is assumed.** `extract_xml_value` takes a
value by exact tag name, so a server that declares the DAV namespace for
unprefixed names and writes `<href>` is read as holding no address books. The
calendar assumes the same and neither has ever been tried against a server.
Ledger 254.

**The card's own element is tried under three spellings**, `card:address-data`,
`C:address-data` and `address-data`. A server writing a fourth is read as having
sent no card. Ledger 255.

**The scan for the address book element runs over the whole response block**
rather than over the resource type alone, which is what the calendar's does. A
server sending a raw angle bracket inside a name it should have escaped could
add a row to a list somebody chooses from. Ledger 258.

## XML unescaping, and the gap it found next door

Everything this file takes out of a document goes through `value_in`, which
takes XML's own escaping off. That answers three things at once: card text
carrying an ampersand or an angle bracket, a line of card text that looks like a
tag, and an address book called `Sam &amp; Co`, which a screen was going to read
out as those characters.

The five references XML defines are turned back, **once**, and anything else is
left exactly as it arrived. Reading once rather than until nothing changes is
what makes `&amp;lt;` come back as `&lt;` rather than as `<`, and leaving
unknown references alone is what means an entity a document declares for itself
is never expanded. `test_a_reference_this_reader_does_not_know_is_left_as_the_text_it_is`
pins both halves.

**The calendar's reader does none of this**, and hands the document it takes out
straight to the calendar parser. A `&amp;` in an event summary comes through as
those five characters there. That is a gap rather than a decision, and this plan
did not reach into `caldav.rs` to fix it: it is another module's defect, found
from outside, and fixing it needs its own red half and its own measured break.

## The address book name unescaping was not in the plan

## What the plan got wrong against the tree

under `-D warnings` is a build failure, so the red commit does not compile with
the narrower visibility. The writer is `pub`, beside its two whole file

half be at least a tenth. The check refused it and the refusal was correct, in

rest of the file said. Padding the doc until the ratio passed would have turned
a real measurement into a number about nothing. The entry landed in task 2's
green commit, which is the first commit where the file's shipped half reads a
document at all.

**3. `FILES_THAT_READ_OR_WRITE_A_DOCUMENT` was `[&str; 9]`, not 8.**
`05.1-03` added `note_document.rs` between the plan being written and this
running. Stale rather than wrong.

**4. Every figure in the premise corrections had moved again**, which the plan
itself says to expect. Measured at the start of this run: `main` at `e5245f4`,
