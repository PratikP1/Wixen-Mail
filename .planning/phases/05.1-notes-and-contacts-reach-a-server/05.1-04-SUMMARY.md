# Phase 05.1 Plan 04: A second backend behind the notes seam, Summary

**A second implementation of the notes seam, shaped from what Microsoft's
reference says a OneNote page does and driven by the same sync as the first,
found four places the contract was written about CalDAV rather than about
backends. Two of them are bugs in code that already ships.**

## Does it work

Yes, and the answer that matters is what it found rather than that it compiled.

Thirty-one tests drive two implementations of `NotesService` through the same
sync. One is shaped like a calendar server's journal collection: a whole
document written in one call, an address the client chose and keeps, an opaque
marker the server changes exactly when the document changes, a collection that
is one string of any shape. The other is shaped like pages in a section of a
notebook: no operation that replaces a body, so reaching an asked-for end state
means removing the page and making another; a name that therefore moves every
time a body changes; a marker that is a reading of a clock the service owns; and
a container of three parts that it refuses if it is not.

Every question is written once against the trait and run against both. A reader
of a test body cannot tell which backend it is driving except by the parameter.

`scripts/check.sh all` was run on the branch before the merge, redirected to a
file rather than piped into anything, and reported "All four checks passed" with
exit status 0. Nothing used `--no-verify`.

**What does not work, said plainly: none of this has met a service.** The second
implementation is a fake. Nothing in it has met a timeout, a partial response, a
redirect, a rate limit, or a sign-in that expired mid-operation. Its four
constraints are a reading of three documentation pages on one day. Seven ledger
entries name the unknowns one at a time.

## Every place the seam turned out to be shaped around CalDAV

Four, hardest to find first, which is the order they are written into
`docs/development/the-notes-seam.md` and the order the next implementer should
check their own backend in.

### 1. A version marker is not optional, and this is the largest one

**What the seam said.** "A version marker is optional. A backend that gives none
is a backend whose copy is always treated as having moved, which is what
`contacts_sync::the_marker_moved` already does and for the reason its comment
gives: a missing marker is not evidence that a copy stayed still, it is no
evidence at all."

**What is wrong with it.** The sentence is right, about the read half. On the
push half the same absence means the opposite: nothing is known to have moved at
the backend, so this computer's copy goes over whatever is there. Two readings
of one absence, in one sync, and neither is visible from the other.

**What it costs.** Measured rather than argued:
`test_a_backend_that_gives_no_marker_loses_a_change_made_at_the_other_end_and_says_nothing`.
A change somebody made at the other end is destroyed and nothing anywhere says
so. Not a count, not a problem, not a question.

**What was changed.** The contract, not the code. Requirement 3 now says a
marker is required of any backend this program writes to, and says why no code
change reconciles the two readings: telling them apart needs the copy the
backend last had, and PIM-08 forbids keeping one. So the requirement moves to the
backend, and a service with no opaque token uses whatever it does have. A
OneNote page's `lastModifiedDateTime` is a marker under requirement 4's reading.

**Why one implementation could not have found it.** The sentence reads as
careful, cites a real precedent in `contacts_sync`, and is correct about the half
of the sync anybody reading it would have in mind. It took writing a backend that
took it at its word.

**Commit:** `9a238bb`.

### 2. The whole clash story lived on the push, and the push does not always run

**What the seam said.** That a backend reports `ItMovedFirst` and writes
nothing, and that whatever drives it holds both copies. Nothing about a sync
whose push never reached a backend at all.

**What is wrong with it.** The setting can refuse a push, nobody may be signed
in, the request can fail. In each of those the change stays here and stays
marked as waiting, on purpose, so that fixing the cause still sends it. The read
that follows in the same sync then wrote the backend's copy over it and cleared
the flag. The sync counted one change as waiting and destroyed it a moment
later, and the count was the only thing anybody was told.

**What was changed.** `take_what_has_arrived` holds both copies through
`conflict_choice` when the copy here has an unsent change and what arrived says
something else. The contract's conflict section gains a requirement on whatever
drives a backend.

**This is not a second backend's problem.** It fails for both implementations,
so it is reachable with the backend that ships today: the setting is off,
somebody edits a note, somebody else edits it at the server, and the sync
destroys the local edit. It was found while writing tests for the second
implementation, not because of anything the second implementation does.

**Commits:** `9a238bb` for the failing tests, `458da20` for the fix.

### 3. A backend has no way to say what it could not keep

**What the seam said.** That `Done` carries an identity, because a write may
change one. Nothing about the words.

**What is wrong with it.** Neither format this program speaks can promise the
bytes. A page is an HTML document and HTML collapses a run of whitespace to one
space and cannot hold one at the end of a line, so `  - Older cable: red` stops
being a nested list item. A calendar journal document has one escape for a line
break and no way to write a carriage return inside a value, which `05.1-03`
measured. Left unsaid, the two copies differ from the moment of the first push,
every later sync compares markers and reports the note unchanged, and the first
thing that moves a marker brings the backend's version of somebody's note down
over theirs with no question asked.

**What was changed.** `WhatTheBackendSaid::Done` carries `what_it_could_keep`,
and the sync writes it down and counts it. A new section of the contract, "Bytes:
what a backend must hand back", says it as three requirements on any backend.

**Commits:** `847626c` for the failing tests, `6fe4580` for the fix.

### 4. A marker may stand still while the note moves

**What the seam said.** "A version marker is not promised to be opaque, and is
not promised to change only when the content does." That is the harmless
direction: a marker that moves for its own reasons costs a fetch nobody needed.

**What is wrong with it.** The other direction is not written down and it costs
somebody their note. A clock reading has a resolution, and two changes inside
one of its ticks carry one reading, so the sync reports the note unchanged and
the change never arrives. An ETag cannot do that, which is why one implementation
could not have found it. Measured as
`test_a_marker_that_stood_still_while_the_note_moved_hides_the_change_from_the_read`.

**What was changed.** Requirement 4 now carries both directions and says which
one is which. How wide a real `lastModifiedDateTime` tick is, and so how likely
the collision is, is ledger 251.

**Commit:** `847626c`.

## What the plan got wrong against the tree

**Constraint 1 compresses its own source, and following the plan's wording
produced a backend no service resembles.** The plan's task 1 says "It has no
version token. Whatever the trait's version marker is, this backend returns
nothing for it, always." The phase README, which is the plan's cited source,
says something narrower: `onenotePage` has no `eTag` property and the update
reference names no `If-Match`, "so OneNote's concurrency is a timestamp the
service owns". A timestamp is a marker.

The first version of the second implementation followed the plan and gave
nothing. It could not raise a clash at all, so the conflict test failed for it
and passed for the other, and the honest reading of that failure is not "the
seam's conflict story is CalDAV's" but "a backend that gives no marker cannot
participate in any conflict story". The implementation was reshaped to give a
service-owned clock reading, which is what the source says, and the no-marker
case was kept as one test that measures what the contract's "optional" costs.
That measurement is finding 1 and it is worth more than the failing test was.

**The guard break the plan asks for cannot be measured.** Task 1 says to "make
the sync call a concrete CalDAV type directly and confirm the second backend's
tests go red and the first backend's do not". `sync_notes` is generic over
`NotesService`, so naming a concrete type in it does not redden a test, it stops
the crate compiling, and a run has no red list to compare. The record taken
instead is the same property with a break a run can see: the sync reading a
container as an address and keeping its last part.

**Task 3's `read_first` names summaries that do not exist.** It asks for "the
summaries of `05.1-02`, `05.1-03` and this plan's tasks 1 and 2". There are no
per-task summaries in this workflow; the commit messages are what carries that.

**Premise 8's guard-record figures held and premise 9's did not.** Re-measured on
this tree: `guards/guards.toml` held 697 records at the start rather than the 683
the plan says, and the census read 192 and 505 rather than 192 and 491. The
per-file counts the premise gives, 0 for `conflict_choice.rs` and 77 for
`contacts_sync.rs`, are unchanged and no `#[test]` was added to either.

## Where the second implementation lives, and what the other choice would have proved

**In `tests/the_notes_seam_takes_a_second_kind_of_backend.rs`, which is the
stronger of the two options premise 4 offers.**

An integration test links the library the way another crate would, so it sees
only what is `pub`. It compiles, which means `NotesService`, `ANoteThere`,
`ANoteAsItStands`, `WhatTheBackendSaid`, `WhatTheBackendKept` and
`notes_sync::sync_notes` are all reachable from outside the crate. Had `05.1-02`
made the trait `pub(crate)`, as `tasks_sync::TaskService` is, this placement
would have been impossible and that would have been the finding. It was not
impossible, and `notes_backend.rs`'s own comment records why: `pub(crate)` is
`dead_code` for a trait with no implementor, so the trait was made `pub` for a
reason that has nothing to do with this plan and happened to make it possible.

**What the other choice would have proved.** Keeping it in the crate would have
proved that the seam takes a second implementation, and nothing about whether an
implementation written elsewhere could be compiled against it, because it could
have reached private items without anybody noticing. Premise 4 asks for one
integration test naming every item an outside implementation would need if that
route is taken; taking this route makes the whole file that test.

**What this placement still does not prove.** An integration test is built
against the same source tree in the same commit, so a change that breaks a
published API breaks it here rather than a version later. It says nothing about
a separately published crate. Ledger 250.

**And what it costs.** The real CalDAV backend cannot be driven from here: it
holds a live client and every call it makes wants a socket. So the first backend
is represented by a stand-in with CalDAV's shape, not by
`service::caldav_journal` itself, and every sentence above about "both backends"
means both shapes. Saying otherwise would claim a network test that does not
exist.

## The seam change, and why it is the good kind

`WhatTheBackendSaid::Done` went from `Done(ANoteThere)` to a struct variant
carrying `known_as` and `what_it_could_keep`, with `WhatTheBackendSaid::done` for
the ordinary answer.

The plan sets the test: "A change that makes the trait more general is the good
case. A change that adds a method only one backend uses is the bad case, and it
is worth stopping over."

It is a field on a variant every backend already returns, not an operation one
backend calls. Every removal uses `done`. And the shipped backend uses it: it
answers by reading its own document back through
`note_document::the_note_in`, the same reader a later sync will use, so a body
typed on Windows is reported as not kept exactly rather than as taken. That
limitation was measured by `05.1-03` and written into a changelog and a module
header, where the person whose note it is never meets it.

**The alternative that was rejected, and why.** The sync could read back what it
wrote and compare. That is one extra request per write on every backend, always a
no-op for a backend that keeps bytes, and it still cannot tell the backend's own
reshaping from a change somebody made in the meantime. Only the backend knows,
and only at the moment it writes.

**The decision inside the decision, and it has a real cost.** The copy here
becomes the copy the backend kept, at the moment of the push. So a note that has
been to a backend which cannot round-trip is no longer the bytes somebody typed.
The alternative keeps their bytes and lets the two copies differ in silence until
something moves a marker, at which point the backend's version arrives over
theirs weeks later for no reason they can see. Between a loss somebody watches
happen and a loss that arrives unannounced, the first is better. Nobody has been
asked, and that is ledger 252.

## The round trip, and exactly which bytes moved

The test asserts on bytes and names the lines rather than saying the word
"normalises". A note holding two levels of Markdown indentation, a run of spaces
used to line something up, and a trailing space:

| typed | what a page kept |
|---|---|
| `  - Older cable: red` | `- Older cable: red` |
| `Terminal  Colour` | `Terminal Colour` |
| `L         brown ` | `L brown` |

Through the documents-shaped backend the same note is byte-identical.

The contract's answer, written as a requirement on any backend rather than as a
description of this one: a backend that cannot round-trip is allowed, it must
report what it kept, it must answer from its own copy rather than from a rule
about itself, and it never resolves the difference.

**The stored form did not change and no note was migrated.**
`test_the_stored_form_of_a_note_did_not_change_to_take_a_second_backend` reads a
note written the way every note has always been written and asserts the bytes,
the format word, and that a note no backend has held carries no identity and no
marker. No column was added by this plan and no schema statement ran.
