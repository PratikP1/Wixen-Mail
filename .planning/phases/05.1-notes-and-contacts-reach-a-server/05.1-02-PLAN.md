<objective>
Build the one place that decides where a note goes, write down what a backend
has to answer, and make the settings screen say plainly that notes stay on this
computer.

Purpose: PIM-07's first `[D]` line, all of PIM-08, and PIM-04's last two. The
decision was made on 2026-08-29 and is recorded in `.planning/REQUIREMENTS.md`:
a note has a backend chosen by the account it belongs to, the local note is a
first-class Markdown document, and the seam is shaped so a hosted service can be
added later without a migration. This plan builds the seam and ships no backend
behind it, which is what PIM-08's last `[D]` line asks for in as many words:
preparing for it means the seam does not forbid it, not that anything half
exists.

Output: one answer to "where do this account's notes go", a written contract for
what a backend has to do, a settings screen that says the honest answer, and a
menu that offers a sync exactly where one is possible.

Which backends exist is settled. Decision 2 of 2026-09-06: all three. CalDAV
VJOURNAL in `05.1-03`, a second implementation that exists only in tests in
`05.1-04`, and OneNote in phase 5.2. This plan builds the seam they all go
behind and ships none of them, which is what PIM-08's last `[D]` line asks for
in as many words.
</objective>

**1. `05-RESEARCH.md` names a function that does not exist, twice.** It says
"`new_item.rs`'s `syncs` predicate is the natural seam and it currently returns
`false` for `Note`" and repeats the claim in its PIM-07 section.
`grep -rn "syncs" src/application/new_item.rs` returns four hits, all prose
inside comments, and no function. `grep -n "^pub fn \|^    pub fn " src/application/new_item.rs`
lists `kept_in`, `label`, `plural`, `shortcut`, `holding`, `holds`,
`account_id`, `spoken`, `supports`, `destination`, `renaming_works`,
`container_destination`, `sends_from`, `default_after_change`,
`deletion_question`, `deletion_reaches_provider`, `the_provider_has_a_copy` and
`deletion_warning`. **The function meant is `supports`**, whose doc comment at
line 238 reads "Whether this account's provider syncs this kind of item". An
executor told to widen `syncs` would spend real time looking for it.

**2. `supports` has exactly one production caller and it is not a sync.**
`grep -rn "supports" src/ tests/ --include=*.rs` returns eighteen hits, of which
one is the definition, one is a comment in `mail_controller.rs` about something
else, four are inside its own tests, several are unrelated words in
`folder_tree.rs`, `message_columns.rs`, `wx_reader.rs` and `imap.rs`, and
**exactly one is a call: `destination()` in the same file**, which decides
whether a newly made item goes to the account or to this computer. Nothing in
any `*_sync.rs` file calls it.

So `supports` is the right *shape* and the wrong *function to widen*. It answers
a bool and the seam needs a which. And widening it would change where a new note
is filed, which is a behaviour change nobody asked for and would land the moment
the first backend shipped. **Write the seam beside it, in its own module, and
have `supports` answer from the seam if that reads better than two answers to
one question.** Say in the summary which was chosen and why.

**3. The green test that has to change is about a constant, and turning it into
a question is the point.** `test_notes_are_not_offered_a_sync_they_cannot_do` in
`src/application/context_menu.rs` asserts `entries_for(Focus::Containers(ContainerKind::NoteFolder))`
does not contain `Action::SyncNow`. Above the `NOTE_FOLDERS` static is a comment
saying "No sync: notes are kept on this computer and go nowhere, so offering to
sync them would be offering something that cannot happen." Both are correct
today. **After this plan they are still correct, because no backend ships**, so
the test does not simply invert. What has to change is that the menu asks the
seam instead of holding a constant, and the test asserts agreement in both
directions rather than an absence, the way
`test_move_is_offered_exactly_where_it_means_something` beside it already does.
That is a real red: an absence assertion is satisfied by a menu that can never
offer it, and an agreement assertion is not.

**4. The menus are static arrays, and a menu that has to ask a question is a
change to how `entries_for` works.** `CALENDARS`, `TASK_LISTS`, `NOTE_FOLDERS`
and `CONTACT_GROUPS` are `static &[Entry]` in `context_menu.rs`, and
`entries_for(Focus::Containers(kind))` returns one of them. A note folder menu
that depends on the account is no longer a constant. **Read `entries_for` and
`Focus` in full before deciding how the account reaches it**, and if the shape
of `Focus` has to change, say so and say what else it costs, because several
tests loop over it. Do not thread an account through every menu because one of
them needs it.

**5. The settings section has a place and a precedent.** `fn build_calendar_pim_tab`
in `src/presentation/wx_settings.rs` builds `section(panel, "Calendar")`, which
is empty today, then Reminders, then Working Day. The Permissions tab's Contacts
section is the worked example of the shape this wants: a `section`, a control,

`set_accessible_name` set to the same string so both Windows channels say it.
Read `build_permissions_tab`'s Contacts block before writing the Notes one.

For a static text the label is what Narrator reads and `set_accessible_name` is

split.

**6. This plan adds no setting, and that is deliberate.** `CLAUDE.md`'s rule is
that every setting a user has is reachable from the settings screen. The
converse is also true here: **a sentence is not a setting.** Where an account
has no notes backend there is nothing to choose, so a switch would be the
"control that does nothing" this project has removed repeatedly, and PIM-04's
own `[D]` line asks for a sentence rather than a switch. If a later backend gives
somebody a real choice, that is a setting and it is introduced in the plan that
introduces the choice.

**7. There is a document guard that a per-account feature can trip.**
