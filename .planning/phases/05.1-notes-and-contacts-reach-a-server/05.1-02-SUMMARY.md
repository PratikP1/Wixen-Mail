# Phase 05.1 Plan 02: One place says where an account's notes go, Summary

**Where an account's notes go is answered once, in `application::notes_backend`,
and the note folder menu, the settings screen and where a new note is filed all
ask it instead of each holding their own copy. Nothing has a notes backend, and
the settings screen says so in words that stay true after all three ship.**

## Does it work

Yes, for what is testable on this computer, and nothing here reaches a network.

The seam answers for a Gmail account, an Outlook account, an account whose
provider this build does not recognise and no account at all, with a reason per
arm rather than one reason for all of them. The note folder menu asks it, in the
library and in the running program: the notes sidebar reads the default account
out of the window state and hands the answer to the menu, rather than passing a
constant `Focus` that names no account. Where a new note is filed asks the same
function rather than keeping its own `false`.

The settings screen has a Notes section on the Calendar and PIM tab that names
the default account and says whether that account's notes leave this computer,
on both Windows accessibility channels.

`scripts/check.sh all` was run on the branch before the merge, not piped, and
reported "All four checks passed" with exit status 0. Nothing used
`--no-verify`.

**What does not work, because it does not exist.** No backend. `NotesService`
has no implementor, `NotesBackend::CalDavJournal` is answered by nothing, and
every account's notes stay here. That is the plan's own output and it is
recorded in the ledger rather than described only here.

## The `syncs` predicate does not exist, and `supports` is what was meant

The plan required this in writing. `05-RESEARCH.md` says twice that
"`new_item.rs`'s `syncs` predicate is the natural seam and it currently returns
`false` for `Note`". There is no such function:

```bash
grep -rn "syncs" src/application/new_item.rs
```

Four hits, every one of them prose inside a comment. The function meant is
`supports`, whose doc comment reads "Whether this account's provider syncs this
kind of item". An executor told to widen `syncs` would have gone looking for it.

## What was done about `supports`, and why

**It answers from the seam.** The plan offered two defensible answers and this
took the second, because the first truth the plan asks for is that one place
decides and every screen and menu asks it. Two functions that could disagree
about one account is what the whole plan is against, and leaving `supports` with
its own `false` would have been a third copy of the fact the other two had just
stopped holding.

The consequence is real and is worth stating plainly: **the moment a backend
ships, a new note made in an account that has one is filed under that account
rather than on this computer.** That is a behaviour change, it is correct, and
it arrives with the backend rather than now. Today the seam answers
`ThisComputer` for every account, so nothing moves.

**No test holds two functions together, because there are not two.** The plan
asked for one if two could disagree. `supports` delegates, so there is one
function and one answer, and a test asserting that a delegating call equals the
thing it delegates to would be a tautology. What does hold it is the second
guard record below, whose break is the seam's fallback arm answering that a
backend exists: it reddens a test in `new_item.rs`, which is the evidence that
`supports` really asks here rather than keeping its own copy.

## The note folder menu test, and why it is a table of literals

`test_the_note_folder_menu_offers_a_sync_exactly_where_the_seam_says_one_exists`
is one row per answer the seam can give, with the expected column written down:

| the seam's answer | does the menu offer Sync now |
|---|---|
| `ThisComputer` | no |
| `CalDavJournal` | yes |
| `Other("something-later")` | no |

**Why not an agreement assertion.** The four checks beside it in that file
compare a menu against a predicate in a different module, `pim_command` or
`new_item`, so a break inside `context_menu.rs` moves one side only. A notes
check written the same way would compare the menu against the seam, and both
sides would come from the seam. The break this plan prescribes, making the seam
always answer that a backend exists, would then move them together and nothing
would go red. The plan's correction said this and the measurement below confirms
which breaks redden what.

**`test_notes_are_not_offered_a_sync_they_cannot_do` was kept unchanged.** It
asserts against a literal, so it goes red when the seam is broken while an
assertion computed from the seam would not, and it is named in the first guard
record's red list for exactly that reason.

**The unrecognised-backend row answers no, and here is the sentence.** A build
that meets the name of a backend it has never heard of has no client for it, so
offering to sync would be offering something that cannot happen, which is the
rule `context_menu`'s own module header is written to. The note is still read,
still edited and still kept, because surviving being read is not the same as
being acted on, and that is what `Other` is for.

answered from its provider, through `mail_auth::provider_of`, which takes an

Fifty-one fields, `default_account_id` among them, and no accounts.

**The section is last on the tab, and the reason is the keyboard.** The three

cannot skim, so the tab's other subject starting after the first one finishes is
what they expect. Between Calendar and Reminders would split a group; first

**The sentence survives three backends shipping.** It says "this account has no

## The contract, and where it knows it has assumed CalDAV

`docs/development/the-notes-seam.md` answers identity, conflict, removal and the
deletion record, each as a requirement on any backend.

**Conflict says in as many words that a backend does not resolve one**, and
names `conflict_choice.rs` and the third `TheOtherCopy` variant a notes backend
adds. The reason is in the document: two conflict models disagree the first time
either is changed, which is what `03-RESEARCH.md` warned about and what SCALE-06
was corrected to avoid.

**The deletion record is the fourth thing, and the requirement does not name
it.** There is no `deleted_notes` table:

```bash
grep -n "CREATE TABLE IF NOT EXISTS deleted" src/data/message_cache/mod.rs
```

Three tables, none of them notes. The document quotes `application::deletions`'s
own account of what happens without one, which is a note somebody deleted coming
back the next time they look, under the backend's own identifier, with nothing
left saying it was ever deleted.

**Which of the three OneNote constraints fell which way**, which the plan
required naming:

| Constraint | Held or given up |
|---|---|
| The version marker | **Held, and narrowed.** Equality is the only comparison allowed. Ordering one, parsing one as a date, or reading a changed marker as proof the text changed are ruled out in writing, so `lastModifiedDateTime` works under the contract even though it is not an ETag |
| The write operation | **Given up.** A OneNote page's body cannot be replaced, only appended to, so the operation asks for an end state and requires the backend to report what it calls the note afterwards, because reaching that end state may change its identity |
| The container identifier | **Held, by making it opaque.** A four-level hierarchy flattens into one string the backend owns and nothing here parses |

The document also names the assumption it knows is weakest, which is that one
note maps to one thing at the backend. A OneNote page is an HTML document with a
structure of its own, and reducing it to a title and a body loses whatever else
was on it. `new_item.rs` has said since before this plan that the mapping is a
decision somebody has to make. The contract does not make it.

## The trait, and the two lints that decided its shape

```rust
pub enum WhatTheBackendSaid {
    Done(ANoteThere),
    ItIsNotThere,
    ItMovedFirst { version_now: Option<String> },
    NotSignedIn,
    NotAllowedToChangeAnything,
    CouldNotBeReached(String),
}
```

Separate variants rather than one error string. The three a person can do
something about have to be tellable from the ones they cannot, because the
sentence differs and so does what it asks of them, and `CouldNotBeReached`'s
string is for the log: text a crate wrote for a developer is not text to speak
to somebody whose notes did not sync.

**Nothing implements it and nothing calls a network.**

```bash
grep -rn "reqwest\|http" src/application/notes_backend.rs
```

Nothing. There is no fake either, deliberately: a second implementation written
the same day as the interface, by the same person, against the same assumptions,
agrees with the interface. `05.1-04` writes one shaped from OneNote's measured
constraints.

**Premise 13 is half right, and the half that is wrong cost a real detour.** It
says a `pub` item in a library crate's public module with no caller compiles
clean under `-D warnings`. That is true, and it is true of the enum and the
functions. It is not the whole story for a trait with `async fn`:

- `pub(crate) trait NotesService`, which is where `TaskService` sits, gives
  `trait NotesService is never used`, because `dead_code` does fire on a
  crate-visible item nothing implements.
- `pub trait NotesService` with `async fn` gives `use of async fn in public
  traits is discouraged`, three times, one per method. That lint is warn by
  default, not allow.

Both are build failures under `-D warnings`, and silencing either with an
`#[allow]` is what `CLAUDE.md` forbids. What is left is the desugared form the
lint itself suggests: `fn ... -> impl Future<Output = ...> + Send`. It states the
`Send` bound a sync spawned on the runtime needs anyway, so the shape the lints
forced is the more honest one. The trait's doc comment records the bind so the
next person does not walk it again.

## A TOML escape that read as a broken guard

Worth a paragraph because the failure looked like something else. The first
version of record 3 was appended with a shell heredoc, and the `\\` meant to
survive into the file arrived as a single `\`. In a TOML basic multi-line string
a backslash at end of line is a line continuation: it strips the newline and the
leading whitespace of the next line. The record's `before` text therefore had
its own line break removed, matched nothing in the file, and
`test_every_guard_record_still_names_one_place_in_the_tree` reported that
somebody had moved the code the guard is about.

The fix is `'''` rather than `"""`. A TOML literal string does no escaping at
all, which is what a record quoting source ought to use, and the Edit tool
rather than a heredoc, which is what `CLAUDE.md` already says about scripted
edits to tracked files.
