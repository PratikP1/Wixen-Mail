# Phase 05.1 Plan 03: A note goes out to a calendar server and comes back, Summary

**A note made on an account that already has a calendar on a calendar server is
now sent to that server's journal entries under the same sign-in, a note changed
there arrives here, a deletion stays deleted and a note that moved in two places
is a question somebody is asked. All of it runs through a sync that does not know
which backend it is talking to, and none of it has ever met a real server.**

## Does it work

Yes, for what is testable on this computer, and nothing here has reached a
network.

A note waiting here is offered once and not again; one the setting held stays
here and goes on waiting; one changed at the backend arrives and replaces the
local copy; one sent in this sync is not taken back down by the read that follows
it. Pinning a note and moving it between folders both mark it as waiting, which
matters because neither goes through `save_note`. Copying a note clears what the
backend calls it, so the first copy of a synced note makes a second note at the
server rather than overwriting the original.

A deletion is written down before it is sent, kept until the backend has taken
it, and kept for a week after that, so a backend whose own list has not caught up
cannot put the note back. Deleting a folder leaves a record for every note in it.

A note that moved in both places is held through `conflict_choice` with both
copies and the fields that differ, and the question says "note" rather than
borrowing the words for a contact, after a restart as well as before it.

`scripts/check.sh all` was run on the branch before the merge, not piped into
anything, and reported "All four checks passed" with exit status 0. Nothing used
`--no-verify`.

**What does not work, said plainly: nothing here has met a server.** Every part
of it has been driven against a stand-in written in this repository. That proves
the program agrees with itself and says nothing about anybody's calendar server,
and nine ledger entries name the unknowns one at a time rather than as one.

## Two premises the plan did not have, and both would have stopped the feature

**The seam had no way to read a note's words.** `NotesService` shipped with three
operations: `notes_it_holds`, which answers identities and version markers, and
two that write. A sync built on that can discover that a backend holds a note it
has never seen and have nothing to write down. `05.1-02` could not have noticed,
because nothing implemented the trait; the first implementation is what a first
implementation is for. A fourth operation was added, `what_a_note_says`, with
`ANoteAsItStands`, and it is asked only for the notes whose marker moved so a
container of five hundred is not read whole on every sync.

**Nothing could make an account answer `CalDavJournal`.** `for_account` reads the
account's mail provider, and `gmail` and `outlook` both answer `ThisComputer` on
purpose. There was no third route, so a CalDAV notes backend would have been
unreachable from anywhere except a test: a stub with a client behind it.

The route taken is the one the plan's own threat register anticipates when it
asks whether this backend reuses the sign-in of a calendar somebody already
added. A calendar server keeps journal entries in the same place it keeps
calendars, under the same sign-in, so an account that already has a calendar on a
server already has everywhere a note needs to go and everything needed to get
there. `has_a_calendar_server` is the lookup, and it asks for the word and the
address together: the word alone counts a row half written by a failed discovery,
and an address alone counts a published feed, which is read and never written to.

**What that cost, and it is the largest deviation in this plan.** `for_account`
takes the fact as a second argument, which means `new_item::supports` and
`destination` do too, and the settings dialog gained one more parameter beside
the accounts `05.1-02` gave it. Around twenty-five call sites, most of them in
tests. The alternative was leaving `supports` with the provider-only answer,
which is two places disagreeing about one account and is exactly what `05.1-02`
was written to end.

## Where this implementation proved or refuted the seam's own assumptions

The contract's last table names four assumptions it knows it made. This is what
the first implementation found.

| Assumption | What happened |
|---|---|
| A version marker is a token compared for equality | **Held, and used exactly that way.** `the_marker_stayed_still` compares for equality and nothing else. A backend that gives no marker has every copy treated as having moved, which is what the contract requires and what `contacts_sync::the_marker_moved` already does |
| The whole document can be written | **Given up, and it was right to give it up even here.** This backend *can* replace a whole document and does not: `the_document_with_the_note_changed` reads what the server holds and replaces two properties, because a document written from nothing throws away categories, class and everything else this program has never modelled. The contract asked for an end state rather than a replacement, and that shape turned out to be the right one for the backend it was written against, not only for the one it was written about |
| A container is one identifier, made opaque | **Held.** The container is a collection address, stored and handed back, and nothing parses it |
| A backend can be asked for everything in one container | **Held, and it is thinner than the contract implies.** A listing answers identities and versions, not content. The contract did not say which, and a sync needs both, which is what the missing fourth operation was |
| One note maps to one thing at the backend | **Held here and it says nothing about OneNote.** A journal entry is a title and a body, so the mapping is free for this backend and the contract's own note that this is the weakest assumption still stands |

**And one thing the contract did not think about at all, which is the finding
most worth carrying.** The phase README says this backend "is the only candidate
whose round trip can be byte-identical, which PIM-04 requires". That is false,
for one specific case. The format has one escape for a line break and no way to
write a carriage return inside a value at all: RFC 5545 section 3.3.11 gives
`\n`, and a literal carriage return would end the content line. So a body typed
on a Windows machine goes out as one break and comes back as LF.

That is a property of the format rather than of this code, and no backend
speaking it can do better. Everything else survives, and it is asserted: a
trailing space, a comma, a semicolon, a backslash, a character outside the basic
multilingual plane, a body long enough to be folded across lines, and a line
inside the body that reads `BEGIN:VEVENT`. Notes kept on this computer are
untouched by any of it; `05.1-01` proved that round trip separately and it still
holds.

**The trailing space took a reader of its own, and it was found by the fixture.**
The first version of `note_document.rs` used the calendar's `value_named_on`,
which trims. That is right for a zone name and wrong for a note: a body is
somebody's text. Two tests failed on the first run and `the_whole_value_on`
exists because of them, with the format on its side, since RFC 5545 section 3.1
puts a value immediately after the delimiter colon.

## Where the identity lives, decided in writing

**On the note row**, in two columns, rather than in a table keyed by note and
backend.

`ProviderIdentity` is per address book for a contact, and its comment records
what went wrong before it was: a flag kept on the contact meant a push refused at
one address book either lost the change at the other or resent it to both for
ever. That failure needs two backends holding one thing at the same time. A note
has one: `for_account` gives one answer per account and a note belongs to one
account, so there is no second place for a refused push to lose the change at.

**What would have to change if a note ever had two backends**, written into the
schema comment where the next person meets it: this becomes a `note_identities`
table keyed by note and backend, the shape `contact_identities` already takes,
and `pending` moves onto it, because that is the moment one push can be accepted
and another refused in the same run.

## The three writers, and the one that would have been missed

`save_note` is the upsert. `toggle_note_pin` writes its own `UPDATE` and would
have bypassed anything kept only in the upsert. `file_under` files a note
somewhere else and its copy branch now clears the identity and the marker, which
premise correction 2a is about: kept, the first copy of a synced note asks the
backend to change its copy of the original, and the original is the one that
moves. That is data loss at somebody's server.

`will_have_to_be_sent`'s note arm answered `false` with a comment naming this
plan, and **nothing pinned it**. Leaving it would have compiled, linted under
`-D warnings` and passed every other test this plan asks for, while announcing
every note move with nothing said about the change waiting. The sentence a moved
note is now announced with, from `pim_command::what_is_waiting`, is the one a
task and an event already get: the move is reported and the clause saying the
account has not been told is appended to it.

## The conflict variant, and the place the compiler is silent about

Four places, as premise correction 4 says, and the compiler names three.
`called()`, `the_thing()` and `stored_kind` are exhaustive matches over the enum
and are compile errors the moment the variant is added. `kind_from_stored`
matches on a `&str` with a catch-all, so without its arm a note conflict **this
build wrote** would read back as an address book conflict.

The two sentences:

> You changed this note here and it changed in your notes backend as well. 1
> field is different: Body. Choose which copy to keep.

> Kept what your notes backend has for Wiring colours. The change made here is
> gone.

And the round trip that proves the stored word comes back as a note is
`test_a_held_note_conflict_comes_back_as_a_note_and_not_as_a_contact` in
`held_conflicts.rs`: it holds a note conflict, reads it back, and asserts the
question names a note and says neither "contact" nor "address book". Quoting the
sentences alone would have been satisfied by code that says "your address book"
about a note after a restart.

**"Your notes backend" and not "your notes"**, although the shorter one reads
better beside its two neighbours. These words go into five sentences and one is
`format!("What {} has", called())`. "What your notes has" is not English. The
phrase is already the one the settings screen says out loud.

**Settling a held note conflict was in no part of the plan and had to be built.**
`settle_a_held_conflict` looks contacts up and calls `save_contact`, so a held
note would have had its hold let go with the choice applied to nothing: a
question somebody answers and nothing acts on. The two endings are the mirror
image of the contact ones, and the reason is that the notes read compares markers
rather than content. Taking their copy therefore leaves the marker stale, which
is what makes the next read fetch it; bringing it up to date would make the read
answer "unchanged" and the copy somebody chose would never arrive.

## The waiting sentence, quoted

```
1 change is waiting here: turn on Allow Changes in Settings to send it
```

It comes from `allowed::changes_waiting_here` rather than a second string, whose
own comment records that two copies of that fact drifted and only one was

## The gate, applied where the client is built

`CalDavClient::for_account` is what `AJournalOnACalendarServer::for_account`
builds, and that is where `allowed_for(account_id).personal_information` is read,
the same way `tasks_api`, `google_api`, `microsoft_graph` and `caldav` all do it.
Nothing in the notes code asks the setting a second time: a client that may not
change anything refuses the request before the network, and that refusal arrives
as an error the adapter turns into `NotAllowedToChangeAnything`, which the sync
counts rather than reports.

## The fake, and what it can do

`Scripted`, in `notes_sync.rs`'s tests. It can refuse for an ordinary reason,
answer that nobody is signed in, refuse because of the setting, say its own copy
moved first, answer an empty container, refuse to be listed at all, and lose a
note between the listing and the reading. It records what it was asked to write
and what it was asked to remove, before answering rather than after, because the
question is whether the call reached it and a refusal is still a call that
reached it.

Which test drives which:

| what the fake does | the test that needs it |
|---|---|
| refuses because of the setting | `test_a_note_the_setting_held_stays_here_and_is_counted_rather_than_reported_as_a_failure` |
| answers an empty container | `test_a_note_waiting_here_is_offered_to_the_backend_and_then_is_not_offered_again` |
| says its copy moved first | `test_a_note_that_moved_in_both_places_is_held_rather_than_written_over` |
| refuses to be listed | `test_a_container_that_cannot_be_read_is_said_rather_than_reported_as_empty` |
| loses a note mid-sync | `test_a_note_the_backend_lost_between_the_listing_and_the_reading_is_not_a_failure` |
| says nobody is signed in | `test_nobody_signed_in_is_said_in_words_rather_than_counted_as_a_problem` |

**One test was written weak and was corrected before the RED commit.** "A note
held for a choice is not offered again" passed against a sync with no hold in it
at all, because the read had written the backend's copy over the unsent change,
so nothing was waiting and nothing was offered. It now asserts that the note is
still waiting and still says what was typed here before it counts anything.

## Every hop from a key press to a note leaving the machine

Somebody presses the menu key, or `Shift+F10`, on a note folder and chooses
"Sync notes now".

1. `wx_context_menu::show` builds that menu from
   `context_menu::note_folder_entries`, which is handed
   `notes_backend::for_the_default_account_in`'s answer, so the line is there
   only for an account whose notes really go somewhere.
2. Choosing it raises `ID_CONTEXT_SYNC_NOW`.
3. Its handler in `wx_app.rs` reads the open module and calls `spawn_notes_sync`.
4. That opens the store on a worker, finds the open account, and calls
   `notes_backend::sync_the_notes_of`.
5. Which asks the seam, finds the account's calendar server with
   `the_calendar_server_of`, builds
   `caldav_journal::AJournalOnACalendarServer::for_account` from that calendar's
   sign-in, and hands it to `notes_sync::sync_notes` with the collection as the
   container.
6. What comes back becomes a status line and a repaint.

Three answers rather than a result and an error: an account whose notes stay here
is told so, an account whose server nobody has signed in to is told that, and a
sync that ran reports what it did.

## Known Stubs

**An account with two calendar servers sends its notes to the first one the
store answers with.** Nothing asks which and nothing says which was chosen.
Ledger 245.

**Note folders on this computer are not mirrored at the server.** Every note
arriving from a server is filed in the account's first note folder, so folders
somebody made here mean nothing at the other end. What a folder *is* at each
backend is a decision somebody has to make, and this plan does not make it. The
module header says so rather than leaving a reader to work out why every arrival
lands in one place. Ledger 246.

**A push that meets `ItIsNotThere` reports it rather than settling it.** A note
this computer thinks the backend holds, which it does not, is reported as a
problem on every sync rather than being created afresh. It is not reachable from
this backend's own code path, because the adapter maps a 404 on a read to "not
there" and the push reads before it writes, so it is a case only a differently
shaped backend produces. `05.1-04` is the plan that produces one.

Nothing else. `notes_sync`, `note_document`, `caldav_journal` and every function
added to `notes_backend` are reached from production through the note folder
menu, and the guard record whose break is the handler calling nothing is what
says so.
