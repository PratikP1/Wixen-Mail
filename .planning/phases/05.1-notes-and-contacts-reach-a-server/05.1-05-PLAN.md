<objective>
Read and write what a CardDAV server exchanges, without a server, and make the
one card reader and the one card writer things that exist so nothing writes a
second.

Purpose: PIM-05's second and fourth `[D]` lines. The fourth asks that the XML and
vCard parsing be pure and unit-testable without a server, per this project's
thin-transport rule, and says the transport stays untested until a live account
exists. The second asks that contacts sync both ways "reusing the existing vCard
reader and writer rather than a second one". That second one is the harder half
and the requirement does not know why: the two functions it points at are not a
reader and a writer of a card. One writes rows to the database while it reads a
whole file, and the other renders every contact in an account into one string
inside a `for` loop.

Output: a per-card reader and a per-card writer that both callers share, and the
two parsers a CardDAV client needs, none of which touches a network.
</objective>

**1. `05-RESEARCH.md` corrected the requirement about where the vCard code
lives, and the correction is still not the whole story.** The research is right

`pub fn import_contacts_from_vcard(&self, account_id: &str, vcard_data: &str) -> Result<CardsRead>`
takes a whole file, reads every stored contact for the account first, matches
each card against cards already read in the same file and against stored
contacts, and writes rows. It is an import, not a parse.

`pub fn export_contacts_to_vcard(&self, account_id: &str) -> Result<String>`
reads every contact for the account and appends `BEGIN:VCARD`, then each
property, then `END:VCARD` inline inside a `for` loop. **There is no function
that turns one contact into one card.**

`grep -n "fn cards_in\|fn contact_from_vcard_block\|fn escape_vcard_text\|fn fold_vcard_line" src/data/message_cache/contacts.rs`
finds four private associated functions, and those are the reusable parts:
`cards_in` splits a file into blocks and `contact_from_vcard_block` turns one
block into a `ContactEntry`.

**So "reuse rather than write a second" means lifting a per-card reader and a
per-card writer out of the two whole-file functions**, and that is task 1. Doing
it any other way writes the second card writer the requirement forbids, and the
two would disagree the first time either was corrected. This project has the
worked example: `days_called_off`'s comment records a gap between a reader that
stripped a property name and a writer that assumed bare digits, and says that
gap is how a cancellation went back to a server with its own property name
written in front of it twice.
