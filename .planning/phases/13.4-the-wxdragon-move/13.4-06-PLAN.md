<objective>
Open every window the main window's tick can open after the tick has returned, so the tick never
runs inside itself and keeps handling mail, sync and send results and reminders while one of
those windows is on screen.

Purpose: at wxDragon 0.9.17 the tick keeps running while the Due now window is open only because
the toolkit lets a handler run again inside itself. At 0.9.23 every handler sits behind a
re-entrancy guard, and a second call while the first is running is skipped with a warning
(`utils/reentrant_callback.rs:70-78`, upstream #238). After the move, a person who leaves a
reminder open would come back to a program that had stopped where it was: no mail announced, no
sync or send result handled, no further reminder. This plan makes the code true to what its
comments already assume, at the version in use today, so the move changes nothing here.

Output: the queue, the six windows moved onto it, a live test and readings that were red first,
three guard records, the changelog, a ledger row for the ear, MAIL-04's dated line, the
completion marks, and a pull request whose Accessibility run is the 0.9.17 baseline.
</objective>

**4. The mechanism, chosen by the planner for Pratik to overrule.** Work queued with a new
`after_the_tick(work: impl FnOnce() + 'static)`: the work goes into a thread-local queue, and if
no drain is already scheduled, one `wxdragon::call_after` is queued whose closure captures
nothing and drains it. `call_after` needs a `Send` closure (`app.rs:37-39` at 0.9.17, `:42-44`
at 0.9.23) and the tick's state is `Rc` and `RefCell`, which is why the queue is thread-local and
the closure empty, the shape 13.4-05 gave every test. A drain that finds another drain running
returns at once and the running one takes what arrived, so one window is open at a time; a guard
resets the running flag if a piece of work panics, so one panic cannot stop the rest for good.
`call_after` closures run from the application's idle handler at both versions (0.9.17
`app.rs:37-96`, `wxdragon-sys` `app.cpp:86` and `:104`; 0.9.23 `app.rs:42-101`), which a modal
loop keeps sending, and the frame's poll timer is a different handler from that one, so it runs
beside the window. The alternative the research offered, a one-shot timer owned by a hidden
child of the frame, was set aside for two reasons: a hidden window is one more object the MSAA
and UI Automation scans walk, and at 0.9.23 a timer restarted while its own handler holds a
window open is a re-entrant call the toolkit skips with a warning. A plain capturing
`call_after` cannot carry the work at all.
