# What the move changed in each window, on both channels

Written by 13.4-12 on 2026-10-25, on branch `13.4-12-every-window-on-both-channels`, cut from
`main` at `e2f0a502`, 13.4-11.1's merge.

**The short answer: nothing a scan can see.** All 49 scanned windows read the same before and
after the move from wxDragon 0.9.17 to 0.9.23, on MSAA and on UI Automation, element by element,
and Axe found the same violations in each. What the scans cannot see, the Tab key, the edit keys,
Esc and the dialog sizes, was checked by the readings and the arithmetic below, and what only a
person can judge is listed at the end for 13.4-13's sitting.

## What was compared

Two Accessibility runs, each the scan of every window the program can open, 49 of them: `main` and
the 48 targets of `ScanTarget::ALL`.

| Side | Run | Pull request | Commit | wxDragon |
|---|---|---|---|---|
| Before | 40155889217 | #223, 13.4-06 | `2b34d39a` | 0.9.17 |
| After | 40171952674 | #224, 13.4-09 | `755424d3` | 0.9.23 |

Both runs ended in success. Each run's `Cargo.lock` was read to confirm the version it built, and
each log shows `wixen-mail` compiled against that version. Both artifacts were downloaded with
`gh run download <id> -n accessibility-scan-results`, each into its own empty folder in the
session scratchpad, and read with a script run by `py -I` from another folder. Nothing in them was
run, and the `.a11ytest` files were opened in memory and never extracted.

**MSAA, the channel NVDA reads for native controls.** Each window's `msaa-names.json` is a flat
list of path, role, name and whether somebody operates the control. Entries were paired by path,
role and their order among entries sharing both, and every name and every operated flag compared.

**UI Automation, the channel Narrator reads.** Each window's `.a11ytest` holds `el.snapshot`, the
tree Axe read, from the desktop down. Only elements of the program's own process were read. Each
was keyed by its top-level window's control type and name, then each ancestor's control type and
its place among siblings of the same type, and its Name, ControlType, LocalizedControlType,
ClassName and IsKeyboardFocusable compared. A window that wrote two files, `page`, `page-window`
and `reader`, was read as one tree with two top-level windows matched by type and name.

**Axe's count**, per window, from each run's log, summed over every summary line a window printed
rather than the first alone.

The script refuses to report when either run has fewer than 49 windows, when a window lacks
`msaa-names.json` or an `.a11ytest`, when an `.a11ytest` holds no `el.snapshot`, or when a tree
holds no element of the program's process. It refused a copy of the after run holding one window.

### Why nothing moved, and what that does not prove

The research expected movement on two fronts: wxWidgets 3.3.4 gives more controls an accessible
object of its own, every button among them, and stops a panel with nothing the keyboard can reach
from taking focus itself. Neither shows in a scan, for different reasons. An object wxWidgets makes
for a control answers with what Windows would have said, so a name that came from Windows reads the
same. And UI Automation's IsKeyboardFocusable for a Win32 pane comes from the window's own style,
which wxWidgets does not change; whether the Tab key stops on a panel is decided inside wxWidgets'
own Tab handling, which no tree records. So the scan cannot see the panel change, and the Tab pass
below is where it is checked.

## The names read where they land

Two kinds of check in the tests were judging names by something other than the name, and both now
read it.

**The editable combo boxes' typing fields.** `tests/an_editable_combo_box_is_named_where_typing_lands.rs`
builds the item form for an event and the contact editor, gives each combo box the keyboard, takes
the handle Windows says has it, and has a reader process read that handle on MSAA and on UI
Automation.

| Box | Where the keyboard lands | MSAA | UI Automation |
|---|---|---|---|
| The item form's Category | `Edit` | `Category` | `Category` |
| The contact editor's Prefix | `Edit` | `Prefix:` | `Prefix:` |
| The contact editor's Suffix | `Edit` | `Suffix:` | `Suffix:` |

All three are named on both channels. Two companions in the same target say why. A combo box with
no label beside it, named on its own handle alone, is heard with that name where typing lands:
unlike a spin control's buddy, the `Edit` inside a combo box answers with the box's name. And one
named by nothing reads nothing, so the reading can see a nameless typing field. The Prefix and
Suffix fields are named by their labels as Windows reads a label, the colon kept, which is how the
labels read on screen.
