# Phase 13.4 Plan 02: A contact or event that would not save is its id in the log

When the Contact Manager cannot save a contact, the log now names her by the id this program
gave her, and the message on screen still names her by her name. On Pratik's answer of
2026-10-24 the same holds for an event the calendar window could not add, change or delete,
named by its title on screen and its id in the log, and the vCard import logs a card it skipped
by its place in the file, "card 2 in the file", rather than its address. Labels, Quick Steps,
signatures and rules say and log exactly what they did before. Ledger 937, on Pratik's yes of
2026-10-23.

From one run of the contact case, after the green:

- the captured ERROR event: `contacts could not be saved: ["contact-z: Error: Failed to save contact: refused for a test"]`
- the channel's one update, `UIUpdate::ErrorOccurred`: `Some contacts could not be saved: Zebediah Quackenbush: Error: Failed to save contact: refused for a test.`

## What was done

- `NotSaved { said, logged }` above `report`, with `the_same` for a sentence naming nothing
  private, `From<String>` delegating to it, and `named_on_screen_and_numbered_in_the_log(id,
  name, why)`, the one constructor for a row somebody else named. Its doc and the save
  function's say why the two sentences differ.
- `report` takes `Vec<F: Into<NotSaved>>`, logs the log sentences with the same
  `tracing::error!` line and says the screen sentences with the same `ErrorOccurred` text.
- `save_what_the_contact_manager_returned` returns `Vec<NotSaved>`: a deletion by her id in both,
  the two save failures through the constructor with her id and her name.
- `NotChanged::Failed` carries a `NotSaved`; `change_an_opened_event` builds it through the
  constructor with the opened event's id. The due window's Details button shows `failed.said`.
- The calendar window's create and delete arms moved into `add_an_event` and
  `remove_an_opened_event`, shaped like `change_an_opened_event`, so each can be run against a
  store that refuses the write. The arms in `manage_calendar` now match the update arm.
- `import_contacts_from_vcard` numbers the cards it reads and logs a refused one as `vCard import
  skipped card N in the file: <error>`.
- Five cases: the contact's end to end through the report under `CapturedLogs`, three for the
  events (add, change, delete) against `take_away_the_table("calendar_events")`, and the vCard
  import's under `CapturedLogs`, asserting no event of any level holds the address.
- Changelog entry under `[Unreleased]`, `### Fixed`, and 13.3-18's sentence "as every other line
  about contacts already did" corrected by a dated paragraph after it; ledger 937 fixed; REAL-01's
  dated line and traceability row; Pratik's answer of 2026-10-24 recorded once in the phase
  README; the four marks.

## Deviations from Plan

1. **[Pratik's answer of 2026-10-24] The two log gaps of premise 7 were fixed here, not
   ledgered.** The brief's answers file said "Fold the other items in." So the calendar window's
   three writes and the vCard import got their cases in the plan's one red commit, named in its
   trailers, two more guard records and one changelog entry with the contact's. The two `todo`
   rows Task 2 would have opened were not opened, and the README records the answer once.
2. **[Design] `report` became generic over `Into<NotSaved>`, with `From<String>`,** rather than
   a string `report` beside a second report for the new value. The five other managers'
   calls are byte for byte as they were, and the reading of `manage_calendar` that looks for
   `report(tx, rt, "calendar events", failures);` keeps its words, which a renamed call would
   have left blind.
3. **[Rule 3, for the fold-in] The calendar window's create and delete moved into functions of
   their own in the red,** with today's words, because both ran inline in `manage_calendar`,
   which needs a window. The delete's refusal is still sent through `send_refusal` and the loop
   goes on to the next action, as the `continue` did.
4. **[Rule 1] Two records came out short at the re-measure** and were corrected, above.
5. **[Order] The re-measure ran with the green on disk before the green commit,** as 13.4-01
   did, so a case red in the red tree would not hand every record to the whole run as short.
6. **[Evidence] The quoted log line and update came from a run with a temporary `eprintln!` in
   the case,** removed before the green's records were measured.
7. **[Tooling] One read-only command was typed with `sed` and `awk` as do-nothing stages, and
   the project's hook refused it before it ran.** Every tracked file was changed by Edit, by
   `cargo fmt` or by `scripts/guards.sh`.

No package added; no schema, setting, key, control, label or mnemonic letter. The version does
not move. Only the log changes, so the branch is not pushed. `docs/privacy.md` is not changed:
premise 9's reason, the two open gaps, is gone, but no audit of every log line about a contact
or an event has been made, so it still makes no promise about them.
