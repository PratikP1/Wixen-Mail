Find out why the Settings tab row is spoken twice on an arrow key, stop the
second reading at its source, and hold each tab to once with a real screen
reader on CI.

small cost per key and a constant one, and the settings screen is the one
place every setting must be reachable, so it is met often. The cause is not
known and nothing in the tree records events, so the instrument comes first.

Output: an event logger in `scripts/`, the capture, the fix the capture
names, a reading that holds it, and an NVDA case waiting for the next push.

remain.

**2. The instrument the issue names is not on this machine, and two others
are.** Accessibility Insights for Windows: `ls "$LOCALAPPDATA/Programs"` shows
Common, Inno Setup 6, Microsoft VS Code, Ollama, Quill Radio, and nothing
under Program Files either, so its event viewer cannot be used here.
`scripts/msaa-names.ps1` walks a tree once and subscribes to nothing. What
can be run here: a PowerShell UI Automation client
(`Add-Type -AssemblyName UIAutomationClient, UIAutomationTypes`), which can
`AddAutomationFocusChangedEventHandler`, `AddAutomationEventHandler` for
`SelectionItemPattern.ElementSelectedEvent` and `AddAutomationPropertyChangedEventHandler`
for `NameProperty`, find the tab control by `ControlType.Tab`, call
`SetFocus()` on it and send `{RIGHT}` through `System.Windows.Forms.SendKeys`.
That logs what the application raises; it does not log what NVDA does with
it. NVDA's own log at debug level records the events NVDA acted on and is the
second channel, on the tester's machine, which the summary asks for if the
first channel shows one event and the tester still hears two. And
`nvda-tests/` drives a real NVDA on CI and records what it said, which is the
proof, on the next push.

**3. Where a second reading could come from, so the capture knows what to
look for.** Two candidates, both from the control and neither from this code:
the tab control raising a selection change and then the page panel (which
Windows names after its tab) receiving focus or a focus event after the
selection settles, so NVDA reads the tab and then the page with the same
name; or the tab control raising a name-changed event on the tab item after
the selection. "Frequently rather than always" points at two events in either
order. The capture settles it; the fix is written after, not before.

**4. The gate.** `scripts/*.ps1` map to no target; the logger is a developer
tool, run by hand, with its own header saying what it is for and how it was
used. `wx_settings.rs` has no unit tests, so the reading goes in a new target
with a record coupling it. `nvda-tests/` is JavaScript reached by
`.github/workflows/nvda.yml` on push; a change under `.github/workflows/`
answers `all` on a branch.
