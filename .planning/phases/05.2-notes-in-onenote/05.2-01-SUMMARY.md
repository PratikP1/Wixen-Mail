## The measurement, and the paragraph the plan asked for twice

**The middle step is a model of the service and not the service.** Nobody here
has a OneNote tenant. Every transformation in the model names the section of
`learn.microsoft.com/en-us/graph/onenote-input-output-html` it was read from,
fetched on 2026-09-11 and dated 2024-11-07 on that page. What the fidelity table
measures is what this program does with what the reference says the service
returns. It does not measure what the service returns, and a table produced
against a simulation is worth having and is not evidence about Microsoft. The
same sentence is in the document, above the table, where somebody reading the
table meets it.

Seven of the twenty-two constructs survive. Of the fifteen that do not:

| Lost where | How many | Which |
|---|---|---|
| OneNote | 7 | a quote, bold, italic, struck-out text, inline code, a code block, a horizontal rule |
| This program's own reader | 6 | a nested list, a list three deep, a link's address, a picture with a description, a picture without one, a line break |
| Both | 1 | a table |
| HTML itself | 1 | a note whose whole content is one space |

The seven are facts about somebody else's service. Either the element is in no
list the reference names, so it is cut before the page is sent, or the service
re-expresses it as inline CSS on a `span` that carries no meaning any reader
here can read. The six are decisions `from_markup` made for reading a message,
where a link read aloud as an address helps nobody, and a note is a different
job. Changing those six is a plan rather than a line, because that module is
shared with every message body and signature this program renders.

**The sharpest single loss is the code block**, and it was nameable before any
code ran: neither `pre` nor `code` is in any list the reference names, so a code
block has no representation on a OneNote page at all. `fusebox --check` on one
line and `fusebox --repair` on the next come back as one line that runs neither.

**The most costly for meaning is struck-out text.** It comes back as ordinary
words, so a job crossed off and a job still to do read alike afterwards.

**The hidden source div was tried, measured and reported.** A `data-id` survives
and a div carrying one is preserved, so a hidden div holding the Markdown source
looks like a way to make the round trip exact. Put through the same model,
`# Colours\n\n- Live is brown\n- Neutral is blue` comes back as
`# Colours - Live is brown - Neutral is blue`: the div survives, and the source
inside it is still text in an HTML document, so its blank lines and the line
starts that made it Markdown are gone. It would not be free even where it
worked, because it puts a second copy of every note inside that note, doubling
its size and giving the two copies something to disagree about, which is the
drift `as_markup`'s own comment says the matched pair exists to prevent.

## The two conversions call the existing pair rather than reimplementing it


```rust

```

No new dependency. `pulldown-cmark`, `scraper`, `ammonia` and `html-escape` were
all already in `Cargo.toml` and `Cargo.toml` is unchanged.

## Decisions Made

**The `div` flattening went inside `onenote_page.rs`, which is the plan's second
answer.** `from_markup`'s block pass has one arm for `p` and `div` together, so
a `div` is read as a single paragraph and every heading, list and blank line
inside it is concatenated. OneNote wraps all body content in at least one `div`.
Handing a page's body over unflattened returns the whole page as one run of
text, and the fidelity table measured through that path would have reported
every construct as lost and attributed it to Microsoft. The plan ruled that
outcome out and it was right to. The flattening is `ammonia` with `div` removed
from the allowlist, which is one line and reuses the behaviour that crate
already has, rather than a second walk of the tree.

**The first answer, changing the `p | div` arm to recurse when a `div` holds
block children, is owed and is not done here.** It is the better fix and it
opens a file that 18 guard records name, one of which has that exact arm in its
`before` block, so it costs a hand re-measurement of that record and puts the
count check in front of every commit that adds a test there. It is a task rather
than a line, and this plan did not need it.

**A table's header cells are written as `td` rather than cut.** The reference
names `table`, `tr` and `td` and does not name `th`. Cut, the two header words
became one text node inside a `tr`, which every HTML parser moves out of the
table and runs together, so `Left` and `Right` arrived as `LeftRight` above the
table. Written as `td` they stay in their own cells and nothing leaves here that
the reference does not name. This was not in the plan; it was found by running
the check and it is a loss made smaller rather than a loss discovered.

The rename is a replacement on text, which would not be safe on arbitrary input.
What reaches it has already been through `ammonia::clean` inside `as_markup`, so
every text node is escaped and the bytes `<th>` or `<th ` can only be a tag.
`test_a_header_cell_somebody_typed_as_text_is_not_rewritten` is the case that
would break if that ever stopped being true.

**`as_markup`'s soft break to hard break conversion is kept for a note**, and
the plan asked for this to be decided either way. `as_markup`'s own comment says
a box somebody typed three lines into is not a document, which was written about
a signature. A note is more like a document, so the question is real. Kept,
because the break does reach the page as a `br`, OneNote keeps `br`, and
somebody looking at their note in OneNote sees the lines they typed. It is
`from_markup`'s inline pass that turns a `br` back into a space, and that is one
of the six losses this program owns. Changing it would reshape every message
body and signature this program renders, so it is not a decision this file gets
to take.

**No `lang` attribute on the page**, though Microsoft's own example carries one.
Nothing in this program knows what language a note is written in, and a wrong
`lang` is read aloud in the wrong voice, which is worse for the person this is
for than no declaration at all.

**`src/service/onenote_page.rs` does not join
`FILES_THAT_READ_OR_WRITE_A_DOCUMENT`, and the reason is not that HTML is
different.** That array's guard looks for 22 specific iCalendar and vCard
property names written in capitals, so putting an HTML reader on it would add a
name to a list whose check cannot see anything about HTML. It would pass
trivially and would dilute what a name on that list means, which is the inverse
of the failure the array's own comment warns about. The rule the array is really
about, that a document's names mean the same however they are written, does
apply here, so this file carries its own test for it:
`test_a_page_written_in_capitals_reads_the_same_as_one_in_small_letters`. The
answer is consistent with `05.1-05`'s, which left `carddav.rs` off for a
different reason: a new file's shipped half is too small a fraction of it in the
red commit that creates it.

**No `docs/changelog.md` entry and no version bump.** Nothing a person can do
has changed. Nothing in the running program calls either function, and the
document that changed is a developer contract rather than a page a user meets.
`Cargo.toml` is in the plan's file list and is untouched for the same reason.
This was considered rather than forgotten, which is what task 1's action asked
for.

## Deviations from Plan

### 1. The guard break the plan named for task 2 reddens nothing

- **Found during:** Task 2, writing the second guard record.
- **Issue:** The plan asked for a record "whose break is the round-trip
  comparison being made on parsed structures rather than on bytes, which is the
  change somebody makes to turn a red table green." Measured rather than
  assumed: with the fidelity table's comparison changed from bytes to
  `long_text::structure`, the whole library passes. 6,930 passed, none failed.
  It cannot redden anything while the table records what really happens, because
  a looser comparison passes a true row as readily as a strict one. The break
  the plan imagined protects against a *softened table*, and a single edit
  cannot both soften the table and loosen the comparison.
- **Fix:** A different break, measured: `without_the_wrapping_divs` replaced by
  the ordinary `ammonia::clean` that a reader would write who took the
  sanitising for the point of the function and the tag removal for tidying. 11
  tests redden out of 6,930, in 62.08 seconds at the default eight threads. It
  guards the finding that makes this measurement about OneNote rather than about
  this program's reader, which is the more valuable thing anyway.
- **Both the finding and the substitute are written into the record**, because a
  candidate break that reddens nothing is a finding about the break.

### 2. The plan's element list omitted three elements the reference names

- **Found during:** Task 1, GREEN.
- **Issue:** The plan's premise 3 gives OneNote's supported inline character
  styles as "`b`, `i`, `u`, `em`, `strong`, `strike`, `sup`, `sub`, `del` and
  `cite`" but the red commit's constant, written from that premise, dropped
  `sup`, `sub` and `del`. `del` is what `pulldown-cmark` emits for
  strikethrough, so the filter would have cut a style OneNote supports, and the
  test's own list of what the reference names would have called it a violation.
- **Fix:** All three added, to the production list and to the test's list, from
  the reference fetched on 2026-09-11. This is a red fixture corrected once the
  code existed, which is the re-read this project asks for.

### 3. `05.1-03`'s summary reports a grep output that nobody ran

- **Found during:** Task 1, running this plan's own acceptance criterion.
- **Issue:** The criterion is that
  `grep -n "reqwest\|Outward\|AskWith" src/service/onenote_page.rs` returns
  nothing. It returns one line: line 8 of the file, the module header quoting
  the command as the thing that proves it. `note_document.rs` does exactly the
  same, and `05.1-03-SUMMARY.md` records that grep with the answer "Nothing"
  under it. The answer is wrong against the tree, today and on the day it was
  written.
- **Fix:** Reported rather than repeated. Nothing in either file changed: the
  header is worth having and the command is the right one. What is wrong is
  reporting a command's output without running it. This summary states the real
  output below.

### 4. Task 2's tests and their harness were written together, and the red was recovered by hand

- **Found during:** Task 2, before the RED commit.
- **Issue:** For a task whose deliverable is a measurement, an expected value
  cannot be written before the measurement exists, so the harness and the
  assertions get written in one go. That is writing the test after the code, and
  it happened here despite task 1 having done the red properly an hour earlier.
- **Fix:** The model was stubbed by hand, the 22 assertions were left saying
  what PIM-04 promises, and the red was taken and committed at `92fb2cb` with
  all 22 failing. The green then replaced each assertion with what really came
  back, each with a comment saying what was expected. Nothing was reverted with
  version control.

**Total deviations:** 4. One is a plan premise measured false, one is a plan
premise incomplete, one is a finding about a previous summary, one is a process
recovery. None changed the shape of what was built.

## Issues Encountered

**The conformance check reported an element nothing produced.** The test reads
element names by re-parsing the produced page, and `html5ever` inserts a `tbody`
around any table's rows because HTML requires one. Read as a producer defect,
both obvious fixes are wrong: adding `tbody` to the reference list would hide a
real one later, and changing the producer would chase something that is not
there. The parser's own insertions are now a separate commented constant, and
the test that skips them asserts the produced bytes carry none, so the skip
cannot become a hole.

**Nine of task 1's 22 tests passed against do-nothing bodies on the first run.**
Seven were absence assertions, one compared two derived values that were both
empty, and one asserted that an empty note round-trips, which nothing at all
also satisfies. Each was paired with a positive assertion in the same fixture
before the red was committed.
