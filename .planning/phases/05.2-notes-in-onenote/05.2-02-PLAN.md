**4. The four page operations, from Microsoft's reference on 2026-09-06.**

- List: `GET {base}/me/onenote/{notebooks | sectionGroups | sections | pages}`.
  (`learn.microsoft.com/en-us/graph/api/resources/onenote-api-overview`)
- Create a page: `POST {base}/me/onenote/sections/{id}/pages` with the input
  HTML. A page with binary content is a multipart request with a "Presentation"
  part; a page that is only text is not.
- Read content with identifiers:
  `GET {base}/me/onenote/pages/{id}/content?includeIDs=true`.
- Change: `PATCH {base}/me/onenote/pages/{id}/content`, `Content-Type:
  application/json`, body a JSON array of patch commands each with `target`,
  `action`, optional `position` and `content`. Success is `204 No Content` with
  no body. (`learn.microsoft.com/en-us/graph/api/page-update` and
  `learn.microsoft.com/en-us/graph/onenote-update-page`)
- Delete: `DELETE {base}/me/onenote/pages/{id}`.
  (`learn.microsoft.com/en-us/graph/api/resources/onenotepage`)

**5. The three constraints the client has to obey, and each is a real
behaviour rather than a note in a comment.**

- **A read precedes every write.** The reference says generated identifiers
  "might change after a page update, so you should get the current values before
  building a PATCH request". So the identifiers from one read may not be used
  for a second write, and a client that caches them is wrong in a way no test
  against a fake will show unless the fake changes them. **Make the loopback
  server change them**, the way `05.1-04`'s second implementation changed its
  identifier on every write.
- **The body cannot be replaced.** `body` supports `append` only. So making a
  page's content equal a new document means removing what is there and appending
  what is new, element by element, by generated identifier. Whether that is what
  this client does, or whether it deletes the page and makes another, is this
  plan's largest design decision and task 3 is where it is made and argued.
- **The title is replaced with `target: "title"`**, which is one of the two
  exceptions to the generated-identifier rule.

**6. The permission is new and an existing account does not have it.**
`Notes.ReadWrite` is the least privileged delegated permission for updating a
page, and the OneNote API does not support app-only authentication.
(`learn.microsoft.com/en-us/graph/api/page-update`) Read `src/service/oauth.rs`
for the scopes a Microsoft account asks for today; notes are not among them.
**An account signed in before this change holds a token without the scope**, and
what happens then is a refusal that has to read as "this account needs signing
in again for notes" rather than as a broken account. `tasks_sync::refused_for_permission`
and `tasks_api::NEEDS_SIGN_IN` are the existing worked example of that and
`push_tasks` sets `needs_sign_in` from it.

**7. Four levels, and a section group is optional and can nest.** notebook,
section group, section, page. `sectionGroups` can contain other section groups.
A model that assumes three levels works for most notebooks and breaks on
somebody's. Decide how deep to follow and bound it, the way
`occurrences.rs` bounds its expansion with `MOST_STEPS` and
`MOST_DAYS_ONE_SERIES_SHOWS`, and say the bound in a comment with its reason.

**8. Guard-record cost.** Re-measure with the awk in `CLAUDE.md`. At `9611b70`

  <action>
    RED first, on a branch.

    **The design decision of this plan is here.** A page's body supports append
    and not replace, so making a page's content equal a new document is one of
    two things and they are different products:

    - **Remove and append.** Read the page with `includeIDs=true`, build one
      patch command per existing element to remove it, and append the new
      content. The page keeps its identifier, its position, its created date and
      any link anybody has to it. It sends more commands and it depends on
      removal by generated identifier working for every element type, which the
      supported-actions table says it does not: `p`, `li`, `h1` to `h6`, `ol`,
      `ul` and `table` support replace by generated identifier, and `body` and
      absolute-positioned elements do not.
    - **Delete and recreate.** One delete and one create. Simple, and it changes
      the page's identifier, loses its position in the section, resets its
      created date, and breaks any `oneNoteClientURL` somebody saved. It is also
      a deletion, and `application::deletions`'s whole module header is about
      what a deletion means when a read may still name the thing.

    **Argue for one in a paragraph and write the reasoning where the code is.**
    Whichever is chosen, the other is named in the comment with what it would
    cost, because the next reader will wonder.

    **Make the loopback server change its generated identifiers between reads.**
    That is not a nicety: the reference says they move, and a client that holds
    them across a write is wrong in a way a fake with stable identifiers will
    never show. This is the same trick `05.1-04`'s second implementation used and
    it is the reason that plan was worth doing.

    **Assert that no command targets `body` with `replace`.** Write it as a test
    over the produced command list with the supported-actions table as a named
    constant, the same shape task 1 of `05.2-01` used for the element set.

    Add a `guards/guards.toml` record whose break is the client reusing
    identifiers from an earlier read. Measure with `--no-fail-fast`, quote the
    red list, correct the census.
