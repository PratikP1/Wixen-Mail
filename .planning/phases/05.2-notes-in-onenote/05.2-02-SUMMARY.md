## A 401 reuses the classification tasks already had, and not its sentence

`onenote_refusal` turns unauthorised and forbidden into
`Error::Authentication(NEEDS_SIGN_IN_FOR_NOTES)`, which is the shape
`tasks_api::refused_change` already used for `NEEDS_SIGN_IN`.

**The sentence is its own constant and that is deliberate.** Both sentences ask
for the same action, and they cannot be one sentence: somebody whose notes were
refused, told to "sign in to this account again to send task changes", does the
right thing for a reason that names the wrong feature, and comes back having
found their tasks were never the problem. That is observation 63's shape, a
refusal sentence inherited by a second caller, and it is the only part a person
ever sees.

**The classification is shared rather than copied.**
`tasks_api::asks_for_a_new_sign_in` holds both sentences, and
`tasks_sync::refused_for_permission` is now one line delegating to it. There is
one predicate in the tree rather than one per feature. It answers true for the
notes sentence as well, which changes nothing for tasks: a notes refusal is built
by a OneNote call and no OneNote call sits on any path that function is on. It
lives in `tasks_api.rs` because that is where the first sentence and the
classification already were, and because that file already named
`microsoft_graph` for a shared time type, so this added no dependency.

## The design decision of this plan: remove and append

**Chosen: remove what is on the page one thing at a time by the identifier Graph
gave it, then append the new content, and replace the title by name.** The
reasoning is in the doc comment on `changing_a_page_to` where the next reader
will ask, with what the other answer would have cost.

A page's body supports appending and nothing else, so there is no command that
makes its content equal a new document, and the two ways round that are different
products.

**What decided it is the failure, not the request count.** A remove-and-append
that stops half way leaves a page holding some of its content: the person can see
it and put it right by editing again. A delete-and-recreate that stops between
its two requests leaves no page at all, and the note is gone from their notebook
with nothing to show it was ever there. `docs/development/the-notes-seam.md` took
exactly this decision on 2026-09-11 for moving a note between folders, create
first and remove second, "so that a failure leaves the note in both folders,
which somebody can see and tidy up" rather than in neither, "which they could not
see at all". This is the same question one level down. Copying the answer is the
point: two orderings of the same two steps, decided twice, disagree the day
either changes.

**The second reason is the seam above.** It stores the name a backend gave a
note. Delete-and-recreate changes that name on every edit, so every edit would
arrive at the seam as a note that vanished and a different one that appeared, and
`application::deletions`' module header is about what a deletion means when a
read may still name the thing. Owing that machinery a reconciliation for what is
really an edit is a cost with nothing bought. Remove-and-append also keeps the
page's place in its section, the date it was made, and any `oneNoteClientURL`
somebody saved.

**What it costs, said rather than left out.** One command per thing on the page
instead of two requests. And it rests on removal by generated identifier working
for everything a page can hold, which nothing in this repository has read the
reference on and nobody has run. That is ledger entry 286.

**`05.2-03` owes the deletion machinery nothing from this choice**, which is the
other half of the plan's question. Had delete-and-recreate been chosen, every
edit would have owed a tombstone and a reconciliation; it was not, so an edit is
an edit and only a real removal is a removal.

## The identifiers move, and the fake moves them

`change_page` reads the page inside itself. There is no signature by which a
caller can hand it identifiers, and nothing caches. The test that would catch a
client doing otherwise is
`test_a_second_change_names_what_the_second_read_said_and_not_the_first`: the
loopback server answers the first read with identifiers spelling `before` and the
second with identifiers spelling `after`, and the test asserts the second PATCH
body carries `div:{after}{1}` and does not carry `div:{before}{1}`. A fake with
stable identifiers could not fail against a client that cached, which is why the
plan asked for this and why it was worth asking for.

`test_a_change_replaces_the_title_by_name_and_never_the_body` reads every command
the builder produced against `WHAT_A_NAMED_TARGET_SUPPORTS`, which holds the
reference's rows for `title` and `body` separately from the code that builds
commands. **Two rows rather than the whole table, because two rows are what this
repository's reading can defend**, and the constant says whose reading and on
what date: the plan's, 2026-09-06, not re-fetched today. The rule that no command
replaces the body is an absence assertion on its own, which an empty command list
satisfies, so it is paired in the same test with an assertion that the list
contains the title replace and an append to the body.

## The bound, and the reason beside the number

`MOST_SECTION_GROUPS_DEEP` is 8. A section group can hold section groups with
nothing in the reference saying how far, and a server answering its own group as
its own child never stops. The comment says the number is a bound on a hostile or
broken answer rather than a limit anybody meets, following `occurrences.rs`.

A group past the bound is **found, named by its parent's listing, and not walked
into**, and the read comes back `complete: false`. The check is made when a child
would be pushed rather than when a container is taken, so a notebook that happens
to be exactly eight deep with nothing below is not reported as cut short.

`PagedRead` is reused rather than a new type minted: its second field already
means "this program ran out of room rather than the provider running out of
items", which is exactly what a bound reached means.

**A second bound was added that the plan did not ask for**, and it is the same
threat through a different door: `MOST_PAGES_OF_ONE_LISTING` is 100, and a
next-page chain longer than that is **refused** rather than truncated, because a
server answering in a circle handed back as part of a notebook lets a sync read
the part it got as the whole of it. Rule 2, a correctness requirement rather than
a feature.
