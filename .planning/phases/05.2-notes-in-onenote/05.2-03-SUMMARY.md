# Phase 05.2 Plan 03: OneNote behind the notes seam Summary

**A note on a Microsoft account now becomes a page in a section of one of their notebooks, through the same sync a calendar server's notes go through, and the real client found four more places the seam was still written about CalDAV. The fake it replaced predicted none of them. Nothing here has met Microsoft.**

## Does it work

Yes, in the sense this project allows that word, and the sentence that matters is the next one.

A note made in a OneNote folder is sent as a page, the note comes back knowing the identifier Graph gave and the time the page was last written, a page changed in OneNote arrives here at the next sync, and a note deleted here is removed at the other end and does not come back. The settings screen says where each account's notes go and names OneNote. The note folder menu offers Sync now for a Microsoft account and not for a Gmail one.

**What does not work, said plainly: none of it has met Microsoft.** Every request is answered by a server the tests start on a loopback port. That proves what this program sends, in what order, and how it reads a reply it was given, which is a great deal better than a fake agreeing with an interface. It proves nothing about what Microsoft sends back. Eleven ledger entries name the unknowns one at a time, on top of the nine `05.2-02` left open.

## The report this plan owes: where the seam had assumed CalDAV

**The three numbers.** Four assumptions `05.1-04`'s fake found. Four the real client found. **Nought** of the second four predicted by the first.

A low third number is the finding rather than the failure. A backend shaped from three documentation pages, by whoever had just read the contract, did not predict a client built against a socket. That is worth knowing before anybody writes a fourth backend against a fourth fake.

### 1. A clash reported by a marker is not a clash

**What the seam said.** A backend reports `ItMovedFirst` when its copy has moved since this computer last looked, and `conflict_choice` then holds both copies and asks. Requirement 4 already allowed a marker to move for reasons the content did not cause, and called that the harmless direction.

**What is wrong with it.** Harmless on the read, not on the push. A backend has only a marker to compare, so it reports a clash; a clash is two copies that disagree; those are different things. Where the words are the same on both sides, somebody is handed a question with one answer given twice: a title and a body read aloud, identical, and two buttons that do the same thing.

**Why an entity tag hid it.** An ETag does not move on its own, so for the backend this sync was written against the two sentences really are one sentence. A clock the service owns moves whenever anything touches a page.

**Reachable with what ships today.** Both backends failed the test. Somebody fixing the same typo in two places meets it on a calendar server.

**What was changed.** `notes_sync::hold_these_two_copies` writes the marker down, stops the note waiting and counts it as unchanged where the words agree. Not as sent: nothing was sent.

### 2. Saying what a backend kept costs a request, and the contract priced it at nothing

**What the seam said.** A backend answers what it could keep from its own copy rather than from a rule about itself. Still right, and not what changed.

**What is wrong with it.** For a backend that builds the document it sends, its own copy is in hand and the answer is free. For a hosted backend it is another request. The contract asks for the honest answer and never says it might cost anything, so anybody pricing a sync from that document gets the wrong number. Making a note here is two requests and changing one is five.

**The fake could not have predicted this.** Its own copy is a field on a struct. No shape of fake makes it visible.

### 3. A marker missing on one call is not a backend with no markers

**What the seam said.** Requirement 3, that a marker is required of any backend this program writes to, written as a property of a backend.

**What is wrong with it.** A real service answers one request at a time, and the question a client faces is what to do when *this* answer carries no marker. The contract gives no answer and the two available are not equal: writing anyway is what `05.1-04` measured as destroying a change made at the other end with nothing said.

**What was changed.** A missing marker refuses the write and the note stays waiting. A refusal costs somebody a sync; the other answer costs them their note.

**The fake's `never_gives_a_marker` is a whole-backend switch set at construction.** It measured the right cost and modelled the wrong shape.

### 4. A container can be the service's answer rather than a row on this computer

**What the seam said.** A container is opaque, a backend with levels above a note flattens them, one container is one note folder, the sync loops over folders. All of that held.

**What is wrong with it.** It says nothing about where the list of containers comes from. `note_folders_for_the_backends_of` is not async because a calendar server's containers are rows this computer already holds. A notebook's sections are Microsoft's answer.

**What was changed.** A Microsoft account's note folders are made during the sync. Somebody sees an empty Notes list until they sync once. Entry 301, recorded rather than defended.

## Where `05.1-04` was right, and where it was wrong

**A report saying the fake was accurate throughout would be a suspicious result. It was not accurate throughout.**

### Right, and the real client confirms it

| The fake's constraint | What the real client does |
|---|---|
| No `eTag` and no `If-Match`; what there is is `lastModifiedDateTime` | The same. `MsOneNotePage` carries no entity tag and the marker is that timestamp, compared for equality |
| No whole-document write; a body can only be appended to | The same. `changing_a_page_to` removes elements one at a time and appends, and no command replaces the body |
| A container more than one level deep | The same. A page lives under a notebook, any number of section groups, and a section |

Its four "could not shake" items also still hold: the container is handed back untouched, a backend is asked for an end state and not an edit, no backend decides a clash, and a write may change what a note is called.

**What that confirmation can carry.** The first two rows are confirmed by the *design* of the client `05.2-02` built, which was itself read off the same documentation. They are not independent measurements of Microsoft. The third is confirmed by the walk, which is also a reading. So "confirmed" here means "two readings of the same pages agree", and it is worth saying because it is weaker than it sounds.

### Wrong, in three ways, and each mattered

**Its identifiers move and the real client's do not.** Constraint 3 says a page gets a new name every time its body changes, because reaching an end state means deleting the page and making another. `05.2-02` chose remove-and-append for reasons about what a half-finished write leaves behind, and that keeps the page and its identifier. So the fake exercised `Done`'s `known_as` on every edit and the real backend exercises it only on a create. The contract's paragraph giving "a OneNote page's body cannot be replaced" as the reason a write may change a note's name is now an argument about a design nobody took. The requirement is still right; its stated reason is not this backend's.

**Its container is three parts and the real one is one.** The fake refuses a container that is not a notebook, a section group and a section. That reads like a fact about OneNote and is an encoding it invented. The real container is the section's own identifier and the four levels are flattened into the folder's *name*. `test_a_container_that_is_not_the_shape_this_backend_needs_is_said_rather_than_guessed_at` is a test about the fake.

**Its model of what a page loses is the wrong loss.** `as_a_page_keeps_it` collapses runs of whitespace, so the fake reports a nested list losing its indentation. `05.2-01` measured the real mapping: nested lists survive, and what is lost is whole constructs, bold, italic, struck-out text, a quotation, inline code, a code block and a horizontal rule. A reader of the fake would have expected the wrong thing to go missing and would not have expected a job crossed off to read like a job still to do.

**And it answers instantly and for free**, which is finding 2.

### What this report's evidence can and cannot carry

`05.2-02` built the client against a loopback server the tests start, and this plan built the backend the same way. **That proves what this program sends and how it reads a reply it was given.** It cannot prove what Microsoft sends back: every fixture answers what Microsoft's reference describes, so a place where the reference is wrong, or where the service differs from its own page, is a place every test here agrees with the mistake.

Of the four findings above, findings 2 and 4 are about this program's own shape and hold whatever Microsoft does. Finding 1 was measured against both backends and holds whatever Microsoft does. Finding 3's cost was measured by `05.1-04` rather than by this plan, and its shape is a fact about HTTP rather than about Graph. **None of the four rests on the documentation being right**, which is the strongest thing that can be said for them and is worth saying because the fidelity table's every row does.

## How OneNote's four levels are stored

**The opaque identifier, which is the answer that keeps the seam a seam.** The container is the section's `id`, handed back untouched, never parsed, never built. The four levels reach the person through the folder's *name*, which `ANotebookOnAMicrosoftAccount::the_folder_name_of` joins with ` / `: a section called Q3 inside a group called Projects inside a notebook called Work becomes `Work / Projects / Q3`.

Identity and name are different jobs and that is why they are different fields. A section renamed at Microsoft keeps its notes, because the lookup is by container and never by name. The name is what somebody reads and it can change freely.

**The separator was chosen here and nobody has heard it.** The seam's document recorded on 2026-09-11 that it was nobody's choice yet and that what a screen reader makes of it at its default punctuation level is unmeasured. It still is. Entry 296.

## The conflict, and the marker that is a clock

**The marker is `lastModifiedDateTime`, compared for equality and nothing else**, which is what requirement 4 already allowed. The argument is in `docs/development/the-notes-seam.md` under "What a backend with no entity tag compares".

The plan offered a content digest as the other candidate. **It falls away for a reason worth writing down rather than on a balance of costs.** A digest of the content this program last saw is kept here, so it answers whether *our* copy has changed, which the waiting flag already answers. It cannot answer whether *theirs* has, because that means holding their copy, and holding their copy means fetching it. Fetching every page on every sync is exactly what `notes_it_holds` and `what_a_note_says` exist to avoid being two names for. The digest is not a weaker marker. It is an answer to a different question.

**A page whose timestamp moved without its content changing.** The read reports it unchanged, writes the new marker down and touches nothing else, which `05.1-04` already built. The push was the gap: it raised a clash nobody caused, and that is finding 1 above. It is fixed for both backends, and what remains is a clash where the words really do differ, which is a real question.

**No backend decides a clash.** `conflict_choice` is untouched by this plan and gained no variant. `TheOtherCopy::ANotesBackend` says "your notes backend" and a fourth variant naming OneNote would cost four places, the words, what the thing is called, and both halves of writing the answer down in `held_conflicts`, and would put a backend's name in `notes_sync`, since something there would have to choose between two variants by asking which backend it was talking to. **Whether "your notes backend" is the right thing to hear is a question for the checkpoint**, not one to settle from the types.

## Deviations from the plan

### 1. [Rule 3, blocking] The third implementation cannot be driven from the `tests/` harness

- **Found during:** Task 1, before the first line was written.
- **Issue:** The plan's task 1 says to extend the harness so the same test bodies run against three implementations. A real client needs a loopback server and a client that may change things. `crate::common::answering` is `#[cfg(test)]` and so is `MsGraphClient::allowed_to_change_things_at`, so a file under `tests/` links a library where neither exists. That is the same fact `05.2-02` measured with a throwaway probe and wrote into its summary, and `Cargo.toml`'s comment above `[features]` has said it for some time. The only public way to build a writing Graph client is `for_account`, which reads the settings really stored on whoever's machine is running.
- **Fix:** The OneNote backend's conformance tests are in `src/service/onenote_notes.rs`, which carried no guard records and cost nothing. The harness was extended, but with two new questions asked of both existing shapes rather than with a third implementation.
- **What was not added, deliberately:** a public constructor taking an address and building a client that may change things. It would have made the plan's instruction satisfiable and it is a way past the Allow Changes gate that anything in the crate, or any consumer of the library, could call. `outward.rs`'s write census exists to stop exactly that.
