## Product purpose and guardrails
- source: docs/principles.md
- Judged by four questions, asked of every change. What is it for: making correspondence and personal information legible to people who cannot see it, treating messages, senders, folders, threads, read state, attachments, events, contacts, tasks, notes and reminders as structured data declared to the platform accessibility API through native controls, each with a name, a role and a state.
- What it strengthens: the independence of its users, the principle that the application declares its meaning rather than the screen reader inferring it from pixels or a scraped DOM, and open protocols (IMAP, SMTP, POP3, CalDAV, iCalendar), with provider APIs supported where they add something rather than as the only door in.
- What it replaces: Outlook, Thunderbird and webmail for its user. Not the screen reader (NVDA, JAWS and Narrator own review cursors, verbosity and speech), not the mail server or provider, not Wixen Terminal or Terminal Access.
- What it allows to be done poorly, each item having already happened in this codebase: accessibility calls that are not accessibility calls (sixteen widgets named with `set_name()`, which is an internal wxWidgets identifier that never reaches the accessibility tree; it compiled, passed the suite and read correctly in review); structure present mistaken for experience good (automated scanning covers roughly half of WCAG); implemented but never wired (all eight PIM update variants handled in the UI and sent by nothing; five modules with storage, sync client, manager and panel rendering empty in every build); stubs that look finished (the note editor filling itself with "Note 1" and "(Note content loaded here)"); breadth over excellence (six modules shipped at once with one working); announcement flooding; privacy through speech; hostile HTML; green checks that check nothing (CI failing for months, an accessibility scan reporting success while its scan step errored); automation that decides for you (a push to `main` cutting two releases nobody asked for and promoting an alpha to beta); absorbing upstream failures.

## Canonical implementation status
- source: docs/IMPLEMENTATION_STATUS.md (source states "Last updated: 2026-08-09"; describes itself as "the canonical answer to 'does this work yet'")
- Wixen Mail is pre-beta. It can send and receive mail. Reading mail is the part that has been used; everything that writes to a server is experimental.
- Working per this source: send over SMTP with TLS/STARTTLS using password or OAuth, with a local outbox that flushes and retries rather than losing a failed send, and drafts saved by hand or automatically; receive over IMAP with TLS/STARTTLS including folders, messages, search, header-derived threading and paged fetching of older mail; POP3 with the same protections and its own local folders, leaving mail on the server unless told otherwise; a local unencrypted cache holding messages, contacts, contact groups, calendars, events, reminders, task lists, tasks, note folders and notes, carrying no credentials because passwords and tokens go to the Windows credential store; six modules (mail, contacts, calendar, reminders, tasks, notes) in one window switched with `Ctrl+Shift+1` through `Ctrl+Shift+6`; accessible names on every list, tree and text field through a `wxAccessible`; announcements prioritised, deduplicated, coalesced by topic and bounded to four per second with drops reported; `Ctrl+M` mute that persists.
- Provider sync: Google and Microsoft Graph clients for contacts and calendars, a calendar-server client for calendars added by address, and subscription feeds, all reachable from the menus, pushing changes back when Allow Changes permits, showing repeating events on the days they land on. None of it has been exercised against a live account.
- Not working per this source: threaded view (present in the View menu and disabled; the data model carries thread identifiers and nothing groups by them); folder management (a folder cannot be created, renamed or deleted, and a whole folder cannot be marked read or emptied); moving a task between lists; anything that writes against a real account.
- Quality gates: four checks run together by `bash scripts/check.sh` (rustfmt, clippy with `-D warnings`, the test suite, a release build), enabled per commit with `git config core.hooksPath .githooks`. A separate non-blocking workflow scans both Windows accessibility channels: Axe.Windows over UI Automation, and `scripts/msaa-names.ps1` over MSAA. The MSAA scan exists because until it did, no accessible name had ever been measured: Windows supplies its own UI Automation provider for an edit box or button that shadows the MSAA object, and `set_accessible_name` writes only to MSAA.
- Measurements recorded: 3362 tests passing (3282 unit, 80 integration) on 2026-08-09; accessibility scan last read 2026-07-26 reporting five findings, all inside WebView2's own tree; line coverage 60.4% measured 2026-07-26 with `cargo llvm-cov --lib --summary-only`, described as the last measurement rather than today's answer.
- Mutation testing results recorded: `service/mime.rs` 33 caught 0 missed; `common/error.rs` 15/0; `data/message_cache/tasks.rs` 16 caught 1 missed, the survivor being dead code (`delete_task_list`, which nothing calls). A 2026-08-01 sweep of filters, due dates, tagging and signatures: 157 mutants, 141 caught, 16 uncompilable, none missed. A 2026-08-12 sweep at commit 0bc0614 over the four modules deciding what becomes of a copy of a message: 66 mutants, 53 caught, 1 missed, 12 uncompilable; the survivor was the closing of the connection an outgoing-mail queue opens.
- Known verification gaps: automated scanning covers roughly half of WCAG; the NVDA-driven workflow is narrow and covers only the interactions its own tests touch; most of the application has not had a full manual pass with a screen reader; the provider sync clients have not been run against live Google, Microsoft or CalDAV accounts.

## Alpha testing scope and the Allow Changes permission model
- source: docs/ALPHA_TESTING.md
- Alpha means specifically that large parts have never been run against a real mail account by anybody. Reading mail is the used path (signing in, listing folders, fetching, reading, searching, threading). Everything that writes is experimental: sending, deleting, moving or copying, marking read on the server, filing a copy in Sent, changing subscriptions, and pushing task, contact or calendar changes back to Google or Microsoft.
- Two separate permissions, because getting them wrong costs different amounts. Mail (sending, deleting, moving, copying, marking read on the server, filing a copy in Sent, read receipts, subscription changes) defaults Off. Tasks, contacts and calendar (pushing changes back to the provider) defaults On. A sent message cannot be recalled and a deleted message may have been the only copy; a task in the wrong place can be moved back. The setting covers every signed-in account; there is no per-account read-only.
- Command line can only ever narrow: `wixen-mail --read-only` changes nothing at any server for that run whatever the settings say; `wixen-mail --allow tasks` allows tasks, contacts and calendar but not mail. Neither can permit anything the settings forbid, so leaving one in a shortcut is safe.
- Gmail browser sign-in carries two Google-imposed limits during testing: only people added by hand to the project's tester list can sign in, that list holds at most a hundred people, and Google expires the sign-in after seven days. Neither limit applies to an app password.
- Feedback wanted, in order: anything a screen reader gets wrong; the message list and reading a message; signing in, especially on providers other than Gmail and Outlook; anything claiming to have worked that did not; keyboard traps; whether the ticks in Folders to Keep Up to Date are announced (Windows draws those check boxes itself, so each row reports itself as a check box with its state, and only a screen reader can answer whether it works); whether the folder list matches the provider, especially Gmail labels; delete, move and copy; whether a copy of a sent message turns up in Sent, and whether Gmail files a second one; read receipts.
- Known missing or unproven: nothing that writes has run against a real account; a task cannot be moved between lists; importing a file can join two people who share a name and nothing else on their cards, and that joined contact is then sent to the real address book; Gmail conversations are worked out from headers so grouping may differ from Gmail's web interface; a folder cannot be created, renamed or deleted; a POP account has never been run against a real POP server; notes do not sync anywhere; cached mail is not encrypted; the installer is not signed.
- Data lives in `%LOCALAPPDATA%\wixen-mail`; logs contain no passwords or message text but may contain folder names and email addresses; `--erase-all-data` removes everything including saved passwords, and the uninstaller runs it.

## Getting started, and the six modules
- source: docs/getting-started.md
- Reading mail is the used path; everything that writes is experimental and has not been run against a real account. The first screen asks what Wixen Mail may change at the provider, starting on an answer that allows nothing to mail, changeable later under Tools, Settings, and covering every signed-in account.
- Add an account with `Ctrl+Shift+A` or Tools, Account Manager. The password goes to the Windows credential store, not to Wixen Mail's own files. Downloaded mail is not encrypted.
- Module keys: Mail `Ctrl+Shift+1`, Contacts `Ctrl+Shift+2`, Calendar `Ctrl+Shift+3`, Reminders `Ctrl+Shift+4`, Tasks `Ctrl+Shift+5`, Notes `Ctrl+Shift+6`. `Ctrl+N` makes a new one of whatever the current area is for.
- Mail is two lists, folders and messages; `F6` moves to the next and says which it arrived at, `Shift+F6` moves back. `Enter` opens a message in its own window with the sender's headings as headings and links as links. `Space` reads the message in place, once for the summary and again for the rest. `Ctrl+F` searches. `F1` opens the page for the current area.

## Accessibility approach, standards and honest gaps
- source: docs/accessibility.md
- Targets WCAG 2.2 Level AA applied to a Windows desktop application. Automated scanning catches roughly half of what WCAG asks for. No Section 508 conformance claim, because nobody has done the checking.
- Two Windows accessibility channels both matter: UI Automation is what Narrator reads; MSAA through `IAccessible` is what NVDA reads for native controls and is the only place this application's `set_accessible_name` calls write. Both are checked in CI on every pull request: an Axe.Windows scan of the UIA tree, and a script walking the MSAA tree naming any control with no MSAA name.
- Screen readers: NVDA is the primary target and the one a small automated CI suite drives for real, launching a real copy, pressing specific keys and checking what it said aloud; that suite is deliberately narrow and non-blocking. Narrator is spot-checked. JAWS has not been run at all, and nothing claims JAWS support until it has.
- Braille follows speech rather than needing its own path: announcements go through `UiaRaiseNotificationEvent`, which Windows both speaks and sends to a connected braille display through whichever screen reader is running.
- Low vision and colour: text checked against 4.5:1 and larger text and UI components against 3:1 in both light and dark themes; nothing meaningful conveyed by colour alone; Light, Dark and a High Contrast choice that hands colours back to Windows entirely, painting nothing of its own under Windows high contrast; `Ctrl+Plus` and `Ctrl+Minus` change reading size; a theme change takes effect as soon as Settings closes with OK.
- Physical and motor: keyboard-only operation with no drag-only interaction; accelerators follow standard Windows conventions; `docs/KEYBOARD_SHORTCUTS.md` is updated in the same commit as a shortcut change, checked both ways by a test (every key a menu binds is named in the document, and the document names no key the code has never heard of). There is no keyboard shortcut customisation yet; shortcuts are fixed.
- Cognitive: plain language; errors say what happened, why and what to do next; the same sidebar, list and preview arrangement and the same `Space`-to-read pattern in every module; a destructive action always asks first and names the specific thing, with Enter answering No rather than Yes.
- Hearing and non-speech audio: every audio cue has a visible or spoken equivalent; captions or transcripts a sender provided are surfaced, and their absence is stated plainly. Earcons and sound schemes exist under Settings, Feedback tab: a scheme picker starting with a built-in synthesised scheme, Import sound scheme for a `.zip` someone else packaged, and Delete sound scheme which stays disabled while only the built-in scheme is present. Speech, earcons, braille and the status line can each be turned on or off independently.
- Vestibular: honours the Windows reduced motion setting; nothing flashes more than three times a second.
- The preview pane renders untrusted HTML in a WebView; once focus is inside, the browser consumes `Esc`, `F6` and every menu accelerator, so the preview never takes focus. `F6` moves between the sidebar and whichever list is open and stops there. A full, readable, focusable view of a message body outside the preview is described as the proper long-term answer and is not built.
- Reporting an accessibility problem: a GitHub issue tagged `accessibility`, naming the assistive technology and version, Windows version, steps and expectation. No email address is listed, deliberately, rather than a placeholder that bounces.

## Layered architecture
- source: docs/architecture.md (corrected 2026-08-29)
- Design principles: accessibility first, modularity, performance, security, testability.
- Four layers with a stated dependency direction. Presentation: WXDragon UI components (main window, message list, composition window, folder tree, reading pane, settings dialog) plus an accessibility layer. Application: account manager, message manager, composition manager, search engine, filter engine, contact manager. Service: IMAP, SMTP and POP3 clients, security service, cache service, attachment handler. Data: MessageCache (SQLite), credential store, configuration manager.
- Accessibility layer components: screen reader bridge (interfaces with Windows UI Automation, provides labels and roles, manages live regions); keyboard handler (centralized shortcut management and focus traversal); focus manager (focus order, dialog focus trapping); announcement queue (prioritises urgent messages, prevents conflicts).
- Keyboard handler, as corrected on 2026-08-29: "Shortcuts are fixed. `register_shortcut` is called once at startup and nothing in Settings reaches it, so there is no way to rebind a key." The earlier claim of custom key binding support was false and is gone. The Configuration Manager settings categories are application preferences, account settings, UI customization, accessibility options and privacy settings; keyboard shortcuts are not among them.
- Further sections cover where files live, technology stack and key dependencies (labelled "Planned"), data models for Account, Message and Folder, the threading model (main UI thread, background workers, communication over `tokio::sync::mpsc`), error handling strategy and logging, security considerations (credential storage, network security, data protection), testing strategy (unit, integration, accessibility, performance), build and deployment, and future considerations (extensibility, cross-platform).

## Release mechanics
- source: docs/BETA_RELEASE.md
- Every alpha and beta build is unsigned, so testers meet "Windows protected your PC" first. The wording to give them is supplied verbatim, ending with the sentence that matters for screen reader users: the Run button only exists after the More info link is activated, and the default button cancels.
- Releases are triggered by hand, never by a push. A push to `main` used to trigger the release workflow, which meant any merge bumped the version and published a tag with nobody deciding to. The real trigger is `workflow_dispatch` from the Actions tab on `.github/workflows/release.yml`, asking one question, How to bump: `patch` or `minor` for ordinary development versions, `alpha`, `beta` or `rc` to start or advance a prerelease series, `release` to drop a prerelease suffix.
- Development happens on plain `0.x.y` with no suffix, because `0.x` already means unstable. A prerelease suffix is added only when a build is about to go to testers.
- The workflow runs a quality gate first on a Windows runner (`cargo fmt --check`, clippy with warnings denied, the test suite), and only then does `cargo release` bump, tag and push. The installer is built with the same `scripts/build-installer.sh` a person would run locally. Published to a GitHub Release: `Wixen-Mail-Setup-<tag>.exe`, `wixen-mail-<tag>.exe`, `Wixen-Mail-<tag>-windows.zip`, and `changelog.md`. A tag carrying `-alpha`, `-beta` or `-rc` publishes as a prerelease automatically.
- There are no in-app update links. The Help menu has Contents, help topics, Load Sample Mailbox and About. A previously documented Check for Updates item and Release Pipeline item never existed in the program.

## Installing, data location and uninstalling
- source: docs/installing.md
- Windows application, installed from `Wixen-Mail-Setup-<version>.exe` on the releases page. Not code signed, so SmartScreen shows "Windows protected your PC"; the Run button is hidden behind the More info link and the visible button cancels. With a screen reader: tab to More info, Enter, then tab to Run anyway, Enter; do not press the button you land on first, which is Don't run.
- Install for me only (`%LOCALAPPDATA%\Programs\Wixen Mail`, no administrator rights) or for all users (`C:\Program Files\Wixen Mail`, elevation prompt). Standard Inno Setup switches accepted: `/SILENT`, `/VERYSILENT`, `/CURRENTUSER`, `/ALLUSERS`, `/DIR=`, `/LOG=`.
- Everything stored is under `%LOCALAPPDATA%\wixen-mail\` in `config\`, `cache\`, `sound_schemes\` and `logs\`. Passwords and sign-in tokens are in the Windows credential store instead. Downloaded mail is not encrypted; BitLocker is the answer if that matters. Back up by copying the whole folder, `config` being the part worth keeping. Credentials do not travel with the folder, by design. `WIXEN_MAIL_DATA` relocates the folder.
- Updating installs over the old version, keeping accounts, settings and downloaded mail. Uninstalling removes everything including saved passwords and tokens, and writes `wixen-mail-uninstall.log` to `%TEMP%` every time saying what went and naming anything left. Two cases leave no note because the program never ran: the program was already gone from its folder, or the uninstaller was closed before it finished. In both, check `%LOCALAPPDATA%\wixen-mail` by hand and clear Credential Manager entries beginning with `wixen-mail`.

## Privacy: what is stored and what leaves the computer
- source: docs/privacy.md
- No analytics, no telemetry, no crash reporting service, and no update check that says who you are. There is no server belonging to this project.
- Attachments are kept in the `cache` folder alongside message text, unencrypted, one file up to 25 MB and all together up to 512 MB, dropping least-recently-read past that; the same file arriving on twenty messages is stored once. Nothing about an attachment is written to the log.
- Signed mail is stored twice: the ordinary way, and once more exactly as it arrived byte for byte, because a signature can only be checked against the exact bytes signed. The second copy is dropped above 25 MB per message and above 128 MB total, least recently read first, except for mail collected over POP and mail brought in from a file, which are never dropped that way because there would be no getting them back. Where there is no second copy, the message says its signature could not be checked here and says plainly that this is not the same as a signature that failed.
- Contact groups stay on this computer: a group made here is never sent to Google or Outlook, and a group already kept at a provider does not appear here.
- Who it talks to: the mail provider (mail over TLS); the same provider for contacts, calendar and tasks when syncing, which a new installation allows; a separate calendar or contacts server if one is set up; an organisation's directory only if named on the account; Google or Microsoft sign-in in the browser; Google Safe Browsing only if switched on; and whoever a sender points a picture at.
- Directory lookup is off until an account names one; the two boxes are empty on a new installation. What goes is the part of the name typed, after typing stops, only once at least three letters are typed. Nothing about the message goes with it. What is typed is never logged. `ldaps://` is encrypted from the start, `ldap://` is not, and both are accepted because some internal directories offer only the second.
- Free/busy lookup asks nothing until Find when everyone is free is chosen. The question goes to the user's own calendar server naming the whole guest list, carrying no title, description, location or note. The reply carries stretches of time and never what anybody is doing. The address posted to must be one the calendar server named and on the same host; an address on a different host is refused rather than followed.
- Saving a meeting with guests happens only with Allow Changes on. A new meeting goes up with its guest list, and adding somebody is what makes a provider email an invitation; Wixen Mail does not send that mail and cannot ask either provider not to. Changing a meeting the provider already holds sends no guest list at all.
- Remote images: two surfaces ask the sender's address for a picture, the preview pane (off until switched on in the View menu) and the conversation window. The window a message opens into on `Enter` is a text control and asks nobody for anything. There is no setting for this yet and the Reading tab says so where the switch would be. Noted as read out of the code rather than measured on the wire.
- Phishing heuristics are on by default and send nothing to anybody: reading happens entirely on the computer over text already there.
- Link checking is off by default and uses the Safe Browsing Update API rather than the Lookup API, so Google's lists come to the computer instead of links going to Google. On a match, four bytes go to Google and every full fingerprint starting with those four bytes comes back, with the comparison happening locally. Google never receives the link, domain, sender, subject, recipient, email address or any part of any message. It needs a Google API key placed in `oauth.toml`; without one the feature does nothing whatever the setting says, and the log says so on startup. Wixen Mail will never say a message is safe.
- The log never contains a password, a sign-in token or the body of a message; it does contain folder names, message counts, provider error messages, and the addresses involved in a failed send.

## Project roadmap and phase checklists
- source: docs/roadmap.md (source's own header still states "Last updated: 2026-08-23"; the file was corrected on 2026-08-29)
- Vision: a fully accessible, lightweight Rust mail client with a Thunderbird/Outlook-inspired experience and first-class screen reader and keyboard support on Windows.
- Phases 1 through 7 are marked Complete: foundation (project setup, core architecture, accessibility framework); mail protocol support (IMAP4rev1 async client, IDLE, folder sync, fetching and caching, full-text search, capability handling, SPECIAL-USE with name fallback, UIDPLUS/MOVE/CONDSTORE/ID/X-GM-EXT-1, STATUS/LSUB/SUBSCRIBE, APPEND/COPY/MOVE; SMTP with PLAIN/LOGIN and TLS/STARTTLS plus an outbox queue; POP3 speaking RFC 1939 over TCP, replacing what the source says was a simulation that opened no socket, ignored the password and answered from three made-up messages, with TLS on 995, STLS on 110, UIDL-keyed sync, leave-on-server with day-based removal, and local folders); user interface; composition and editing; advanced features; OAuth and multi-account; offline mode and polish.
- Thread view is unticked, with the explanation added on 2026-08-29: "The Thread View item is on the View menu and disabled: the data model carries the identifiers, and nothing groups the list by them. Opening one conversation works. Press Enter on a message to see the messages around it as a tree." This agrees with docs/IMPLEMENTATION_STATUS.md and docs/USER_GUIDE.md.
- Other unticked items within those phases: an accessibility testing framework; QRESYNC; CREATE, RENAME and DELETE for folder management; Gmail's X-GM-THRID and X-GM-RAW, both recorded as blocked on the IMAP library rather than on this code; drag-and-drop and inline image insertion for attachments; colour coding, folder favourites and smart folders; spam filtering integration; a local callback server for the OAuth redirect; network status detection and conflict resolution; accessibility compliance testing with screen readers; performance benchmarking. Spell checking is marked partial: Windows' own checker on Windows and a built-in list elsewhere, checked at send time, with check-as-you-type and native announcement of misspellings waiting on a rich editor control that can carry the marks.
- Phase 8 (Release Preparation) is marked Planned: "Windows installer (MSI or NSIS)", auto-update and desktop shortcuts unticked; virtual scrolling ticked "for the message list and for every other list in the application"; large mailbox testing, memory profiling and startup time unticked; beta testing unticked; documentation mostly ticked with release notes and changelog unticked. The unticked installer line is about MSI or NSIS specifically; an Inno Setup installer ships, per docs/installing.md, docs/BETA_RELEASE.md and the requirements backlog. See INGEST-CONFLICTS.md INFO 8.

## Competitive positioning against Thunderbird and Outlook
- source: docs/comparison.md
- Measures against Thunderbird, which most blind Windows users are pointed at, and Outlook, which most have to use at work. The interesting comparison is that being complete has not made either good to use by ear.
- Cites a 2025 Thunderbird accessibility study commissioned through Fable, mapping each finding to where Wixen Mail stands: shortcuts not following common norms (Wixen Mail follows Windows and matches Outlook and Thunderbird where they agree, with the shortcut document checked against the code by a test); confusing search and filter results (search announces its result count, rules say how many they sorted); NVDA users meeting structures lacking expected context (the message list is a report-view list with named columns, every row readable in full with Space); Narrator giving no confirmation for actions like moving messages (every action that changes something announces what it did); Narrator not recognising menu stage changes in submenus (not verified, no Narrator pass done); JAWS unable to read message bodies on a braille display (the reading surface writes text rather than a rendered view, not verified with a display); JAWS opening filter menus silently (not verified with JAWS).
- Behind: templates; several identities per account; signing or encrypting outgoing mail (signed mail that arrives is read and checked, nothing goes out signed or encrypted, and there is no OpenPGP at all); vacation or automatic replies. Stated as decisions rather than gaps: no advertising, no telemetry, no account required, and cached mail not encrypted.
- Ahead: reading a row without opening it (`Space`, again for full, `Shift+Space` for details, same in every module); structure spoken rather than implied; reading dates the way a person asked for; nothing changing at a server without permission, with permission split by cost and three places able to say no, the safest answer winning; feedback on more than one channel (speech, earcon, braille, status line), distinguishable and rate limited; a mute for reading aloud; every action using the account the message is in.
- Records that the four items previously ranked as next have since been built (signatures, rules on arriving mail, one list for every inbox, labels on the number keys), three of which turned out to have storage, editor and tests already written with nothing calling the last step. Import and export has since been built (mbox files, single messages, folders inside zip archives, Outlook data files, in and out, keeping folder structure), on the reasoning that a client somebody cannot leave is one they should be wary of joining. Saved searches have since been built. What is left, in the order somebody would miss it: templates, several identities per account, signing and encrypting outgoing mail.

## How the protocols were joined to the interface
- source: docs/integration-guide.md (rewritten 2026-08-29)
- The source opens by saying what it used to be and why that was wrong: "The previous version was a three-phase build plan from early in the project. All three phases finished, but the document went on describing Phase 1 as in progress, counted 64 tests against the 5,269 that run today, and ticked a 95% coverage target that was never met. It is kept as a record of how the layers were joined, not as a plan."
- States plainly that this is not a guide to integrating anything with Wixen Mail: it is a desktop application, not a library, and nothing in it is a public interface.
- Four layers joined in one direction, a layer never reaching upward: `presentation` (windows, controls, announcements; `wx_app.rs`), `application` (what a command means and the rules it follows; `mail_controller.rs`), `service` (protocols and providers; `protocols/imap.rs`), `data` (the SQLite cache and account records; `message_cache/`).
- `application::mail_controller` is the join between the interface and the protocols. It owns the async runtime, so the window never blocks on a socket: work goes to a Tokio task and the answer comes back as a `UIUpdate` the message pump applies on the interface thread.
- Three things recorded as harder than the original plan allowed. A window cannot wait: every protocol call is async and every widget call must happen on the interface thread, so a worker never touches a widget and a `UIUpdate` never carries a live handle. Announcing a change is not the same as making it: reads, flags and moves are applied to the row on screen and announced at once because a keystroke that waits on a round trip feels broken, which means an announcement can turn out wrong, so a refused change is put back and the reason said (`wx_app.rs` for flags, `spawn_server_change` for the server). None of it has run against a real account: the protocol code is tested against parsing and loopback servers, which is why coverage in `service/protocols` and the provider clients is low, and that is tracked as work rather than as a gap in the tests.
- Where the old plan's phases ended up: connecting IMAP and SMTP to the interface, done through `mail_controller`; persistent caching and HTML rendering, done, with the cache at `data/message_cache/`, bodies split into `bodies.rs` under a size budget, and HTML sanitized with `ammonia` before it reaches the preview; advanced features and polish, overtaken, with what shipped recorded in the changelog rather than against phase numbers.

## Mutation testing sweep plan and findings
- source: docs/plans/20260801-mutation-sweep.md
- Mutation testing changes the code in small ways and runs the suite; a change nothing notices means either the behaviour is unpinned or the code is dead. Four modules have been through it and are clean; everything else has not. The document records the order so an interrupted run can be picked up rather than restarted.
- Scale: 4,171 mutants outside the four already done, at roughly one every twenty-six seconds on this machine with no parallelism, putting a full sweep near thirty hours, a background job measured in days rather than a commit step. Each directory pays its own baseline build of about five minutes, so running one large directory beats running its files one at a time.
- Order, highest cost of being wrong first: `common` (89 mutants, errors and types everything else is built on), `service/protocols` (327, mail parsing, where a bug loses or corrupts somebody's mail), `data` (513, storage), `application` (1,307, the decisions about what to fetch, file and say), the rest of `service` (211, safe browsing, spelling, OAuth, security), `presentation` excluding the window (725, reading surfaces, columns, dates). The wxWidgets layer is excluded in `mutants.toml` and stays excluded, because it cannot be exercised without a display so every mutant there would survive and say nothing except "this needs a person"; its verification is a screen reader pass.
- Pattern from the first four modules: the tests covered the paths somebody would think to write a test for and left whole families untouched (four of the fields a filter rule can name, six of the eleven ways it can match, five of the actions it can carry out), each family having one member with a test. "Where to look first in any report: a function that switches on a string."
- Run with `scripts/mutants.sh src/common`, and read a run as finished only when the process has exited; reading `mutants.out` early once produced a commit message claiming seventeen of eighteen caught when the finished figure was thirty-seven of fifty-one.
- Further sections record what `common`, `service/protocols`, `data`, `service` and `presentation` turned up, twelve mutants left standing on purpose in `data`, how a shared file between runs makes a whole report a lie, how to read a report against a tree that has moved, what reading a module turns up that a mutant does not, progress, and two things the sweep got wrong about itself.
